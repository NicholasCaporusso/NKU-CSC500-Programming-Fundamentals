2. From arrays to lists

Up to this point, arrays have been our primary way to store a collection of values.

For example:

int[] scores = new int[5];

scores[0] = 87;
scores[1] = 93;
scores[2] = 78;

Arrays have many advantages.

They are:

  • simple,
  • efficient,
  • fast to access by index,
  • and built directly into Java.

But they have one important limitation:

The size of an array cannot change after the array has been created.

Consider:

int[] scores = new int[5];

This array will always contain exactly five locations.

We can change the values stored in those locations, but we cannot turn the array itself into an array of length 6.

3. The fixed-size problem

Suppose we are writing a program that stores students registered for a course.

We might write:

String[] students = new String[30];

But what happens if 31 students register?

We could initially allocate more space:

String[] students = new String[1000];

But now we may waste a large amount of memory.

More importantly, we usually do not know in advance exactly how much data a program will eventually need to store.

Examples include:

  • users currently logged into a system,
  • messages in an inbox,
  • products in a shopping cart,
  • search results,
  • files in a directory,
  • transactions in a bank account,
  • vertices in a graph,
  • tasks in a scheduler.

We therefore want a collection whose size can grow and shrink while the program is running.

This leads us to the idea of a list.

4. What is a list?

A list is an ordered collection of elements.

For example:

[17, 23, 41, 8]

or

["Alice", "Bob", "Carlos"]

The word ordered is important.

It means that elements have positions.

For example, in:

["Alice", "Bob", "Carlos"]

"Alice" comes before "Bob", and "Bob" comes before "Carlos".

A typical list supports operations such as:

add(value)
get(index)
set(index, value)
remove(index)
size()
contains(value)

At this point we need to distinguish two important ideas:

What a data structure does

and

How the data structure is implemented

5. Abstract data types

An Abstract Data Type, or ADT, describes:

  • what kind of data is represented,
  • what operations are allowed,
  • and what those operations mean.

It does not specify exactly how those operations are implemented.

For example, a List ADT might support:

add(element)
remove(index)
get(index)
size()

There are multiple ways to implement a list.

Two important implementations are:

Array-based list
Linked list

Both implement essentially the same conceptual abstraction:

LIST

But internally they store data in very different ways.

This distinction becomes extremely important in computer science.

6. Interface versus implementation

We can think about this distinction as:

WHAT               HOW

List                Array
operations          Linked nodes

For example:

List ADT
    |
    +---- Array-based implementation
    |
    +---- Linked implementation

A user of a list may care about operations such as:

list.add("Alice");
list.remove(0);
list.get(2);

The user does not necessarily need to know how the list stores those values internally.

This separation is one of the central themes of software engineering:

Separate what something does from how it does it.

7. Java's ArrayList

Java provides a dynamic array implementation called:

ArrayList

To use it:

import java.util.ArrayList;

Example:

ArrayList<String> names = new ArrayList<>();

We can add elements:

names.add("Alice");
names.add("Bob");
names.add("Carlos");

The list now conceptually contains:

Alice
Bob
Carlos

We can ask for its size:

System.out.println(names.size());

Output:

3

8. Accessing ArrayList elements

ArrayList indexing works similarly to array indexing.

String name = names.get(1);

This returns:

Bob

Notice the syntax difference.

For an array:

array[index]

For an ArrayList:

list.get(index)

For example:

String[] a = new String[10];
String x = a[3];

versus:

ArrayList<String> a = new ArrayList<>();
String x = a.get(3);

9. Modifying ArrayList elements

We can replace an existing value using set.

names.set(1, "Barbara");

Now the list contains:

Alice
Barbara
Carlos

Be careful:

names.set(3, "David");

does not append a new element if index 3 does not yet exist.

To append an element, use:

names.add("David");

10. Removing elements

We can remove an element by index:

names.remove(1);

Suppose the list originally contains:

0: Alice
1: Bob
2: Carlos
3: Diana

After:

names.remove(1);

the list becomes:

0: Alice
1: Carlos
2: Diana

Notice that the elements after Bob shift one position to the left.

This detail will matter when we analyze performance.

11. Iterating over an ArrayList

We can use a standard for loop:

for (int i = 0; i < names.size(); i++) {
    System.out.println(names.get(i));
}

Or an enhanced for loop:

for (String name : names) {
    System.out.println(name);
}

The enhanced loop is especially useful when we simply want to visit every element.

12. Example: computing an average

ArrayList<Double> scores = new ArrayList<>();

scores.add(87.5);
scores.add(92.0);
scores.add(76.5);
scores.add(100.0);

double total = 0;

for (double score : scores) {
    total += score;
}

double average = total / scores.size();

System.out.println(average);

This behaves similarly to working with an array, but the collection can grow as needed.

13. Why is it called ArrayList?

Despite its ability to grow, an ArrayList is internally based on an array.

Conceptually:

ArrayList
   |
   v

+----+----+----+----+----+----+----+----+
|  A |  B |  C |  D |    |    |    |    |
+----+----+----+----+----+----+----+----+

The underlying array may have more space than the list currently needs.

Suppose the list contains four elements:

size = 4

but the underlying array may have capacity for eight:

capacity = 8

These are different concepts.

14. Size versus capacity

Consider:

Underlying array:

+----+----+----+----+----+----+----+----+
| 17 | 21 | 33 | 48 |    |    |    |    |
+----+----+----+----+----+----+----+----+

size = 4
capacity = 8

The size is the number of actual list elements.

The capacity is the number of elements the underlying storage can currently hold without allocating a new array.

The user normally cares about the size.

The implementation cares about both.

15. What happens when an ArrayList becomes full?

Suppose we have:

+----+----+----+----+
| A  | B  | C  | D  |
+----+----+----+----+

and the underlying array is full.

Now we execute:

list.add("E");

The implementation cannot make the existing Java array larger.

Instead, it roughly performs these steps:

  1. Allocate a larger array.
  2. Copy the existing elements into it.
  3. Add the new element.
  4. Replace the old array reference with the new array reference.

Conceptually:

OLD:

+----+----+----+----+
| A  | B  | C  | D  |
+----+----+----+----+

NEW:

+----+----+----+----+----+----+----+----+
| A  | B  | C  | D  | E  |    |    |    |
+----+----+----+----+----+----+----+----+

The details of the resizing policy are an implementation decision.

The important idea is:

A dynamic array does not literally stretch. It occasionally creates a larger array and copies its elements.

16. Why not resize every time?

Suppose a list grew like this:

size 1 -> allocate array of size 1
size 2 -> allocate array of size 2
size 3 -> allocate array of size 3
size 4 -> allocate array of size 4
...

Every insertion would require copying all previous elements.

That would be extremely inefficient.

Instead, dynamic arrays typically grow by a larger factor.

For example, conceptually:

capacity:

4
8
16
32
64
...

The exact growth strategy is not important for CSC500.

The important lesson is:

Dynamic arrays reserve extra capacity so that most additions do not require resizing.

17. ArrayList time complexity

Suppose the list contains n elements.

Typical performance is approximately:

OperationComplexity
get(index)O(1)
set(index, value)O(1)
append with add(value)O(1) amortized
insert near beginningO(n)
remove near beginningO(n)
search for valueO(n)

Why is indexed access O(1)?

Because the underlying array allows direct access to any position.

Why can insertion be O(n)?

Because later elements may need to shift.

18. Inserting into an array-based list

Suppose we have:

[A][B][C][D][ ]

and want to insert X at index 1.

We cannot simply overwrite B.

Instead:

Before:

[A][B][C][D][ ]

Shift D:
[A][B][C][D][D]

Shift C:
[A][B][C][C][D]

Shift B:
[A][B][B][C][D]

Insert X:
[A][X][B][C][D]

The number of elements shifted depends on where the insertion occurs.

In the worst case, approximately n elements must move.

Therefore:

Insertion near front: O(n)

19. A different idea

Could we store list elements without requiring them to occupy consecutive positions in an array?

Yes.

Instead of storing elements next to one another in memory, we can let each element tell us where the next element is.

This gives us a:

Linked list

20. Review: Java references

Before understanding linked lists, we must be comfortable with references.

Consider:

Student s1 = new Student("Alice");
Student s2 = s1;

We do not have two Student objects.

We have:

s1 -----+
        |
        v
     +---------+
     | Alice   |
     +---------+
        ^
        |
s2 -----+

Both variables refer to the same object.

If we change the object through one reference:

s1.setName("Alicia");

then:

System.out.println(s2.getName());

prints:

Alicia

References are what allow us to connect objects into larger structures.

21. A node

A linked list consists of objects called nodes.

Each node stores:

  1. some data,
  2. a reference to another node.

A simple node might look like this:

public class Node {
    int data;
    Node next;
}

Each Node contains:

data
next

For example:

+------+------+
|  17  | next |
+------+------+

The next field can refer to another Node.

22. Connecting two nodes

Consider:

Node first = new Node();
first.data = 10;

Node second = new Node();
second.data = 20;

first.next = second;

We now have:

first
  |
  v
+----+------+       +----+------+
| 10 |   ---------> | 20 | null |
+----+------+       +----+------+

The first node contains a reference to the second node.

The second node's next reference is currently null.

23. What does null mean?

null means:

This reference currently refers to no object.

For the final node of a singly linked list:

node.next == null

indicates that we have reached the end of the list.

For example:

head
 |
 v
+----+---+     +----+---+     +----+------+
| 10 | ------> | 20 | ------> | 30 | null |
+----+---+     +----+---+     +----+------+

24. The head reference

A linked list normally keeps a reference to its first node.

We often call this:

head

Example:

Node head;

If the list is empty:

head == null

If the list contains data:

head
 |
 v
[node] -> [node] -> [node] -> null

This is extremely important.

If we lose the head reference and have no other reference to the first node, we may lose our ability to reach the entire list.

25. A better node class

A more useful definition is:

private static class Node {
    int data;
    Node next;

    Node(int data) {
        this.data = data;
        this.next = null;
    }
}

Now we can create nodes more easily:

Node n = new Node(42);

Conceptually:

+------+------+
|  42  | null |
+------+------+

26. Building a list manually

Consider:

Node first = new Node(10);
Node second = new Node(20);
Node third = new Node(30);

first.next = second;
second.next = third;

Diagram:

first
 |
 v
+----+---+
| 10 | ----+
+----+---+  |
            v
         +----+---+
         | 20 | ----+
         +----+---+  |
                     v
                  +----+------+
                  | 30 | null |
                  +----+------+

Normally we would not keep separate variables named first, second, and third.

Instead, we keep only:

head

and follow next references.

27. Traversing a linked list

Suppose:

head
 |
 v
[10] -> [20] -> [30] -> null

We want to print every value.

We can create a temporary reference:

Node current = head;

Then repeatedly:

  1. process the current node,
  2. move to the next node.
while (current != null) {
    System.out.println(current.data);
    current = current.next;
}

This is the standard linked-list traversal pattern.

Memorize the pattern:

Node current = head;

while (current != null) {
    // process current
    current = current.next;
}

28. Tracing traversal

Suppose:

head
 |
 v
[7] -> [12] -> [25] -> null

Initially:

current = head

So:

current -> 7

After:

current = current.next;

we have:

current -> 12

Then:

current -> 25

Then:

current -> null

At that point, the loop stops.

29. A critical point about traversal

This code is safe:

Node current = head;

while (current != null) {
    System.out.println(current.data);
    current = current.next;
}

This code is dangerous:

while (head != null) {
    System.out.println(head.data);
    head = head.next;
}

Why?

Because we are changing head.

After the loop:

head == null

and the list has effectively been lost.

The nodes may still exist temporarily in memory, but our data structure no longer has a way to reach them.

Therefore:

Use a temporary traversal reference unless you intentionally want to modify head.

30. Counting the nodes

How could we compute the number of elements?

public int size() {
    int count = 0;
    Node current = head;

    while (current != null) {
        count++;
        current = current.next;
    }

    return count;
}

Runtime:

O(n)

because we must visit every node.

We could alternatively maintain a separate size field.

Then:

size()

could be O(1).

This illustrates an important data-structure design idea:

Sometimes we store extra information to make certain operations faster.

31. Searching a linked list

To determine whether a linked list contains a value:

public boolean contains(int target) {
    Node current = head;

    while (current != null) {
        if (current.data == target) {
            return true;
        }

        current = current.next;
    }

    return false;
}

Worst-case runtime:

O(n)

Why?

Because the target might:

  • be the final element,
  • or not exist at all.

32. Accessing element i

With an array:

array[i]

is O(1).

But suppose we want element 4 of a linked list.

We cannot jump directly there.

We have:

head
 |
 v
[0] -> [1] -> [2] -> [3] -> [4]

We must follow the links:

head
 ->
node 1
 ->
node 2
 ->
node 3
 ->
node 4

Therefore:

get(index)

for a linked list is:

O(n)

in the general case.

33. Adding to the front of a linked list

Suppose:

head
 |
 v
[20] -> [30] -> null

We want to add 10.

First create a node:

Node newNode = new Node(10);

Now:

newNode -> [10] -> null

head -> [20] -> [30] -> null

Next:

newNode.next = head;

Now:

newNode -> [10] -> [20] -> [30] -> null
                     ^
                     |
                    head

Finally:

head = newNode;

Result:

head
 |
 v
[10] -> [20] -> [30] -> null

Code:

public void addFirst(int value) {
    Node newNode = new Node(value);
    newNode.next = head;
    head = newNode;
}

34. Why order matters

Suppose we accidentally write:

head = newNode;
newNode.next = head;

What happens?

After:

head = newNode;

we have already changed head.

Then:

newNode.next = head;

means:

newNode.next = newNode

We create a cycle:

+------+
|      |
v      |
[10] --+

and we lose access to the old list.

Reference-manipulation statements often look simple, but their order matters enormously.

A useful rule is:

Preserve references to existing structures before changing the references that reach them.

35. Adding to the front is o(1)

The operation:

newNode.next = head;
head = newNode;

requires the same number of operations regardless of whether the list contains:

3 nodes
300 nodes
3,000,000 nodes

Therefore:

addFirst = O(1)

This is one major advantage of linked lists.

36. Adding to the end

Suppose:

head
 |
 v
[10] -> [20] -> [30] -> null

We want:

[10] -> [20] -> [30] -> [40] -> null

We must locate the final node.

Node current = head;

while (current.next != null) {
    current = current.next;
}

At the end of this loop:

current
 |
 v
[30] -> null

Then:

current.next = new Node(40);

37. Handling the empty list

There is a special case.

If:

head == null

then there is no final node.

So:

public void addLast(int value) {

    Node newNode = new Node(value);

    if (head == null) {
        head = newNode;
        return;
    }

    Node current = head;

    while (current.next != null) {
        current = current.next;
    }

    current.next = newNode;
}

The special case for an empty structure is extremely common when working with linked data structures.

38. Complexity of addlast

With only a head reference:

addLast = O(n)

because we must traverse the list.

Could we make it faster?

Yes.

We could store another reference:

Node tail;

where tail always refers to the final node.

Then:

head
 |
 v
[10] -> [20] -> [30] -> null
                 ^
                 |
                tail

Appending can now be O(1).

Again we see a recurring data-structure principle:

Additional stored information can make some operations faster.

39. Inserting in the middle

Suppose:

[10] -> [20] -> [40]

and we want to insert 30 between 20 and 40.

Let:

current -> [20]

and create:

Node newNode = new Node(30);

First:

newNode.next = current.next;

Now:

[30] -> [40]

Then:

current.next = newNode;

Result:

[10] -> [20] -> [30] -> [40]

The order is important.

40. Incorrect insertion

Suppose we reverse the order:

current.next = newNode;
newNode.next = current.next;

After the first statement:

current.next

already refers to newNode.

So the second statement becomes effectively:

newNode.next = newNode;

Again, we accidentally create a self-reference.

Correct:

newNode.next = current.next;
current.next = newNode;

41. Removing the first node

Suppose:

head
 |
 v
[10] -> [20] -> [30] -> null

To remove 10:

head = head.next;

Now:

head
 |
 v
[20] -> [30] -> null

The first node is no longer reachable from the list.

Java's garbage collector can eventually reclaim it.

42. Garbage collection

Unlike languages such as C or C++, Java programmers do not normally explicitly free objects.

Consider:

head = head.next;

If no reference points to the old first node, then the old node becomes unreachable.

Java's garbage collector can reclaim that memory later.

Conceptually:

Before:

head -> [10] -> [20] -> [30]


After:

       [10]      head -> [20] -> [30]
        ^
        |
   unreachable

You should not assume that garbage collection happens immediately.

The important concept is simply that unreachable objects are eligible for collection.

43. Removing a node from the middle

Suppose:

[10] -> [20] -> [30] -> [40]

and we want to remove 30.

If:

current -> [20]

then we can write:

current.next = current.next.next;

Before:

current
 |
 v
[20] -> [30] -> [40]

After:

current
 |
 v
[20] ----------> [40]

[30] becomes unreachable

This is one of the most important linked-list operations to understand.

44. Removing a value

A more complete implementation might be:

public boolean remove(int target) {

    if (head == null) {
        return false;
    }

    if (head.data == target) {
        head = head.next;
        return true;
    }

    Node current = head;

    while (current.next != null) {

        if (current.next.data == target) {
            current.next = current.next.next;
            return true;
        }

        current = current.next;
    }

    return false;
}

Notice that we examine:

current.next.data

rather than only:

current.data

Why?

Because to remove a node, we need access to the node before it.

45. Why removal requires the previous node

Suppose:

A -> B -> C

and we want to remove B.

We need to change:

A.next

from:

B

to:

C

Therefore we need access to A.

That is why linked-list algorithms frequently maintain:

current
previous

or deliberately stop one node before the target.

46. A simple linked-list class

Here is a complete simplified implementation.

public class IntLinkedList {

    private static class Node {

        int data;
        Node next;

        Node(int data) {
            this.data = data;
            this.next = null;
        }
    }

    private Node head;
    private int size;

    public IntLinkedList() {
        head = null;
        size = 0;
    }

    public int size() {
        return size;
    }

    public boolean isEmpty() {
        return size == 0;
    }

    public void addFirst(int value) {

        Node newNode = new Node(value);

        newNode.next = head;
        head = newNode;

        size++;
    }

    public void addLast(int value) {

        Node newNode = new Node(value);

        if (head == null) {
            head = newNode;
            size++;
            return;
        }

        Node current = head;

        while (current.next != null) {
            current = current.next;
        }

        current.next = newNode;
        size++;
    }

    public boolean contains(int value) {

        Node current = head;

        while (current != null) {

            if (current.data == value) {
                return true;
            }

            current = current.next;
        }

        return false;
    }

    public void print() {

        Node current = head;

        while (current != null) {
            System.out.print(current.data + " ");
            current = current.next;
        }

        System.out.println();
    }
}

47. Using our linked list

public class Main {

    public static void main(String[] args) {

        IntLinkedList numbers = new IntLinkedList();

        numbers.addFirst(30);
        numbers.addFirst(20);
        numbers.addFirst(10);

        numbers.addLast(40);

        numbers.print();

        System.out.println(numbers.size());
        System.out.println(numbers.contains(20));
        System.out.println(numbers.contains(99));
    }
}

Output:

10 20 30 40
4
true
false

48. Generic linked lists

Our example stores only integers:

int data;

But a general-purpose list should be able to store arbitrary object types.

Java generics allow us to write:

public class MyLinkedList<T>

A node can then contain:

T data;

For example:

private class Node {

    T data;
    Node next;

    Node(T data) {
        this.data = data;
    }
}

Then we could create:

MyLinkedList<String> names =
    new MyLinkedList<>();

MyLinkedList<Student> students =
    new MyLinkedList<>();

Students do not need to master generic data-structure implementation yet, but they should understand why Java collection classes use syntax such as:

ArrayList<String>
ArrayList<Integer>
LinkedList<Student>

49. Java's LinkedList

Java already provides a linked-list implementation:

import java.util.LinkedList;

Example:

LinkedList<String> names =
    new LinkedList<>();

names.add("Alice");
names.add("Bob");
names.add("Carlos");

Java's implementation is more sophisticated than our example.

We implement our own linked list because doing so teaches us:

  • references,
  • dynamic memory structures,
  • data-structure invariants,
  • algorithmic tradeoffs,
  • and how library collections work internally.

In production code, we normally use a tested library implementation unless there is a specific reason not to.

50. ArrayList versus LinkedList

Both represent a list.

But they represent it differently.

ArrayList

Conceptually:

+----+----+----+----+----+
| A  | B  | C  | D  |    |
+----+----+----+----+----+

Elements occupy indexed positions in an underlying array.

Linked list

Conceptually:

[A | *] -> [B | *] -> [C | *] -> [D | null]

Each element is stored in a node that points to another node.

For a typical array-based list and singly linked list:

For example:

52. Random access

An array gives us random access.

That means we can access arbitrary positions directly.

array[0]
array[500]
array[999999]

Each access is O(1).

A linked list provides sequential access.

To reach element 999, we generally must walk through:

0
1
2
3
...
999

So repeated indexed access can be particularly expensive.

53. A common performance mistake

Consider a linked list called list.

Suppose we conceptually write:

for (int i = 0; i < list.size(); i++) {
    System.out.println(list.get(i));
}

If:

get(i) = O(n)

then repeatedly calling it can make the entire traversal approximately:

O(n²)

A proper linked traversal is:

Node current = head;

while (current != null) {
    System.out.println(current.data);
    current = current.next;
}

which is:

O(n)

The larger lesson:

Choosing the wrong operation for a data structure can dramatically change the performance of an algorithm.

54. Memory tradeoffs

Arrays store values compactly.

A linked node must store both:

data
reference to next node

For example:

Array:

[10][20][30][40]


Linked:

[10|*] -> [20|*] -> [30|*] -> [40|null]

Those references require additional memory.

Furthermore, linked nodes are separate objects.

Thus, linked structures generally have greater memory overhead.

55. Which is better?

Neither data structure is universally better.

The correct question is:

Which representation better supports the operations our program performs frequently?

If a program frequently performs:

get(index)

an array-based list is attractive.

If a program frequently adds and removes values at the front, a linked representation may be attractive.

This is the heart of data-structure selection:

Choose a representation based on the operations that matter.

56. Example: student roster

Suppose a course has 100 students.

The program frequently needs:

students.get(i)

and rarely removes students.

An ArrayList is likely appropriate.

Why?

  • fast indexed access,
  • simple iteration,
  • low overhead,
  • occasional insertion/removal cost is acceptable.

57. Example: processing incoming tasks

Suppose tasks continuously arrive, and we repeatedly remove the oldest task.

We need operations resembling:

add at one end
remove from another end

A linked structure may be attractive.

Next week we will see that this behavior corresponds to a particular abstract data type:

Queue

This illustrates an important connection:

Lists are building blocks for more specialized data structures.

58. Structural invariants

When implementing a data structure, certain facts should always remain true.

These are called invariants.

For a simple singly linked list:

  1. head == null if the list is empty.
  2. Every node except the final node has a valid next-node reference.
  3. The final node has next == null.
  4. Every node belonging to the list is reachable from head.
  5. If a size field exists, it equals the number of reachable nodes.

A bug in a linked-list operation often means we have broken an invariant.

59. How linked lists break

Common bugs include:

Losing part of the list

current.next = newNode;

before saving the original value of current.next.

Creating a cycle

A -> B -> C
     ^    |
     |____|

Now traversal may never reach null.

Incorrectly changing head

head = head.next;

when we did not intend to remove the first node.

Dereferencing null

current.next.data

when:

current.next == null

Forgetting the empty-list case

Code that assumes:

head != null

may fail when the list is empty.

60. Nullpointerexception and linked lists

Consider:

Node current = head;

while (current.next != null) {
    current = current.next;
}

What happens when:

head == null

?

Then:

current == null

and attempting:

current.next

causes:

NullPointerException

That is why we often handle an empty list separately.

66. In-class question

Suppose a linked list contains one million nodes.

How many nodes must we inspect to retrieve element 900,000?

Approximately:

900,001 nodes

Therefore:

O(n)

Compare this to an array:

array[900000]

67. In-class question

Suppose a linked list contains one million nodes.

How many existing nodes must move when we insert a new node at the front?

Answer:

0

We only change references.

newNode.next = head;
head = newNode;

Therefore:

O(1)

Compare this with an array-based list, where all existing elements may need to shift.

68. Designing data structures

When evaluating a data structure, ask:

  1. What data must we represent?
  2. Which operations must we support?
  3. Which operations happen most frequently?
  4. What runtime do those operations have?
  5. What memory costs are involved?
  6. How complicated is the implementation?
  7. Are there library implementations we should use?

Do not choose a data structure because it sounds more sophisticated.

Choose it because its properties fit the problem.

71. Programming to an interface

Instead of:

ArrayList<String> names =
    new ArrayList<>();

Java programmers often write:

    new ArrayList<>();

after importing:

import java.util.ArrayList;

Why?

Because the variable describes what we need:

a List

while the constructor specifies which implementation we choose:

ArrayList

Later we might change:

    new LinkedList<>();

without changing much of the surrounding code.

This is an important example of programming against an abstraction rather than a specific implementation.

72. Array versus ArrayList versus LinkedList

Students should be able to distinguish these clearly.

Array

String[] names = new String[10];

Properties:

  • fixed length,
  • built into Java,
  • direct indexed access,
  • can store primitives directly.

ArrayList

ArrayList<String> names =
    new ArrayList<>();

Properties:

  • dynamically sized,
  • internally array-based,
  • direct indexed access,
  • inserts/removals may shift elements.

LinkedList

LinkedList<String> names =
    new LinkedList<>();

Properties:

  • dynamically sized,
  • internally node-based,
  • sequential traversal,
  • no efficient arbitrary indexed access,
  • some insert/remove operations can be very efficient.

73. Important note about Java's LinkedList

Students sometimes hear:

"Linked lists are faster than array lists."

That statement is too simplistic.

Java's LinkedList is often not the best choice in real applications.

An ArrayList has excellent memory locality and low overhead, and modern computers are heavily optimized for contiguous memory access.

For CSC500, however, linked lists are important because they introduce the general idea of:

dynamically connected nodes

This idea appears throughout computer science in:

  • trees,
  • graphs,
  • hash tables,
  • queues,
  • memory managers,
  • syntax trees,
  • operating systems,
  • and many other structures.

74. The bigger idea: dynamic data structures

A linked list is our first major example of a dynamic data structure.

Instead of allocating one fixed block:

[ ][ ][ ][ ][ ][ ][ ]

we create individual objects as needed:

[node] -> [node] -> [node]

The shape of the structure can change while the program runs.

Later data structures extend this idea.

A tree might look like:

        [A]
       /   \
     [B]   [C]
     / \
   [D] [E]

A graph might look like:

[A] ---- [B]
 |      / |
 |     /  |
[C] ---- [D]

The linked list is therefore a conceptual bridge from arrays to much richer structures.

76. Concept check

Question 1

Why can an ArrayList grow if Java arrays have fixed size?

Answer: It allocates a new, larger array when necessary and copies existing values.

Question 2

Why is ArrayList.get(i) O(1)?

Answer: The underlying array provides direct indexed access.

Question 3

Why is LinkedList.get(i) generally O(n)?

Answer: The implementation must follow links from one node to another until reaching the desired position.

Question 4

Why is adding to the front of a singly linked list O(1)?

Answer: Only a constant number of references need to change.

Question 5

Why can insertion into an ArrayList be O(n)?

Answer: Existing elements may need to shift to create space.

77. Common misconceptions

Misconception 1

"An ArrayList is not an array."

More precisely:

An ArrayList is a list abstraction implemented using an underlying array.

Misconception 2

"Linked lists are always faster."

False.

Their performance depends on the operation.

Misconception 3

"Linked lists provide O(1) insertion everywhere."

Not necessarily.

The reference update can be O(1), but finding the insertion position may require O(n).

Misconception 4

"current = current.next changes the list."

Usually it does not.

It changes which object the local variable current refers to.

Misconception 5

"head = head.next and current = current.next are equivalent."

They may follow a reference in the same way, but their effects are very different.

Changing head changes the data structure itself.

Changing a local traversal reference usually does not.

78. Debugging strategy for linked lists

When a linked-list program does not behave correctly:

Step 1

Draw the list before the operation.

Step 2

Draw every reference variable.

For example:

head
current
previous
newNode

Step 3

Execute one assignment at a time.

Step 4

After each assignment, redraw the arrows.

Step 5

Ask:

Can every intended node still be reached from head?

Step 6

Check special cases:

empty list
one-element list
first element
last element
element not found

This approach is much more reliable than randomly changing code.

79. Suggested live coding exercise

Implement:

Possible implementation:

public int get(int index) {

    if (index < 0 || index >= size) {
        throw new IndexOutOfBoundsException();

81. Challenge exercise: reverse a linked list

Given:

10 -> 20 -> 30 -> 40 -> null

produce:

40 -> 30 -> 20 -> 10 -> null

This requires carefully reversing the direction of each reference.

A standard iterative solution uses:

Node previous = null;
Node current = head;

while (current != null) {

    Node next = current.next;

    current.next = previous;

    previous = current;
    current = next;
}

head = previous;

This algorithm is an excellent test of reference reasoning.

Do not simply memorize it.

Trace it node by node.

82. Tracing the reverse algorithm

Initially:

previous = null

current
 |
 v
[10] -> [20] -> [30] -> null

Save:

Node next = current.next;

so:

next -> 20

Then:

current.next = previous;

becomes:

[10] -> null

Then:

previous = current;
current = next;

Now:

previous -> 10
current  -> 20

Repeat until:

previous
 |
 v
[30] -> [20] -> [10] -> null

Finally:

head = previous;

83. Why we saved next

Imagine writing:

current.next = previous;
current = current.next;

After the first statement, current.next no longer points forward through the original list.

It points backward.

Therefore we would lose access to the rest of the original structure.

That is why we first store:

Node next = current.next;

This pattern occurs frequently in dynamic data-structure algorithms:

Save the reference you will need before modifying it.
