Week 12: Lists and dynamic data structures

Course index

1. Overview

Until now, arrays have been our main tool for storing collections of values.

Arrays are simple and efficient:

int[] scores = new int[5];

scores[0] = 87;
scores[1] = 93;
scores[2] = 78;

However, arrays have an important limitation:

Once an array is created, its length cannot change.

This week introduces dynamic data structures—structures whose logical size can change while a program is running.

We will study two important ways to implement a list:

  1. an array-based dynamic list, represented in Java by ArrayList;
  2. a linked list, built from objects connected by references.

These representations support many of the same conceptual operations, but they organize memory differently. Because of this, their operations have different performance characteristics.

The central question for this week is:

How does the way we represent data affect the operations we can perform efficiently?

3. From arrays to dynamic collections

Suppose we want to store the students registered for a course.

We could write:

String[] students = new String[30];

But what happens if student number 31 registers?

The array cannot simply become larger.

We might instead create:

String[] students = new String[1000];

but then we might allocate far more storage than we need.

The deeper problem is that many programs do not know their final amount of data in advance.

Examples include:

  • names read from a file,
  • users currently logged into a system,
  • search results,
  • shopping-cart items,
  • messages,
  • transactions,
  • files in a directory,
  • tasks waiting to be processed.

For these situations, we want a collection whose number of elements can change while the program executes.

4. Dynamic data structures

A dynamic data structure is a structure whose size can change during program execution.

For example:

ArrayList<String> names = new ArrayList<>();

names.add("Ada");
names.add("Grace");
names.add("Alan");

names.remove("Grace");

The number of elements stored in names changes over time.

A dynamic structure does not have unlimited memory. It still depends on the memory available to the program.

"Dynamic" means that the programmer does not have to decide one permanent fixed size when the structure is created.

Compare:

int[] values = new int[10];

with:

ArrayList<Integer> values = new ArrayList<>();

The array permanently has length 10.

The ArrayList can logically grow and shrink.

5. What is a list?

A list is an ordered sequence of elements.

For example:

[17, 23, 41, 8]

or:

["Alice", "Bob", "Carlos"]

"Ordered" means that elements have positions relative to one another.

In:

["Alice", "Bob", "Carlos"]

we know that:

  • "Alice" is first,
  • "Bob" comes after "Alice",
  • "Carlos" comes after "Bob".

A list commonly supports operations such as:

add(element)
add(index, element)
get(index)
set(index, element)
remove(index)
size()
contains(element)

Notice that none of those operations tells us how the data must be stored internally.

That leads to an important computer-science distinction.

6. Abstract data types

An Abstract Data Type, or ADT, describes:

  • what type of information is represented;
  • what operations are available;
  • what those operations mean.

It does not require one particular internal representation.

For example, a List ADT might support:

add
remove
get
set
size
contains

But the list could internally be represented using:

an array

or:

linked nodes

We can visualize this as:

                 List ADT
                    |
          +---------+---------+
          |                   |
          v                   v
   array-based list      linked list

The distinction is:

WHAT                        HOW

List operations             resizable array
                            linked nodes

This separation is fundamental in both data structures and object-oriented design.

An abstraction describes behavior. An implementation determines how that behavior is achieved.

9. Adding elements to an ArrayList

The simplest form of add appends an element.

ArrayList<String> names = new ArrayList<>();

names.add("Alice");
names.add("Bob");
names.add("Carlos");

After these statements:

0: Alice
1: Bob
2: Carlos

We can also insert at a particular position:

names.add(1, "Diana");

Now:

0: Alice
1: Diana
2: Bob
3: Carlos

The previous elements at positions 1 and later had to move one position to the right.

This will become important when we discuss time complexity.

10. Accessing elements

Use get(index):

String name = names.get(1);

If:

0: Alice
1: Bob
2: Carlos

then:

names.get(1)

returns:

Bob

Just like arrays, ArrayList uses zero-based indexing.

So for a list of size n, the valid indices are:

0 through n - 1

11. Replacing elements with set

Use:

names.set(1, "Barbara");

If the list was:

[Alice, Bob, Carlos]

it becomes:

[Alice, Barbara, Carlos]

set replaces an existing element.

It does not append.

For example, if:

names.size() == 3

then:

names.set(3, "David");

is invalid because index 3 does not yet exist.

To append "David":

names.add("David");

12. Removing elements

You can remove by index:

names.remove(1);

Suppose:

0: Alice
1: Bob
2: Carlos
3: Diana

After:

names.remove(1);

the list becomes:

0: Alice
1: Carlos
2: Diana

The elements after the removed value shift left.

Conceptually:

Before:

[Alice][Bob][Carlos][Diana]

Remove Bob:

[Alice][   ][Carlos][Diana]

Shift:

[Alice][Carlos][Diana]

This shifting is why removal near the front of an array-based list can require O(n) work.

13. Iterating over an ArrayList

A traditional for loop works well when indices matter:

for (int i = 0; i < names.size(); i++) {
    System.out.println(i + ": " + names.get(i));
}

An enhanced for loop works well when we simply need each element:

for (String name : names) {
    System.out.println(name);
}

Example:

ArrayList<Double> scores = new ArrayList<>();

scores.add(87.5);
scores.add(92.0);
scores.add(76.5);
scores.add(100.0);

double total = 0;

for (double score : scores) {
    total += score;
}

double average = total / scores.size();

System.out.println("Average: " + average);

14. Generics and wrapper classes

Notice the syntax:

ArrayList<String>

The type inside < > tells Java what kind of element the list stores.

Examples:

ArrayList<String> names = new ArrayList<>();
ArrayList<Double> prices = new ArrayList<>();
ArrayList<Student> students = new ArrayList<>();

Java generics do not directly use primitive types.

This is invalid:

ArrayList<int> numbers;      // invalid

Instead, use Java's wrapper classes.

PrimitiveWrapper
intInteger
doubleDouble
charCharacter
booleanBoolean

Therefore:

ArrayList<Integer> numbers = new ArrayList<>();

works.

Java can automatically convert:

numbers.add(5);

from primitive int to Integer.

This is called autoboxing.

Likewise:

int x = numbers.get(0);

automatically converts an Integer back to int.

This is called unboxing.

15. How can an ArrayList grow if arrays cannot?

An important fact is:

ArrayList is internally based on an array.

Suppose the logical contents are:

[A][B][C]

The internal representation might conceptually look like:

+---+---+---+---+---+---+
| A | B | C |   |   |   |
+---+---+---+---+---+---+

size = 3
capacity = 6

The ArrayList has three logical elements, but its underlying array has extra unused locations.

16. Size versus capacity

These terms describe different things.

Size

The size is the number of actual elements currently stored.

list.size()

Capacity

The capacity is the amount of underlying storage currently available before a larger array is required.

For example:

+----+----+----+----+----+----+----+----+
| 17 | 21 | 33 | 48 |    |    |    |    |
+----+----+----+----+----+----+----+----+

size = 4
capacity = 8

Application code normally cares about the size.

The ArrayList implementation manages capacity internally.

17. Resizing an ArrayList

Suppose the underlying array is full:

+---+---+---+---+
| A | B | C | D |
+---+---+---+---+

and we execute:

list.add("E");

The existing array itself cannot become larger.

Instead, the implementation conceptually:

  1. allocates a larger array;
  2. copies the existing elements into it;
  3. places the new element into the new storage;
  4. begins using the new array.

Conceptually:

OLD

+---+---+---+---+
| A | B | C | D |
+---+---+---+---+


NEW

+---+---+---+---+---+---+---+---+
| A | B | C | D | E |   |   |   |
+---+---+---+---+---+---+---+---+

A dynamic array does not literally stretch.

It occasionally replaces its underlying array with a larger one.

18. Why not resize on every add?

Imagine resizing exactly to the new size every time:

size 1 -> allocate capacity 1
size 2 -> allocate capacity 2 and copy
size 3 -> allocate capacity 3 and copy
size 4 -> allocate capacity 4 and copy
...

This would cause frequent copying.

Instead, dynamic array implementations reserve extra capacity.

Conceptually, capacity might grow something like:

4
8
16
32
64
...

The exact strategy is an implementation detail.

The important principle is:

Extra unused capacity makes most append operations inexpensive.

19. ArrayList time complexity

For a list containing n elements, typical costs are:

OperationTypical Complexity
get(index)O(1)
set(index, value)O(1)
append using add(value)O(1) amortized
insert near frontO(n)
remove near frontO(n)
search by valueO(n)
traverse all elementsO(n)

Why is get(index) O(1)?

Because the underlying array provides direct indexed access.

Why can insertion be O(n)?

Because existing elements may need to shift.

Suppose:

[A][B][C][D][ ]

and we insert X at index 1.

The implementation must conceptually create space:

[A][B][C][D][D]
[A][B][C][C][D]
[A][B][B][C][D]
[A][X][B][C][D]

The closer the insertion is to the beginning, the more elements may need to move.

20. Amortized O(1)

Appending to an ArrayList is commonly described as:

O(1) amortized

Why not simply O(1)?

Most additions require only placing the new element into an unused location.

Occasionally, however, the internal array becomes full and a larger one must be allocated and copied.

So individual append operations are not all equally cheap.

However, when the occasional resizing cost is averaged across many append operations, the average cost per append remains constant.

That is the idea behind amortized constant time.

For CSC 500, the important conclusion is:

ArrayList.add(value) is usually very efficient when adding to the end.

21. A different representation: Linked structures

An ArrayList still depends on contiguous array storage.

Could we build a collection in which elements do not have to occupy neighboring array positions?

Yes.

Instead of storing values beside one another, we can create separate objects and connect them with references.

This produces a linked structure.

The simplest important example is the singly linked list.

22. Review of Java references

Before learning linked lists, we must understand object references.

Consider:

Student s1 = new Student("Alice");
Student s2 = s1;

This does not create two Student objects.

Conceptually:

s1 -----+
        |
        v
      +-------+
      | Alice |
      +-------+
        ^
        |
s2 -----+

Both variables refer to the same object.

Therefore:

s1.setName("Alicia");

System.out.println(s2.getName());

prints:

Alicia

because s1 and s2 refer to the same object.

23. Copying a reference is not copying an object

Consider:

Node a = new Node(10);
Node b = a;

This does not create a second node.

It copies the reference.

Conceptually:

a -------+
         |
         v
      +------+
      |  10  |
      +------+
         ^
         |
b -------+

If we change the object through b:

b.data = 99;

then:

System.out.println(a.data);

also prints:

99

because there is only one node object.

24. Aliasing

When two or more references refer to the same object, we call this aliasing.

Example:

Node first = new Node(10);
Node second = first;

first and second are aliases.

Aliasing is important in linked structures because several variables may temporarily refer to the same node.

For example:

head
 |
 v
[A] -> [B] -> [C]
 ^
 |
current

Here, both head and current refer to the same node.

Changing current itself does not necessarily change head.

25. What is a node?

A node is a small object used as a building block for a linked structure.

A simple node might be:

private static class Node {
    int data;
    Node next;

    Node(int data) {
        this.data = data;
        this.next = null;
    }
}

Each node contains:

  1. data;
  2. a reference to another node.

Conceptually:

+------+------+
|  17  | next |
+------+------+

The field:

Node next;

does not physically contain another whole node.

It contains a reference to another Node object.

26. Connecting nodes

Consider:

Node first = new Node(10);
Node second = new Node(20);

first.next = second;

Conceptually:

first
 |
 v
+----+-----+        +----+------+
| 10 |  o---------->| 20 | null |
+----+-----+        +----+------+

The objects are separate.

The reference stored in first.next connects them.

We can add another node:

Node third = new Node(30);
second.next = third;

Now:

first
 |
 v
[10] -> [20] -> [30] -> null

27. The meaning of null

A reference value of:

null

means that the reference currently refers to no object.

In a normal singly linked list, the final node has:

next == null

Example:

[10] -> [20] -> [30] -> null

The null tells a traversal algorithm that it has reached the end.

28. The head reference

A linked-list object usually stores a reference to the first node.

We commonly call it:

head

For an empty list:

head == null

For a non-empty list:

head
 |
 v
[10] -> [20] -> [30] -> null

head is extremely important because it gives us access to the chain of nodes.

If the list contains:

head -> [A] -> [B] -> [C]

and we incorrectly overwrite head:

head = new Node("X");

then the list object may no longer have any path to A, B, or C.

29. Reachability

A node is reachable if the program can get to it through some chain of references.

For:

head -> [A] -> [B] -> [C] -> null

all three nodes are reachable from head.

Suppose we execute:

head = head.next;

Now:

head -> [B] -> [C] -> null

[A]

If no other variable refers to A, then A is no longer reachable.

This matters both structurally and for memory management.

30. Garbage collection

Java automatically manages object memory.

When an object becomes unreachable, it becomes eligible for garbage collection.

Example:

Node n = new Node(10);
n = null;

If no other reference reaches that node, the program can no longer use it.

Java may eventually reclaim its memory.

Likewise, if:

head = head.next;

removes the only reference path to the original first node, that node can eventually be collected.

Important:

Garbage collection is not necessarily immediate.

The key conceptual idea is that unreachable objects are eligible to be reclaimed.

31. A singly linked list

A singly linked list consists of nodes where each node stores one link to the next node.

head
 |
 v
+----+---+     +----+---+     +----+------+
| 10 | o------>| 20 | o------>| 30 | null |
+----+---+     +----+---+     +----+------+

The structure itself is determined by the references.

The nodes do not have to be stored next to one another in memory.

32. Traversing a linked list

Unlike an array, we cannot simply write:

list[i]

to jump to an arbitrary linked node.

Instead, we follow references.

A standard traversal pattern is:

Node current = head;

while (current != null) {
    System.out.println(current.data);
    current = current.next;
}

There are three important steps:

  1. begin at head;
  2. process the current node;
  3. move to the next node.

Repeat until:

current == null

33. Tracing a traversal

Suppose:

head
 |
 v
[7] -> [12] -> [25] -> null

Initially:

Node current = head;

So:

current -> 7

After:

current = current.next;

we have:

current -> 12

After another:

current = current.next;

we have:

current -> 25

After another:

current = current.next;

we have:

current -> null

The loop stops.

No node moved.

Only the reference stored in current changed.

34. current = current.next does not modify the list

This distinction is crucial.

current = current.next;

changes which object the variable current refers to.

It normally does not modify any node.

Compare:

current = current.next;

with:

current.next = newNode;

The first changes a local variable.

The second changes the next field inside a node, so it changes the structure.

A useful mental model is:

variable = ...

usually changes what the variable refers to.

object.field = ...

changes part of the object itself.

35. Why we should not traverse using head

This is safe:

Node current = head;

while (current != null) {
    System.out.println(current.data);
    current = current.next;
}

This is dangerous:

while (head != null) {
    System.out.println(head.data);
    head = head.next;
}

At the end of the second version:

head == null

The list object has lost its reference to the chain.

Therefore:

Use a temporary traversal variable unless changing head is intentionally part of the operation.

36. Complexity of traversal

If the list has n nodes, a complete traversal visits all n.

Therefore:

O(n)

This applies to operations such as:

  • printing every node;
  • counting every node;
  • searching an unsorted list;
  • finding the final node if no tail reference exists.

37. Searching a linked list

A typical search:

public boolean contains(int target) {
    Node current = head;

    while (current != null) {
        if (current.data == target) {
            return true;
        }

        current = current.next;
    }

    return false;
}

Worst case:

  • the target is the last node; or
  • the target is absent.

Then every node must be inspected.

Therefore:

O(n)

38. Searching lists of objects

For primitive int values:

if (current.data == target)

is appropriate.

For objects such as String, the meaning of equality matters.

For example:

String a = new String("hello");
String b = new String("hello");

Then:

a == b

asks whether a and b refer to the same object.

It is normally false.

But:

a.equals(b)

compares their logical string values and is true.

Therefore a linked list of strings might search with:

if (current.data.equals(target)) {
    return true;
}

39. Accessing element at index i

Arrays provide direct access:

array[i]

A linked list does not.

Suppose:

head
 |
 v
[0] -> [1] -> [2] -> [3] -> [4]

To retrieve index 4, we must follow the links.

A possible implementation:

public int get(int index) {
    if (index < 0 || index >= size) {
        throw new IndexOutOfBoundsException();
    }

    Node current = head;

    for (int i = 0; i < index; i++) {
        current = current.next;
    }

    return current.data;
}

Worst-case complexity:

O(n)

This is one of the most important differences between arrays and linked lists.

40. Random access versus sequential access

Arrays and ArrayList provide random access.

For example:

array[900000]

or:

list.get(900000)

can directly locate the desired position in an array-based representation.

Linked lists provide sequential access.

To reach a node far into the list, the program usually has to follow every preceding link.

Therefore:

Array / ArrayList indexed access: O(1)

Singly linked-list indexed access: O(n)

41. A common linked-list performance mistake

Suppose get(i) on a linked list takes O(n).

Then code such as:

for (int i = 0; i < list.size(); i++) {
    System.out.println(list.get(i));
}

can be expensive.

Each call to get(i) walks through the list again.

Conceptually:

get(0):  short traversal
get(1):  traversal again
get(2):  traversal again
...
get(n):  long traversal

The complete loop may therefore approach:

O(n²)

A single pointer-based traversal:

Node current = head;

while (current != null) {
    System.out.println(current.data);
    current = current.next;
}

requires only:

O(n)

The lesson is broader than linked lists:

The same logical task can have very different performance depending on how we use the data structure.

42. Adding at the front

Suppose:

head
 |
 v
[20] -> [30] -> null

We want:

head
 |
 v
[10] -> [20] -> [30] -> null

Create a new node:

Node newNode = new Node(10);

Initially:

newNode -> [10] -> null

head    -> [20] -> [30] -> null

First preserve the existing list:

newNode.next = head;

Now:

newNode -> [10] -> [20] -> [30]
                     ^
                     |
                    head

Then:

head = newNode;

Final result:

head
 |
 v
[10] -> [20] -> [30] -> null

Method:

public void addFirst(int value) {
    Node newNode = new Node(value);

    newNode.next = head;
    head = newNode;
}

43. Why assignment order matters

This order is correct:

newNode.next = head;
head = newNode;

Consider reversing it:

head = newNode;
newNode.next = head;

After:

head = newNode;

both head and newNode refer to the newly created node.

Therefore:

newNode.next = head;

becomes equivalent to:

newNode.next = newNode;

We create:

 +------+
 |      |
 v      |
[10] ---+

and we may lose access to the original list.

Important rule:

Preserve the reference you still need before overwriting the reference that reaches it.

44. Complexity of adding at the front

The operation:

newNode.next = head;
head = newNode;

takes the same number of reference assignments whether the list contains:

3 nodes
300 nodes
3,000,000 nodes

No existing nodes move.

Therefore:

addFirst = O(1)

45. Adding at the end

Suppose:

head
 |
 v
[10] -> [20] -> [30] -> null

and we want:

[10] -> [20] -> [30] -> [40] -> null

Without any additional information, we first locate the last node:

Node current = head;

while (current.next != null) {
    current = current.next;
}

Then:

current.next = new Node(40);

A complete version must also handle the empty list:

public void addLast(int value) {
    Node newNode = new Node(value);

    if (head == null) {
        head = newNode;
        return;
    }

    Node current = head;

    while (current.next != null) {
        current = current.next;
    }

    current.next = newNode;
}

46. Empty-list boundary case

If:

head == null

then code such as:

while (current.next != null)

is unsafe if:

current == null

because evaluating:

current.next

would throw a:

NullPointerException

Dynamic data-structure methods often require explicit attention to the empty structure.

47. Adding a tail reference

If we only store:

Node head;

then appending requires traversing to the last node:

O(n)

We can instead store:

Node head;
Node tail;

For:

head
 |
 v
[A] -> [B] -> [C] -> null
              ^
              |
             tail

we already know where the final node is.

Then appending can be:

O(1)

because we do not need to search for the end.

For a non-empty list:

tail.next = newNode;
tail = newNode;

48. head and tail for an empty list

A common representation is:

head = null;
tail = null;

When the first element is inserted:

head
 |
 v
[A]
 ^
 |
tail

both references point to the same node.

In code:

if (head == null) {
    head = newNode;
    tail = newNode;
}

This is an example of a boundary case that must be handled carefully.

49. Inserting after a node

Suppose:

[A] -> [B] -> [C]

and:

current -> B

We want to insert X:

[A] -> [B] -> [X] -> [C]

Create:

Node newNode = new Node("X");

First preserve the link to C:

newNode.next = current.next;

Then change B's link:

current.next = newNode;

Complete operation:

newNode.next = current.next;
current.next = newNode;

50. Why the insertion order matters

Incorrect:

current.next = newNode;
newNode.next = current.next;

After the first statement:

current.next

already refers to newNode.

Therefore the second statement becomes:

newNode.next = newNode;

again creating a self-reference.

Correct:

newNode.next = current.next;
current.next = newNode;

Always think about the arrows after every assignment.

51. Removing the first node

Suppose:

head
 |
 v
[10] -> [20] -> [30] -> null

To remove the first node:

head = head.next;

Now:

head
 |
 v
[20] -> [30] -> null

If nothing else refers to the old node containing 10, it becomes unreachable and eligible for garbage collection.

Removing the front of a singly linked list therefore requires:

O(1)

reference work.

52. Removing a node from the middle

Suppose:

[10] -> [20] -> [30] -> [40]

and:

current -> [20]

To remove the node containing 30:

current.next = current.next.next;

Before:

current
 |
 v
[20] -> [30] -> [40]

After:

current
 |
 v
[20] ----------> [40]

[30]

The node containing 30 has been bypassed.

53. Why we often need the previous node

Suppose:

[A] -> [B] -> [C]

We want to remove B.

The reference that must change is not inside B.

It is:

A.next

We need to change:

A.next -> B

into:

A.next -> C

This is why singly linked-list deletion algorithms often:

  • keep a previous reference;
  • or inspect current.next and stop one node before the target.

54. Removing a value

One possible implementation:

public boolean remove(int target) {

    if (head == null) {
        return false;
    }

    if (head.data == target) {
        head = head.next;
        return true;
    }

    Node current = head;

    while (current.next != null) {

        if (current.next.data == target) {
            current.next = current.next.next;
            return true;
        }

        current = current.next;
    }

    return false;
}

Notice that the loop examines:

current.next.data

because current needs to remain positioned at the node whose next field must be changed.

55. Singly versus doubly linked lists

A singly linked node has:

Node next;

Conceptually:

[A] -> [B] -> [C]

A doubly linked list stores both:

Node next;
Node previous;

Conceptually:

null <- [A] <-> [B] <-> [C] -> null

Advantages of doubly linked lists include:

  • traversal in both directions;
  • easier access to a preceding node when the current node is already known;
  • some removals become easier to express.

Costs include:

  • an additional reference per node;
  • more links to update;
  • more opportunities for reference errors.

For CSC 500, the central goal is understanding this representation tradeoff rather than memorizing a complete doubly linked-list implementation.

56. Maintaining a size field

A linked list can calculate its size by traversing:

public int size() {
    int count = 0;

    Node current = head;

    while (current != null) {
        count++;
        current = current.next;
    }

    return count;
}

This requires:

O(n)

time.

Alternatively, the object can store:

private int size;

and update it on every modification.

Then:

public int size() {
    return size;
}

takes:

O(1)

The tradeoff is that every modifying operation must maintain the field correctly.

For example:

public void addFirst(int value) {
    Node newNode = new Node(value);
    newNode.next = head;
    head = newNode;

    size++;
}

For removal:

size--;

must happen exactly when an element is successfully removed.

57. Structural invariants

An invariant is a condition that should remain true whenever the data structure is in a valid state.

For a simple singly linked list, possible invariants include:

  1. If the list is empty:
   head == null
  1. Every node belonging to the list is reachable from head.
  1. The final node has:
   next == null
  1. If a size field exists, it equals the number of reachable nodes.
  1. If a tail field exists and the list is non-empty:
   tail.next == null
  1. If both head and tail are used, an empty list typically satisfies:
   head == null && tail == null

Thinking in terms of invariants is a powerful debugging strategy.

Instead of asking only:

"Why is my output wrong?"

ask:

"Which structural rule became false, and which assignment caused it?"

58. A simple linked-list class

Here is a complete basic implementation:

public class IntLinkedList {

    private static class Node {
        int data;
        Node next;

        Node(int data) {
            this.data = data;
            this.next = null;
        }
    }

    private Node head;
    private int size;

    public IntLinkedList() {
        head = null;
        size = 0;
    }

    public int size() {
        return size;
    }

    public boolean isEmpty() {
        return size == 0;
    }

    public void addFirst(int value) {
        Node newNode = new Node(value);

        newNode.next = head;
        head = newNode;

        size++;
    }

    public void addLast(int value) {
        Node newNode = new Node(value);

        if (head == null) {
            head = newNode;
            size++;
            return;
        }

        Node current = head;

        while (current.next != null) {
            current = current.next;
        }

        current.next = newNode;
        size++;
    }

    public boolean contains(int value) {
        Node current = head;

        while (current != null) {
            if (current.data == value) {
                return true;
            }

            current = current.next;
        }

        return false;
    }

    public int get(int index) {
        if (index < 0 || index >= size) {
            throw new IndexOutOfBoundsException();
        }

        Node current = head;

        for (int i = 0; i < index; i++) {
            current = current.next;
        }

        return current.data;
    }

    public int removeFirst() {
        if (head == null) {
            throw new IllegalStateException("List is empty");
        }

        int removedValue = head.data;
        head = head.next;
        size--;

        return removedValue;
    }

    public boolean remove(int target) {
        if (head == null) {
            return false;
        }

        if (head.data == target) {
            head = head.next;
            size--;
            return true;
        }

        Node current = head;

        while (current.next != null) {
            if (current.next.data == target) {
                current.next = current.next.next;
                size--;
                return true;
            }

            current = current.next;
        }

        return false;
    }

    public void print() {
        Node current = head;

        while (current != null) {
            System.out.print(current.data + " ");
            current = current.next;
        }

        System.out.println();
    }

    public void clear() {
        head = null;
        size = 0;
    }
}

63. Sentinel nodes

A linked list can also be implemented using a sentinel, or dummy, node.

Instead of:

head -> [A] -> [B] -> [C]

the structure could be:

sentinel -> [A] -> [B] -> [C]

The sentinel is not ordinary user data.

Its purpose is to simplify certain boundary cases.

For example, insertion and deletion at the logical beginning of the list can become more similar to insertion and deletion elsewhere.

A sentinel is an implementation technique, not a requirement.

It illustrates a useful design principle:

Sometimes a small amount of additional structure can simplify algorithms.

64. Common linked-list bugs

Reference-based structures can fail in ways that ordinary numeric code does not.

Bug 1: Losing part of the list

Suppose:

[A] -> [B] -> [C]

and you overwrite the reference to B before preserving it.

A portion of the chain may become unreachable.

Bug 2: Creating a self-reference

For example:

newNode.next = newNode;

when this was not intended.

Then:

 +------+
 |      |
 v      |
[X] ----+

Bug 3: Creating a cycle

Example:

Node a = new Node(10);
Node b = new Node(20);

a.next = b;
b.next = a;

produces:

[A] -> [B]
 ^      |
 |______|

A traversal waiting for null will never terminate.

Bug 4: Forgetting to advance

Node current = head;

while (current != null) {
    System.out.println(current.data);

    // missing:
    // current = current.next;
}

This repeatedly processes the same node forever.

Bug 5: Dereferencing null

current.next.data

requires current and current.next to refer to valid objects.

If either is null, the statement can cause a NullPointerException.

Bug 6: Mishandling the empty list

Code may assume:

head != null

when the structure is empty.

Bug 7: Mishandling the one-element list

If both head and tail are used, removing the only element may require both to become:

null

Bug 8: Incorrect size

Forgetting:

size++;

after insertion or:

size--;

after removal breaks the representation's invariants.

Bug 9: Comparing objects incorrectly

Using:

==

when logical value comparison requires:

.equals()

can make searches behave incorrectly.

65. Understanding NullPointerException

Consider:

Node current = null;

System.out.println(current.data);

This fails because current does not refer to an object.

Similarly:

while (current.next != null) {
    ...
}

is unsafe if current might itself be null.

An important debugging question is:

Is the reference to the left of the dot guaranteed to refer to an actual object?

Examples:

current.next
student.getName()

all require the reference before . to be non-null.

69. Drawing references before coding

70. Reverse a linked list: Reference-reasoning challenge

Suppose:

10 -> 20 -> 30 -> 40 -> null

We want:

40 -> 30 -> 20 -> 10 -> null

A standard iterative algorithm uses three references:

Node previous = null;
Node current = head;

while (current != null) {
    Node next = current.next;

    current.next = previous;

    previous = current;
    current = next;
}

head = previous;

The key statement is:

Node next = current.next;

Why must we save next first?

Because:

current.next = previous;

changes the forward link.

If we did not preserve the original next node, we could lose access to the rest of the list.

This illustrates a general principle:

Save a reference before modifying the link through which you will still need to travel.

71. Array-based lists versus linked lists

The two structures represent a list differently.

Array-based list

+---+---+---+---+---+
| A | B | C | D |   |
+---+---+---+---+---+

Elements occupy indexed positions in an underlying array.

Linked list

[A | o] -> [B | o] -> [C | o] -> [D | null]

Each element is stored in a separate node connected by references.

73. Why linked-list insertion is not automatically O(1)

Students often hear:

"Insertion in a linked list is O(1)."

That statement requires an important qualification.

If we already have a reference to the correct predecessor node, then:

newNode.next = current.next;
current.next = newNode;

does require only constant work.

But suppose the program says:

Insert at position 800,000.

We first have to locate that position.

That search can take:

O(n)

Therefore:

locate position: O(n)
change references: O(1)
overall: O(n)

The location cost matters.

74. Memory tradeoffs

Arrays store their contents compactly.

Conceptually:

[10][20][30][40]

A singly linked node must store both:

data
next reference

So:

[10|o] -> [20|o] -> [30|o] -> [40|null]

Each node is also a separate object.

Linked structures therefore generally use more per-element memory than a compact array representation.

This is another example of a data-structure tradeoff:

Improving one kind of operation may require additional memory or structural complexity.

75. Which representation is better?

There is no universally best data structure.

Instead ask:

  1. What data must the program represent?
  2. Which operations are required?
  3. Which operations occur most frequently?
  4. Is indexed access important?
  5. Where do insertions and removals occur?
  6. Do we already know the relevant node location?
  7. How much memory overhead is acceptable?
  8. How complicated is the implementation?
  9. Does Java already provide a suitable library implementation?

The correct goal is not:

"Choose the most advanced structure."

It is:

Choose the representation whose properties match the problem.

76. Choosing between array, ArrayList, and linked list

Consider an array when:

  • size is known and fixed;
  • indexed access is important;
  • primitives are stored directly;
  • low overhead matters.

Example:

double[] monthlyTemperatures = new double[12];

The number of months is fixed.

Consider ArrayList when:

  • the collection must grow or shrink;
  • indexed access is common;
  • most insertion happens near the end;
  • you want a general-purpose Java list.

Example:

ArrayList<Student> students = new ArrayList<>();

For many ordinary Java list problems, ArrayList is a reasonable default.

Consider a linked representation when:

  • structural insertion/removal is central;
  • the relevant node positions are already known;
  • sequential access is natural;
  • the design naturally involves links.

The point is not that linked lists are universally faster.

Performance depends on how the structure is used.

81. Common misconceptions

Misconception 1: "ArrayList does not use arrays."

Incorrect.

ArrayList provides a dynamic List abstraction but uses an underlying array internally.

Misconception 2: "ArrayList grows by stretching its array."

Incorrect.

Java arrays cannot change length.

An ArrayList occasionally creates a larger array and copies its existing contents.

Misconception 3: "A linked list is always faster than an ArrayList."

Incorrect.

Performance depends on the operation.

Examples:

indexed access:
ArrayList O(1)
linked list O(n)

while:

remove first:
ArrayList O(n)
linked list O(1)

Misconception 4: "Linked-list insertion is always O(1)."

Not necessarily.

Changing the references may be O(1) once the location is known.

Finding the correct location may require:

O(n)

Misconception 5: "Node b = a; copies the node."

Incorrect.

It copies the reference.

Both variables then refer to the same object.

Misconception 6: "A node contains the entire next node."

Incorrect.

A field such as:

Node next;

stores only a reference to another node.

Misconception 7: "current = current.next changes the list."

Usually false.

It moves the variable current.

It does not normally alter any next field.

Misconception 8: "head = head.next is equivalent to current = current.next."

They may both follow a next reference, but their structural meaning differs.

current = current.next;

normally moves a temporary variable.

head = head.next;

changes which node the list considers its first node.

Misconception 9: "Linked nodes physically move during traversal."

No.

Nodes remain where they are.

References change which node a variable denotes.

Misconception 10: "null is a node."

No.

null means the reference points to no object.

83. Concept checks

1. Why can an ArrayList grow if an array cannot?

Because the ArrayList can allocate a new, larger array and copy existing elements into it.

2. What is the difference between size and capacity?

Size is the number of logical elements.

Capacity is the amount of underlying array storage currently available.

3. Why is ArrayList.get(i) O(1)?

Because the underlying array provides direct indexed access.

4. Why is linked-list get(i) O(n)?

Because the list generally must follow links from the beginning until reaching position i.

5. Why is adding to the front of a singly linked list O(1)?

Because only a constant number of references change.

6. Why can adding near the front of an ArrayList be O(n)?

Because later elements must shift.

7. What does head represent?

A reference to the first node.

8. What does null represent at the end of a singly linked list?

There is no next node.

9. Does this copy a node?

Node b = a;

No. It copies a reference.

10. Why should traversal normally use current instead of changing head?

Because head represents the structure's entry point. Changing it can remove access to nodes.

11. Why is assignment order important during insertion?

Because overwriting a reference too early can destroy the only path to existing nodes or create a self-reference/cycle.

12. Why might we maintain a tail reference?

To avoid traversing the list whenever we append.

13. Why might we maintain a size field?

So size() can run in O(1) instead of traversing all nodes.

14. What is an invariant?

A condition that should remain true whenever the data structure is in a valid state.

15. Is a linked list an ADT?

More precisely, the List is the abstraction. A linked list is one possible implementation strategy.

86. End-of-week comparison

Array

String[] names = new String[10];

Characteristics:

  • fixed length;
  • built into Java;
  • direct indexed access;
  • can directly store primitives;
  • compact representation.

ArrayList

ArrayList<String> names =
        new ArrayList<>();

Characteristics:

  • dynamically sized;
  • implemented with an array;
  • direct indexed access;
  • convenient list API;
  • insertions/removals may shift elements;
  • append is normally inexpensive.

Linked list

Conceptually:

[data|next] -> [data|next] -> [data|null]

Characteristics:

  • dynamically sized;
  • node-based representation;
  • uses references;
  • sequential rather than random access;
  • efficient insertion/removal when the relevant node location is already known;
  • higher per-element memory overhead;
  • reference manipulation requires careful reasoning.

90. Final study strategy

Linked lists become much easier when you stop treating them as mysterious code and begin treating them as diagrams.

For every operation, ask:

  1. What objects exist before the operation?
  2. What references exist before the operation?
  3. Which reference do I need to preserve?
  4. Which arrow must change?
  5. What should the structure look like afterward?
  6. Can every intended node still be reached from head?
  7. Could any reference be null?
  8. What happens for an empty list?
  9. What happens for a one-element list?
  10. Are head, tail, and size still consistent?

For example, do not memorize:

newNode.next = current.next;
current.next = newNode;

Instead, begin with:

[A] -> [B]

decide that you want:

[A] -> [X] -> [B]

and reason that the required links are:

X.next -> B
A.next -> X

The Java statements then follow naturally.

91. Week 12 summary

This week moves us from fixed collections toward dynamic data structures.

An array gives us:

[A][B][C][D]

with fixed length and efficient indexed access.

An ArrayList extends that idea:

[A][B][C][D][ ][ ][ ]

by maintaining extra capacity and occasionally allocating larger array storage.

A linked list takes a fundamentally different approach:

[A|o] -> [B|o] -> [C|null]

where separate node objects are connected through references.

The most important ideas are:

  • a list is an abstraction;
  • one abstraction can have multiple implementations;
  • ArrayList uses an underlying array;
  • linked lists use nodes and references;
  • array-based representations support efficient indexed access;
  • linked representations support efficient structural changes when the relevant location is already known;
  • reference assignment order matters;
  • dynamic structures must maintain invariants;
  • boundary cases such as empty and one-element lists must be tested deliberately;
  • there is no universally best data structure;
  • data-structure choice depends on the operations a program performs.

The larger lesson is:

Data structures are not merely containers for values. They are representations that determine how efficiently a program can access, modify, and organize information.

And the linked list introduces an idea that will become increasingly important:

objects connected by references

Once this model is understood, more complex dynamic structures become much easier to reason about.
