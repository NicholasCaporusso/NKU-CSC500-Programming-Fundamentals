Learning objectives

By the end of this week, students should be able to:

  • distinguish between a class and an object
  • identify appropriate classes in a problem description
  • use encapsulation to protect an object's internal state
  • explain the difference between instance members and static members

1. From programming to program design

So far, we have learned how to write Java programs using:

  • variables
  • conditionals
  • loops
  • methods
  • arrays
  • strings
  • classes and objects

Knowing how to write individual Java statements is important, but larger programs require another skill:

How should we organize the program?

Suppose we want to build a program for a university.

We might need to represent:

  • students
  • courses
  • instructors
  • departments
  • enrollments
  • grades

One approach would be to place everything in one large class.

For example:

public class UniversityProgram {

    public static void main(String[] args) {

        String studentName = "Alice";
        int studentId = 12345;

        String courseName = "Programming Fundamentals";
        String courseCode = "CSC500";

        String instructorName = "Dr. Smith";

        // hundreds of additional variables and methods
    }
}

This approach quickly becomes difficult to manage.

Instead, object-oriented programming encourages us to organize a program around objects that represent meaningful concepts in the problem domain.

We might create:

Student
Course
Instructor
Department
Enrollment

Each class becomes responsible for representing one concept.

2. Review: classes and objects

A class describes a type of object.

An object is an instance of that class.

For example:

public class Student {

    private String name;
    private int id;

    public Student(String name, int id) {
        this.name = name;
        this.id = id;
    }

    public String getName() {
        return name;
    }

    public int getId() {
        return id;
    }
}

We can create objects from this class:

Student s1 = new Student("Alice", 12345);
Student s2 = new Student("Bob", 67890);

Here:

Student

is the class.

And:

s1
s2

refer to two different Student objects.

Each object has its own state.

3. State and behavior

Objects typically contain two things:

State

State describes what an object currently knows.

Examples for a student:

name
student ID
GPA
major
number of credits

These are usually represented using instance variables.

For example:

private String name;
private int id;
private double gpa;

Behavior

Behavior describes what an object can do.

Examples:

register for a course
change major
calculate academic standing
display student information

These behaviors are represented using methods.

Example:

public void changeMajor(String newMajor) {
    major = newMajor;
}

A useful design question is therefore:

What information should this object know, and what operations should it perform?

4. Encapsulation

One of the central principles of object-oriented programming is encapsulation.

Encapsulation means:

An object controls access to its internal state.

Suppose we have a bank account.

A poor design might look like this:

public class BankAccount {

    public double balance;
}

Now another part of the program can write:

BankAccount account = new BankAccount();

account.balance = -1000000;

Nothing prevents the balance from becoming invalid.

A better design hides the field:

public class BankAccount {

    private double balance;

    public BankAccount(double initialBalance) {
        balance = initialBalance;
    }

    public double getBalance() {
        return balance;
    }

    public void deposit(double amount) {
        if (amount > 0) {
            balance += amount;
        }
    }
}

Now outside code cannot directly change the balance.

Instead, changes must go through controlled methods.

5. Why encapsulation matters

Encapsulation helps us enforce the rules of an object.

For example:

public void withdraw(double amount) {

    if (amount > 0 && amount <= balance) {
        balance -= amount;
    }
}

The BankAccount class is responsible for ensuring that the account remains valid.

This idea is important:

The class that owns the data should usually enforce the rules for that data.

A class should not simply expose all of its fields.

For example, avoid:

public double balance;
public String accountNumber;
public String owner;

Prefer:

private double balance;
private String accountNumber;
private String owner;

and provide appropriate operations.

6. Getters and setters

Students often learn the following pattern:

private int age;

public int getAge() {
    return age;
}

public void setAge(int age) {
    this.age = age;
}

But object-oriented design does not mean automatically creating a getter and setter for every field.

Consider:

public void setBalance(double balance) {
    this.balance = balance;
}

This method allows outside code to bypass the rules of the bank account.

Instead, we might provide meaningful operations:

deposit(amount)
withdraw(amount)
transfer(amount)

This is usually better than:

setBalance(...)

because the methods describe actual operations in the problem domain.

7. Instance variables and instance methods

An instance variable belongs to a particular object.

Example:

public class Student {

    private String name;
}

If we create:

Student s1 = new Student("Alice");
Student s2 = new Student("Bob");

then each object has its own name.

Conceptually:

s1
name = "Alice"

s2
name = "Bob"

An instance method operates on a particular object.

For example:

public String getName() {
    return name;
}

When we call:

s1.getName();

the method operates on the object referred to by s1.

8. Static variables

A static variable belongs to the class, rather than to one particular object.

For example:

public class Student {

    private String name;

    private static int numberOfStudents = 0;

    public Student(String name) {
        this.name = name;
        numberOfStudents++;
    }
}

Every student object shares the same:

numberOfStudents

Suppose we create:

Student s1 = new Student("Alice");
Student s2 = new Student("Bob");
Student s3 = new Student("Carlos");

There are three different name variables, but only one shared:

numberOfStudents = 3

9. Static methods

Static methods belong to the class rather than to a particular object.

Example:

public static int getNumberOfStudents() {
    return numberOfStudents;
}

We call it using the class name:

Student.getNumberOfStudents();

This is different from an instance method:

s1.getName();

A useful rule:

If a method depends on the state of a particular object, it should usually be an instance method.

If it represents behavior associated with the class as a whole, a static method may be appropriate.

10. The Math class as an example

Java's Math class contains static methods.

For example:

double x = Math.sqrt(25);
double y = Math.pow(2, 10);

We do not create a Math object:

Math m = new Math();

Instead, we call methods directly on the class.

This is appropriate because sqrt does not depend on the state of a particular Math object.

11. Class relationships

Real programs usually contain many classes.

Those classes interact with one another.

Consider a course registration system.

Possible classes include:

Student
Course
Instructor
Department

These classes are related.

For example:

A Course has an Instructor.
A Department has Courses.
A Student has a list of Courses.

This leads to an important OOP concept:

composition

12. Composition

Composition means that one object contains or uses another object.

Example:

public class Instructor {

    private String name;

    public Instructor(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }
}

Now consider:

public class Course {

    private String code;
    private Instructor instructor;

    public Course(String code, Instructor instructor) {
        this.code = code;
        this.instructor = instructor;
    }
}

A Course contains a reference to an Instructor.

We describe this relationship as:

A Course has an Instructor.

13. Creating objects with composition

We can create objects like this:

Instructor instructor =
        new Instructor("Dr. Smith");

Course course =
        new Course("CSC500", instructor);

Conceptually:

course
   |
   +-- code = "CSC500"
   |
   +-- instructor -----> Instructor object
                         name = "Dr. Smith"

Notice that the Course object does not contain a copy of the instructor.

Instead, it stores a reference to the Instructor object.

14. Objects can share other objects

Suppose an instructor teaches two courses.

Instructor professor =
        new Instructor("Dr. Smith");

Course c1 =
        new Course("CSC500", professor);

Course c2 =
        new Course("CSC510", professor);

Both courses refer to the same instructor object.

Conceptually:

c1 ----\
        \
         ---> Instructor
        /
c2 ----/

This illustrates an important idea:

Object variables contain references to objects.

15. Composition with collections

Objects often contain multiple related objects.

For example:

public class Student {

    private String name;
    private ArrayList<Course> courses;

    public Student(String name) {
        this.name = name;
        courses = new ArrayList<>();
    }
}

We might add a method:

public void enroll(Course course) {
    courses.add(course);
}

Now a student can contain references to many courses.

16. “has-a” relationships

Composition typically represents a:

has-a relationship

Examples:

A Car has an Engine.

A Course has an Instructor.

A University has Students.

An Order has Products.

A Playlist has Songs.

When identifying classes, look for these relationships.

For example, if the problem says:

Each customer has a shopping cart.

we might design:

Customer
ShoppingCart

with a composition relationship.

17. “is-a” vs. “has-a”

Object-oriented design frequently involves two important relationships.

Has-a

Example:

A Car has an Engine.

This suggests composition.

Is-a

Example:

A Dog is an Animal.

This suggests inheritance.

Inheritance will be studied in more detail next week.

For now, remember:

has-a → composition
is-a → inheritance

18. Prefer composition when appropriate

Suppose we have:

Car
Engine

A car is not an engine.

Therefore this would be incorrect:

public class Car extends Engine {
}

The correct relationship is:

A Car has an Engine.

So we use composition:

public class Car {

    private Engine engine;
}

This distinction becomes very important when designing larger programs.

19. Responsibility

A good class should have a clear responsibility.

Consider a class named:

Student

Reasonable responsibilities might include:

store student information
track registered courses
calculate credit totals

But perhaps not:

print university payroll
manage database backups
calculate instructor salaries

Those tasks belong to other classes.

A useful principle is:

Each class should have a focused purpose.

This idea is sometimes called the Single Responsibility Principle.

At this stage, students do not need to memorize formal design principles, but they should begin asking:

Does this behavior really belong in this class?

20. Example: poor class design

Consider:

public class Student {

    private String name;

    public void calculatePayroll() {
        // ...
    }

    public void sendUniversityEmail() {
        // ...
    }

    public void backupDatabase() {
        // ...
    }

    public void registerForCourse() {
        // ...
    }
}

This class is doing too many unrelated things.

Better:

Student
PayrollSystem
EmailService
DatabaseBackup
RegistrationSystem

Each class has a more focused responsibility.

21. Designing classes from a problem description

Suppose we receive this requirement:

Build a system for a library. The library contains books and members. Members may borrow books. Each book has a title, author, and ISBN. A member has a name and member ID.

Before writing code, identify important nouns.

Possible nouns:

Library
Book
Member
Author
ISBN

Not every noun necessarily becomes a class.

For example:

title → String
ISBN → String
name → String

Possible classes:

Library
Book
Member

22. Identifying responsibilities

Now ask what each class should know and do.

Book

State:

title
author
ISBN
availability

Behavior:

check out
return
display information

Member

State:

name
member ID
borrowed books

Behavior:

borrow book
return book

Library

State:

collection of books
collection of members

Behavior:

add book
register member
find book
lend book

This gives us an initial design.

23. Example Book class

public class Book {

    private String title;
    private String author;
    private String isbn;
    private boolean available;

    public Book(String title,
                String author,
                String isbn) {

        this.title = title;
        this.author = author;
        this.isbn = isbn;
        available = true;
    }

    public String getTitle() {
        return title;
    }

    public boolean isAvailable() {
        return available;
    }

    public void checkout() {
        if (available) {
            available = false;
        }
    }

    public void returnBook() {
        available = true;
    }
}

Notice that users cannot directly write:

book.available = false;

because the field is private.

Instead, they must call:

book.checkout();

This keeps the logic inside the Book class.

24. Representing state with booleans

The previous class used:

private boolean available;

This works because the book has two possible states:

available
not available

But sometimes objects have more than two states.

For example, suppose an order can be:

NEW
PROCESSING
SHIPPED
DELIVERED
CANCELLED

Using several boolean variables would be dangerous.

For example:

boolean shipped;
boolean cancelled;
boolean delivered;

What happens if:

shipped = true
cancelled = true
delivered = true

The state becomes inconsistent.

Java provides a better solution.

25. Enumerations (enum)

An enum represents a fixed set of values.

Example:

public enum OrderStatus {

    NEW,
    PROCESSING,
    SHIPPED,
    DELIVERED,
    CANCELLED
}

Now an order can contain:

private OrderStatus status;

The constructor might initialize it:

public Order() {
    status = OrderStatus.NEW;
}

Later:

status = OrderStatus.SHIPPED;

This is safer and clearer than using strings.

Avoid:

status = "Shippd";

With enums, the compiler helps prevent invalid values.

26. Enums with conditionals

Enums work naturally with conditional statements.

if (status == OrderStatus.SHIPPED) {
    System.out.println("The order is on the way.");
}

Or with switch:

switch (status) {

    case NEW:
        System.out.println("Order received.");
        break;

    case PROCESSING:
        System.out.println("Preparing order.");
        break;

    case SHIPPED:
        System.out.println("Order shipped.");
        break;

    case DELIVERED:
        System.out.println("Order delivered.");
        break;

    case CANCELLED:
        System.out.println("Order cancelled.");
        break;
}

Enums are useful whenever a variable should contain one value from a small, predefined set.

Examples:

DayOfWeek
OrderStatus
LetterGrade
AccountType
Direction
MembershipLevel

27. Packages

As programs become larger, we need to organize classes.

Java uses packages.

For example:

package university;

A project might contain:

university.Student
university.Course
university.Instructor

Larger systems might use several packages:

university.students
university.courses
university.registration
university.billing

Packages provide:

  • organization
  • namespaces
  • access control
  • easier project maintenance

28. Importing classes

Suppose a class is in another package.

We may need to import it.

Example:

import java.util.ArrayList;

Then we can write:

ArrayList<String> names = new ArrayList<>();

Instead of:

java.util.ArrayList<String> names =
    new java.util.ArrayList<>();

You have already used Java packages whenever you write imports such as:

import java.util.Scanner;

or:

import java.util.ArrayList;

29. Designing before coding

Beginning programmers often start writing code immediately.

For larger problems, this creates problems.

Instead, begin by asking:

  1. What are the important entities?
  2. Which entities should become classes?
  3. What information should each class store?
  4. What operations should each class perform?
  5. How are the classes related?
  6. Which object should be responsible for each operation?

This is the beginning of object-oriented design.

30. Example design problem

Suppose we want to create a restaurant ordering system.

Requirements:

A restaurant has menu items. Customers create orders. An order contains several menu items. Each menu item has a name and price. An order can calculate its total price.

Possible classes:

Restaurant
MenuItem
Order
Customer

Possible relationships:

Restaurant has MenuItems.
Customer has Orders.
Order has MenuItems.

31. Designing MenuItem

public class MenuItem {

    private String name;
    private double price;

    public MenuItem(String name, double price) {
        this.name = name;
        this.price = price;
    }

    public String getName() {
        return name;
    }

    public double getPrice() {
        return price;
    }
}

32. Designing Order

import java.util.ArrayList;

public class Order {

    private ArrayList<MenuItem> items;

    public Order() {
        items = new ArrayList<>();
    }

    public void addItem(MenuItem item) {
        items.add(item);
    }

    public double calculateTotal() {

        double total = 0;

        for (MenuItem item : items) {
            total += item.getPrice();
        }

        return total;
    }
}

Notice where the calculation belongs.

The total is a property of an order.

Therefore:

calculateTotal()

belongs naturally in the Order class.

33. Object interaction

A program's behavior often emerges from objects collaborating.

Example:

MenuItem burger =
    new MenuItem("Burger", 9.99);

MenuItem fries =
    new MenuItem("Fries", 3.99);

Order order = new Order();

order.addItem(burger);
order.addItem(fries);

System.out.println(order.calculateTotal());

The Order object collaborates with several MenuItem objects.

This is an important shift in thinking.

Instead of asking:

What sequence of statements should my program execute?

we also ask:

Which objects should exist, and how should they interact?

34. Reference variables

Consider:

MenuItem burger =
    new MenuItem("Burger", 9.99);

The variable:

burger

does not contain the entire object directly.

It contains a reference to the object.

This becomes important when multiple variables refer to the same object.

Example:

MenuItem item1 =
    new MenuItem("Burger", 9.99);

MenuItem item2 = item1;

Now both variables refer to the same object.

Conceptually:

item1 ----\
           ---> MenuItem object
item2 ----/

Changes through either reference affect the same object.

35. Reference equality

Consider:

Student s1 =
    new Student("Alice", 123);

Student s2 =
    new Student("Alice", 123);

Although they contain identical information:

s1 == s2

is normally:

false

Why?

Because == compares object references.

The two variables refer to two different objects.

Later in the course, students will learn how Java classes can define logical equality using:

equals()

36. Null references

An object reference may also contain:

null

Example:

Instructor instructor = null;

This means:

The variable currently refers to no object.

If we write:

instructor.getName();

Java produces a:

NullPointerException

Understanding references helps explain one of the most common errors in Java.

37. Class invariants

A useful design concept is an invariant.

An invariant is a condition that should always remain true for a valid object.

For example, a bank account might require:

balance >= 0

A course might require:

capacity > 0

A product might require:

price >= 0

Encapsulation helps classes preserve these invariants.

Example:

public void setPrice(double price) {

    if (price >= 0) {
        this.price = price;
    }
}

Better still, invalid values might be rejected using exceptions, which we will study later.

38. Tell objects what to do

Consider this design:

if (account.getBalance() >= amount) {

    double newBalance =
        account.getBalance() - amount;

    account.setBalance(newBalance);
}

Here, outside code is responsible for the withdrawal rules.

A better design is:

account.withdraw(amount);

Now the BankAccount object handles its own rules.

This reflects a useful OOP idea:

Tell an object what you want it to do rather than manipulating its internal data from the outside.

39. Common design mistake: the “god class”

A common beginner mistake is creating one class that does everything.

Example:

UniversitySystem

with:

100 fields
75 methods
student management
course management
payroll
billing
registration
email
reporting

This becomes difficult to understand and maintain.

Instead, divide responsibilities among smaller classes.

For example:

Student
Course
Registration
Invoice
Instructor
Department

40. Common design mistake: too many tiny classes

The opposite problem is also possible.

Not every value needs its own class.

For example:

FirstName
LastName
Age
StreetNumber
ZIPCode

could theoretically all become classes.

But doing so may unnecessarily complicate the program.

Object-oriented design requires judgment.

Ask:

Does this concept have meaningful state and behavior of its own?

If the answer is no, a primitive or String may be sufficient.

41. A practical design process

When designing a small Java application:

Step 1 - read the requirements

Understand what the program must do.

Step 2 - identify candidate classes

Look for meaningful nouns.

Step 3 - assign responsibilities

What should each class know and do?

Step 4 - identify relationships

Ask:

has-a?
is-a?
uses-a?

Step 5 - design public interfaces

Determine what methods other objects should be allowed to call.

Step 6 - protect internal state

Use private fields unless there is a strong reason not to.

Step 7 - implement incrementally

Create and test one class at a time.

42. Mini design exercise

Consider the following requirement:

A fitness application tracks users and workouts. Each user has a name and age. A workout records a type, duration, and calories burned. Each user may have many workouts. The application should calculate the total calories burned by a user.

Candidate classes:

User
Workout
FitnessApplication

Possible design:

User
    name
    age
    workouts

Workout
    type
    duration
    caloriesBurned

Relationship:

User has Workouts.

Where should this method belong?

calculateTotalCaloriesBurned()

A reasonable answer is:

User

because the calculation operates on that user's collection of workouts.

43. Example implementation

public class Workout {

    private String type;
    private int durationMinutes;
    private int caloriesBurned;

    public Workout(String type,
                   int durationMinutes,
                   int caloriesBurned) {

        this.type = type;
        this.durationMinutes = durationMinutes;
        this.caloriesBurned = caloriesBurned;
    }

    public int getCaloriesBurned() {
        return caloriesBurned;
    }
}

And:

import java.util.ArrayList;

public class User {

    private String name;
    private int age;
    private ArrayList<Workout> workouts;

    public User(String name, int age) {

        this.name = name;
        this.age = age;
        workouts = new ArrayList<>();
    }

    public void addWorkout(Workout workout) {
        workouts.add(workout);
    }

    public int calculateTotalCaloriesBurned() {

        int total = 0;

        for (Workout workout : workouts) {
            total += workout.getCaloriesBurned();
        }

        return total;
    }
}

This example demonstrates:

  • classes
  • objects
  • encapsulation
  • composition
  • collections
  • object interaction
  • responsibility assignment

44. Design discussion

Why not store each workout as three arrays?

For example:

String[] workoutTypes;
int[] durations;
int[] calories;

This is possible, but the data logically belongs together.

Instead:

Workout

groups related information into one meaningful abstraction.

Then:

ArrayList<Workout>

expresses the program's meaning more clearly.

This demonstrates an important advantage of object-oriented programming:

Classes allow us to create abstractions that match concepts in the problem we are solving.

45. Abstraction

An abstraction hides unnecessary detail.

Consider a car.

To drive it, we use:

steering wheel
accelerator
brake
gear selector

The driver does not directly manipulate:

fuel injectors
transmission gears
engine valves
spark timing

The interface hides implementation details.

Software objects work similarly.

A user of:

ArrayList<String>

calls:

list.add("Alice");

without needing to know exactly how the array list internally manages memory.

Good class design creates useful abstractions.

46. Public interface vs. private implementation

Consider:

public class Counter {

    private int count;

    public void increment() {
        count++;
    }

    public int getCount() {
        return count;
    }
}

The public interface is:

increment()
getCount()

The internal representation is:

private int count;

Outside code should depend primarily on the public interface.

This gives the class freedom to change how it works internally.

47. Why interfaces matter even before Java interfaces

The word interface has two meanings.

Later, we will learn Java's formal:

interface

keyword.

But more generally, a class's interface means:

The set of operations available to users of the class.

For example:

account.deposit(100);
account.withdraw(50);
account.getBalance();

These methods form part of the public interface of BankAccount.

Good object-oriented design tries to keep that interface small, clear, and meaningful.
