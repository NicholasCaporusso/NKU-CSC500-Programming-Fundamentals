1. Overview

During the previous weeks, we learned many of the basic tools needed to write Java programs:

  • variables and expressions,
  • conditionals,
  • loops,
  • methods,
  • arrays and strings,
  • classes,
  • objects,
  • fields,
  • constructors,
  • and instance methods.

Knowing how to write these individual pieces of Java is necessary, but it is not enough to build larger programs.

As programs grow, a new question becomes increasingly important:

How should we organize the program?

Suppose we are developing software for a university. The software might need to represent:

  • students,
  • instructors,
  • courses,
  • departments,
  • enrollments,
  • grades,
  • classrooms,
  • and academic programs.

We could theoretically store everything inside one enormous class:

public class UniversityProgram {

    public static void main(String[] args) {

        String studentName = "Alice";
        int studentId = 12345;

        String courseCode = "CSC500";
        String courseTitle = "Programming Fundamentals";

        String instructorName = "Dr. Smith";

        // Hundreds of additional variables...
        // Hundreds of additional operations...
    }
}

This might work for a tiny program, but it becomes increasingly difficult to understand as the system grows.

Object-oriented design encourages a different approach.

We identify meaningful concepts in the problem and represent those concepts using classes:

Student
Course
Instructor
Department
Enrollment

Each class has a clear purpose and collaborates with other classes.

This week therefore moves from simply asking:

How do I write a Java class?

to asking:

What classes should exist, what should each class be responsible for, and how should those classes work together?

That question is the heart of object-oriented design.

3. Object-oriented programming vs. object-oriented design

The terms object-oriented programming and object-oriented design are related, but they refer to different activities.

Object-oriented programming

Object-oriented programming, or OOP, refers to the programming features and techniques used to work with objects.

Examples include:

class Student {
    ...
}
Student student = new Student(...);

and concepts such as:

  • fields,
  • constructors,
  • methods,
  • objects,
  • access modifiers,
  • composition,
  • inheritance,
  • and polymorphism.

OOP gives us a collection of programming tools.

Object-oriented design

Object-oriented design, or OOD, is the process of deciding how those tools should be used.

OOD asks questions such as:

  • What classes should exist?
  • What concept does each class represent?
  • What information should each object remember?
  • What operations should each object provide?
  • Which class should perform a particular operation?
  • Which objects contain or use other objects?
  • Which fields should be private?
  • What rules must each object preserve?
  • Which values belong to individual objects?
  • Which values belong to the entire class?
  • How should the classes interact?

Consider a university registration system.

Possible classes might include:

Student
Course
Instructor
Enrollment

Writing this Java syntax:

public class Student {
}

is programming.

Deciding that an Enrollment should connect a Student with a Course is design.

Similarly, deciding that a Course should be responsible for determining whether it has available seats is a design decision.

A useful summary is:

OOP provides the tools. OOD determines how to use those tools effectively.

4. Review: Classes and objects

A class defines a type of object.

An object is an individual instance of a class.

For example:

public class Student {

    private String name;
    private int id;

    public Student(String name, int id) {
        this.name = name;
        this.id = id;
    }

    public String getName() {
        return name;
    }

    public int getId() {
        return id;
    }
}

Student is a class.

We can construct multiple objects from it:

Student student1 = new Student("Alice", 12345);
Student student2 = new Student("Bob", 67890);

These are two different Student objects.

Conceptually:

student1
    |
    v
Student object
    name = "Alice"
    id   = 12345


student2
    |
    v
Student object
    name = "Bob"
    id   = 67890

Both objects have the same structure because they were created from the same class, but each object has its own state.

5. State and behavior

One useful way to think about an object is that it combines:

  1. state, and
  2. behavior.

5.1 State

State describes what an object currently knows or remembers.

A student might have:

name
student ID
major
GPA
completed credits
email address

In Java, state is usually represented using instance fields:

private String name;
private int id;
private String major;
private double gpa;
private int completedCredits;

Each Student object receives its own copies of these fields.

5.2 Behavior

Behavior describes what an object can do.

A student object might support operations such as:

change major
update email
calculate academic standing
register completed credits

These operations become methods.

For example:

public void changeMajor(String newMajor) {
    major = newMajor;
}

The central design question is therefore:

What should this object know, and what should this object do?

This question helps us decide both the fields and methods of a class.

6. Abstraction

One of the most important ideas in object-oriented design is abstraction.

Abstraction means:

Focus on the essential features of something while hiding details that users do not need to know.

Consider driving a car.

A driver interacts with:

  • the steering wheel,
  • brake pedal,
  • accelerator,
  • gear selector.

The driver normally does not directly manipulate:

  • fuel injectors,
  • individual engine valves,
  • spark timing,
  • transmission gears.

The controls provide an abstraction.

They expose the operations the driver needs while hiding the internal complexity.

Software classes can work the same way.

Consider:

ArrayList<String> names = new ArrayList<>();

names.add("Alice");
names.add("Bob");

A programmer can use add() without knowing exactly:

  • how the ArrayList allocates memory,
  • when its underlying storage grows,
  • how elements are copied internally,
  • or how much unused capacity currently exists.

The class gives us a useful abstraction.

7. Abstraction in our own classes

Consider a BankAccount.

public class BankAccount {

    private double balance;

    public BankAccount(double initialBalance) {
        balance = initialBalance;
    }

    public void deposit(double amount) {
        if (amount > 0) {
            balance += amount;
        }
    }

    public boolean withdraw(double amount) {
        if (amount > 0 && amount <= balance) {
            balance -= amount;
            return true;
        }

        return false;
    }

    public double getBalance() {
        return balance;
    }
}

Code using this class can write:

BankAccount account = new BankAccount(500.0);

account.deposit(100.0);
account.withdraw(75.0);

System.out.println(account.getBalance());

The caller thinks in terms of meaningful banking operations:

deposit
withdraw
check balance

The caller does not need to know exactly how the balance is stored or updated internally.

That is abstraction.

A useful question is:

What should users of this class be able to do without knowing how the class performs those operations?

8. Encapsulation

Encapsulation is closely related to abstraction, but the two concepts are not identical.

Encapsulation means:

An object controls access to its own internal state and implementation.

Consider this poor design:

public class BankAccount {

    public double balance;
}

Outside code can now write:

BankAccount account = new BankAccount();

account.balance = -1000000;

Nothing prevents the object from entering an invalid state.

A better design is:

public class BankAccount {

    private double balance;

    public double getBalance() {
        return balance;
    }

    public void deposit(double amount) {
        if (amount > 0) {
            balance += amount;
        }
    }

    public boolean withdraw(double amount) {

        if (amount > 0 && amount <= balance) {
            balance -= amount;
            return true;
        }

        return false;
    }
}

Now the field is private:

private double balance;

Outside code cannot directly write:

account.balance = -1000000;   // compile-time error

Changes must go through methods whose logic is controlled by the class.

9. Abstraction vs. encapsulation

These two ideas often work together.

Consider:

public class Temperature {

    private double celsius;

    public Temperature(double celsius) {
        this.celsius = celsius;
    }

    public double getCelsius() {
        return celsius;
    }

    public double getFahrenheit() {
        return celsius * 9.0 / 5.0 + 32;
    }
}

Encapsulation

This field is private:

private double celsius;

The representation is protected.

That is encapsulation.

Abstraction

A caller can write:

temperature.getFahrenheit();

without knowing how the conversion formula works.

That is abstraction.

A useful summary is:

Encapsulation → protect the inside.

Abstraction   → expose the right outside.

Good class design normally uses both.

10. Public interface and private implementation

Every class has a collection of operations that other code is allowed to use.

Consider:

public class Counter {

    private int count;

    public void increment() {
        count++;
    }

    public int getCount() {
        return count;
    }
}

The private implementation includes:

private int count;

The public interface includes:

increment()
getCount()

Outside code should generally interact with the object through its public interface:

Counter counter = new Counter();

counter.increment();
counter.increment();

System.out.println(counter.getCount());

The class can later change how it stores the count internally without necessarily changing the code that uses it.

For example, the implementation might change, but as long as:

counter.increment();
counter.getCount();

continue to work in the same way, callers may not need to change.

11. A note about the word interface

The word interface has two meanings in Java discussions.

In this week, when we say a class's public interface, we mean:

The public operations through which other code interacts with the class.

For example:

account.deposit(100);
account.withdraw(50);
account.getBalance();

Later, we will study Java's actual:

interface

language feature.

Do not confuse the general design idea of a public interface with the Java interface keyword.

12. Why fields are usually private

As a general design rule:

Instance fields should usually be private.

Why?

Because the class should control its own state.

Suppose we have:

public class Course {

    public int capacity;
    public int enrollmentCount;
}

Outside code could write:

course.capacity = -100;
course.enrollmentCount = 500000;

The object may now contain meaningless information.

Instead:

public class Course {

    private int capacity;
    private int enrollmentCount;
}

The Course class can provide operations that maintain valid state.

For example:

public boolean hasSpace() {
    return enrollmentCount < capacity;
}

and:

public boolean enrollStudent() {

    if (enrollmentCount < capacity) {
        enrollmentCount++;
        return true;
    }

    return false;
}

The class is now responsible for enforcing its own rules.

13. Getters and setters are not automatic requirements

A common beginner habit is:

  1. declare every field private;
  2. create a getter;
  3. create a setter;
  4. repeat for every field.

For example:

private double balance;

public double getBalance() {
    return balance;
}

public void setBalance(double balance) {
    this.balance = balance;
}

The field is technically private, but we have now created a public operation that allows almost any value to be assigned.

Outside code can write:

account.setBalance(-9999999);

This defeats much of the purpose of encapsulation.

Instead, think about meaningful operations in the problem domain:

deposit(...)
withdraw(...)
transfer(...)

rather than:

setBalance(...)

A useful design principle is:

Getters and setters are tools, not requirements.

Before creating a getter, ask:

Does outside code genuinely need to read this value?

Before creating a setter, ask:

Should outside code really be allowed to replace this value directly?

14. Tell objects what to do

Compare these two designs.

Design A

if (account.getBalance() >= amount) {

    double newBalance =
        account.getBalance() - amount;

    account.setBalance(newBalance);
}

The caller:

  • examines the account,
  • knows the withdrawal rule,
  • calculates the new balance,
  • and updates the account.

This gives outside code too much responsibility.

Design B

boolean success = account.withdraw(amount);

Now the account handles its own rules.

This reflects an important object-oriented idea:

Tell an object what you want it to do rather than manipulating its internal state from the outside.

The object that owns the data is often the best place to enforce rules involving that data.

15. Class responsibilities

A responsibility is something a class is responsible for knowing or doing.

Suppose we have:

public class Rectangle {

    private double width;
    private double height;

    public double area() {
        return width * height;
    }
}

A Rectangle object knows:

width
height

It is responsible for:

calculating its area

This leads to one of the most important questions in object-oriented design:

Which class should contain this method?

If a method requires information that one object already owns, that object is often a good place for the method.

For example, if a ShoppingCart stores its items:

private ArrayList<Item> items;

then:

calculateTotal()

probably belongs in ShoppingCart.

16. Give each class a focused purpose

Consider this class:

public class Student {

    private String name;

    public void changeMajor(String major) {
        // ...
    }

    public void calculatePayroll() {
        // ...
    }

    public void backupDatabase() {
        // ...
    }

    public void repairNetworkServer() {
        // ...
    }

    public void sendMarketingEmails() {
        // ...
    }
}

The name Student suggests that the class represents a student.

Operations such as:

changeMajor
updateEmail
calculateCompletedCredits

make sense.

But:

backupDatabase
calculatePayroll
repairNetworkServer

do not naturally belong there.

A better design might separate responsibilities into classes such as:

Student
PayrollSystem
BackupService
RegistrationSystem
EmailService

The goal is not to create the largest number of classes.

The goal is to give each class a coherent responsibility.

17. Single responsibility

A useful design guideline is sometimes called the Single Responsibility Principle.

For CSC 500, think of it simply as:

A class should have one clear overall purpose.

That does not mean that a class should contain only one method.

A Student class might reasonably have:

getName()
getId()
changeMajor(...)
updateEmail(...)
getCompletedCredits()

These operations all relate to representing and managing a student.

A practical question is:

Can I describe the purpose of this class in one short sentence?

For example:

Course represents a university course and manages its enrollment-related information.

That is reasonably focused.

If your sentence becomes:

This class handles students and billing and databases and printing and emails and course registration...

the class is probably doing too much.

18. Cohesion

Cohesion describes how closely related the responsibilities inside one class are.

A highly cohesive class has responsibilities that belong together.

For example:

public class GradeBook {

    public void addGrade(...) {
        // ...
    }

    public double calculateAverage(...) {
        // ...
    }

    public LetterGrade determineLetterGrade(...) {
        // ...
    }
}

All of these operations relate to grades.

Compare that with:

public class Miscellaneous {

    public void calculateGrade() {
        // ...
    }

    public void sendEmail() {
        // ...
    }

    public void calculateTax() {
        // ...
    }

    public void drawChart() {
        // ...
    }

    public void backupDatabase() {
        // ...
    }
}

This class has no clear purpose.

In general, we prefer:

high cohesion

meaning that the responsibilities inside a class fit naturally together.

19. Coupling

Coupling describes how strongly one class depends on another.

For example:

public class Report {

    private Student student;

    public Report(Student student) {
        this.student = student;
    }
}

Report depends on Student.

That is coupling.

Coupling is not automatically bad.

Objects have to collaborate.

A program in which no classes interact would not be useful.

The design goal is to avoid unnecessary or excessive coupling.

Highly coupled systems can be difficult to:

  • change,
  • understand,
  • test,
  • and reuse.

Suppose ten unrelated classes directly access the fields of Student.

Then changing how Student stores its data might force us to modify all ten classes.

Encapsulation helps reduce this problem.

If callers use:

student.getName()

rather than directly depending on the internal field representation, the Student class has more freedom to change internally.

A common design goal is therefore:

high cohesion within classes
reasonable coupling between classes

20. Identifying classes from requirements

Suppose we receive this requirement:

Build a library system. The library contains books and members. Members may borrow books. Every book has a title, author, and ISBN. Every member has a name and member ID.

Before writing Java, identify important concepts.

Possible nouns include:

Library
Book
Member
title
author
ISBN
name
member ID

Not every noun should automatically become a class.

We might decide:

Library → class
Book    → class
Member  → class

while:

title     → String
author    → String
ISBN      → String
name      → String
member ID → String

may simply be fields.

A useful class-candidate checklist is:

  1. Does the concept need to store information?
  2. Does the concept have meaningful behavior?
  3. Will multiple objects of this type exist?
  4. Does it have an independent role in the problem?
  5. Would representing it as a class make the program easier to understand?

21. Avoid the “every noun becomes a class” rule

Looking for nouns is useful, but it is only a starting point.

Consider:

The library prints a message when a book is overdue.

The word message is a noun.

That does not mean we necessarily need:

public class Message {
}

Likewise, in:

A member has a name.

we probably do not need:

public class Name {
}

for a simple CSC 500 application.

Often:

private String name;

is sufficient.

Object-oriented design requires judgment.

22. The opposite mistake: Too many tiny classes

It is possible to over-design.

For example:

FirstName
LastName
Age
StreetNumber
ZipCode
Minutes
Calories

could theoretically each be modeled as a separate class.

But for many introductory applications, doing so would add complexity without providing meaningful behavior.

Ask:

Does this concept have meaningful state or behavior of its own?

If not, a primitive type, String, or existing Java type may be sufficient.

23. Relationships between classes

Real programs usually contain multiple classes, and those classes interact.

At this level, it is useful to recognize several kinds of relationships.

23.1 Dependency

One class temporarily uses another.

Example:

public void printStudent(Student student) {
    System.out.println(student.getName());
}

The method uses a Student, but the containing object may not permanently store one.

23.2 Association

Two objects have some meaningful relationship.

For example:

Instructor teaches Course
Student registers for Course

23.3 Composition

One object contains or uses another as part of its state.

For example:

public class Course {

    private Instructor instructor;
}

23.4 Inheritance

One class is a specialized type of another.

For example:

GraduateStudent is a Student

Inheritance will be studied carefully in Week 8.

For Week 7, our main focus is composition.

24. Composition

Composition means:

One object contains or uses other objects as part of its state.

Suppose we have:

public class Instructor {

    private String name;

    public Instructor(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }
}

Now consider:

public class Course {

    private String code;
    private Instructor instructor;

    public Course(String code, Instructor instructor) {
        this.code = code;
        this.instructor = instructor;
    }
}

The Course object contains:

private Instructor instructor;

This means that a course has a relationship with an instructor.

We describe it as:

A Course has an Instructor.

25. Creating objects with composition

We might write:

Instructor professor =
    new Instructor("Dr. Smith");

Course course =
    new Course("CSC500", professor);

Conceptually:

professor
    |
    v
+--------------------+
| Instructor object  |
| name = "Dr. Smith" |
+--------------------+
           ^
           |
           |
+-------------------------+
| Course object           |
| code = "CSC500"         |
| instructor -------------+
+-------------------------+
           ^
           |
         course

The Course does not contain an independent copy of the instructor's data.

It stores a reference to an Instructor object.

26. Objects can share other objects

Suppose the same professor teaches two courses:

Instructor professor =
    new Instructor("Dr. Smith");

Course course1 =
    new Course("CSC500", professor);

Course course2 =
    new Course("CSC510", professor);

Both Course objects refer to the same Instructor.

Conceptually:

course1 ----\
             \
              ---> Instructor("Dr. Smith")
             /
course2 ----/

This is important:

Object fields can contain references to other objects.

Multiple objects can therefore collaborate with or refer to the same object.

27. Has-a relationships

Composition is commonly associated with a has-a relationship.

Examples:

A Car has an Engine.

A Course has an Instructor.

A Student has an Address.

An Order has MenuItems.

A Playlist has Songs.

A Hotel has Rooms.

When reading a problem description, look for relationships of this form.

Suppose the requirement says:

Each customer has a shopping cart.

That suggests:

Customer
ShoppingCart

with a composition relationship.

One possible implementation is:

public class Customer {

    private String name;
    private ShoppingCart cart;

    public Customer(String name) {
        this.name = name;
        this.cart = new ShoppingCart();
    }
}

28. Has-a vs. is-a

Two important relationships in object-oriented design are:

has-a
is-a

Has-a

Example:

A Car has an Engine.

This suggests composition.

Is-a

Example:

A Dog is an Animal.

This suggests inheritance.

The distinction is important.

Consider:

Car
Engine

Does this make sense?

A Car is an Engine.

No.

Therefore this design would not represent the relationship correctly:

public class Car extends Engine {
}

Instead:

A Car has an Engine.

So composition is more appropriate:

public class Car {

    private Engine engine;
}

For now, remember:

has-a → composition

is-a  → inheritance

Inheritance itself is the subject of Week 8.

29. Composition with collections of objects

An object may contain one related object:

private Instructor instructor;

or many related objects.

For example:

import java.util.ArrayList;

public class Student {

    private String name;
    private ArrayList<Course> courses;

    public Student(String name) {
        this.name = name;
        courses = new ArrayList<>();
    }

    public void enroll(Course course) {
        courses.add(course);
    }
}

Conceptually:

Student
   |
   +---- Course
   |
   +---- Course
   |
   +---- Course

The ArrayList<Course> stores references to Course objects.

This lets us represent one-to-many relationships.

Examples include:

Student has many Courses.
Playlist has many Songs.
Order has many MenuItems.
Library has many Books.
Hotel has many Rooms.

30. Why objects are often better than parallel arrays

Suppose a fitness application records:

workout type
duration
calories burned

One possible design is:

String[] workoutTypes;
int[] durations;
int[] calories;

This requires us to remember that:

workoutTypes[3]
durations[3]
calories[3]

all describe the same workout.

A more meaningful design is:

public class Workout {

    private String type;
    private int durationMinutes;
    private int caloriesBurned;
}

Then:

ArrayList<Workout> workouts;

groups related information naturally.

This is a major advantage of object-oriented programming:

Classes let us build abstractions that correspond to concepts in the problem domain.

31. Reference variables

Consider:

MenuItem burger =
    new MenuItem("Burger", 9.99);

The variable:

burger

is a reference variable.

Conceptually, it points to an object.

burger
   |
   v
+---------------------+
| MenuItem object     |
| name = "Burger"     |
| price = 9.99        |
+---------------------+

This becomes important when we assign one reference variable to another.

MenuItem item1 =
    new MenuItem("Burger", 9.99);

MenuItem item2 = item1;

Now both variables refer to the same object:

item1 ----\
           \
            ---> MenuItem object
           /
item2 ----/

No second MenuItem was constructed.

32. Shared references and mutation

Suppose MenuItem has:

public void setPrice(double price) {
    if (price >= 0) {
        this.price = price;
    }
}

Now:

MenuItem item1 =
    new MenuItem("Burger", 9.99);

MenuItem item2 = item1;

item2.setPrice(10.99);

If we then ask:

System.out.println(item1.getPrice());

the result is:

10.99

Why?

Because item1 and item2 refer to the same object.

This behavior is particularly important when objects contain references to other objects.

33. Object identity and ==

Consider:

Student s1 =
    new Student("Alice", 123);

Student s2 =
    new Student("Alice", 123);

The two objects contain the same data.

But:

System.out.println(s1 == s2);

is normally:

false

because there are two different objects.

For object references:

==

tests whether the two references refer to the same object.

Compare:

Student s1 =
    new Student("Alice", 123);

Student s2 = s1;

Now:

System.out.println(s1 == s2);

is:

true

because both references point to exactly the same object.

34. Identity is not the same as logical equality

There are two different questions:

Question 1

Are these references pointing to the exact same object?

That is an identity question.

Question 2

Do these two objects represent equivalent information?

That is a logical equality question.

Java classes can define logical equality using:

equals()

We will not develop custom equals() implementations in depth this week.

For now, remember:

== on object references usually does not mean "these objects contain the same information."

A familiar example is String:

String a = "hello";
String b = new String("hello");

To compare the text contents, use:

a.equals(b)

rather than relying on:

a == b

35. null references

A reference variable can also contain:

null

Example:

Instructor instructor = null;

This means:

The variable currently refers to no object.

Conceptually:

instructor ----> nothing

If we then write:

instructor.getName();

Java attempts to invoke a method on an object that does not exist.

This causes a:

NullPointerException

Understanding object references makes this common Java error easier to understand.

36. Avoiding accidental null

Consider:

public class Course {

    private Instructor instructor;

    public Course(String code, Instructor instructor) {
        this.instructor = instructor;
    }
}

If callers are allowed to construct:

Course course =
    new Course("CSC500", null);

then code such as:

course.getInstructor().getName();

may eventually fail.

Sometimes null is a valid representation of "not assigned yet."

Other times it represents an invalid state.

This is a design decision.

Ask:

Is it meaningful for this relationship not to exist?

For example:

Course without an instructor

might be temporarily valid.

But:

Enrollment without a student

might not make sense.

37. Instance fields

An instance field belongs to an individual object.

Consider:

public class Student {

    private String name;

    public Student(String name) {
        this.name = name;
    }
}

Now:

Student a = new Student("Ana");
Student b = new Student("Marcus");
Student c = new Student("Priya");

Conceptually:

a object:
    name = "Ana"

b object:
    name = "Marcus"

c object:
    name = "Priya"

There are three different name fields.

Each belongs to one particular object.

38. Instance methods

An instance method operates on a particular object.

Example:

public String getName() {
    return name;
}

When we call:

a.getName();

the method operates on the object referred to by a.

When we call:

b.getName();

the same method definition operates on a different object.

Inside an instance method, fields such as:

name

refer to the state of the current object.

39. Static fields

A static field belongs to the class itself, rather than to one individual object.

Example:

public class Student {

    private String name;

    private static int studentCount = 0;

    public Student(String name) {
        this.name = name;
        studentCount++;
    }
}

Now:

Student a = new Student("Ana");
Student b = new Student("Marcus");
Student c = new Student("Priya");

creates:

three separate names
one shared studentCount

Conceptually:

Student class
    studentCount = 3

a object
    name = "Ana"

b object
    name = "Marcus"

c object
    name = "Priya"

40. Static methods

A static method also belongs to the class.

For example:

public static int getStudentCount() {
    return studentCount;
}

Call it using the class name:

System.out.println(Student.getStudentCount());

This is different from:

a.getName();

which operates on a particular object.

Compare:

a.getName()

with:

Student.getStudentCount()

The first asks about one particular student.

The second asks about the Student class as a whole.

41. Why a static method cannot directly use an instance field

Consider:

public class Student {

    private String name;

    public static void printName() {
        System.out.println(name); // error
    }
}

Why does this not make sense?

Suppose we have:

Student a = new Student("Ana");
Student b = new Student("Marcus");

and call:

Student.printName();

Which name should Java print?

Ana?
Marcus?

There is no particular Student object associated with that static method call.

Therefore static methods cannot directly access instance-specific state unless an object is explicitly provided.

For example:

public static void printStudentName(Student student) {
    System.out.println(student.getName());
}

Now the method knows which object to use because the object is passed as a parameter.

42. When should we use static?

Use static when something logically belongs to the class as a whole.

Common examples include:

Shared counters

private static int numberOfStudents;

Constants

public static final int MAX_CREDITS = 18;

Utility operations

public static double milesToKilometers(double miles) {
    return miles * 1.60934;
}

Java library methods

Math.sqrt(25);
Math.pow(2, 10);

These calculations do not require a particular Math object.

A useful rule is:

If an operation depends on the state of a particular object, it should usually be an instance method.

Do not make methods static merely because calling them appears easier.

43. A common mistake: Making everything static

Beginning programmers sometimes write:

public class Student {

    static String name;
    static int id;

    public static void setName(String newName) {
        name = newName;
    }
}

Now every Student object effectively shares the same name.

That is probably not what we want.

Student information belongs to individual students.

Therefore:

private String name;
private int id;

should be instance fields.

static is not a substitute for understanding objects.

44. final and constants

The keyword:

final

means that a variable cannot be reassigned after it is initialized.

A class-wide constant commonly combines:

public static final

For example:

public static final int MAX_CREDITS = 18;

Meaning:

  • public — other classes may access it;
  • static — one value belongs to the class;
  • final — the value cannot be reassigned.

Call it with:

Student.MAX_CREDITS

Java convention writes constants using uppercase letters:

MAX_CREDITS
DEFAULT_CAPACITY
TAX_RATE
PI

45. final references

Be careful with objects.

Consider:

final ArrayList<String> names =
    new ArrayList<>();

This is allowed:

names.add("Alice");

Why?

Because final means the variable names cannot be reassigned to a different list.

It does not automatically make the object immutable.

This would fail:

names = new ArrayList<>();

because that tries to make names refer to a different object.

46. Class invariants

A class invariant is a rule that should remain true for every valid object of a class.

Examples:

For a bank account:

balance >= 0

For a course:

capacity > 0
active enrollment count <= capacity

For a product:

price >= 0

For a rectangle:

width > 0
height > 0

The class's constructor and methods should protect these rules.

47. Protecting an invariant

Consider a product:

public class Product {

    private String name;
    private double price;

    public Product(String name, double price) {

        this.name = name;

        if (price >= 0) {
            this.price = price;
        } else {
            this.price = 0;
        }
    }

    public boolean changePrice(double newPrice) {

        if (newPrice < 0) {
            return false;
        }

        price = newPrice;
        return true;
    }

    public double getPrice() {
        return price;
    }
}

The class tries to preserve:

price >= 0

Notice that outside code cannot simply write:

product.price = -25;

because the field is private.

Encapsulation therefore helps classes preserve their invariants.

Later in the course, we will learn more systematic ways to signal invalid arguments using exceptions.

48. Store essential state; calculate derived state

Suppose a rectangle stores:

private double width;
private double height;
private double area;

At first this seems reasonable.

But what happens if:

width

changes and:

area

is not updated?

The object might contain:

width  = 10
height = 5
area   = 20

These values contradict one another.

Instead, store:

private double width;
private double height;

and calculate:

public double getArea() {
    return width * height;
}

Now the area is always consistent with the dimensions.

This principle is useful in many designs.

Instead of storing:

firstName
lastName
fullName

we might store:

firstName
lastName

and calculate:

public String getFullName() {
    return firstName + " " + lastName;
}

Avoid storing redundant information when it can easily be derived from existing state.

49. Enums

Sometimes a variable should contain exactly one value from a small, fixed set.

Suppose an order can be:

NEW
PROCESSING
SHIPPED
DELIVERED
CANCELLED

One poor approach is to use several booleans:

boolean shipped;
boolean delivered;
boolean cancelled;

This permits contradictory combinations such as:

shipped = true
delivered = true
cancelled = true

Another approach is to use a string:

String status = "SHIPPED";

But strings allow typing mistakes:

"SHIPED"
"shipped"
"Shippd"
"COMPLETE"

Java provides a better solution:

public enum OrderStatus {
    NEW,
    PROCESSING,
    SHIPPED,
    DELIVERED,
    CANCELLED
}

50. Using an enum

A class can contain an enum field:

public class Order {

    private OrderStatus status;

    public Order() {
        status = OrderStatus.NEW;
    }

    public OrderStatus getStatus() {
        return status;
    }
}

Now:

OrderStatus status = OrderStatus.SHIPPED;

must contain one of the values declared by OrderStatus.

The compiler helps enforce the set of legal possibilities.

51. Enums with if

We can compare enum values:

if (status == OrderStatus.SHIPPED) {
    System.out.println("The order is on the way.");
}

For enums, comparing enum constants with:

==

is appropriate.

52. Enums with switch

Enums work naturally with switch:

switch (status) {

    case NEW:
        System.out.println("Order received.");
        break;

    case PROCESSING:
        System.out.println("Preparing order.");
        break;

    case SHIPPED:
        System.out.println("Order shipped.");
        break;

    case DELIVERED:
        System.out.println("Order delivered.");
        break;

    case CANCELLED:
        System.out.println("Order cancelled.");
        break;
}

Enums are useful for concepts such as:

OrderStatus
Direction
LetterGrade
MembershipLevel
RoomType
ReservationStatus
EnrollmentStatus
AccountType

53. Enums can also have data

Java enums can contain fields and methods.

For example:

public enum LetterGrade {

    A(4.0),
    B(3.0),
    C(2.0),
    D(1.0),
    F(0.0);

    private final double points;

    LetterGrade(double points) {
        this.points = points;
    }

    public double getPoints() {
        return points;
    }
}

Usage:

LetterGrade grade = LetterGrade.A;

System.out.println(grade.getPoints());

Output:

4.0

For Week 7, the most important idea is still simpler:

Use an enum when a value must come from a fixed set of meaningful possibilities.

54. Packages

As a Java program grows, putting every class into one location becomes difficult to manage.

Java uses packages to organize related classes.

For example:

package university;

A project might contain:

university.Student
university.Course
university.Instructor
university.Enrollment

A larger system might have:

university.students
university.courses
university.registration
university.billing

Packages help with:

  • organization,
  • naming,
  • avoiding class-name conflicts,
  • access control,
  • and maintainability.

55. Fully qualified class names

A package becomes part of a class's complete name.

For example:

java.util.ArrayList

means:

package: java.util
class:   ArrayList

Similarly:

java.util.Scanner

contains:

package: java.util
class:   Scanner

Two different packages may contain classes with the same short name.

For example:

java.util.Date
java.sql.Date

The complete package names distinguish them.

56. Imports

An import allows us to use a class's short name.

Without an import:

java.util.ArrayList<String> names =
    new java.util.ArrayList<>();

With:

import java.util.ArrayList;

we can write:

ArrayList<String> names =
    new ArrayList<>();

An import does not copy the other class into your source code.

It tells the compiler which class you mean when you use the short name.

57. Classes available without imports

Some classes belong to:

java.lang

and are automatically available.

Examples include:

String
Math
System
Integer
Double

That is why we can write:

String name = "Alice";

and:

double result = Math.sqrt(25);

without writing:

import java.lang.String;
import java.lang.Math;

58. Organizing a small multi-class project

For a small CSC 500 project, a simple structure might look like:

registration/
    model/
        Student.java
        Course.java
        Enrollment.java
        EnrollmentStatus.java

    app/
        RegistrationApp.java

The model package contains classes representing important problem-domain concepts.

The app package contains the class that starts and coordinates the application.

For introductory programs, keep package organization simple.

Do not create dozens of packages unless they genuinely make the project easier to understand.

59. Designing before coding

Beginning programmers often start with:

public static void main(String[] args) {

and immediately begin typing code.

For very small programs, that can work.

For multi-class systems, it is usually better to think first.

Before implementation, ask:

  1. What are the important concepts?
  2. Which concepts deserve classes?
  3. What information should each class store?
  4. What behavior should each class provide?
  5. Which fields must be private?
  6. What rules must each class maintain?
  7. How are the classes related?
  8. Which object should be responsible for each operation?
  9. Which relationships are has-a relationships?
  10. Is anything truly shared by all objects?
  11. Should any value be an enum?
  12. Am I storing information that could instead be calculated?

This is object-oriented design.

60. A practical object-oriented design process

A useful design workflow is:

Step 1 — Read the requirements carefully

Do not start coding until you understand what the program must do.

Step 2 — Identify candidate classes

Look for important concepts and nouns.

Step 3 — Determine state

Ask:

What does each object need to remember?

Step 4 — Determine behavior

Ask:

What should each object be able to do?

Step 5 — Assign responsibilities

Ask:

Which class has the information needed for this operation?

Step 6 — Identify relationships

Ask:

has-a?
uses-a?
is-a?

Step 7 — Identify invariants

Ask:

What must always remain true for a valid object?

Step 8 — Design the public interface

Determine which operations outside code should be allowed to perform.

Step 9 — Protect internal state

Make fields private unless there is a clear reason not to.

Step 10 — Implement incrementally

Create and test the design one class at a time.

61. Worked design example: Restaurant ordering system

Consider the following requirement:

A restaurant has menu items. Customers create orders. An order contains several menu items. Each menu item has a name and price. An order can calculate its total price.

Before writing Java, identify important concepts.

Possible classes:

Restaurant
MenuItem
Order
Customer

Possible relationships:

Restaurant has MenuItems.
Customer has Orders.
Order has MenuItems.

Now consider responsibilities.

MenuItem

Should know:

name
price

Should provide:

getName()
getPrice()

Order

Should know:

items in the order

Should provide:

addItem(...)
calculateTotal()

The total belongs naturally to Order because the order contains the items needed for the calculation.

62. Implementing MenuItem

public class MenuItem {

    private String name;
    private double price;

    public MenuItem(String name, double price) {
        this.name = name;

        if (price >= 0) {
            this.price = price;
        } else {
            this.price = 0;
        }
    }

    public String getName() {
        return name;
    }

    public double getPrice() {
        return price;
    }
}

Notice:

  • fields are private;
  • the constructor protects the price invariant;
  • outside code can read the price;
  • outside code cannot directly replace it.

63. Implementing Order

import java.util.ArrayList;

public class Order {

    private ArrayList<MenuItem> items;

    public Order() {
        items = new ArrayList<>();
    }

    public void addItem(MenuItem item) {
        if (item != null) {
            items.add(item);
        }
    }

    public double calculateTotal() {

        double total = 0.0;

        for (MenuItem item : items) {
            total += item.getPrice();
        }

        return total;
    }

    public int getItemCount() {
        return items.size();
    }
}

Notice that we do not store:

private double total;

because the total can be derived from the list of items.

This prevents inconsistent state.

64. Objects collaborating

Now use the classes:

MenuItem burger =
    new MenuItem("Burger", 9.99);

MenuItem fries =
    new MenuItem("Fries", 3.99);

MenuItem drink =
    new MenuItem("Drink", 2.49);

Order order = new Order();

order.addItem(burger);
order.addItem(fries);
order.addItem(drink);

System.out.println(
    "Items: " + order.getItemCount()
);

System.out.println(
    "Total: $" + order.calculateTotal()
);

The Order object collaborates with MenuItem objects.

Inside:

calculateTotal()

the order asks each item for its price:

item.getPrice()

This is normal object-oriented collaboration.

65. A major shift in thinking

Earlier programming problems often encouraged us to ask:

What sequence of statements should execute?

That question is still important.

Object-oriented design adds another question:

Which objects should exist, and how should those objects collaborate?

For example:

Order
    asks MenuItem for price

Course
    stores Enrollment objects

Student
    stores Workout objects

Reservation
    refers to Room and Guest

A large object's behavior often emerges from several smaller objects collaborating.

66. Major case study: Course registration

We now combine many Week 7 concepts in one example.

Requirements

Build a program that allows students to enroll in university courses. Each course has a capacity. An enrollment can be active or dropped. The program must prevent new enrollment once the course reaches capacity.

Before writing code, identify concepts:

Student
Course
Enrollment
EnrollmentStatus

67. Why use an Enrollment class?

We might initially think:

Student has Course

But an enrollment itself contains meaningful information.

For example:

student
course
status

In a larger system it might eventually also contain:

registration date
grade
credit type

Therefore Enrollment is a meaningful concept.

It connects students and courses.

68. EnrollmentStatus

The requirement says an enrollment can be:

active
dropped

This is a perfect use case for an enum.

public enum EnrollmentStatus {

    ACTIVE,
    DROPPED
}

Now invalid values such as:

"sort of active"
"droped"
"maybe"

cannot be assigned to an EnrollmentStatus.

69. Student

public class Student {

    private String studentId;
    private String name;

    public Student(String studentId, String name) {
        this.studentId = studentId;
        this.name = name;
    }

    public String getStudentId() {
        return studentId;
    }

    public String getName() {
        return name;
    }
}

This class has a focused responsibility:

Represent basic information about one student.

70. Enrollment

public class Enrollment {

    private Student student;
    private EnrollmentStatus status;

    public Enrollment(Student student) {
        this.student = student;
        this.status = EnrollmentStatus.ACTIVE;
    }

    public Student getStudent() {
        return student;
    }

    public EnrollmentStatus getStatus() {
        return status;
    }

    public boolean isActive() {
        return status == EnrollmentStatus.ACTIVE;
    }

    public void drop() {
        status = EnrollmentStatus.DROPPED;
    }
}

This demonstrates composition:

Enrollment has a Student.

The enrollment also controls its own status.

Instead of outside code writing:

enrollment.status = EnrollmentStatus.DROPPED;

we provide:

enrollment.drop();

This creates a more meaningful public interface.

71. Course

import java.util.ArrayList;

public class Course {

    private String courseCode;
    private int capacity;
    private ArrayList<Enrollment> enrollments;

    public Course(String courseCode, int capacity) {

        this.courseCode = courseCode;

        if (capacity > 0) {
            this.capacity = capacity;
        } else {
            this.capacity = 1;
        }

        enrollments = new ArrayList<>();
    }

    public String getCourseCode() {
        return courseCode;
    }

    public int getCapacity() {
        return capacity;
    }

    public int getActiveEnrollmentCount() {

        int count = 0;

        for (Enrollment enrollment : enrollments) {

            if (enrollment.isActive()) {
                count++;
            }
        }

        return count;
    }

    public boolean hasAvailableSeat() {
        return getActiveEnrollmentCount() < capacity;
    }

    public boolean enroll(Student student) {

        if (student == null) {
            return false;
        }

        if (!hasAvailableSeat()) {
            return false;
        }

        enrollments.add(
            new Enrollment(student)
        );

        return true;
    }
}

72. Why does Course.enroll() make sense?

Consider the requirement:

The program must prevent enrollment once the course reaches capacity.

Which class has the information needed to enforce that rule?

The Course.

It knows:

capacity
current enrollments

Therefore:

course.enroll(student);

is a natural design.

Compare with:

if (course.getActiveEnrollmentCount()
        < course.getCapacity()) {

    // Caller manually modifies enrollment data.
}

The first design keeps the rule inside the object that owns the relevant information.

73. Derived state in the course example

Notice that Course stores:

private ArrayList<Enrollment> enrollments;

but does not necessarily need:

private int activeEnrollmentCount;

Instead:

public int getActiveEnrollmentCount() {

    int count = 0;

    for (Enrollment enrollment : enrollments) {

        if (enrollment.isActive()) {
            count++;
        }
    }

    return count;
}

calculates the answer from the source data.

That avoids the risk of:

enrollments list says 14 active
activeEnrollmentCount says 12

74. Course invariants

Important rules might include:

capacity > 0

active enrollment count <= capacity

The class protects the second invariant by checking:

if (!hasAvailableSeat()) {
    return false;
}

before adding another enrollment.

This is object-oriented design in action.

The class does not merely store information.

It protects the meaning and validity of that information.

75. Driver program

A simple driver might be:

public class RegistrationApp {

    public static void main(String[] args) {

        Student alice =
            new Student("S1001", "Alice");

        Student bob =
            new Student("S1002", "Bob");

        Student carlos =
            new Student("S1003", "Carlos");

        Course course =
            new Course("CSC500", 2);

        System.out.println(
            course.enroll(alice)
        );

        System.out.println(
            course.enroll(bob)
        );

        System.out.println(
            course.enroll(carlos)
        );

        System.out.println(
            course.getActiveEnrollmentCount()
        );
    }
}

Expected output:

true
true
false
2

The third enrollment fails because the course has capacity 2.

76. What does main() do in a multi-class program?

A useful role for main() is to:

  1. construct objects;
  2. connect those objects;
  3. request operations;
  4. display results.

For example:

Student student = new Student(...);

Course course = new Course(...);

course.enroll(student);

main() should not necessarily contain all the business rules.

Bad:

public static void main(String[] args) {

    // 400 lines of:
    // enrollment rules
    // account rules
    // pricing rules
    // report calculations
    // object state manipulation
}

Better:

course.enroll(student);
order.calculateTotal();
account.withdraw(amount);
reservation.calculateCost();

The objects themselves handle behavior related to their responsibilities.

77. Common design mistake: The God class

A God class is an informal term for one enormous class that tries to do almost everything.

For example:

UniversitySystem
    student management
    registration
    payroll
    email
    billing
    reports
    database operations
    course management

Such a class becomes difficult to:

  • understand,
  • modify,
  • test,
  • reuse,
  • and debug.

A better design divides responsibilities:

Student
Course
Enrollment
Invoice
Instructor
Department
RegistrationSystem

Do not confuse this with the idea that every class must be tiny.

The goal is focused responsibility.

78. Common design mistake: Too many classes

The opposite problem also occurs.

Suppose we create:

FirstName
LastName
Age
Minutes
CaloriesBurned
RoomNumber
Price

as individual classes even though they have no useful behavior.

The program may become harder rather than easier to understand.

Good design requires balance.

79. Common design mistake: Public fields

Avoid designs such as:

public class BankAccount {

    public double balance;
}

because outside code can modify the object without respecting its rules.

Prefer:

private double balance;

and meaningful operations such as:

deposit(...)
withdraw(...)

80. Common design mistake: Setter for everything

Avoid automatically producing:

setId(...)
setBalance(...)
setEnrollmentCount(...)
setOrderTotal(...)
setStatus(...)

without asking whether those operations make sense.

For example, an order's total might be calculated:

order.calculateTotal();

rather than directly assigned:

order.setTotal(123.45);

81. Common design mistake: Everything in main()

Object-oriented syntax does not automatically create object-oriented design.

This program may still be poorly designed:

public class Program {

    public static void main(String[] args) {

        // create objects

        // then manually perform all object logic
        // here for hundreds of lines
    }
}

A good driver class coordinates objects.

It should not necessarily perform every domain operation itself.

82. Common design mistake: Making everything static

If nearly every field and method is:

static

ask whether you are actually modeling individual objects.

For example:

public static String studentName;

would mean one class-wide student name.

That does not make sense if the system has many students.

Use instance state for information belonging to each individual object.

83. Common design mistake: Arbitrary strings for fixed states

If the only valid states are:

PENDING
APPROVED
REJECTED

avoid:

String status;

when an enum better expresses the constraint.

Prefer:

public enum ApplicationStatus {
    PENDING,
    APPROVED,
    REJECTED
}

84. Common design mistake: Redundant state

Avoid storing information that can be reliably calculated.

Potentially problematic:

private int quantity;
private double unitPrice;
private double totalPrice;

If:

totalPrice = quantity * unitPrice

then storing all three creates an opportunity for inconsistency.

Prefer:

public double getTotalPrice() {
    return quantity * unitPrice;
}

unless there is a compelling design reason to cache the result.

85. Common design mistake: Misusing inheritance

Inheritance is studied next week, but one Week 7 design rule is already useful.

Do not use inheritance merely because two classes interact.

Incorrect reasoning:

Car uses Engine
therefore Car extends Engine

The relationship must make conceptual sense.

Ask:

Is a Car an Engine?

No.

Ask:

Does a Car have an Engine?

Yes.

Therefore composition fits the relationship.

86. How to evaluate an object-oriented design

There is rarely exactly one perfect class design.

Instead, evaluate the design using questions.

Classes

  • Does each class represent a meaningful concept?
  • Does every class have a clear reason to exist?
  • Have we avoided unnecessary tiny classes?

Responsibilities

  • Does each class have a focused purpose?
  • Are related data and behavior kept together?
  • Is an operation placed in the class that has the information needed to perform it?

Encapsulation

  • Are fields normally private?
  • Can callers accidentally place objects into invalid states?
  • Are public methods meaningful?

Relationships

  • Can we clearly explain why each class refers to another?
  • Are has-a relationships represented through composition?
  • Are we avoiding inheritance where there is no genuine is-a relationship?

State

  • Are invariants protected?
  • Are we storing redundant information?
  • Can derived values be calculated instead?

Static members

  • Does this member really belong to the class rather than an individual object?

Enums

  • Is a fixed set of valid values represented clearly?

Understandability

  • Could another programmer understand how to use the classes from their public methods?

87. A design checklist before writing a class

Before implementing a new class, ask:

  1. What concept does this class represent?
  2. What information must each object remember?
  3. What operations should each object provide?
  4. Which fields should be private?
  5. What invariants must remain true?
  6. What other objects does this class use?
  7. Does it have any has-a relationships?
  8. Is any proposed relationship really an is-a relationship?
  9. Does anything belong to the class itself rather than individual instances?
  10. Would an enum represent any field more safely?
  11. Am I storing a value that could instead be calculated?
  12. Does this class have one clear overall purpose?
  13. Is its public interface understandable?

If you can answer these questions, you are doing object-oriented design rather than merely writing Java syntax.

public class Workout {

            int caloriesBurned) {

        this.type = type;

        this.caloriesBurned = caloriesBurned;
    }

    public String getType() {

    }

90. User

import java.util.ArrayList;

public class User {

    private String name;
    private int age;
    private ArrayList<Workout> workouts;

    public User(String name, int age) {

        this.name = name;
        this.age = age;

        workouts = new ArrayList<>();
    }

    public void addWorkout(Workout workout) {

        if (workout != null) {
            workouts.add(workout);
        }
    }

    public int calculateTotalCaloriesBurned() {

        int total = 0;

        for (Workout workout : workouts) {
            total += workout.getCaloriesBurned();
        }

        return total;
    }
}

Where does:

calculateTotalCaloriesBurned()

belong?

User is a reasonable choice because the User owns the collection of workouts needed for the calculation.

public class Reservation {

    private Guest guest;
    private Room room;
    private int numberOfNights;
    private ReservationStatus status;

    public Reservation(
            Guest guest,
            Room room,
            int numberOfNights) {

        this.room = room;
        this.numberOfNights = numberOfNights;

        return status;

96. Common questions and answers

Q1. Does every noun in a problem description become a class?

No.

Nouns are useful starting points, not rules.

A concept usually deserves a class when it has meaningful:

  • state,
  • behavior,
  • identity,
  • or an independent role in the system.

Q2. Should every field have a getter?

No.

Only expose information that outside code genuinely needs.

Q3. Should every field have a setter?

Definitely not.

A setter can allow callers to bypass the rules of the class.

Prefer meaningful operations such as:

withdraw(...)
deposit(...)
enroll(...)
drop(...)
confirm(...)
cancel(...)

when those operations better describe the problem.

Q4. What is the simplest difference between abstraction and encapsulation?

Think:

Abstraction:
    What should the user see?

Encapsulation:
    What should the class protect?

Q5. Why make fields private if getters expose them anyway?

Reading and modifying are different capabilities.

A getter such as:

getBalance()

lets callers observe a balance.

It does not necessarily let them replace it.

The class can expose exactly the operations callers need.

Q6. Can one object contain another object?

Yes.

For example:

private Instructor instructor;

This is one of the foundations of composition.

Q7. Can two objects refer to the same object?

Yes.

For example:

Instructor professor =
    new Instructor("Dr. Smith");

Course c1 =
    new Course("CSC500", professor);

Course c2 =
    new Course("CSC510", professor);

Both courses refer to the same Instructor.

Q8. Why does changing an object through one reference affect another reference?

Because both variables may point to the same object.

Student a = new Student(...);
Student b = a;

There is one object and two references.

Q9. What exactly does null mean?

It means:

This reference currently points to no object.

Q10. When should a field be static?

When there should be one class-wide value rather than one value per object.

Example:

private static int studentCount;

Q11. Why not make everything static?

Because most object state belongs to individual objects.

If every student shared one static name, we could not correctly represent multiple students.

Q12. What is a good static method?

A method that logically does not depend on one object's state.

For example:

Math.sqrt(25);

or:

TemperatureConverter
    .celsiusToFahrenheit(20);

Q13. When should I use an enum?

When the allowed values come from a fixed, meaningful set.

Examples:

ACTIVE / DROPPED
PENDING / APPROVED / REJECTED
SINGLE / DOUBLE / SUITE
NEW / SHIPPED / DELIVERED

Q14. Why is an enum better than a string?

Because a string allows arbitrary values.

String status = "shiped";

is valid Java even though it may be invalid for the application.

An enum limits values to those explicitly declared.

Q15. Does composition mean objects are physically copied inside each other?

No.

Java object variables contain references.

A field such as:

private Instructor instructor;

stores a reference to an Instructor object.

Q16. Is every relationship composition?

No.

A class may:

  • temporarily use another class,
  • store another object,
  • be associated with another object,
  • or eventually inherit from another class.

The important question is what the relationship means.

Q17. Should I always prefer composition over inheritance?

This week, prefer composition when the relationship is naturally:

has-a

Inheritance is appropriate for a genuine:

is-a

relationship and will be studied in Week 8.

Q18. Where should a calculation method go?

Usually in the class that owns the information needed for the calculation.

For example:

Rectangle owns width and height
→ Rectangle.area()

Order owns items
→ Order.calculateTotal()

User owns workouts
→ User.calculateTotalCaloriesBurned()

Q19. Should I store a calculated value in a field?

Usually not if it can be cheaply and reliably derived.

Storing duplicated state increases the chance that two pieces of information become inconsistent.

Q20. What is a class invariant?

A rule that should always remain true for a valid object.

Examples:

price >= 0
capacity > 0
enrollment count <= capacity

Q21. How does encapsulation help invariants?

If fields are private, callers cannot freely change them.

The class can require all changes to pass through methods that check its rules.

Q22. Is it bad for one object to call methods on another object?

No.

Object collaboration is fundamental to object-oriented programming.

For example:

total += item.getPrice();

means the Order is asking a MenuItem for information.

That is completely normal.

Q23. What is cohesion?

Cohesion asks:

Do the responsibilities inside this class belong together?

Good classes usually have high cohesion.

Q24. What is coupling?

Coupling asks:

How much does one class depend on another?

Some coupling is necessary, but unnecessary dependencies make programs harder to change.

Q25. How many classes should my program have?

There is no universal number.

Use enough classes to represent meaningful concepts with focused responsibilities.

Avoid both:

one enormous class

and:

a separate class for every tiny value

101. Week 7 summary

The central lesson of Week 7 is that programming is not merely writing statements that compile.

We must also decide how a program should be structured.

Classes model meaningful concepts

Examples:

Student
Course
Order
Workout
Reservation

Objects contain state and behavior

State is represented mainly with fields.

Behavior is represented with methods.

Abstraction exposes useful operations

Users of a class should be able to ask the object to perform meaningful operations without understanding every implementation detail.

Encapsulation protects internal state

Fields should usually be private.

The class should control how its state changes.

Public methods form an object's usable interface

Prefer meaningful operations such as:

withdraw(...)
enroll(...)
drop(...)
calculateTotal()

instead of exposing internal fields unnecessarily.

Responsibilities should be assigned carefully

Ask:

Which class should know or do this?

A class should have a clear, coherent purpose.

Composition models has-a relationships

Examples:

Course has Instructor.
Order has MenuItems.
Student has Workouts.
Reservation has Room.

Objects interact through references

Object variables refer to objects, and several references may point to the same object.

null means no object

Calling an instance method through a null reference causes a NullPointerException.

== compares reference identity

Two separate objects can contain the same data while still being different objects.

Instance members belong to individual objects

Example:

private String studentName;

Each student gets its own value.

Static members belong to the class

Example:

private static int studentCount;

One value is shared by the class.

Enums represent fixed sets of values

Example:

public enum EnrollmentStatus {
    ACTIVE,
    DROPPED
}

Packages organize Java programs

They group related classes and create namespaces.

Invariants describe rules valid objects must obey

Examples:

price >= 0
capacity > 0
enrollment count <= capacity

Avoid unnecessary duplicate state

If a value can easily be derived, calculate it rather than storing another field that may become inconsistent.

Design before implementation

Before writing code, ask:

What concepts exist?

Which concepts deserve classes?

What should each object know?

What should each object do?

How should the objects interact?

What rules must remain true?

That reasoning is the foundation of object-oriented design.

102. Final perspective

A successful Week 7 program is not the one with:

  • the greatest number of classes,
  • the greatest amount of Java syntax,
  • the most getters and setters,
  • the most static methods,
  • or the most complicated relationships.

A successful design is one whose structure makes sense.

You should be able to explain:

  • why each class exists;
  • what each class represents;
  • what information it owns;
  • what behavior it provides;
  • why its fields are private;
  • why one class contains another;
  • why an operation belongs to a particular class;
  • why something is static or instance-based;
  • why an enum was used;
  • and what rules the class protects.

The most important question to develop as an object-oriented programmer is therefore:

What are the important concepts in this problem, what responsibilities should they have, and how should they collaborate?

Being able to answer that question is the beginning of software design—not merely programming.
