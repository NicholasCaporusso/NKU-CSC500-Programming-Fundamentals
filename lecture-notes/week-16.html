3. From programming syntax to computational problem solving

At the beginning of the semester, programming problems often looked like this:

int x = scanner.nextInt();

if (x > 0) {
    System.out.println("Positive");
}

The main challenge was understanding syntax.

Later, we wrote programs involving classes:

public class Student {
    private String name;
    private double gpa;

    public Student(String name, double gpa) {
        this.name = name;
        this.gpa = gpa;
    }

    public String getName() {
        return name;
    }

    public double getGpa() {
        return gpa;
    }
}

Eventually, our programs included collections:

ArrayList<Student> students = new ArrayList<>();

and algorithms:

for (Student student : students) {
    if (student.getGpa() > highestGpa) {
        highestGpa = student.getGpa();
    }
}

The important observation is that the Java syntax is no longer the most difficult part.

The difficult questions are now:

  • What information should the program represent?
  • Which objects should exist?
  • Which data structures should store the information?
  • Which algorithms should operate on it?
  • How should responsibilities be divided among classes?
  • How efficient does the solution need to be?
  • How can we determine whether the program is correct?

These are computer science questions rather than Java syntax questions.

4. A general problem-solving process

When given a programming problem, resist the temptation to immediately begin writing code.

Instead, use the following process.

Step 1: understand the problem

Determine:

  • What are the inputs?
  • What outputs are required?
  • What rules constrain the solution?
  • What unusual cases can occur?
  • How large might the input become?

Suppose we are asked to build a system that stores student records and allows users to:

  • add a student
  • remove a student
  • find a student by ID
  • list all students
  • calculate average GPA

Before coding, we should determine what information a student record contains.

For example:

Student
-------
student ID
name
GPA
major

Step 2: identify the data

Ask:

What information must the program remember?

The student system must remember multiple student objects.

Possible representations include:

Student[] students;

or:

ArrayList<Student> students;

or:

HashMap<Integer, Student> students;

Each representation has advantages and disadvantages.

The correct choice depends on how the data will be used.

Step 3: identify the operations

Ask:

What must the program do with the data?

For the student system:

add
remove
search
display
calculate statistics

These operations often become methods.

Step 4: choose appropriate abstractions

The system might contain:

Student
StudentDatabase
Main

Student represents one student.

StudentDatabase manages a collection of students.

Main handles user interaction.

This division is preferable to putting the entire program inside one very large main method.

Step 5: select algorithms and data structures

Suppose students are stored in an ArrayList.

Finding a student by ID may require searching through the entire list.

Worst-case complexity:

O(n)

If the system frequently searches by student ID, a HashMap may be more appropriate.

HashMap<Integer, Student> students;

Average lookup time is approximately:

O(1)

The important lesson is:

Data-structure choices influence algorithm performance.

Step 6: consider edge cases

Examples:

  • What happens if the database is empty?
  • What happens if a student ID does not exist?
  • What happens if the same ID is added twice?
  • What happens if GPA is outside the range 0.0–4.0?

Professional programs must consider invalid and unusual situations.

Step 7: implement incrementally

Do not write the entire system before testing anything.

Instead:

  1. Implement Student.
  2. Test Student.
  3. Implement adding students.
  4. Test adding students.
  5. Implement searching.
  6. Test searching.
  7. Add file input/output.
  8. Test file operations.

Small steps make bugs easier to locate.

5. Review: the fundamental programming building blocks

Almost every program we write is constructed from a small number of concepts.

Variables

Variables represent program state.

int score = 95;
double average = 87.4;
boolean passed = true;

A useful conceptual model is:

variable = name associated with a value

Selection

Selection allows programs to make decisions.

if (score >= 90) {
    grade = 'A';
} else if (score >= 80) {
    grade = 'B';
} else {
    grade = 'C';
}

The fundamental question is:

Which path through the program should execute?

Iteration

Loops repeat computation.

for (int i = 0; i < values.length; i++) {
    System.out.println(values[i]);
}

The fundamental question is:

Which computation must be repeated?

Methods

Methods create reusable units of computation.

public static int max(int a, int b) {
    if (a > b) {
        return a;
    }

    return b;
}

Methods allow us to separate:

what a computation does

from

how the computation works

6. Review: objects and abstraction

Object-oriented programming allows programs to model systems as interacting objects.

Consider:

public class BankAccount {

    private double balance;

    public BankAccount(double initialBalance) {
        balance = initialBalance;
    }

    public void deposit(double amount) {
        balance += amount;
    }

    public double getBalance() {
        return balance;
    }
}

Users of the class do not need to know exactly how the balance is stored.

They interact with the object through its methods.

This is an example of abstraction.

The user thinks:

deposit $100

rather than:

modify a particular memory location containing a floating-point value

Good abstraction hides unnecessary implementation details.

7. Encapsulation

Encapsulation protects internal program state.

Prefer:

private double balance;

instead of:

public double balance;

Why?

Because with public state, another part of the program could write:

account.balance = -1000000;

With encapsulation, the class controls how state changes.

public void withdraw(double amount) {
    if (amount > 0 && amount <= balance) {
        balance -= amount;
    }
}

The class is responsible for preserving its own valid state.

8. Composition vs. inheritance

One important design decision is deciding how classes relate to one another.

Inheritance

Inheritance represents an is-a relationship.

class Animal {
}
class Dog extends Animal {
}

A dog is an animal.

Composition

Composition represents a has-a relationship.

class Car {
    private Engine engine;
}

A car has an engine.

In many software systems, composition is simpler and more flexible than inheritance.

Do not use inheritance merely to reuse code.

Inheritance should represent a genuine conceptual relationship.

9. Polymorphism

Suppose we define:

public interface Shape {
    double area();
}

Two classes implement the interface.

public class Circle implements Shape {

    private double radius;

    public Circle(double radius) {
        this.radius = radius;
    }

    @Override
    public double area() {
        return Math.PI * radius * radius;
    }
}
public class Rectangle implements Shape {

    private double width;
    private double height;

    public Rectangle(double width, double height) {
        this.width = width;
        this.height = height;
    }

    @Override
    public double area() {
        return width * height;
    }
}

We can now write:

ArrayList<Shape> shapes = new ArrayList<>();

shapes.add(new Circle(5));
shapes.add(new Rectangle(4, 6));

Then:

for (Shape shape : shapes) {
    System.out.println(shape.area());
}

The loop does not need to ask whether the object is a circle or rectangle.

Each object knows how to calculate its own area.

That is polymorphism.

10. Interfaces and implementations

One of the most important ideas in computer science is the distinction between:

what something does

and:

how something does it

Consider the concept of a list.

A list supports operations such as:

add
remove
get
size

But there are multiple implementations.

For example:

ArrayList
LinkedList

Both represent lists.

However, they represent the data differently internally.

This gives us two levels:

List
   ↓
abstract behavior

ArrayList / LinkedList
   ↓
concrete implementation

This same idea appears everywhere in computer science:

Stack
Queue
Set
Map
Tree
Graph
Database
Network protocol
File system

A major goal of computer science is learning how to reason about abstractions independently of their implementations.

11. Choosing a data structure

Suppose a program needs to store 1,000,000 usernames.

Which data structure should we use?

The answer depends on the operations.

If we mostly access users by numeric position:

ArrayList

may be appropriate.

If we repeatedly ask:

"Does this username exist?"

then:

HashSet

may be better.

If we associate each username with user information:

HashMap<String, User>

may be appropriate.

If order matters and we frequently manipulate elements near the beginning or middle, other structures may become relevant.

A useful rule is:

Choose a data structure based on the operations the program performs most frequently.

12. Review of major data structures

Array

Conceptually:

index:  0   1   2   3   4
value: 12  18   4  27   9

Advantages:

  • fast indexing
  • simple
  • memory efficient

Limitations:

  • fixed size
  • insertion may require shifting elements

ArrayList

Provides a dynamically sized array.

ArrayList<String> names = new ArrayList<>();

Useful operations include:

names.add("Alice");
names.get(0);
names.remove(0);
names.size();

Linked list

A linked list stores elements in nodes.

[Alice] → [Bob] → [Carlos] → null

Each node contains:

data
reference to next node

Unlike an array, nodes do not need to occupy consecutive memory positions.

Stack

A stack follows:

Last In, First Out

Example:

push A
push B
push C

top

 B
 A

Removing produces:

C

Common uses include:

  • function calls
  • expression evaluation
  • undo operations
  • depth-first search

Queue

A queue follows:

First In, First Out

Example:

Common uses include:

  • job scheduling
  • task processing
  • simulations
  • breadth-first search

Set

A set stores unique values.

{Alice, Bob, Carlos}

Adding "Alice" again does not create a duplicate.

Useful when the main question is:

Map

13. Algorithmic thinking

Programming is not simply about expressing commands.

It is about designing procedures for solving problems.

An algorithm is a precise sequence of steps used to solve a problem.

Consider finding a number in an array.

One algorithm is linear search.

public static int linearSearch(int[] values, int target) {

    for (int i = 0; i < values.length; i++) {
        if (values[i] == target) {
            return i;
        }
    }

    return -1;
}

In the worst case, every element must be examined.

For n elements:

O(n)

14. Binary search

If the array is sorted, we can do much better.

Consider:

3  8  12  19  25  31  40  52

Suppose we are searching for 40.

Instead of checking every number, binary search repeatedly eliminates half of the remaining possibilities.

Possible sequence:

19
31
40

This produces complexity:

O(log n)

For very large collections, the difference is enormous.

For one billion elements:

linear search:
up to 1,000,000,000 comparisons

binary search:
approximately 30 comparisons

This illustrates why algorithm design matters.

15. Big-o: what it actually means

Big-O describes how the amount of work performed by an algorithm grows as input size grows.

Suppose:

for (int i = 0; i < n; i++) {
    System.out.println(i);
}

The loop executes approximately n times.

Therefore:

O(n)

Now consider:

for (int i = 0; i < n; i++) {
    for (int j = 0; j < n; j++) {
        System.out.println(i + " " + j);
    }
}

The inner operation occurs approximately:

n × n

times.

Therefore:

O(n²)

16. Common complexity classes

Students should recognize these common categories:

ComplexityInformal description
O(1)constant
O(log n)logarithmic
O(n)linear
O(n log n)efficient sorting range
O(n²)quadratic
O(2ⁿ)exponential

Efficiency generally becomes worse as we move down the table.

For small inputs, the difference may not matter.

For large inputs, it can determine whether a program is practical.

17. Example: comparing two solutions

Suppose we want to determine whether an array contains duplicate values.

Approach 1: compare every pair

public static boolean containsDuplicate(int[] values) {

    for (int i = 0; i < values.length; i++) {
        for (int j = i + 1; j < values.length; j++) {
            if (values[i] == values[j]) {
                return true;
            }
        }
    }

    return false;
}

Worst-case complexity:

O(n²)

Approach 2: use a HashSet

public static boolean containsDuplicate(int[] values) {

    HashSet<Integer> seen = new HashSet<>();

    for (int value : values) {

        if (seen.contains(value)) {
            return true;
        }

        seen.add(value);
    }

    return false;
}

Average complexity:

O(n)

This example demonstrates an important relationship:

better data structure
        ↓
better algorithm
        ↓
better performance

18. Recursion revisited

Recursion occurs when a method solves a problem by solving a smaller version of the same problem.

Example:

public static int factorial(int n) {

    if (n == 0) {
        return 1;
    }

    return n * factorial(n - 1);
}

A recursive algorithm needs:

  1. a base case
  2. progress toward the base case

Without a correct base case, recursion may never stop.

19. Recursion and data structures

Recursion becomes particularly natural when the data itself is recursive.

Consider a binary tree.

A tree contains:

value
left subtree
right subtree

Therefore, tree algorithms often look recursive.

public static int countNodes(Node node) {

    if (node == null) {
        return 0;
    }

    return 1
        + countNodes(node.left)
        + countNodes(node.right);
}

The structure of the algorithm mirrors the structure of the data.

This pattern appears frequently in computer science.

20. Correctness before efficiency

Students sometimes become overly concerned about writing the fastest possible algorithm.

A better priority is:

1. Correctness
2. Clarity
3. Efficiency

A fast program that produces incorrect results is not useful.

Start by designing a correct solution.

Then determine whether performance needs improvement.

21. Reading code as a graduate student

Graduate courses will frequently give you code that you did not write.

You must be able to read and reason about unfamiliar programs.

Consider:

public static int mystery(int[] values) {

    int result = values[0];

    for (int i = 1; i < values.length; i++) {
        if (values[i] > result) {
            result = values[i];
        }
    }

    return result;
}

Do not begin by asking:

What does the variable result mean?

Instead, trace the algorithm.

For:

values = [4, 9, 2, 7]

Execution:

result = 4

compare 9 with 4
result = 9

compare 2 with 9
result = 9

compare 7 with 9
result = 9

Therefore:

mystery returns the maximum value in the array

22. Code-tracing exercise

Consider:

public static int mystery2(int[] values) {

    int count = 0;

    for (int i = 0; i < values.length; i++) {

        for (int j = i + 1; j < values.length; j++) {

            if (values[i] == values[j]) {
                count++;
            }
        }
    }

    return count;
}

Questions:

  1. What does this method calculate?
  2. What is its time complexity?
  3. What happens with the input:
[3, 5, 3, 7, 5]
  1. Could a different data structure make the computation more efficient?

23. Debugging as a systematic process

A beginner often debugs like this:

Change something.
Run the program.
Change something else.
Run it again.

This is inefficient.

Instead, debugging should be hypothesis-driven.

Suppose your program produces:

Expected: 42
Actual: 0

Ask:

Where could the incorrect value have first appeared?

Inspect intermediate values.

For example:

System.out.println("DEBUG total = " + total);

or use a debugger.

A systematic debugging process is:

1. Reproduce the bug.
2. Identify where the incorrect behavior first appears.
3. Develop a hypothesis.
4. Test the hypothesis.
5. Fix the cause.
6. Verify the fix.
7. Test related cases.

24. Types of errors

Syntax errors

The program does not compile.

Example:

int x = 5

Missing semicolon.

Runtime errors

The program compiles but crashes while running.

Example:

int[] values = new int[5];

System.out.println(values[10]);

This produces an exception.

Logic errors

The program runs but produces incorrect results.

Example:

double average = total / count;

If both variables are integers, integer division may produce an incorrect result.

Logic errors are frequently the hardest errors to locate.

25. Testing

Testing is not simply running the program once.

Good testing includes multiple categories.

Suppose we write:

public static int max(int[] values)

We should test:

normal case:
[3, 8, 2, 6]

maximum first:
[9, 4, 2]

maximum last:
[1, 3, 10]

negative values:
[-10, -2, -7]

single element:
[5]

And we should decide what happens for:

[]

Testing should deliberately explore boundaries and unusual conditions.

26. Invariants

An invariant is something that should always remain true at a particular point in a program.

For a bank account:

balance >= 0

might be an invariant.

For a sorted collection:

values[i] <= values[i + 1]

must remain true.

Thinking in terms of invariants is important because advanced CS courses often require reasoning about whether algorithms are correct.

27. A larger integrated example

Consider the following problem.

Create a library system that stores books and supports adding books, borrowing books, returning books, searching by ISBN, and displaying all available books.

We begin by identifying concepts.

Book
Library

Book class

public class Book {

    private String isbn;
    private String title;
    private String author;
    private boolean borrowed;

    public Book(String isbn, String title, String author) {
        this.isbn = isbn;

    }

        return title;
    }

    }

    public void returnBook() {

28. Choosing the collection

One possibility:

private ArrayList<Book> books;

Searching for an ISBN would require:

O(n)

A better choice may be:

private HashMap<String, Book> books;

Then:

public Book findBook(String isbn) {
    return books.get(isbn);
}

Average lookup complexity:

O(1)

The data structure is chosen based on the application's operations.

29. Library class

import java.util.HashMap;

public class Library {

    private HashMap<String, Book> books;

    public Library() {
        books = new HashMap<>();
    }

    public void addBook(Book book) {
        books.put(book.getIsbn(), book);
    }

    public Book findBook(String isbn) {
        return books.get(isbn);
    }

    public boolean borrowBook(String isbn) {

        Book book = books.get(isbn);

        if (book == null || book.isBorrowed()) {
            return false;
        }

        book.borrow();
        return true;
    }
}

objects
encapsulation
methods
references
HashMap
conditionals
algorithmic efficiency

Real software rarely uses concepts in isolation.

31. What makes code "good"?

A program can produce the correct answer and still be poorly designed.

Consider:

32. Characteristics of good code

Good programs generally have:

Meaningful names

Prefer:

studentCount

instead of:

x

Small, focused methods

Prefer:

calculateAverage()
findStudent()
saveFile()

instead of one 300-line method.

Appropriate abstraction

33. Refactoring

Refactoring means changing the internal organization of code without changing its external behavior.

Consider:

if (score >= 90) {
    System.out.println(name + ": A");
}

if (score >= 80 && score < 90) {
    System.out.println(name + ": B");
}

Repeated grading logic might be moved into:

public static char calculateGrade(int score)

Refactoring improves program structure while preserving correctness.

Professional programming involves frequent refactoring.

37. What transfers between programming languages?

Syntax changes.

For example, Java:

    System.out.println(i);
}

Python:

for i in range(10):
    print(i)

The syntax is different.

The underlying concept is the same:

iteration

Likewise, languages may use different syntax for:

functions
classes
collections
exceptions

38. The most important habit: decomposition

Consider the problem:

Read one million transaction records from a file and report the ten customers with the highest total spending.

A beginner may see one enormous problem.

An experienced programmer sees several smaller problems:

1. Read transactions.
2. Parse each record.
3. Associate spending with customers.
4. Accumulate totals.
5. Identify the ten largest totals.
6. Display results.

Each piece can be solved separately.

This ability to decompose problems is more valuable than memorizing syntax.

39. An integrated design exercise

Consider the following specification:

Design a package-delivery system. Each package has a tracking number, destination, weight, and status. The system must add packages, update package status, locate a package by tracking number, list all packages with a particular status, and calculate the total weight of packages awaiting delivery.

Before writing code, answer:

Question 1

What classes might exist?

Possible answer:

Package
DeliverySystem

Perhaps:

DeliveryStatus enum

Question 2

What should Package contain?

Possible fields:

String trackingNumber;
String destination;
double weight;
DeliveryStatus status;

Question 3

What collection should store packages?

An ArrayList<Package> might work.

However, packages are frequently located using tracking numbers.

Therefore:

HashMap<String, Package>

may be more appropriate.

Question 4

What is the complexity of locating a package?

With an array list:

O(n)

With a hash map:

average O(1)

Question 5

What design should handle package status?

An enum might be appropriate:

public enum DeliveryStatus {
    RECEIVED,
    IN_TRANSIT,
    OUT_FOR_DELIVERY,
    DELIVERED
}

Using an enum is preferable to arbitrary strings such as:

"delivered"
"Delivered"
"DELIVERED"
"done"

41. Don't optimize too early

Suppose you are processing 30 student records.

Whether your algorithm requires:

30 operations

or:

900 operations

may not matter.

For 30 million records, the difference may matter enormously.

Optimization decisions should consider:

input size
frequency of operation
memory constraints
required response time
code complexity

The theoretically fastest algorithm is not automatically the best engineering choice.

42. Time-space tradeoffs

Algorithms often trade memory for speed.

The duplicate detection example demonstrates this.

Nested loops use little additional memory:

space: O(1)
time: O(n²)

Using a HashSet requires additional storage:

space: O(n)
time: O(n)

We use more memory to reduce runtime.

This is called a time-space tradeoff.

Such tradeoffs appear throughout computer science.

44. How to get unstuck

Every programmer gets stuck.

A productive sequence is:

1. Read the error message carefully.
2. Identify the smallest failing example.
3. Trace the program state.
4. Check assumptions.
5. Consult documentation.
6. Simplify the problem.
7. Test one component independently.
8. Explain the problem aloud.

A powerful technique is explaining your program line-by-line to another person-or even to an empty chair.

Often the mistake becomes obvious while explaining it.

45. Error messages are information

Do not treat compiler messages and exceptions as enemies.

They are diagnostic information.

Consider:

NullPointerException

Instead of asking:

Why does Java hate my program?

Ask:

Which reference is null at this location, and why?

Consider:

ArrayIndexOutOfBoundsException

Ask:

Which index did I attempt to access, and what was the array length?

Programming becomes easier when error messages are treated as evidence.

54. A final code-analysis problem

Consider:

public static HashMap<String, Integer>
    countWords(ArrayList<String> words) {

    HashMap<String, Integer> counts = new HashMap<>();

    for (String word : words) {

        if (counts.containsKey(word)) {
            counts.put(word, counts.get(word) + 1);
        } else {
            counts.put(word, 1);
        }
    }

    return counts;
}

Students should now be able to explain:

What does the method do?

It calculates the frequency of each word.

What data structure is used?

HashMap

Why is a map appropriate?

Each word can serve as a key and its frequency as the associated value.

What is approximately the average runtime?

There are n words.

Each hash-map operation is approximately constant time on average.

Therefore:

O(n)

What programming concepts appear?

method
parameter
return value
generic types
ArrayList
HashMap
enhanced for loop
conditional
object references
algorithm analysis

This is what integration means.

58. Habits to continue developing

Write code regularly

Programming is a skill.

Reading programming books alone is not enough.

You improve by writing, debugging, modifying, and explaining code.

Read other people's code

Reading unfamiliar code develops a different skill than writing your own.

Both are important.

Ask why

Instead of only learning:

HashMap lookup is fast

ask:

Why is it fast?

Instead of only learning:

binary search is O(log n)

ask:

Why does repeatedly dividing the search space in half lead to logarithmic complexity?

Computer science is built on understanding why techniques work.

Predict before running

Before executing a program, ask:

What do I think this program will do?

Then run it.

If your prediction differs from the result, investigate why.

This develops precise reasoning.

Trace algorithms by hand

For algorithms and data structures, draw diagrams.

For arrays:

index:
0  1  2  3

For linked lists:

A → B → C

For trees:

      A
     / \
    B   C

Visual representations often make algorithms easier to understand.

59. Five principles to remember

If you remember only five ideas from CSC500, remember these.

Principle 1: decompose problems

Large problems are solved by dividing them into smaller problems.

Principle 2: choose representations carefully

The way data is represented strongly influences how easily and efficiently a problem can be solved.

Principle 3: use abstraction

Hide unnecessary details and reason at the appropriate level.

Principle 4: think about efficiency

A solution that works for 10 elements may not work for 10 million.

Principle 5: test your assumptions

Programs often fail because the programmer assumed something that was not actually true.

63. Suggested in-class activities

Activity 1 - code reading

Give students an unfamiliar Java method of approximately 20–30 lines.

Ask them to identify:

  • inputs
  • output
  • important variables
  • data structures
  • algorithm
  • expected complexity

Do not allow them to run the code initially.

They must reason about it first.

Activity 2 - data-structure selection

For each scenario, students select a data structure and justify the choice.

Scenario a

Store browser history where the most recently visited page should be retrieved first.

Likely answer:

Stack

Scenario b

Process customer-support requests in arrival order.

Likely answer:

Queue

Scenario C

Determine whether a username has already been registered.

Likely answer:

HashSet

Scenario D

Find account information given an account number.

Likely answer:

HashMap

Scenario e

Represent the directory structure on a computer.

Likely answer:

Tree

Activity 3 - complexity identification

Determine the approximate complexity of each fragment.

A

return values[0];

Answer:

O(1)

B

for (int value : values) {
    System.out.println(value);
}

Answer:

O(n)

C

for (int x : values) {
    for (int y : values) {
        System.out.println(x + y);
    }
}

Answer:

O(n²)

D

Repeatedly divide a sorted search range in half.

Answer:

O(log n)

Activity 4 - architecture exercise

Give students the following system:

Design a movie-streaming application that stores users, movies, ratings, and watch histories.

In small groups, ask students to identify:

  • classes
  • relationships
  • collections
  • method responsibilities
  • likely search operations
  • potential performance concerns

Have groups compare their designs.

Emphasize that multiple reasonable designs may exist.
