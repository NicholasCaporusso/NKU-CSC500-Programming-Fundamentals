Week 11: algorithm analysis, searching, and sorting

1. Overview

Up to this point in the course, we have mostly asked:

Can we write a program that solves the problem?

This week, we introduce a second question:

How efficiently does the program solve the problem?

Two programs can produce exactly the same output but behave very differently as the amount of input data grows.

For a collection containing 10 elements, those differences may not matter. For a collection containing 10 million elements, they can matter enormously.

This week introduces three closely related topics:

  1. Algorithm analysis
  2. Searching
  3. Sorting

Our main goal is not to memorize algorithms. The goal is to learn how to compare alternative solutions and reason about their performance.

2. Learning objectives

By the end of this week, you should be able to:

  • explain what an algorithm is;
  • distinguish an algorithm from a particular Java implementation;
  • identify the input size of a problem;
  • count important operations in simple algorithms;
  • explain why we focus on growth rate rather than exact running time;
  • interpret common Big-O complexity classes;
  • analyze simple loops and nested loops;
  • implement linear search;

  • explain why binary search requires sorted data;
  • compare linear search and binary search;
  • implement selection sort;

  • reason about the time complexity of simple searching and sorting algorithms;
  • recognize that different algorithms can solve the same problem with dramatically different efficiency.

Part I - algorithms and efficiency

3. What is an algorithm?

An algorithm is a precise sequence of steps for solving a problem.

Consider the problem:

Find the largest number in an array.

One algorithm is:

  1. Assume the first element is the largest.
  2. Examine every remaining element.
  3. Whenever a larger element is found, remember it.
  4. After all elements have been examined, return the remembered value.

In Java:

public static int findMax(int[] values) {
    int max = values[0];

    for (int i = 1; i < values.length; i++) {
        if (values[i] > max) {
            max = values[i];
        }
    }

    return max;
}

The algorithm is the general procedure.

The Java code is one implementation of that algorithm.

The distinction matters because the same algorithm could be implemented in Java, Python, C++, or another language.

4. What does it mean for an algorithm to be efficient?

There are several types of efficiency.

Two especially important ones are:

  • time efficiency - how much computation an algorithm performs;
  • space efficiency - how much additional memory an algorithm uses.

In this course, we will focus primarily on time efficiency.

Suppose two algorithms solve the same problem.

Algorithm A performs roughly:

n operations

Algorithm B performs roughly:

n² operations

For small values of n, both might seem fast.

If:

n = 10

then approximately:

Algorithm A: 10 operations
Algorithm B: 100 operations

That is not a major difference.

But if:

n = 1,000,000

then approximately:

Algorithm A: 1,000,000 operations
Algorithm B: 1,000,000,000,000 operations

The difference becomes enormous.

This is why computer scientists study how algorithms behave as the size of their input increases.

5. Input size

When analyzing an algorithm, we usually represent the size of its input using the variable:

n

For an array:

int[] values;

we usually define:

n = values.length

If the array contains 100 elements, then:

n = 100

If it contains 1 million elements:

n = 1,000,000

Not every problem measures input size in exactly the same way.

Examples:

ProblemPossible meaning of n
Searching an arrayNumber of elements
Sorting a listNumber of elements
Processing a stringNumber of characters
Processing a fileNumber of records
Working with a graphNumber of vertices and/or edges

Before analyzing an algorithm, always ask:

What does n represent?

6. Counting operations

Consider:

for (int i = 0; i < values.length; i++) {
    System.out.println(values[i]);
}

If the array contains n elements, the body of the loop executes:

n times

We therefore say the amount of work grows approximately in proportion to n.

Now consider:

for (int i = 0; i < values.length; i++) {
    for (int j = 0; j < values.length; j++) {
        System.out.println(values[i] + " " + values[j]);
    }
}

The outer loop runs n times.

For every outer-loop iteration, the inner loop also runs n times.

Therefore:

n × n = n²

The body executes approximately n² times.

This difference is one of the most important patterns to recognize in algorithm analysis.

7. Exact runtime is usually the wrong measure

We could measure an algorithm using a stopwatch.

For example:

Program A took 0.27 seconds.
Program B took 0.31 seconds.

But this tells us relatively little about the algorithms themselves.

Actual execution time depends on:

  • processor speed;
  • memory;
  • operating system;
  • Java version;
  • compiler and JVM optimizations;
  • other programs running on the machine;
  • characteristics of the particular input.

Instead, we want a machine-independent way to describe how computational effort grows.

This leads us to asymptotic analysis and Big-O notation.

Part II - big-o notation

8. The basic idea

Big-O notation describes how the amount of work performed by an algorithm grows as the input size grows.

Suppose an algorithm performs:

3n + 5

operations.

As n becomes very large, the 3n term dominates the constant 5.

We therefore classify the algorithm as:

O(n)

Read this as:

Big-O of n

or:

Order n

The important idea is that we focus on the growth rate.

9. Ignore constant factors

Suppose one algorithm performs:

5n

operations.

Another performs:

100n

Both are classified as:

O(n)

Why?

Because doubling n approximately doubles the work for both algorithms.

Their growth pattern is the same.

This does not mean constants never matter in real programs.

It means Big-O deliberately ignores them so that we can reason about scalability.

10. Ignore lower-order terms

Suppose the number of operations is:

4n² + 7n + 12

For very large n, the n² term dominates.

So we classify the algorithm as:

O(n²)

Similarly:

n + 10       → O(n)

3n² + n      → O(n²)

7            → O(1)

n³ + n² + n → O(n³)

11. Common complexity classes

You should become familiar with the following growth rates.

O(1) - constant time

The amount of work does not grow with the input size.

Example:

int first = values[0];

Accessing an array element by index takes roughly the same amount of time whether the array contains 10 elements or 10 million.

Another example:

return values[values.length - 1];

Complexity:

O(1)

O(log n) - logarithmic time

The problem gets significantly smaller after each operation.

Binary search is the most important example we will study.

For binary search, each step eliminates approximately half of the remaining possibilities.

Complexity:

O(log n)

Logarithmic algorithms scale extremely well.

O(n) - linear time

The amount of work increases proportionally with the input size.

Example:

for (int value : values) {
    System.out.println(value);
}

Complexity:

O(n)

If the input doubles, the amount of work roughly doubles.

O(n log n)

Many efficient sorting algorithms have this complexity.

Examples include:

  • merge sort;
  • heapsort;
  • average-case quicksort.

We will encounter these algorithms later in computer science courses.

For now, recognize that:

O(n log n)

grows substantially more slowly than:

O(n²)

O(n²) - quadratic time

Quadratic behavior often appears when we process all pairs of input elements.

Example:

for (int i = 0; i < n; i++) {
    for (int j = 0; j < n; j++) {
        // constant-time work
    }
}

Complexity:

O(n²)

Selection sort and insertion sort have quadratic worst-case behavior.

O(2ⁿ) - exponential time

The amount of work roughly doubles whenever n increases by 1.

These algorithms become impractical very quickly.

Certain naive recursive algorithms can exhibit exponential behavior.

12. Comparing growth rates

Consider these values:

Notice how slowly logarithmic growth increases.

For one million elements:

log₂(1,000,000) ≈ 20

This fact explains the power of binary search.

Part III - analyzing Java code

13. Sequential statements

Consider:

int x = values[0];

for (int value : values) {
    System.out.println(value);
}

The first statement is:

O(1)

The loop is:

O(n)

Together:

O(1) + O(n)

The dominant term is n.

Therefore:

O(n)

14. Consecutive loops

Consider:

for (int value : values) {
    System.out.println(value);
}

for (int value : values) {
    System.out.println(value * 2);
}

Each loop runs n times.

Total work:

n + n = 2n

Ignore the constant factor:

O(n)

A common mistake is to assume that two loops always mean O(n²).

They do not.

Nested loops multiply.

Consecutive loops add.

15. Nested loops

for (int i = 0; i < n; i++) {
    for (int j = 0; j < n; j++) {
        System.out.println(i + ", " + j);
    }
}

The outer loop executes n times.

For each iteration, the inner loop executes n times.

Total:

n × n = n²

Therefore:

O(n²)

16. A triangular nested loop

What about:

for (int i = 0; i < n; i++) {
    for (int j = 0; j < i; j++) {
        System.out.println(i + ", " + j);
    }
}

The number of iterations is approximately:

0 + 1 + 2 + 3 + ... + (n - 1)

This sum is:

n(n - 1) / 2

which is approximately:

n² / 2

Ignoring constants and lower-order terms:

O(n²)

The inner loop does not need to execute exactly n times for the overall algorithm to be quadratic.

Part IV - searching

17. The search problem

A common computational problem is:

Given a collection of values and a target, determine whether the target appears in the collection.

For example:

Array:
[14, 8, 21, 5, 17]

Target:
21

A search algorithm should determine that 21 appears in the array.

It may return:

  • true or false;
  • the index where the element occurs;
  • the element itself.

We will use the convention of returning the index and returning -1 if the element is not found.

18. Linear search

The simplest searching algorithm is linear search.

The idea:

  1. Start with the first element.
  2. Compare it to the target.
  3. If it matches, return its index.
  4. Otherwise examine the next element.
  5. Continue until the target is found or the array ends.

Example:

Array:
[12, 7, 19, 4, 25]

Target:
19

Search:

12 → not 19
 7 → not 19
19 → found

The answer is index:

2

19. Linear search in Java

public static int linearSearch(int[] values, int target) {
    for (int i = 0; i < values.length; i++) {
        if (values[i] == target) {
            return i;
        }
    }

    return -1;
}

Example:

int[] numbers = {12, 7, 19, 4, 25};

int index = linearSearch(numbers, 19);

System.out.println(index);

Output:

2

20. Analyzing linear search

Suppose the array contains n elements.

Best case

The target is the first element.

Only one comparison is required.

O(1)

Worst case

The target is:

  • the last element; or
  • not present at all.

We must inspect all n elements.

O(n)

Average case

On average, we examine some constant fraction of the array.

That is still linear growth.

O(n)

When we state the complexity of linear search, we commonly say:

O(n)

21. Does linear search require sorted data?

No.

Linear search works on:

[8, 17, 2, 91, 4]

and also on:

[2, 4, 8, 17, 91]

Its advantage is simplicity.

Its disadvantage is that it may have to examine every element.

Part V - binary search

22. The key idea

Suppose we want to find the number 73 in the following sorted array:

[4, 11, 19, 27, 32, 45, 58, 66, 73, 81, 90]

A linear search would start at the beginning.

Binary search does something smarter.

It looks near the middle.

Suppose the middle value is:

45

Since:

73 > 45

and the array is sorted, we know that 73 cannot appear anywhere to the left of 45.

We can immediately discard approximately half of the array.

That is the crucial insight.

23. Binary search procedure

Given a sorted array:

  1. Identify the middle element.
  2. Compare the middle element with the target.
  3. If they are equal, we are done.
  4. If the target is smaller, search only the left half.
  5. If the target is larger, search only the right half.
  6. Repeat.

Each comparison removes approximately half of the remaining search space.

24. Binary search example

Search for:

31

in:

[3, 7, 12, 18, 22, 27, 31, 36, 42, 49, 55]

First range:

[3, 7, 12, 18, 22, 27, 31, 36, 42, 49, 55]
                    ^
                   27

Since:

31 > 27

discard the left half.

Remaining:

[31, 36, 42, 49, 55]
         ^
        42

Since:

31 < 42

discard the right half.

Remaining:

[31, 36]
 ^
31

Found.

We searched an 11-element array in only three comparisons.

25. Binary search in Java

public static int binarySearch(int[] values, int target) {
    int low = 0;
    int high = values.length - 1;

    while (low <= high) {
        int mid = low + (high - low) / 2;

        if (values[mid] == target) {
            return mid;
        } else if (target < values[mid]) {
            high = mid - 1;
        } else {
            low = mid + 1;
        }
    }

    return -1;
}

Three variables define the current search region:

low
high
mid

At all times, if the target exists, it must be between:

low and high

26. Why use this formula for mid?

You may see:

int mid = (low + high) / 2;

For many beginner programs, this works.

A safer version is:

int mid = low + (high - low) / 2;

The second version avoids possible integer overflow when low and high are very large.

The important conceptual point is simply that mid represents the middle of the current search interval.

27. Binary search requires sorted data

Binary search relies on statements like:

Since the target is greater than the middle value, it cannot be in the left half.

That reasoning only works if the values are ordered.

Consider:

[40, 2, 99, 7, 15]

Suppose the middle value is:

99

and we are looking for:

40

Because 40 < 99, binary search might discard the right side.

But the relative position of 40 tells us nothing useful because the array is not sorted.

Therefore:

Binary search requires sorted data.

This is a precondition of the algorithm.

28. Why is binary search o(log n)?

Suppose an array contains:

1,024 elements

Each comparison approximately halves the remaining data:

1024
512
256
128
64
32
16
8
4
2
1

It takes roughly 10 halvings.

Why?

Because:

2¹⁰ = 1024

Therefore:

log₂(1024) = 10

In general, the number of times we can repeatedly divide n by 2 is approximately:

log₂ n

So binary search runs in:

O(log n)

This is an enormous difference.

30. But sorting has a cost

Suppose your data is not already sorted.

You cannot simply say:

Binary search is faster, so always use binary search.

You might first have to sort the data.

That sorting process itself takes time.

If you need to search only once, sorting first may not be worthwhile.

If you need to search the same dataset thousands of times, sorting once and then using binary search repeatedly may be extremely beneficial.

Algorithm choice depends on the larger context.

This is an important principle:

The fastest individual operation does not always produce the best overall solution.

Part VI - sorting

31. What is sorting?

Sorting means rearranging data according to some ordering.

For numbers:

Before:
[7, 2, 9, 1, 5]

After:
[1, 2, 5, 7, 9]

For strings:

Before:
["pear", "apple", "orange"]

After:
["apple", "orange", "pear"]

Sorting is useful because organized data is often easier to:

  • search;
  • display;
  • compare;
  • group;
  • analyze.

Many computer science problems involve sorting either directly or indirectly.

Part VII - selection sort

32. Selection sort idea

Selection sort repeatedly chooses the smallest remaining value.

Suppose:

[29, 10, 14, 37, 13]

We divide the array conceptually into:

sorted region | unsorted region

Initially:

| 29 10 14 37 13

Find the smallest element:

10

Swap it with the first position:

10 | 29 14 37 13

Now find the smallest value in the remaining unsorted region:

13

Swap:

10 13 | 14 37 29

Continue:

10 13 14 | 37 29

Then:

10 13 14 29 | 37

Finished.

33. Selection sort in Java

public static void selectionSort(int[] values) {
    for (int i = 0; i < values.length - 1; i++) {

        int minIndex = i;

        for (int j = i + 1; j < values.length; j++) {
            if (values[j] < values[minIndex]) {
                minIndex = j;
            }
        }

        int temp = values[i];
        values[i] = values[minIndex];
        values[minIndex] = temp;
    }
}

34. Understanding selection sort

The variable:

i

represents the position we are currently filling.

The variable:

minIndex

stores the location of the smallest value found so far.

The inner loop searches the unsorted region.

Then we swap the smallest value into position i.

35. Tracing selection sort

Consider:

[6, 3, 8, 2, 5]

Pass 1

Find smallest among:

6 3 8 2 5

Smallest:

2

Swap with 6:

[2, 3, 8, 6, 5]

Pass 2

Search:

3 8 6 5

Smallest:

3

Already in correct position.

[2, 3, 8, 6, 5]

Pass 3

Search:

8 6 5

Smallest:

5

Swap:

[2, 3, 5, 6, 8]

Pass 4

Search:

6 8

Smallest:

6

Finished:

[2, 3, 5, 6, 8]

36. Complexity of selection sort

The first pass examines approximately:

n elements

The second examines approximately:

n - 1

Then:

n - 2

and so on.

Total comparisons are approximately:

n + (n - 1) + (n - 2) + ... + 1

which is approximately:

n² / 2

Therefore:

O(n²)

Notice something interesting:

Even if the array is already sorted, selection sort still searches the remaining unsorted region on every pass.

Its best and worst cases are therefore both quadratic in terms of comparisons.

Part VIII - insertion sort

37. The basic idea

Insertion sort works similarly to the way people often organize playing cards in their hands.

Imagine you receive cards one at a time.

You keep the cards already in your hand sorted.

Whenever you receive a new card, you move it left until it reaches the correct position.

That is essentially insertion sort.

38. Insertion sort example

Start with:

[7, 4, 5, 2]

Treat the first value as already sorted:

7 | 4 5 2

Insert 4 into the sorted portion:

4 7 | 5 2

Insert 5:

4 5 7 | 2

Insert 2:

2 4 5 7

Done.

39. Insertion sort in Java

public static void insertionSort(int[] values) {
    for (int i = 1; i < values.length; i++) {

        int current = values[i];
        int j = i - 1;

        while (j >= 0 && values[j] > current) {
            values[j + 1] = values[j];
            j--;
        }

        values[j + 1] = current;
    }
}

40. Understanding the code

Suppose:

[3, 7, 9, 4, 8]

and:

current = 4;

The left portion is already sorted:

[3, 7, 9]

We need to insert 4.

Compare with 9.

Shift 9 right:

[3, 7, 9, 9, 8]

Compare with 7.

Shift 7 right:

[3, 7, 7, 9, 8]

Compare with 3.

Since:

3 < 4

stop shifting.

Insert 4:

[3, 4, 7, 9, 8]

The sorted region has grown by one element.

41. Complexity of insertion sort

In the worst case, the array may be in reverse order:

[5, 4, 3, 2, 1]

Each new value may need to move across nearly the entire sorted portion.

The number of operations grows approximately as:

1 + 2 + 3 + ... + (n - 1)

Therefore the worst-case complexity is:

O(n²)

However, insertion sort has an interesting advantage.

Suppose the array is already sorted:

[1, 2, 3, 4, 5]

The inner loop does almost no work.

The algorithm can finish in approximately:

O(n)

in the best case.

Insertion sort can therefore perform quite well on small or nearly sorted datasets.

42. Selection sort vs. insertion sort

The important point is not that one is universally better.

The important point is that algorithms have different performance characteristics.

Part IX - why do we study slow sorting algorithms?

43. A reasonable question

If selection sort is O(n²), and faster sorting algorithms exist, why study it?

Because simple algorithms help us understand important concepts:

  • nested loops;
  • invariants;
  • swapping;
  • partitioning data into processed and unprocessed regions;
  • algorithm analysis;
  • comparison of alternative strategies.

Selection sort and insertion sort are conceptually manageable enough that we can understand every operation.

Later, more sophisticated sorting algorithms build on similar reasoning.

44. Java already knows how to sort

In normal Java programs, we often use a library method instead of implementing a sorting algorithm ourselves.

For arrays:

import java.util.Arrays;

int[] numbers = {7, 2, 9, 1, 5};

Arrays.sort(numbers);

For lists:

import java.util.ArrayList;
import java.util.Collections;

ArrayList<Integer> numbers = new ArrayList<>();

numbers.add(7);
numbers.add(2);
numbers.add(9);

Collections.sort(numbers);

Why implement sorting ourselves in this class?

Because our goal is not merely to produce a sorted array.

Our goal is to understand how algorithms work.

This distinction appears throughout computer science:

In application development, use good libraries. In computer science education, understand what those libraries are doing conceptually.

Part X - empirical analysis

45. Theory and experiment

Big-O gives us a theoretical model.

We can also measure algorithms experimentally.

For example:

long start = System.nanoTime();

selectionSort(values);

long end = System.nanoTime();

long elapsed = end - start;

System.out.println(elapsed);

This produces an empirical measurement of running time.

But individual measurements can be noisy.

To perform a meaningful experiment, we might:

  1. Generate arrays of different sizes.
  2. Run the algorithm several times.
  3. Average the measurements.
  4. Compare how runtime changes as n increases.

46. An experiment

Suppose we time selection sort using arrays of increasing size.

Imagine we observe:

nApproximate time
1,0002 ms
2,0008 ms
4,00032 ms
8,000128 ms

Notice what happens when n doubles:

1,000 → 2,000

Runtime increases by approximately four times.

Why?

Because:

(2n)² = 4n²

This behavior is consistent with an:

O(n²)

algorithm.

47. Experimental evidence does not replace analysis

Suppose an algorithm appears fast when tested on:

n = 100

That does not prove it scales well.

Likewise, benchmarking can be influenced by:

  • JVM startup;
  • garbage collection;
  • caching;
  • processor scheduling;
  • other applications;
  • input distribution.

We therefore use both:

theoretical analysis

and

experimental measurement

to understand algorithms.

Part XI - important distinctions

48. Best case, worst case, and average case

The same algorithm may require different amounts of work for different inputs.

Linear search

Array:

[7, 4, 9, 3, 8]

Searching for 7:

best case

One comparison.

Searching for 100:

worst case

Every element must be checked.

We therefore sometimes describe:

  • best-case complexity;
  • worst-case complexity;
  • average-case complexity.

Unless otherwise specified, introductory discussions of Big-O frequently focus on the worst-case upper growth rate.

49. Big-o is not a stopwatch

If algorithm A is:

O(n)

and algorithm B is:

O(n²)

that does not guarantee A is faster for every possible input size.

For very small n, constants and implementation details can dominate.

Big-O tells us primarily how algorithms behave as:

n becomes large.

50. Big-o describes growth, not exact work

Consider:

for (int i = 0; i < n; i++) {
    doSomething();
}

Suppose doSomething() takes 500 machine instructions.

The loop might really involve something like:

500n

operations.

But:

500n

still has linear growth.

So we write:

O(n)

Part XIII - common mistakes

57. Mistake: "every loop is o(n)"

No.

Consider:

for (int i = 0; i < 100; i++) {
    ...
}

This always performs 100 iterations regardless of the size of the input.

Therefore, relative to input size n, it is:

O(1)

58. Mistake: "two loops mean o(n²)"

Not necessarily.

Consecutive loops:

for (...) {
}

for (...) {
}

often give:

O(n + n) = O(n)

Nested loops:

for (...) {
    for (...) {
    }
}

often give:

O(n²)

59. Mistake: binary search works on any array

False.

Binary search requires:

sorted data

Without sorting, comparing the target with the middle value tells us nothing about which half can safely be discarded.

60. Mistake: o(n²) means exactly n² operations

False.

Big-O describes a growth class.

An algorithm performing:

0.5n² + 20n + 7

is still:

O(n²)

61. Mistake: faster big-o always means faster for every input

False.

For small data, implementation details may matter more.

Big-O is primarily a statement about scalability.

Part XIV - a broader view of algorithm choice

62. Algorithms encode tradeoffs

Suppose you have a million unsorted records and need to search them once.

Linear search may be completely reasonable.

Suppose you have the same million records and need to search them one million times.

Now it may be worthwhile to:

  1. sort the records;
  2. perform repeated binary searches.

Later in computer science, you will encounter data structures that provide even more sophisticated tradeoffs.

Examples include:

  • hash tables;
  • balanced search trees;
  • heaps;
  • graphs.

An important skill in computer science is not merely knowing algorithms.

It is knowing:

Which algorithm or data structure is appropriate for this situation?

Part XVIII - key takeaways

The most important ideas from this week are:

  1. Correctness is not the only property of a program that matters.

We also care about efficiency.

  1. Big-O describes growth.

It tells us how the amount of computational work changes as the input becomes larger.

  1. Constant factors and lower-order terms are ignored in asymptotic analysis.

For example:

``text 5n + 20 → O(n) ``

  1. Linear search is O(n).

It may need to examine every item.

  1. Binary search is O(log n).

It repeatedly removes half of the remaining search space.

  1. Binary search requires sorted data.
  1. Selection sort is O(n²).
  1. Insertion sort is O(n²) in the worst case but O(n) in the best case.
  1. Algorithm choice depends on context.

The best solution depends on the size and organization of the data and on what operations will be performed.

  1. Efficiency becomes increasingly important as data grows.

A solution that is perfectly acceptable for 100 values may be unusable for 100 million values.
