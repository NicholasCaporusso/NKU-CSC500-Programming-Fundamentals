1. Overview

Up to this point, we have spent most of our time asking questions such as:

Can we write a program that correctly solves the problem?

That question remains essential. A program that produces incorrect results is not useful, no matter how fast it runs.

This week, however, we introduce a second major question:

How efficiently does the program solve the problem?

Two programs may produce exactly the same output and yet behave very differently as the amount of data grows.

For an array containing 10 elements, those differences may be invisible.

For an array containing 10 million elements, they may be enormous.

Consider two hypothetical algorithms:

  • Algorithm A performs approximately n operations.
  • Algorithm B performs approximately n² operations.

If:

n = 10

then:

Algorithm A:       about 10 operations
Algorithm B:       about 100 operations

Both are small.

But if:

n = 1,000,000

then:

Algorithm A:       about 1,000,000 operations
Algorithm B:       about 1,000,000,000,000 operations

The difference has become dramatic.

This week therefore introduces three closely related topics:

  1. Algorithm analysis
  2. Searching
  3. Sorting

We will also see our first important example of a broader algorithm-design strategy called divide and conquer.

The goal is not to memorize a collection of Java methods.

The larger goal is to learn how to ask:

  • What work is this algorithm performing?
  • How does that work grow as the input gets larger?
  • What assumptions does the algorithm require?
  • Is another algorithm better for this situation?
  • What tradeoffs are involved?

These questions appear throughout computer science.

Part I — Algorithms and efficiency

3. What is an algorithm?

An algorithm is a finite, well-defined sequence of steps for solving a problem or performing a computation.

Consider the problem:

Find the largest number in an array.

Suppose the array is:

[8, 12, 3, 27, 15]

One algorithm is:

  1. Assume that the first element is the largest.
  2. Examine every remaining element.
  3. Whenever a larger element is found, remember it.
  4. After all elements have been examined, return the remembered value.

A Java implementation might be:

public static int findMax(int[] values) {
    int max = values[0];

    for (int i = 1; i < values.length; i++) {
        if (values[i] > max) {
            max = values[i];
        }
    }

    return max;
}

The algorithm is the general procedure.

The Java method is one implementation of the algorithm.

The same algorithm could be implemented in:

  • Java,
  • Python,
  • C++,
  • JavaScript,
  • or another programming language.

This distinction is important because algorithm analysis is primarily concerned with the underlying procedure, not with one particular programming language.

3.1 Properties of a good algorithm

A useful algorithm should normally be:

Correct

It produces the required result.

Finite

It eventually terminates.

Unambiguous

Its steps are clearly defined.

General

It solves a class of inputs rather than one particular example.

Efficient enough

Its resource requirements are reasonable for the intended problem.

Notice the phrase efficient enough.

The theoretically fastest possible solution is not always necessary.

An algorithm that processes 20 values in a fraction of a millisecond may be perfectly acceptable even if another algorithm is asymptotically better.

Algorithm choice depends on context.

4. Correctness comes before efficiency

Suppose we create an extremely fast search method:

public static int search(int[] data, int target) {
    return 0;
}

Its runtime is constant.

But unless the target always happens to be at index 0, the result is wrong.

So efficiency alone is meaningless.

A sensible development process is:

  1. Clearly understand the problem.
  2. Design an algorithm.
  3. Make the algorithm correct.
  4. Test it.
  5. Analyze its performance.
  6. Improve it if improvement is necessary.

This principle is worth remembering:

A fast wrong answer is still a wrong answer.

5. What does efficiency mean?

Two major resources matter when analyzing algorithms.

5.1 Time efficiency

Time complexity describes how the amount of computational work grows as the input becomes larger.

We might count:

  • comparisons;
  • assignments;
  • arithmetic operations;
  • array accesses;
  • loop iterations;
  • method calls.

We usually do not need to count every machine instruction.

Instead, we choose operations that provide a useful model of the algorithm's work.

5.2 Space efficiency

Space complexity describes how much additional memory an algorithm requires.

Consider:

public static int sum(int[] data) {
    int total = 0;

    for (int value : data) {
        total += value;
    }

    return total;
}

No matter how large data becomes, the method only needs a few variables.

Its additional space is approximately:

O(1)

Now imagine an algorithm that creates another array:

int[] copy = new int[data.length];

If data contains n elements, the new array also contains n elements.

Its additional storage grows as:

O(n)

CSC 500 primarily focuses on time complexity this week, but space complexity is another important part of algorithm design.

6. Input size

Before analyzing an algorithm, ask:

What exactly does n represent?

For an array:

int[] data;

we normally define:

n = data.length

Examples:

ProblemPossible meaning of n
Search an arrayNumber of elements
Sort an arrayNumber of elements
Process a stringNumber of characters
Process a fileNumber of records
Examine a matrixNumber of rows and/or columns
Process a graphNumber of vertices and/or edges

For Week 11, most of our examples involve arrays, so unless otherwise stated:

n = number of elements in the array

7. Choosing a basic operation

When analyzing an algorithm, it is often useful to identify one operation that represents most of the algorithm's work.

For linear search:

if (data[i] == target)

the important operation might be the comparison:

data[i] == target

For selection sort:

if (data[j] < data[minIndex])

the comparison:

data[j] < data[minIndex]

is a useful operation to count.

The goal is not to model every CPU instruction.

The goal is to understand how the amount of important work changes when n changes.

8. Counting work: A first example

Consider:

for (int i = 0; i < data.length; i++) {
    System.out.println(data[i]);
}

If:

n = data.length

then the loop body executes:

n times

The amount of work therefore grows approximately in proportion to n.

Now consider:

for (int i = 0; i < data.length; i++) {
    for (int j = 0; j < data.length; j++) {
        System.out.println(data[i] + ", " + data[j]);
    }
}

The outer loop executes n times.

During each outer iteration, the inner loop executes n times.

Therefore:

n × n = n²

The body executes approximately n² times.

This distinction will appear repeatedly throughout this week.

Part II — Asymptotic analysis and Big-O

9. Why not just use a stopwatch?

We could compare programs by saying:

Program A: 0.21 seconds
Program B: 0.34 seconds

But this does not tell us very much about the algorithms themselves.

Elapsed time can depend on:

  • processor speed;
  • available memory;
  • operating system;
  • Java version;
  • JVM implementation;
  • just-in-time compilation;
  • garbage collection;
  • CPU cache behavior;
  • other applications running;
  • input arrangement;
  • implementation details.

The same Java method may take different amounts of time on two different computers.

We therefore need a more general way to describe how algorithms scale.

That leads to asymptotic analysis.

10. The central idea of Big-O

Big-O notation describes how computational work grows as the input size becomes large.

Suppose an algorithm performs approximately:

3n + 5

operations.

For:

n = 10

the expression is:

35

For:

n = 1,000,000

it is:

3,000,005

As n becomes large, the 3n part determines the overall growth pattern.

The constant 5 matters less and less.

So we classify the algorithm as:

O(n)

Read:

Big-O of n

The crucial point is:

Big-O describes growth, not exact elapsed time.

11. Simplifying complexity expressions

Two rules are especially useful at this level.

Rule 1: Ignore constant multipliers

Suppose:

T(n) = 5n

or:

T(n) = 500n

Both have the same general growth pattern.

If n doubles, the work approximately doubles.

Therefore:

5n     → O(n)
500n   → O(n)

This does not mean that 5 and 500 are identical in real performance.

Big-O deliberately hides such constant factors so we can focus on scalability.

Rule 2: Keep the dominant term

Suppose:

T(n) = 4n² + 7n + 12

For large n, the n² term grows much more quickly than the others.

Therefore:

4n² + 7n + 12 → O(n²)

More examples:

7                  → O(1)
3n + 10            → O(n)
100n + 2           → O(n)
n² + n             → O(n²)
12n² + 500n + 3    → O(n²)
n³ + n² + n        → O(n³)

12. Common complexity classes

From slower-growing to faster-growing:

O(1)
O(log n)
O(n)
O(n log n)
O(n²)
O(n³)
O(2ⁿ)
O(n!)

For CSC 500, the most important ones this week are:

O(1)
O(log n)
O(n)
O(n log n)
O(n²)

12.1 O(1) — Constant time

The amount of work does not depend on the size of the input.

Example:

int first = data[0];

or:

int last = data[data.length - 1];

Whether the array contains:

10 elements

or:

10,000,000 elements

accessing a known index still takes approximately the same amount of work.

Therefore:

O(1)

Important:

O(1) does not necessarily mean exactly one machine operation.

It means the work does not grow with n.

12.2 O(log n) — Logarithmic time

Logarithmic behavior often appears when each step reduces the remaining problem by a constant factor.

Binary search is our primary example.

Suppose we begin with:

1024 possibilities

and repeatedly remove half:

1024
512
256
128
64
32
16
8
4
2
1

Only about 10 reductions are required.

Why?

2¹⁰ = 1024

so:

log₂(1024) = 10

The complexity is:

O(log n)

12.3 O(n) — Linear time

The amount of work grows in proportion to the input size.

Example:

for (int value : data) {
    System.out.println(value);
}

If the array doubles in size, the number of loop iterations approximately doubles.

Therefore:

O(n)

Linear search has O(n) worst-case behavior.

12.4 O(n log n) — Linearithmic time

Many efficient general-purpose sorting algorithms have complexity near:

O(n log n)

Examples include algorithms such as merge sort and heapsort, and typical efficient quicksort behavior.

We are not implementing those algorithms this week.

For now, the important observation is:

O(n log n)

grows substantially more slowly than:

O(n²)

for large values of n.

12.5 O(n²) — Quadratic time

Quadratic behavior commonly appears when an algorithm performs work involving many pairs of elements.

Example:

for (int i = 0; i < n; i++) {
    for (int j = 0; j < n; j++) {
        doSomething();
    }
}

The total number of inner operations is:

n × n = n²

so:

O(n²)

Selection sort and insertion sort have O(n²) worst-case time.

12.6 A brief look at O(2ⁿ)

An exponential algorithm may approximately double its work whenever n increases by one.

For example:

n = 10   → about 1,024 possibilities
n = 20   → about 1,048,576 possibilities
n = 30   → about 1,073,741,824 possibilities

Some naive recursive algorithms can have exponential growth.

We will not study exponential algorithms deeply this week, but they help illustrate why growth rate matters.

Part III — Analyzing Java code

14. A practical analysis strategy

For simple code, use this process:

  1. Identify what n means.
  2. Identify the important operation.
  3. Determine how often that operation executes.
  4. Write an expression for the work.
  5. Keep the fastest-growing term.
  6. Remove constant multipliers.
  7. State the Big-O class.

Do not classify code merely by looking at how many loops appear.

Analyze the actual loop bounds.

15. Constant work

int x = data[0];
int y = data[data.length - 1];
int sum = x + y;

Each statement performs a fixed amount of work.

The number of statements does not increase when the array grows.

Therefore:

O(1)

16. One linear loop

for (int i = 0; i < data.length; i++) {
    System.out.println(data[i]);
}

The body executes n times.

Therefore:

O(n)

17. A loop that skips elements

for (int i = 0; i < data.length; i += 2) {
    System.out.println(data[i]);
}

The loop executes approximately:

n / 2

times.

But:

O(n / 2) = O(n)

because constant factors are ignored.

18. A constant-size loop

for (int i = 0; i < 100; i++) {
    System.out.println(i);
}

This always performs 100 iterations.

The number does not depend on n.

Therefore:

O(1)

A loop is not automatically O(n).

19. Consecutive loops

for (int value : data) {
    System.out.println(value);
}

for (int value : data) {
    System.out.println(value * 2);
}

First loop:

n

Second loop:

n

Total:

n + n = 2n

Therefore:

O(n)

A very common mistake is:

"There are two loops, so it must be O(n²)."

That is incorrect.

These loops are consecutive, not nested.

20. Nested loops

for (int i = 0; i < n; i++) {
    for (int j = 0; j < n; j++) {
        doSomething();
    }
}

Outer loop:

n iterations

Inner loop for each outer iteration:

n iterations

Total:

n × n = n²

Therefore:

O(n²)

A useful intuition is:

  • consecutive blocks often add;
  • nested blocks often multiply.

But this is only a guideline. Always inspect the loop bounds.

21. Nested does not automatically mean O(n²)

Consider:

for (int i = 0; i < n; i++) {
    for (int j = 0; j < 10; j++) {
        doSomething();
    }
}

The outer loop executes n times.

The inner loop always executes exactly 10 times.

Total:

10n

Therefore:

O(n)

22. Triangular nested loops

Consider:

for (int i = 0; i < n; i++) {
    for (int j = 0; j < i; j++) {
        doSomething();
    }
}

The inner loop does not always run n times.

Its execution counts are approximately:

0 + 1 + 2 + 3 + ... + (n - 1)

The sum is:

n(n - 1) / 2

Expanding:

(n² - n) / 2

The dominant term is n².

Therefore:

O(n²)

This pattern will help us understand the sorting algorithms later.

23. Sequential blocks with different complexities

Consider:

for (int i = 0; i < n; i++) {
    taskA();
}

for (int i = 0; i < n * n; i++) {
    taskB();
}

The first block is:

O(n)

The second is:

O(n²)

Together:

O(n + n²)

The n² term dominates.

Therefore:

O(n²)

24. Conditionals

Consider:

if (condition) {
    linearSearch(data, target);
} else {
    binarySearch(sortedData, target);
}

Suppose:

linear search → O(n)
binary search → O(log n)

Only one branch executes.

For worst-case analysis, the more expensive branch gives:

O(n)

We do not automatically add mutually exclusive branches.

25. Early break and return

Consider:

for (int i = 0; i < data.length; i++) {
    if (data[i] == target) {
        break;
    }
}

The loop might stop immediately.

But what if the target:

  • is the last element, or
  • does not occur?

Then all n elements are examined.

So the worst case remains:

O(n)

The same reasoning applies to an early return.

An early exit can improve some cases without changing worst-case complexity.

26. Logarithmic loops

Consider:

int value = n;

while (value > 1) {
    value /= 2;
}

The values might be:

1024
512
256
128
64
32
16
8
4
2
1

The loop does not execute n times.

Instead, it repeatedly halves the remaining value.

Therefore:

O(log n)

The reverse pattern also appears:

for (int i = 1; i < n; i *= 2) {
    doSomething();
}

The values of i are:

1, 2, 4, 8, 16, 32, ...

Again:

O(log n)

Repeated multiplication or division by a fixed factor is an important clue that logarithmic behavior may be present.

Part IV — Best, average, and worst cases

27. Why input arrangement matters

The same algorithm may perform different amounts of work on different inputs.

Consider linear search:

public static int linearSearch(int[] data, int target) {
    for (int i = 0; i < data.length; i++) {
        if (data[i] == target) {
            return i;
        }
    }

    return -1;
}

Suppose:

[7, 4, 9, 3, 8]

Searching for 7 requires one comparison.

Searching for 8 requires five.

Searching for 100 also requires five.

This motivates three useful ideas.

27.1 Best case

The most favorable input.

For linear search, the target could be first:

O(1)

27.2 Worst case

The least favorable input.

For linear search, the target could be:

  • last, or
  • absent.

Then every element must be examined:

O(n)

27.3 Average case

The expected amount of work over some assumed collection of typical inputs.

A successful linear search might examine approximately half of the elements on average:

n / 2

But:

O(n / 2) = O(n)

So average successful linear search is still linear.

In introductory algorithm analysis, when no case is explicitly stated, we often discuss worst-case Big-O.

Part V — Searching

28. The search problem

A search problem has:

  • a collection of values;
  • a target;
  • a question about whether or where the target occurs.

For example:

Array:
[14, 8, 21, 5, 17]

Target:
21

A search algorithm might return:

  • true or false;
  • the matching value;
  • an index;
  • an object.

For our implementations, we will use this convention:

return the index if found
return -1 if not found

Why -1?

Valid array indices begin at:

0

So -1 can safely mean:

not found

29. Linear search

Linear search examines values one at a time from the beginning until either:

  • the target is found; or
  • the end of the collection is reached.

Example:

Array:
[12, 7, 19, 4, 25]

Target:
19

Trace:

index 0: 12 == 19? no
index 1:  7 == 19? no
index 2: 19 == 19? yes

Return:

2

30. Linear search in Java

public static int linearSearch(int[] data, int target) {
    for (int i = 0; i < data.length; i++) {
        if (data[i] == target) {
            return i;
        }
    }

    return -1;
}

Example:

public class SearchDemo {

    public static int linearSearch(int[] data, int target) {
        for (int i = 0; i < data.length; i++) {
            if (data[i] == target) {
                return i;
            }
        }

        return -1;
    }

    public static void main(String[] args) {
        int[] numbers = {12, 7, 19, 4, 25};

        int index = linearSearch(numbers, 19);

        if (index >= 0) {
            System.out.println("Found at index " + index);
        } else {
            System.out.println("Not found");
        }
    }
}

Output:

Found at index 2

31. Complexity of linear search

Suppose the array contains n elements.

Best case

Target appears at index 0.

1 comparison
O(1)

Worst case

Target is last or absent.

n comparisons
O(n)

Average successful case

Approximately:

n / 2 comparisons

which is:

O(n)

Therefore, we normally describe linear search as:

O(n)

in the worst case.

32. Does linear search require sorted data?

No.

Linear search works on:

[8, 17, 2, 91, 4]

and:

[2, 4, 8, 17, 91]

Its major advantages are:

  • simplicity;
  • no sorting requirement;
  • no setup cost.

Its disadvantage is that it may need to inspect every element.

33. Duplicate values and linear search

Suppose:

[4, 8, 8, 8, 12]

and we search for:

8

Our implementation returns as soon as it finds a match.

Therefore it returns:

1

It does not automatically find every occurrence.

This illustrates an important algorithm-design lesson:

Before implementing an algorithm, know exactly what the required output means.

Possible specifications include:

  • find any matching index;
  • find the first matching index;
  • find the last matching index;
  • count all matches;
  • return all matching indices.

Those are different problems.

34. When is linear search a good choice?

Linear search can be entirely reasonable when:

  • the data is unsorted;
  • the collection is small;
  • only one or a few searches are required;
  • data changes frequently;
  • simplicity is important.

Do not assume:

"Binary search is faster, therefore binary search is always better."

The entire problem matters.

Part VI — Binary search

35. The key idea

Suppose the array is sorted:

[4, 11, 19, 27, 32, 45, 58, 66, 73, 81, 90]

We want:

73

Linear search begins at the start.

Binary search instead examines the middle.

Middle value:

45

Since:

73 > 45

and the array is sorted, we immediately know:

73 cannot be anywhere left of 45

Almost half of the possibilities disappear after one comparison.

That is the fundamental insight behind binary search.

36. Binary search procedure

Given a sorted array:

  1. Define the current search interval.
  2. Examine the middle value.
  3. If it equals the target, return its index.
  4. If the target is smaller, discard the right half.
  5. If the target is larger, discard the left half.
  6. Repeat while candidates remain.
  7. If no candidates remain, report failure.

Each comparison removes approximately half of the remaining possibilities.

38. Binary search in Java

public static int binarySearch(int[] data, int target) {
    int low = 0;
    int high = data.length - 1;

    while (low <= high) {
        int mid = low + (high - low) / 2;

        if (data[mid] == target) {
            return mid;
        } else if (target < data[mid]) {
            high = mid - 1;
        } else {
            low = mid + 1;
        }
    }

    return -1;
}

39. Understanding low, high, and mid

These three variables define the search interval.

int low;
int high;
int mid;

At any point:

low ... high

represents the part of the array that still could contain the target.

This leads to an important invariant:

If the target exists in the array, it must be inside the current interval from low through high.

Each iteration preserves that statement while shrinking the interval.

Thinking in terms of this invariant helps explain why binary search is correct.

40. Why low <= high?

The loop condition is:

while (low <= high)

Why include equality?

Because:

low == high

means exactly one candidate remains.

That element still has to be checked.

When:

low > high

the interval is empty.

There are no possible positions left.

Therefore the target is absent.

Using:

while (low < high)

without carefully redesigning the surrounding logic can skip the final candidate.

This is a classic off-by-one error.

41. Why update to mid - 1 or mid + 1?

Suppose:

data[mid] < target

We already checked mid, and it does not match.

Because the data is sorted, neither mid nor anything to its left can be the target.

So:

low = mid + 1;

Similarly, if:

data[mid] > target

then:

high = mid - 1;

Using only:

low = mid;

or:

high = mid;

can cause the search interval to stop shrinking, possibly producing an infinite loop.

42. Why use this midpoint formula?

You may see:

int mid = (low + high) / 2;

For ordinary small arrays, that works.

A safer version is:

int mid = low + (high - low) / 2;

Why?

If low and high are extremely large, their sum could theoretically overflow an int.

The second expression avoids directly adding two large indices.

For this course, however, the central idea is simply:

mid must identify an element inside the current search interval.

43. Binary search requires sorted data

Consider:

[40, 2, 99, 7, 15]

Suppose we search for 40.

The middle value is 99.

Since:

40 < 99

could we safely discard everything to the right?

No.

Could we infer anything reliable about where 40 lies?

No.

The array is not ordered.

Binary search works because sorted order supports deductions such as:

If the target is smaller than the middle value, every element to the right is too large.

Without ordering, that reasoning fails.

Therefore:

Sorted data is a precondition of ordinary binary search.

A precondition is something that must be true before an algorithm is used correctly.

44. Complexity of binary search

Suppose:

n = 1,024

Each comparison reduces the search interval roughly like this:

1024
512

64

1

Only about 10 reductions.

Because:

2¹⁰ = 1024

we have:

log₂(1024) = 10

In general:

number of halvings ≈ log₂ n

Therefore binary search is:

O(log n)

44.1 What if there are one million elements?

Approximately:

log₂(1,000,000) ≈ 20

So binary search needs only around 20 comparisons in the worst case for a sorted array of roughly one million elements.

Linear search might need:

1,000,000 comparisons

That contrast shows how strongly different growth rates can affect performance.

45. Binary search and divide-and-conquer thinking

Binary search introduces an important algorithmic idea:

Solve a large problem by repeatedly reducing it to a much smaller problem.

At each step:

current search interval
        ↓
compare with middle
        ↓
discard one half
        ↓
continue with remaining half

This resembles the broader divide-and-conquer strategy.

A full divide-and-conquer algorithm often involves three conceptual steps:

  1. Divide a problem into smaller subproblems.
  2. Conquer the relevant subproblems.
  3. Combine their results when necessary.

Binary search is especially simple because after the comparison, only one half needs further searching, and there is essentially nothing to combine.

This same idea—reducing a large problem through structured subdivision—appears in many advanced algorithms.

46. Iterative and recursive binary search

Because Week 10 introduced recursion, binary search provides a useful connection.

The iterative version uses a loop:

public static int binarySearch(int[] data, int target) {
    int low = 0;
    int high = data.length - 1;

    while (low <= high) {
        int mid = low + (high - low) / 2;

        if (data[mid] == target) {
            return mid;
        } else if (target < data[mid]) {
            high = mid - 1;
        } else {
            low = mid + 1;
        }
    }

    return -1;
}

A recursive version expresses the same algorithm differently:

public static int binarySearchRecursive(
        int[] data,
        int target,
        int low,
        int high) {

    if (low > high) {
        return -1;
    }

    int mid = low + (high - low) / 2;

    if (data[mid] == target) {
        return mid;
    }

    if (target < data[mid]) {
        return binarySearchRecursive(
                data, target, low, mid - 1);
    }

    return binarySearchRecursive(
            data, target, mid + 1, high);
}

Call it using:

int index = binarySearchRecursive(
        data,
        target,
        0,
        data.length - 1);

Both versions perform logarithmically many search steps.

The purpose here is not to argue that one implementation is always superior.

It is to recognize that:

Algorithm and implementation style are different ideas.

47. Duplicate values in binary search

Suppose:

[2, 5, 5, 5, 8, 10]

and the target is:

5

A basic binary search may return any matching index that it encounters.

It does not automatically guarantee:

  • the first 5;
  • the last 5;
  • all occurrences of 5.

If the specification requires the first or last occurrence, the algorithm must be modified.

Again:

Correctness is defined relative to the exact problem specification.

49. Sorting has a cost

Suppose you have one million unsorted values and need to search for one target.

Part VII — Sorting

50. What is sorting?

Sorting rearranges values according to an ordering rule.

Numbers:

Before:
[7, 2, 9, 1, 5]

After:
[1, 2, 5, 7, 9]

Strings:

Before:
["pear", "apple", "orange"]

After:
["apple", "orange", "pear"]

Objects might be sorted according to:

  • student ID;
  • name;
  • score;
  • date;
  • price;
  • priority.

Sorting is useful because ordered data is often easier to:

  • search;
  • display;
  • compare;
  • group;
  • summarize;
  • process.

Part VIII — Selection sort

51. Selection sort: Main idea

Selection sort repeatedly finds the smallest value remaining in the unsorted part of the array and places it into the next position.

Conceptually, divide the array into:

sorted region | unsorted region

Initially:

| 29 10 14 37 13

Find the smallest value:

10

Swap it into the first position:

10 | 29 14 37 13

Find the smallest remaining value:

13

Move it into the second position:

10 13 | 14 37 29

Continue:

10 13 14 | 37 29

then:

10 13 14 29 | 37

The array is sorted.

52. Selection sort invariant

At the beginning of each outer-loop iteration:

The elements before index i are already in their final sorted positions.

This is an example of an invariant.

An invariant describes something that remains true at a particular stage throughout an algorithm.

Understanding invariants is useful because they explain why an algorithm works, not merely what its code does.

53. Selection sort in Java

public static void selectionSort(int[] data) {
    for (int i = 0; i < data.length - 1; i++) {

        int minIndex = i;

        for (int j = i + 1; j < data.length; j++) {
            if (data[j] < data[minIndex]) {
                minIndex = j;
            }
        }

        int temp = data[i];
        data[i] = data[minIndex];
        data[minIndex] = temp;
    }
}

54. Understanding selection sort variables

i

int i

represents the position that we are currently filling.

Everything before i is already sorted.

minIndex

int minIndex

stores the index of the smallest value found so far in the unsorted region.

j

int j

scans the remaining unsorted elements.

56. Complexity of selection sort

The first pass performs approximately:

n - 1 comparisons

The second:

n - 2

Then:

n - 3

and so forth.

Total:

(n - 1) + (n - 2) + ... + 2 + 1

This sum is:

n(n - 1) / 2

Expand:

(n² - n) / 2

Ignore the constant factor and lower-order term:

O(n²)

56.1 What if the array is already sorted?

Suppose:

[1, 2, 3, 4, 5]

Selection sort still scans the remaining unsorted region to verify the minimum during each pass.

Its comparison count remains quadratic.

Therefore:

Best-case comparisons:  O(n²)
Worst-case comparisons: O(n²)

Input order does not greatly improve its comparison complexity.

57. Selection sort and swaps

Although selection sort makes many comparisons, it performs relatively few swaps.

Typically, at most about:

n - 1 swaps

This illustrates an important point:

Two algorithms with the same Big-O time complexity may perform very different kinds and quantities of operations.

Big-O is essential, but it is not the whole performance story.

Part IX — Insertion sort

58. Insertion sort: Main idea

Insertion sort behaves somewhat like organizing playing cards in your hand.

Imagine receiving cards one at a time.

You keep the cards already received in sorted order.

Whenever a new card arrives, you insert it into the correct position.

For:

[7, 4, 5, 2]

treat the first element as sorted:

7 | 4 5 2

Insert 4:

4 7 | 5 2

Insert 5:

4 5 7 | 2

Insert 2:

2 4 5 7

59. Insertion sort invariant

Before each outer-loop iteration:

The portion of the array before index i is already sorted.

Unlike selection sort, those values are sorted but not necessarily in their final positions yet.

A newly inserted value may cause several existing values to shift right.

60. Insertion sort in Java

public static void insertionSort(int[] data) {
    for (int i = 1; i < data.length; i++) {

        int current = data[i];
        int j = i - 1;

        while (j >= 0 && data[j] > current) {
            data[j + 1] = data[j];
            j--;
        }

        data[j + 1] = current;
    }
}

61. Why does i start at 1?

Insertion sort treats:

data[0]

as a sorted region containing one element.

A one-element collection is automatically sorted.

Therefore the first element that needs to be inserted is:

data[1]

which explains:

for (int i = 1; i < data.length; i++)

62. Understanding current

Consider:

[3, 7, 9, 4, 8]

Suppose:

current = 4;

The sorted region is:

[3, 7, 9]

We need to make room for 4.

Shift 9 right:

[3, 7, 9, 9, 8]

Shift 7 right:

[3, 7, 7, 9, 8]

Compare 3 with 4.

Since:

3 <= 4

stop.

Insert 4:

[3, 4, 7, 9, 8]

The sorted region has grown.

Notice why we store:

int current = data[i];

before shifting.

The original position may be overwritten as values move right, so we must preserve the value being inserted.

63. Why j >= 0 comes first

The loop is:

while (j >= 0 && data[j] > current) {

Java evaluates && from left to right and uses short-circuit evaluation.

If:

j < 0

then:

j >= 0

is false.

Java does not evaluate:

data[j]

so it avoids an invalid negative array index.

Writing the conditions in the opposite order:

while (data[j] > current && j >= 0)

could attempt to evaluate:

data[-1]

before checking the boundary.

That would cause an exception.

This is a good example of how algorithm logic and Java evaluation rules interact.

65. Complexity of insertion sort

Worst case

Consider reverse order:

[5, 4, 3, 2, 1]

When inserting the second element, approximately one value shifts.

Then approximately two.

Then three.

Then four.

In general:

1 + 2 + 3 + ... + (n - 1)

which is quadratic.

Therefore:

O(n²)

Best case

Consider an already sorted array:

[1, 2, 3, 4, 5]

For each current, the comparison:

data[j] > current

is immediately false.

No long sequence of shifts occurs.

The outer loop still executes approximately n times.

Therefore:

O(n)

best case.

This is an important difference between insertion sort and selection sort.

Nearly sorted data

Suppose:

[1, 2, 3, 5, 4, 6, 7, 8]

Only a small amount of movement is required.

Insertion sort can therefore perform well on small or nearly sorted datasets.

This illustrates why worst-case Big-O alone does not tell us everything about algorithm behavior.

67. What does in-place mean?

An in-place algorithm rearranges the original data while using only a small amount of additional storage.

Selection sort uses variables such as:

int minIndex;
int temp;

but does not create another array of size n.

Insertion sort similarly uses variables such as:

int current;
int j;

Therefore both use approximately:

O(1)

additional space and are commonly described as in-place sorting algorithms.

68. What does stable mean?

A sorting algorithm is stable if equal-key elements keep their original relative order.

Suppose students appear as:

Ana    90
Ben    75
Cara   90
Dan    80

If we sort by score using a stable sort:

Ben    75
Dan    80
Ana    90
Cara   90

Ana remains before Cara because both have score 90 and Ana appeared first originally.

Stability becomes particularly important when sorting objects by multiple fields.

For the standard implementations discussed here:

  • insertion sort using > rather than >= naturally preserves equal elements and is stable;
  • ordinary swap-based selection sort is generally not considered stable.

Stability does not affect whether numeric values end up in sorted order. It matters when equal sorting keys correspond to distinct records.

69. Why study simple O(n²) sorts?

Java already provides:

Arrays.sort(data);

So why implement selection sort and insertion sort manually?

Because the goal is not merely to produce a sorted array.

These algorithms teach:

  • array manipulation;
  • indexing;
  • nested-loop analysis;
  • swapping;
  • shifting;
  • invariants;
  • processed vs. unprocessed regions;
  • correctness reasoning;
  • best-case vs. worst-case behavior;
  • algorithmic tradeoffs.

In application development:

Prefer reliable standard-library algorithms unless you have a reason not to.

In a programming fundamentals course:

Implement simple algorithms so that you understand the ideas hidden behind library operations.

  1. several input sizes;
  2. repeated trials;
  3. comparable input data;

Suppose selection sort produces approximately:

1,0002 ms

n → 2n

   → 4n²

Theoretical analysis asks:

Part XIII — Common mistakes

78. Mistake: Big-O is exact runtime

Incorrect:

O(n) means n milliseconds.

No.

Big-O does not specify seconds, milliseconds, or nanoseconds.

It describes growth.

79. Mistake: O(n) means exactly n operations

An algorithm performing:

n

operations may be O(n).

So may one performing:

5n + 20

or:

1000n + 8

All have linear growth.

80. Mistake: Keeping constants

Do not write:

O(4n)

as the final simplified class.

Write:

O(n)

Similarly:

O(n² / 2)

simplifies to:

O(n²)

81. Mistake: Keeping lower-order terms

O(n² + n + 10)

simplifies to:

O(n²)

The fastest-growing term dominates.

82. Mistake: Every loop is O(n)

This loop:

for (int i = 0; i < 100; i++) {
    doSomething();
}

has a fixed number of iterations.

Relative to input size:

O(1)

83. Mistake: Two loops mean O(n²)

Consecutive:

for (...) {
}

for (...) {
}

often produce:

O(n + n) = O(n)

Nested:

for (...) {
    for (...) {
    }
}

may produce:

O(n²)

But even nested loops require inspection of their bounds.

84. Mistake: break makes a loop O(1)

A break may terminate early.

But worst-case analysis asks what happens on the least favorable input.

If the loop can still examine all n elements:

O(n)

85. Mistake: Binary search works on any array

False.

Binary search requires ordered data.

Without sorted order, the middle comparison cannot tell us which half is safe to discard.

86. Mistake: Binary search is always the best search

Not necessarily.

If the data is unsorted and only one search is required, sorting everything just to perform one binary search may cost more work than simply scanning once.

Algorithm choice depends on the broader problem.

87. Mistake: Same Big-O means same speed

Suppose:

Algorithm A: 2n operations
Algorithm B: 100n operations

Both are:

O(n)

but A might be substantially faster for realistic inputs.

Similarly, two O(n²) sorting algorithms can behave differently because of:

  • constants;
  • comparisons;
  • swaps;
  • shifts;
  • cache behavior;
  • input arrangement;
  • implementation details.

Big-O is a powerful scalability model, not a complete performance measurement.

88. Mistake: Lower Big-O always wins for every n

An O(n²) algorithm can sometimes outperform an O(n log n) algorithm on very small inputs.

Why?

The supposedly faster-growth algorithm might have:

  • lower setup cost;
  • simpler operations;
  • smaller constants.

Big-O becomes especially valuable as n becomes large.

Part XIV — Algorithm choice and tradeoffs

89. Choosing between linear and binary search

Ask:

Is the data sorted?

If no:

ordinary binary search cannot be used directly

How many searches will be performed?

One search:

linear search may be perfectly reasonable

Thousands or millions of searches:

sorting once + repeated binary search may be worthwhile

How large is the collection?

For 10 values, the difference may be irrelevant.

For millions of values, logarithmic searching can be dramatically more efficient.

Does the data change frequently?

Maintaining sorted order has a cost.

If values are constantly added or changed, the larger design tradeoff becomes more complicated.

90. Do not sort unless sorting helps the problem

Suppose your only goal is:

Find the smallest value once.

You can scan the array:

O(n)

Sorting the entire array first might require:

O(n log n)

with an efficient sort, or:

O(n²)

with the simple sorts studied here.

Sorting would solve a larger problem than necessary.

This is a general computer science principle:

Do not perform expensive work merely because a familiar algorithm is available.

Solve the problem that actually needs solving.

Part XV — Complete Java example

92. Searching and sorting utility class

import java.util.Arrays;

public class AlgorithmDemo {

    public static int linearSearch(int[] data, int target) {
        for (int i = 0; i < data.length; i++) {
            if (data[i] == target) {
                return i;
            }
        }

        return -1;
    }

    public static int binarySearch(int[] data, int target) {
        int low = 0;
        int high = data.length - 1;

        while (low <= high) {
            int mid = low + (high - low) / 2;

            if (data[mid] == target) {
                return mid;
            } else if (target < data[mid]) {
                high = mid - 1;
            } else {
                low = mid + 1;
            }
        }

        return -1;
    }

    public static void selectionSort(int[] data) {
        for (int i = 0; i < data.length - 1; i++) {
            int minIndex = i;

            for (int j = i + 1; j < data.length; j++) {
                if (data[j] < data[minIndex]) {
                    minIndex = j;
                }
            }

            int temp = data[i];
            data[i] = data[minIndex];
            data[minIndex] = temp;
        }
    }

    public static void insertionSort(int[] data) {
        for (int i = 1; i < data.length; i++) {
            int current = data[i];
            int j = i - 1;

            while (j >= 0 && data[j] > current) {
                data[j + 1] = data[j];
                j--;
            }

            data[j + 1] = current;
        }
    }

    public static boolean isSorted(int[] data) {
        for (int i = 0; i < data.length - 1; i++) {
            if (data[i] > data[i + 1]) {
                return false;
            }
        }

        return true;
    }

    public static void main(String[] args) {
        int[] original = {29, 10, 14, 37, 13};

        int index = linearSearch(original, 14);
        System.out.println("Linear search index: " + index);

        int[] selectionData =
                Arrays.copyOf(original, original.length);

        selectionSort(selectionData);

        System.out.println(
                "Selection sort: "
                + Arrays.toString(selectionData));

        int binaryIndex =
                binarySearch(selectionData, 14);

        System.out.println(
                "Binary search index: "
                + binaryIndex);

        int[] insertionData =
                Arrays.copyOf(original, original.length);

        insertionSort(insertionData);

        System.out.println(
                "Insertion sort: "
                + Arrays.toString(insertionData));

        System.out.println(
                "Sorted correctly? "
                + isSorted(insertionData));
    }
}

Important:

Arrays.copyOf(...)

is used because both sorting methods modify their input arrays.

If we sorted original directly before testing another algorithm, later experiments would no longer receive the same original input.

Part XIX — Frequently asked questions

110. Does O(n) mean exactly n operations?

No.

It means the work grows linearly with n.

All of these can be O(n):

n
2n
100n
5n + 10

111. Why do we ignore constants if they affect real performance?

Because Big-O answers a particular question:

How does performance scale as input size grows?

Constants still matter in engineering.

Big-O deliberately abstracts them away to reveal growth.

112. Are two O(n²) algorithms equally fast?

No.

They belong to the same asymptotic growth class, but may differ in:

  • number of comparisons;
  • number of assignments;
  • number of swaps;
  • memory access;
  • constants;
  • behavior on particular inputs.

113. Does an early return change complexity?

It can change the best case.

Linear search:

if (data[i] == target) {
    return i;
}

can finish immediately:

best case O(1)

but may still examine the entire array:

worst case O(n)

114. Why is binary search so much faster?

Because it does not merely move one position at a time.

It removes approximately half of the candidates after each comparison.

That creates logarithmic rather than linear growth.

115. Why doesn't binary search work on unsorted data?

Because comparing the target with the middle value provides no information about which side contains larger or smaller values.

Sorted order is what makes half of the data safely removable.

116. What is an off-by-one error?

A boundary error involving one extra or missing index.

Example:

for (int i = 0; i <= data.length; i++) {
    System.out.println(data[i]);
}

This is wrong because the last valid index is:

data.length - 1

Correct:

for (int i = 0; i < data.length; i++) {
    System.out.println(data[i]);
}

Off-by-one errors are particularly common in binary search.

117. Why doesn't selection sort become O(n) on sorted data?

Because it still has to scan the remaining unsorted region to confirm that the current value is the smallest.

The comparisons remain quadratic.

118. Why can insertion sort be O(n) on sorted data?

Because no values need to shift.

Each new element is already at least as large as the previous sorted elements.

The inner loop stops almost immediately on every pass.

119. Why use Arrays.sort() in real programs?

Because standard library methods are:

  • tested;
  • optimized;
  • maintained;
  • easier to read;
  • less error-prone.

We implement sorting algorithms manually in CSC 500 to learn algorithmic reasoning.

120. What should I memorize?

Do not focus only on memorizing complexity labels.

You should be able to explain why they occur.

For example:

Linear search → O(n)

because it may inspect every item.

Binary search → O(log n)

because each comparison removes approximately half of the remaining candidates.

Selection sort → O(n²)

because it repeatedly scans the unsorted region.

Insertion sort → O(n²) worst case

because each insertion may shift through most of the already processed elements.

Understanding the reasoning is more valuable than memorizing the table alone.

122. Linear search

public static int linearSearch(int[] data, int target) {
    for (int i = 0; i < data.length; i++) {
        if (data[i] == target) {
            return i;
        }
    }

    return -1;
}
Requirement:         none
Best-case time:      O(1)
Worst-case time:     O(n)
Extra space:         O(1)

123. Binary search

public static int binarySearch(int[] data, int target) {
    int low = 0;
    int high = data.length - 1;

    while (low <= high) {
        int mid = low + (high - low) / 2;

        if (data[mid] == target) {
            return mid;
        } else if (target < data[mid]) {
            high = mid - 1;
        } else {
            low = mid + 1;
        }
    }

    return -1;
}
Requirement:         sorted data
Best-case time:      O(1)
Worst-case time:     O(log n)
Extra space:         O(1) iterative

124. Selection sort

public static void selectionSort(int[] data) {
    for (int i = 0; i < data.length - 1; i++) {
        int minIndex = i;

        for (int j = i + 1; j < data.length; j++) {
            if (data[j] < data[minIndex]) {
                minIndex = j;
            }
        }

        int temp = data[i];
        data[i] = data[minIndex];
        data[minIndex] = temp;
    }
}
Best-case comparisons:  O(n²)
Worst-case time:         O(n²)
Extra space:             O(1)
In-place:                yes

125. Insertion sort

public static void insertionSort(int[] data) {
    for (int i = 1; i < data.length; i++) {
        int current = data[i];
        int j = i - 1;

        while (j >= 0 && data[j] > current) {
            data[j + 1] = data[j];
            j--;
        }

        data[j + 1] = current;
    }
}
Best-case time:      O(n)
Worst-case time:     O(n²)
Extra space:         O(1)
In-place:            yes
Stable as written:   yes

Part XXI — Key takeaways

The most important ideas from Week 11 are:

  1. Correctness comes first.

An efficient algorithm that produces the wrong result is not useful.

  1. Efficiency becomes increasingly important as data grows.

Differences that are invisible at n = 10 may dominate at n = 10,000,000.

  1. Big-O describes growth rather than exact runtime.

It does not tell us an exact number of milliseconds or machine operations.

  1. Identify what n means before analyzing code.
  1. Ignore constant factors and lower-order terms when simplifying Big-O.
   5n + 20 → O(n)
   3n² + 7n + 10 → O(n²)
  1. Do not classify code merely by counting loops.

Analyze how many times those loops actually execute.

  1. Consecutive loops generally add work.
   O(n) + O(n) = O(n)
  1. Nested loops may multiply work.
   n × n = n²
  1. Repeated halving is a major clue for logarithmic behavior.
  1. Linear search is simple and works on unsorted data.
    O(n) worst case
  1. Binary search is dramatically more scalable but requires sorted data.
    O(log n)
  1. Binary search demonstrates the power of reducing a problem substantially at each step.
  1. Selection sort repeatedly selects the smallest remaining value.
    O(n²)
  1. Insertion sort repeatedly inserts an item into an already sorted region.
    O(n²) worst case
    O(n) best case
  1. Two algorithms with the same Big-O can still behave differently.
  1. Theoretical analysis and experimental measurement complement one another.
  1. Algorithm choice depends on context.

Ask about:

  • input size;
  • whether data is sorted;
  • how often operations occur;
  • whether data changes;
  • memory requirements;
  • implementation complexity.
  1. The real skill is not memorizing algorithms.

The real skill is learning to ask:

How much work does this solution perform, how does that work grow, and is this the right algorithm for the problem?
