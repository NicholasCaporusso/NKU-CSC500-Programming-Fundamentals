Part I — Abstract data types

3. What is an abstract data type?

An Abstract Data Type, usually abbreviated ADT, describes:

  • what kind of information a collection represents,
  • what operations can be performed,
  • and what those operations mean.

An ADT focuses on behavior.

It does not necessarily describe exactly how the data is represented in memory.

Consider a stack.

A stack supports operations such as:

push
pop
peek
isEmpty

Those operations tell us what we can do with a stack.

They do not tell us whether the stack is internally implemented using:

  • an array,
  • an ArrayList,
  • a linked list,
  • or some other representation.

That distinction is important.

3.1 ADT versus implementation

We can visualize the relationship as:

                 Stack ADT
                    |
          -----------------------
          |          |          |
        Array     ArrayList    Linked
                               Structure

Each implementation may store data differently.

However, if each implementation obeys the required stack behavior, a programmer using the stack may not care about the internal representation.

This is closely related to the object-oriented principle of abstraction.

You use an object according to its public behavior without needing to understand every internal detail.

3.2 Interface versus implementation in Java

Java makes this idea concrete through interfaces.

For example:

Deque<Integer> stack = new ArrayDeque<>();

There are two types visible here:

Deque<Integer>

and:

ArrayDeque<Integer>

Deque describes a set of operations.

ArrayDeque is a concrete implementation that provides those operations.

Similarly:

Queue<String> customers = new ArrayDeque<>();

Here:

  • Queue<String> describes the behavior we want,
  • ArrayDeque<String> provides a concrete implementation.

For sets:

Set<String> names = new HashSet<>();

For maps:

Map<String, Integer> scores = new HashMap<>();

This programming style is sometimes called:

Programming to an interface rather than an implementation.

It allows the intended behavior of a variable to be clear.

3.3 ADT versus data structure

The terms ADT and data structure are related but not identical.

An ADT describes what operations should exist.

A data structure describes how data is physically or logically organized to implement those operations.

For example:

Stack

is an ADT.

Possible implementations include:

array-backed stack
ArrayList-backed stack
linked-list-backed stack

Similarly:

Queue

is an ADT.

Possible implementations include:

circular array
linked list
deque

A map is also an ADT.

Possible implementations include:

hash table
search tree

The same ADT can therefore have multiple implementations with different performance characteristics.

Part II — Stacks

4. The stack ADT

A stack is a collection in which the most recently inserted element is the first element removed.

This behavior is called:

Last In, First Out (LIFO)

The word last refers to insertion order.

The last item added becomes the first item available for removal.

4.1 Physical analogy: a stack of plates

Imagine placing three plates onto a table.

First:

A

Then place B on top:

B
A

Then place C on top:

C    <- top
B
A

You normally remove the top plate first.

Therefore the removal order is:

C
B
A

The last plate added, C, is the first plate removed.

That is LIFO behavior.

5. Core stack operations

A stack usually supports four fundamental operations.

OperationMeaning
push(x)Add x to the top
pop()Remove and return the top element
peek()Return the top element without removing it
isEmpty()Determine whether the stack is empty

Many implementations also support size().

5.1 push

push inserts an element on top of the stack.

Suppose the stack contains:

Top
 B
 A

Perform:

push(C)

Now:

Top
 C
 B
 A

C becomes the new top.

5.2 pop

pop removes and returns the top element.

Suppose:

Top

 B
 A

Calling:

pop()

returns:

C

and leaves:

Top
 B
 A

Notice that pop() does two things:

  1. retrieves the top element,
  2. removes it from the stack.

5.3 peek

peek retrieves the top element without removing it.

Suppose:

Top
 C
 B
 A

Calling:

peek()

returns:

C

but the stack remains:

Top

 B
 A

The difference between peek() and pop() is therefore extremely important.

peek -> inspect
pop  -> inspect and remove

5.4 isEmpty

isEmpty() checks whether the stack contains any elements.

For example:

if (stack.isEmpty()) {
    System.out.println("Nothing to remove");
}

Checking for an empty stack is important because some stack operations cannot be performed when no elements exist.

7. Why are stacks useful?

Stacks are useful whenever the most recently created, visited, or stored item should be processed first.

Common applications include:

  • method calls,
  • recursion,
  • undo operations,
  • browser navigation,
  • expression evaluation,
  • matching parentheses and brackets,
  • parsing,
  • depth-first search,
  • maze solving,
  • backtracking,
  • reversing data.

A useful problem-recognition rule is:

If the words most recent, previous, undo, nested, reverse, or backtrack appear in the problem, consider whether a stack is appropriate.

8. The call stack

You have already been using a stack throughout this course.

Java uses a call stack to manage active method calls.

Consider:

public static void main(String[] args) {
    methodA();
}

public static void methodA() {
    methodB();
}

public static void methodB() {
    System.out.println("Hello");
}

Execution begins in main.

Conceptually:

Top
main

When main calls methodA:

Top
methodA
main

When methodA calls methodB:

Top
methodB
methodA
main

methodB finishes first because it is the most recent active call.

Then:

Top
methodA
main

Next methodA finishes:

Top
main

Finally main finishes.

8.1 Connection to recursion

This explains why recursion naturally uses a stack.

Every recursive method call creates another stack frame containing information such as:

  • parameters,
  • local variables,
  • where execution should return after the method finishes.

For example:

factorial(4)

may create calls conceptually like:

factorial(1)
factorial(2)
factorial(3)
factorial(4)
main

The deepest call finishes first.

This is LIFO behavior.

Deep or infinite recursion can eventually consume too much call-stack space and produce:

StackOverflowError

9. Using a stack in Java

Java has an older class called:

Stack

For example:

Stack<Integer> stack = new Stack<>();

However, modern Java code commonly uses the Deque interface with an implementation such as ArrayDeque.

import java.util.ArrayDeque;
import java.util.Deque;

public class StackDemo {

    public static void main(String[] args) {

        Deque<Integer> stack = new ArrayDeque<>();

        stack.push(10);
        stack.push(20);
        stack.push(30);

        System.out.println(stack.pop());
        System.out.println(stack.peek());
    }
}

Output:

30
20

The declaration:

Deque<Integer> stack = new ArrayDeque<>();

can be read as:

Create an ArrayDeque object, but use it through the Deque abstraction.

9.1 Important Deque stack methods

MethodPurpose

pop()Remove top
peek()Inspect top

Example:

Deque<String> history = new ArrayDeque<>();

history.push("Page A");
history.push("Page B");
history.push("Page C");

System.out.println(history.peek()); // Page C
System.out.println(history.size()); // 3

9.2 What happens if the stack is empty?

Consider:

Deque<Integer> stack = new ArrayDeque<>();

stack.pop();

Calling pop() on an empty deque throws a:

NoSuchElementException

Therefore, a common safe pattern is:

if (!stack.isEmpty()) {
    int value = stack.pop();
    System.out.println(value);
}

For this course, an important rule is:

Before removing an element, think about what should happen if the collection is empty.

10. Example — Reversing a string with a stack

A stack naturally reverses insertion order.

Suppose we want to reverse:

computer

Push the characters one at a time.

Conceptually:

push(c)
push(o)
push(m)
push(p)
push(u)
push(t)
push(e)
push(r)

After all pushes, the most recently inserted character is r.

Popping produces:

r
e
t
u
p
m
o
c

Therefore the reversed string is:

retupmoc

Java implementation:

import java.util.ArrayDeque;
import java.util.Deque;

public class ReverseString {

    public static String reverse(String text) {

        Deque<Character> stack = new ArrayDeque<>();

        for (char ch : text.toCharArray()) {
            stack.push(ch);
        }

        StringBuilder result = new StringBuilder();

        while (!stack.isEmpty()) {
            result.append(stack.pop());
        }

        return result.toString();
    }

    public static void main(String[] args) {
        System.out.println(reverse("computer"));
    }
}

Output:

retupmoc

10.1 Complexity

Suppose the input contains n characters.

We push each character once:

n pushes

and pop each character once:

n pops

Therefore the algorithm requires:

O(n)

time.

The stack stores up to n characters, so the additional memory is also:

O(n)

11. Example — Balanced parentheses

Stacks are particularly useful when processing nested structures.

Consider:

(a + b) * (c - d)

The parentheses are balanced.

But:

(a + b))(

is not balanced.

For several bracket types, consider:

{[(a + b) * c]}

This is balanced.

But:

([)]

is not.

Why?

The symbols close in the wrong order.

11.1 Stack algorithm

When scanning from left to right:

  1. If the character is an opening symbol:
  • (
  • [
  • {

push it onto the stack.

  1. If the character is a closing symbol:
  • )
  • ]
  • }

inspect the most recent opening symbol.

  1. If the stack is empty when a closing symbol appears, the expression is invalid.
  1. If the opening and closing symbols do not match, the expression is invalid.
  1. At the end, the stack must be empty.

11.2 Trace

Input:

{ [ ( ) ] }

Trace:

Read {     stack: {

Read [     stack: [
                   {

Read (     stack: (
                   [
                   {

Read )     pop (

Read ]     pop [

Read }     pop {

End        stack is empty

Therefore the expression is balanced.

11.3 Complete Java solution

import java.util.ArrayDeque;
import java.util.Deque;

public class BalancedBrackets {

    public static boolean isBalanced(String text) {

        Deque<Character> stack = new ArrayDeque<>();

        for (char ch : text.toCharArray()) {

            if (ch == '(' || ch == '[' || ch == '{') {
                stack.push(ch);
            }

            else if (ch == ')' || ch == ']' || ch == '}') {

                if (stack.isEmpty()) {
                    return false;
                }

                char opening = stack.pop();

                if (!matches(opening, ch)) {
                    return false;
                }
            }
        }

        return stack.isEmpty();
    }

    private static boolean matches(char opening, char closing) {

        return (opening == '(' && closing == ')')
            || (opening == '[' && closing == ']')
            || (opening == '{' && closing == '}');
    }

    public static void main(String[] args) {

        System.out.println(isBalanced("([]{})"));
        System.out.println(isBalanced("([)]"));
        System.out.println(isBalanced("((()))"));
        System.out.println(isBalanced("(()"));
    }
}

Output:

true
false
true
false

11.4 Why a stack is exactly the right structure

Suppose we encounter:

{
[
(

The next closing delimiter must match the most recently encountered opening delimiter.

That means:

last opening symbol
        ↓
first symbol that must close

This is exactly LIFO behavior.

11.5 Complexity

If the expression has n characters, each character is processed once.

Each stack operation is constant time under the usual implementation assumptions.

Therefore:

Time: O(n)

In the worst case, all n characters could be opening brackets, so:

Space: O(n)

Part III — Queues

12. The queue ADT

A queue stores elements so that the oldest waiting element is processed first.

This behavior is called:

First In, First Out (FIFO)

Think about customers waiting in line.

Suppose they arrive in this order:

Alice
Bob
Carol

The queue becomes:

Front                         Back
Alice        Bob        Carol

Alice arrived first.

Therefore Alice is served first.

After serving Alice:

Front                 Back
Bob          Carol

13. Core queue operations

Conceptually, a queue supports:

dequeueRemove the element at the front
peekInspect the element at the front
isEmpty()Check whether the queue is empty

Java commonly expresses these operations using:

Queue conceptJava method
enqueueoffer()
dequeuepoll()
peekpeek()

Notice that the oldest item is always removed first.

15. Why are queues useful?

Queues are useful whenever work should generally occur in arrival order.

Examples include:

  • printer jobs,
  • customer-service requests,
  • call-center customers,
  • web requests,
  • messages,
  • events,
  • simulations,
  • task scheduling,
  • breadth-first search,
  • buffering.

Useful clues include:

  • first come, first served
  • arrival order
  • waiting
  • pending jobs
  • next customer
  • oldest request
  • level-by-level

These often suggest FIFO behavior.

16. Using a queue in Java

A common Java implementation is:

import java.util.ArrayDeque;
import java.util.Queue;

public class QueueDemo {

    public static void main(String[] args) {

        Queue<String> customers = new ArrayDeque<>();

        customers.offer("Alice");
        customers.offer("Bob");
        customers.offer("Carol");

        System.out.println(customers.peek());
        System.out.println(customers.poll());
        System.out.println(customers.peek());
    }
}

Output:

Alice
Alice
Bob

Why?

Before removal:

Front                         Back
Alice        Bob        Carol

peek() returns Alice without removing her.

Then:

customers.poll();

removes Alice.

Bob becomes the new front.

17. Queue method families

Java's Queue interface provides pairs of methods that perform similar operations but behave differently when an operation cannot be completed.

OperationException-styleSpecial-value style
Insertadd()offer()
Removeremove()poll()
Examineelement()peek()

17.1 add() versus offer()

Both attempt to insert an item.

queue.add("Alice");

and:

queue.offer("Alice");

often appear to do the same thing.

The distinction matters for some bounded queues:

  • add() may throw an exception when insertion fails.
  • offer() typically returns false.

For ordinary queue code in CSC500, offer() clearly expresses queue insertion.

17.2 remove() versus poll()

Both remove the front element.

If the queue is empty:

queue.remove();

throws an exception.

But:

queue.poll();

returns:

null

17.3 element() versus peek()

Both examine the front element.

If the queue is empty:

queue.element();

throws an exception.

But:

queue.peek();

returns:

null

A useful summary is:

add       remove       element
 |           |            |
exception-style operations

offer     poll         peek
 |          |            |
special-value-style operations

18. What is a deque?

A deque is a:

double-ended queue

It is pronounced approximately:

deck

A deque supports insertion and removal from both ends.

For example:

Deque<Integer> numbers = new ArrayDeque<>();

numbers.addFirst(10);
numbers.addLast(20);
numbers.addFirst(5);

System.out.println(numbers);

Conceptually:

Front          Back
5     10       20

A deque can therefore implement:

  • stack behavior,
  • queue behavior.

This is why Java's ArrayDeque appears in both of our examples.

18.1 ArrayDeque used as a stack

Deque<Integer> stack = new ArrayDeque<>();

stack.push(10);
stack.push(20);
stack.pop();

We are choosing LIFO operations.

18.2 ArrayDeque used as a queue

Queue<Integer> queue = new ArrayDeque<>();

queue.offer(10);
queue.offer(20);
queue.poll();

We are choosing FIFO operations.

The object type may be similar, but the behavior we expose through the interface is different.

20. Example — Customer queue simulation

Suppose customers arrive at a coffee shop.

We want customers to be served in arrival order.

import java.util.ArrayDeque;
import java.util.Queue;

public class CoffeeShop {

    public static void main(String[] args) {

        Queue<String> customers = new ArrayDeque<>();

        customers.offer("Alice");
        customers.offer("Bob");
        customers.offer("Carlos");

        while (!customers.isEmpty()) {
            String customer = customers.poll();
            System.out.println("Serving " + customer);
        }
    }
}

Output:

Serving Alice
Serving Bob
Serving Carlos

The queue itself enforces the desired policy.

We do not need to manually search for the customer who arrived first.

20.1 More realistic simulations

A more sophisticated simulation might track:

  • arrival time,
  • service time,
  • multiple servers,
  • current queue length,
  • maximum queue length,
  • average waiting time.

For example:

class Customer {

    private String name;
    private int arrivalTime;

    public Customer(String name, int arrivalTime) {
        this.name = name;
        this.arrivalTime = arrivalTime;
    }

    public String getName() {
        return name;
    }

    public int getArrivalTime() {
        return arrivalTime;
    }
}

Then:

Queue<Customer> line = new ArrayDeque<>();

line.offer(new Customer("Alice", 0));
line.offer(new Customer("Bob", 2));
line.offer(new Customer("Carlos", 5));

Notice how this connects data structures with object-oriented design.

The queue determines processing order.

The Customer objects contain the data being processed.

Part IV — Sets

21. The set ADT

A set is a collection in which each element occurs at most once.

In ordinary language:

A set stores unique elements.

For example:

{10, 20, 30}

is a set.

Adding 20 again does not create:

{10, 20, 20, 30}

The set still contains only:

{10, 20, 30}

22. Why use a set?

Suppose the following users visit a website:

alice
bob
alice
carol
bob
david

If we care about all visits, including repeated visits, we might use a list.

But suppose we ask:

How many unique users visited?

The relevant values are:

alice
bob
carol
david

A set directly represents the idea of uniqueness.

22.1 Typical set questions

Sets are particularly useful for questions such as:

Have I already seen this item?
Does this item exist?
How many distinct values exist?
Are there any duplicates?
Which users have registered?
Which locations have been visited?

Words that often suggest a set include:

  • unique,
  • distinct,
  • duplicate,
  • membership,
  • seen,
  • visited,
  • registered,
  • exists.

23. Java Set and HashSet

Java provides the Set interface.

A common implementation is:

HashSet

Example:

import java.util.HashSet;
import java.util.Set;

public class SetDemo {

    public static void main(String[] args) {

        Set<String> names = new HashSet<>();

        names.add("Alice");
        names.add("Bob");
        names.add("Carol");
        names.add("Alice");

        System.out.println(names.size());
    }
}

Output:

3

Even though "Alice" was added twice, the set contains only one logically equal "Alice".

24. Important set operations

24.1 Add an element

names.add("Alice");

The return type of add is boolean.

boolean added = names.add("Alice");

It returns:

true

if the set changed.

It returns:

false

if an equal element was already present.

That behavior can be very useful.

24.2 Check membership

names.contains("Alice");

returns a boolean.

Example:

if (names.contains("Alice")) {
    System.out.println("Alice is registered");
}

24.3 Remove an element

names.remove("Alice");

24.4 Get the number of elements

names.size();

24.5 Check whether the set is empty

names.isEmpty();

25. Important warning — HashSet has no required insertion order

Suppose:

Set<String> names = new HashSet<>();

names.add("Alice");
names.add("Bob");
names.add("Carlos");

Do not assume that iteration will produce:

Alice
Bob
Carlos

A HashSet does not promise insertion-order iteration.

For example:

for (String name : names) {
    System.out.println(name);
}

might print the values in an order different from insertion order.

The important rule is:

Never depend on an ordering guarantee that the collection does not provide.

If preserving order is essential, the data structure choice must reflect that requirement.

26. Example — Detecting duplicates

Suppose:

int[] numbers = {10, 20, 30, 20, 40};

We want to determine whether any value appears more than once.

A straightforward nested-loop approach could compare every element against many others.

That can require:

O(n²)

time.

A set lets us ask:

Have I already seen this value?

26.1 Version using contains

import java.util.HashSet;
import java.util.Set;

public class DuplicateDetector {

    public static boolean containsDuplicate(int[] values) {

        Set<Integer> seen = new HashSet<>();

        for (int value : values) {

            if (seen.contains(value)) {
                return true;
            }

            seen.add(value);
        }

        return false;
    }

    public static void main(String[] args) {

        int[] a = {1, 2, 3, 4};
        int[] b = {1, 2, 3, 2};

        System.out.println(containsDuplicate(a));
        System.out.println(containsDuplicate(b));
    }
}

Output:

false
true

26.2 More compact version

Because add() returns false when an equal value already exists:

public static boolean containsDuplicate(int[] values) {

    Set<Integer> seen = new HashSet<>();

    for (int value : values) {

        if (!seen.add(value)) {
            return true;
        }
    }

    return false;
}

This code combines:

check whether already present
+
insert if absent

into one operation.

26.3 Complexity

For each of n values, we perform a hash-set operation that is expected to take approximately constant time.

Therefore:

Expected time: O(n)

The set may store up to n values:

Space: O(n)

Compare that with the nested-loop approach:

Time: O(n²)
Space: O(1)

This illustrates an important idea:

Faster algorithms sometimes use additional memory.

27. Example — Counting distinct values

Suppose:

10 20 10 30 20 40

How many distinct values occur?

We can insert them into a set.

import java.util.HashSet;
import java.util.Set;

public class DistinctValues {

    public static void main(String[] args) {

        int[] values = {10, 20, 10, 30, 20, 40};

        Set<Integer> unique = new HashSet<>();

        for (int value : values) {
            unique.add(value);

import java.util.HashMap;

                counts.put(word, oldCount + 1);

                counts.put(word, 1);
            }
        }

        System.out.println(counts);
    }
}

37. getOrDefault()

Frequency counting is so common that Java provides a convenient map operation:

Instead of:

    counts.put(word, 1);
}

we can write:

counts.put(
    word,
    counts.getOrDefault(word, 0) + 1
);

Or more compactly:

for (String word : words) {
    counts.put(word, counts.getOrDefault(word, 0) + 1);
}

37.1 How to read this statement

Break it into pieces.

First:

counts.getOrDefault(word, 0)

means:

Give me the current count for word. If the key does not exist yet, use 0.

Then:

+ 1

increments the count.

Finally:

counts.put(word, ...)

stores the new count.

This pattern appears frequently in programming.

41. The lookup problem

Suppose we have:

1,000,000 usernames

and want to answer:

If the usernames are stored in an unsorted list, we may need to perform a linear search.

Worst-case linear search requires examining:

O(n)

Hash-based data structures try to make operations such as lookup much faster on average.

Typical expected performance is approximately:

  • key lookup in a HashMap.

Different keys can sometimes map to the same bucket.

48. What does O(1) average mean?

O(1) does not mean:

The method always executes exactly one instruction.

It means that, under the assumptions behind the data structure, the expected amount of work does not grow proportionally with the number of stored elements.

For example, looking up a key in a good hash table containing:

100 items

and looking up a key in one containing:

1,000,000 items

may both require only a relatively small amount of work.

This is very different from linear search, where the amount of work can grow directly with n.

Because several things can happen:

  • collisions,
  • table resizing,
  • poor hash distributions,
  • many keys ending up in the same internal region.

In an unfavorable case, more searching may be necessary.

For CSC500, use this mental model:

HashSet membership: expected O(1)

HashMap key lookup: expected O(1)

Unsorted list membership: O(n)

Do not turn:

50. equals() and hashCode()

Hash-based collections rely heavily on two Java methods:

equals()

and:

hashCode()

Conceptually:

  • hashCode() helps determine where to look.
  • equals() helps determine whether this is actually the same logical key or element.

50.1 The fundamental contract

An extremely important Java rule is:

If two objects are equal according to equals(), they must have the same hash code.

In symbolic form:

a.equals(b) == true
          ↓
a.hashCode() == b.hashCode()

However, the reverse is not required.

This is possible:

a.hashCode() == b.hashCode()

while:

a.equals(b) == false

That is simply a collision.

51. Identity versus logical equality

For Java objects:

a == b

usually asks:

Do these two references point to the exact same object?

This is identity.

By contrast:

a.equals(b)

usually asks:

Should these objects be considered logically equal?

Consider:

String a = new String("CSC500");
String b = new String("CSC500");

Conceptually:

a ----> String object "CSC500"

b ----> another String object "CSC500"

The objects can have different identities while representing equal text.

Hash-based collections care about logical equality, not simply object identity.

52. Custom objects in a HashSet

Suppose:

class Student {

    private String id;

    public Student(String id) {
        this.id = id;
    }
}

Now:

Set<Student> students = new HashSet<>();

students.add(new Student("123"));
students.add(new Student("123"));

A human may think:

Both represent student 123.

But unless Student defines appropriate logical equality, Java may treat the two objects as distinct.

If students should be considered equal based on id, then the class should define consistent:

equals()

and:

hashCode()

methods.

52.1 Example implementation

import java.util.Objects;

public class Student {

    private String id;
    private String name;

    public Student(String id, String name) {
        this.id = id;
        this.name = name;
    }

    @Override
    public boolean equals(Object other) {

        if (this == other) {
            return true;
        }

        if (!(other instanceof Student)) {
            return false;
        }

        Student that = (Student) other;

        return Objects.equals(this.id, that.id);
    }

    @Override
    public int hashCode() {
        return Objects.hash(id);
    }
}

Here, student identity for the collection is based on:

id

Therefore two Student objects with equal IDs are logically equal.

53. Why equal objects need equal hash codes

Imagine:

a.equals(b) == true

but:

a.hashCode() != b.hashCode()

A hash table might use the hash codes to send the objects to different buckets:

a -> bucket 2

b -> bucket 8

The collection would then have difficulty behaving consistently because the two objects are supposed to represent the same logical key.

Therefore Java requires:

equal objects
      ↓
equal hash codes

54. Mutable keys can be dangerous

Suppose a Student object's ID determines:

  • equality,
  • hash code.

Imagine inserting:

Student s = new Student("123", "Alice");

map.put(s, 95);

If the student's ID is later changed to:

999

then its hash code may change.

Conceptually, the map originally stored the object according to one hash location:

ID 123 -> bucket 4

but afterward the object may claim it belongs somewhere else:

ID 999 -> bucket 7

The object has not physically moved in the map.

This can lead to extremely confusing lookup behavior.

A useful design principle is:

Prefer immutable map keys, or at least do not change fields involved in equals() and hashCode() while an object is being used as a hash key.

67. Worked Problem 1 — Valid brackets

Write:

public static boolean valid(String text)

that returns whether brackets are balanced.

Examples:

([]{})

returns:

true

but:

([)]

returns:

false

Step 1 — Identify the behavior

When a closing bracket appears, it must correspond to the most recent unmatched opening bracket.

That suggests:

LIFO

Therefore use a:

Stack

Step 2 — Algorithm

create empty stack

for each character:

    if opening bracket:
        push

    if closing bracket:
        if stack empty:
            false

        pop most recent opening bracket

        if types do not match:
            false

return whether stack is empty

Step 3 — Java

public static boolean valid(String text) {

    Deque<Character> stack = new ArrayDeque<>();

    for (char ch : text.toCharArray()) {

        if (ch == '(' || ch == '[' || ch == '{') {

            stack.push(ch);

        } else if (ch == ')' || ch == ']' || ch == '}') {

            if (stack.isEmpty()) {
                return false;
            }

            char open = stack.pop();

            if (open == '(' && ch != ')') {
                return false;
            }

            if (open == '[' && ch != ']') {
                return false;
            }

            if (open == '{' && ch != '}') {
                return false;
            }
        }
    }

    return stack.isEmpty();
}

70. Worked Problem 4 — First non-repeated word

Input:

cat dog bird cat dog mouse

We want the first word whose frequency is exactly one.

The answer is:

bird

A useful strategy is:

  1. Use a map to count frequencies.
  2. Scan the original sequence a second time.
  3. Return the first word whose count is 1.
public static String firstUnique(String[] words) {

    Map<String, Integer> counts = new HashMap<>();

    for (String word : words) {
        counts.put(
            word,
            counts.getOrDefault(word, 0) + 1
        );
    }

    for (String word : words) {

        if (counts.get(word) == 1) {
            return word;
        }
    }

    return null;
}

Why scan the original array again?

Because the HashMap does not guarantee the original word order.

71. Worked Problem 5 — Inventory

Suppose we want:

product -> quantity

For example:

Laptop   -> 12
Keyboard -> 35
Mouse    -> 20

A map naturally represents this relationship.

import java.util.HashMap;
import java.util.Map;

public class Inventory {

    private Map<String, Integer> quantities;

    public Inventory() {
        quantities = new HashMap<>();
    }

    public void add(String product, int amount) {

        int oldQuantity =
            quantities.getOrDefault(product, 0);

        quantities.put(
            product,
            oldQuantity + amount
        );
    }

    public boolean sell(String product, int amount) {

        int current =
            quantities.getOrDefault(product, 0);

        if (current < amount) {
            return false;
        }

        quantities.put(
            product,
            current - amount
        );

        return true;
    }

    public int getQuantity(String product) {

        return quantities.getOrDefault(product, 0);
    }
}

This combines:

  • object-oriented design,
  • encapsulation,
  • a HashMap,
  • state updates,
  • key-based lookup.

import java.util.ArrayDeque;

    private Queue<Task> tasks;

    public TaskScheduler() {
        tasks = new ArrayDeque<>();
    }

    public void addTask(Task task) {
        tasks.offer(task);
    }

    public Task nextTask() {
        return tasks.peek();
    }

    public Task processTask() {
        return tasks.poll();
    }

    public boolean hasTasks() {
        return !tasks.isEmpty();
    }
}

The TaskScheduler does not manually track which task arrived first.

The queue representation guarantees the required behavior.

Part XI — Common mistakes

73. Mistake — Using a stack when you need a queue

Suppose requests arrive:

A
B
C

If they should be handled fairly in arrival order:

A
B
C

you need FIFO behavior.

A stack would instead produce:

C
B
A

Always identify:

LIFO?

or:

FIFO?

before selecting the structure.

74. Mistake — Confusing pop() and peek()

For a stack:

stack.peek();

does not remove the value.

But:

stack.pop();

does.

If you accidentally use pop() when you only intended to inspect the top, your program changes the collection.

75. Mistake — Forgetting empty-collection behavior

This can fail:

stack.pop();

if the stack is empty.

Likewise:

queue.remove();

can fail if the queue is empty.

Use appropriate checks or choose methods whose failure behavior matches the program.

76. Mistake — Assuming HashSet preserves order

This code:

Set<String> values = new HashSet<>();

values.add("A");
values.add("B");
values.add("C");

does not promise:

A B C

during iteration.

Do not confuse:

contains unique elements

with:

preserves insertion order

They are separate properties.

77. Mistake — Assuming HashMap sorts keys

A HashMap is not a sorted table.

Its primary purpose is efficient key-based access.

If ordering is part of the problem, ordering must be considered separately.

78. Mistake — Confusing containsKey() with containsValue()

grades.containsKey("Alice");

asks whether "Alice" is a key.

grades.containsValue(95);

asks whether some entry has the value 95.

These are completely different questions.

79. Mistake — Forgetting that get() may return null

This:

grades.get("David");

may return:

null

if the key is absent.

Depending on the problem, use:

containsKey()

or:

getOrDefault()

instead of assuming a value always exists.

80. Mistake — Assuming hashing means no collisions

A hash function does not need to give every possible key a unique hash code.

Different keys can collide.

Correct hash-table implementations are designed to handle collisions.

81. Mistake — Overriding equals() but not hashCode()

If custom objects are stored in a HashSet or used as map keys, logical equality and hashing must agree.

The rule is:

equal objects -> equal hash codes

Failure to maintain that relationship can cause incorrect collection behavior.

82. Mistake — Mutating hash keys

Do not casually change fields that determine an object's equality/hash code after placing that object in a HashMap or HashSet.

Prefer stable keys.

83. Mistake — Choosing a structure because you know its syntax

Do not reason:

I remember ArrayList, therefore I will use ArrayList.

Instead reason:

What operations does this problem require?

Then choose the structure.

Part XIV — Frequently asked questions

94. Is a stack a Java class or an idea?

Both concepts exist, but distinguish them carefully.

A stack ADT is the abstract idea of LIFO behavior.

Java also has concrete classes and interfaces that can implement that behavior.

For CSC500, when we say:

Use a stack,

we primarily mean:

Choose LIFO behavior.

95. Why do we use Deque if we want a stack?

Because Deque supports efficient operations at both ends and includes convenient stack methods:

push()
pop()
peek()

A concrete implementation such as:

ArrayDeque

can therefore provide stack behavior efficiently.

96. Can ArrayDeque also be a queue?

Yes.

For example:

Queue<String> q = new ArrayDeque<>();

uses the same implementation family through a queue abstraction.

Typical queue methods are:

offer()
poll()
peek()

97. Why doesn't a queue use push()?

The concept matters more than the method name.

When using Java's Queue interface, the conventional insertion method is:

offer()

This communicates that the object is being used with FIFO queue behavior.

98. Can a set contain duplicates?

No, not according to the set's equality rules.

Attempting to add an equal element again does not produce another independent entry.

99. Can a map contain duplicate keys?

No.

Each key has at most one associated value.

A later:

put()

with the same key replaces the earlier value.

100. Can map values repeat?

Yes.

For example:

Alice -> 90
Bob   -> 90

is valid.

101. Does a HashSet preserve insertion order?

You should not assume that it does.

Its important properties for this week are:

  • uniqueness,
  • efficient expected membership testing.

102. Does a HashMap preserve insertion order?

You should not assume that it does.

Use it because you want efficient key-value association and lookup.

103. What is the main difference between a set and a map?

A set stores elements:

{A, B, C}

A map stores associations:

A -> 10
B -> 20
C -> 30

A set asks:

Is x present?

A map asks:

What value is associated with key x?

104. Why is hashing faster than scanning a list?

A list may require looking through many elements.

Hashing uses the key to determine where the value is likely to be stored.

Instead of:

search everything

we approximately do:

hash key
   ↓
locate bucket
   ↓
inspect relevant entries

That is why hash tables can provide approximately constant expected lookup time.

105. Are collisions errors?

No.

Collisions are normal.

The data structure must handle them correctly.

106. Why do I need both hashCode() and equals()?

hashCode() helps locate a relevant storage region.

equals() determines whether the found object is logically the same key or element.

Both play different roles.

107. Does equal hash code mean equal objects?

No.

Two different objects can have the same hash code.

That is a collision.

The required relationship is only:

equal objects -> equal hash codes

not:

equal hash codes -> equal objects

108. Should I always use HashSet instead of a list because lookup is faster?

No.

A list and set provide different semantics.

Use a list when:

  • duplicates matter,
  • sequence matters,
  • index-based access matters.

Use a set when:

  • uniqueness matters,
  • membership testing is central.

Performance is only one part of data-structure selection.

109. Should I always use HashMap when I have two pieces of data?

No.

Use a map when one value naturally acts as a key used to retrieve another value.

For example:

student ID -> Student

is a natural map.

But two related fields inside a single object may simply belong in a class:

class Student {
    private String name;
    private double gpa;
}

A map is not a replacement for class design.

110. Why use entrySet() when iterating through a map?

If both the key and value are needed:

for (Map.Entry<String, Integer> entry : map.entrySet()) {
    ...
}

directly gives access to both:

entry.getKey()
entry.getValue()

This clearly communicates that the program is processing mappings.

111. What is the most important thing to remember this week?

Do not memorize only:

push
pop
offer
poll
contains
put
get

Instead understand four questions for each structure:

  1. What behavior does this structure guarantee?
  2. What operations does it naturally support?
  3. What problem motivates those operations?
  4. Why would another structure be less appropriate?

If you can answer those questions, the Java method names become much easier to remember.

Part XVI — Week 13 summary

This week introduced several data structures that organize data according to how the data will be used.

Stack

A stack follows:

LIFO

Typical operations:

push
pop
peek

Common applications:

  • method calls,
  • recursion,
  • undo,
  • backtracking,
  • expression processing,
  • reversing data.

Typical Java representation:

Deque<E> stack = new ArrayDeque<>();

Queue

A queue follows:

FIFO

Typical operations:

offer
poll
peek

Common applications:

  • waiting lines,
  • scheduling,
  • request processing,
  • simulations,
  • breadth-first algorithms.

Typical Java representation:

Queue<E> queue = new ArrayDeque<>();

Deque

A deque is a:

double-ended queue

It supports insertion and removal from both ends.

ArrayDeque can therefore provide either stack or queue behavior.

Set

A set stores:

unique elements

Typical operations:

add
contains
remove

Common applications:

  • uniqueness,
  • duplicate detection,
  • membership testing,
  • visited-element tracking,
  • counting distinct values.

Typical Java representation:

Set<E> set = new HashSet<>();

Map

A map stores:

key -> value

associations.

Typical operations:

put
get
containsKey
remove

Common applications:

  • lookup tables,
  • phone directories,
  • inventories,
  • word frequencies,
  • ID-to-object relationships.

Typical Java representation:

Map<K, V> map = new HashMap<>();

Hashing

Hashing conceptually performs:

key
 |
 v
hash function
 |
 v
hash code
 |
 v
bucket

Important ideas:

  • hash functions,
  • hash codes,
  • buckets,
  • collisions,
  • expected constant-time operations,
  • equals() and hashCode() consistency.

Remember:

HashSet membership
    expected O(1)

HashMap key lookup
    expected O(1)

but not every individual operation is guaranteed to be constant time.

Final perspective

The central lesson of Week 13 is larger than any one Java collection.

Programming is not only about storing values and making code execute correctly.

A programmer must decide:

How should this information be organized?

That decision depends on how the program needs to retrieve and process the information.

When you see:

most recent first

think:

Stack

When you see:

arrival order

think:

Queue

When you see:

unique / already seen / membership

think:

Set

When you see:

key -> value

think:

Map

And always ask:

What operations matter most for this problem?

That question is the bridge from merely writing code to designing good algorithms and data structures.
