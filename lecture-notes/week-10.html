1. Why study recursion?

Until now, most repetition in our programs has been expressed using loops:

for
while
do-while

For example:

for (int i = 5; i >= 1; i--) {
    System.out.println(i);
}

Recursion provides another way to express repeated computation.

Instead of saying:

Repeat these statements.

a recursive solution often says:

Solve this problem by solving a smaller version of the same problem.

This is an important change in perspective.

Recursion is not merely an alternative syntax for loops. More importantly, it introduces a way of decomposing problems into smaller subproblems.

That way of thinking becomes increasingly important in algorithms and data structures.

2. What is recursion?

A method is recursive if it calls itself, directly or indirectly.

Consider:

public static void countdown(int n) {
    if (n == 0) {
        System.out.println("Blastoff!");
        return;
    }

    System.out.println(n);
    countdown(n - 1);
}

Calling:

countdown(3);

produces:

3
2
1
Blastoff!

The method calls occur conceptually like this:

countdown(3)
    countdown(2)
        countdown(1)
            countdown(0)

Notice what happens.

countdown(3) does not itself print all four lines. It prints one number and asks:

countdown(2)

to handle the rest.

That call prints one number and asks:

countdown(1)

to handle the rest.

Each invocation solves one piece of the problem and delegates the remaining work to another invocation of the same method.

3. Recursive mathematical definitions

Recursion appears naturally in mathematics.

Consider factorial.

For a nonnegative integer n:

n! = n × (n-1) × ⋯ × 2 × 1

For example:

5! = 5 × 4 × 3 × 2 × 1 = 120

Factorial can also be defined recursively:

0! = 1

and for n &gt; 0:

n! = n × (n-1)!

This definition contains two ideas.

First, there is a value whose answer is already known:

0! = 1

Second, a larger factorial is defined using a smaller factorial:

5! = 5 × 4!
4! = 4 × 3!
3! = 3 × 2!
...

This translates almost directly into Java:

public static int factorial(int n) {
    if (n == 0) {
        return 1;
    }

    return n * factorial(n - 1);
}

Calling:

factorial(4)

conceptually expands as:

factorial(4)
= 4 * factorial(3)

= 4 * (3 * factorial(2))

= 4 * (3 * (2 * factorial(1)))

= 4 * (3 * (2 * (1 * factorial(0))))

= 4 * 3 * 2 * 1 * 1

= 24

This is the essential idea of recursion:

Solve a problem using a smaller instance of the same problem.

4. The essential parts of recursion

A well-designed recursive method usually contains at least two major parts:

  1. a base case;
  2. a recursive case.

There is also a third requirement that is just as important:

  1. every recursive call must make progress toward the base case.

4.1 The base case

The base case handles a problem small enough to solve immediately.

For factorial:

if (n == 0) {
    return 1;
}

No recursive call is needed.

The answer is known directly.

A useful question when designing a recursive method is:

What is the smallest version of this problem whose answer I already know?

Examples:

ProblemPossible base case
factorialfactorial(0) = 1
sum 1...nsum(0) = 0
process a stringempty string
process an arrayindex has reached array length
palindromestring length is 0 or 1
binary searchsearch interval is empty

4.2 The recursive case

The recursive case expresses the current problem in terms of a smaller problem.

For factorial:

return n * factorial(n - 1);

We are saying:

If I can correctly compute factorial(n - 1), then I can compute factorial(n) by multiplying that result by n.

The current method call does not need to solve the entire remaining problem itself.

4.3 Progress toward the base case

A base case alone is not enough.

The recursive call must actually move toward it.

Correct:

factorial(n - 1)

because n decreases.

Incorrect:

factorial(n)

because the argument does not change.

Also incorrect for positive n:

factorial(n + 1)

because the argument moves away from zero.

A useful recursion checklist begins with three questions:

1. What is the base case?
2. How does the recursive call make the problem smaller?
3. Why must the recursive calls eventually reach the base case?

5. Recursion is still just method calling

Recursion can initially seem mysterious.

There is no special "recursion machine" inside Java.

A recursive call is a normal method call.

Java essentially does the same thing it does with any method:

  1. call the method;
  2. create an execution context for the call;
  3. store its parameters and local variables;
  4. execute its statements;
  5. possibly call another method;
  6. wait for that method to finish;
  7. continue;
  8. return to the caller.

The unusual part is simply that the method eventually calls another invocation of itself.

6. The call stack

To understand recursion, we need to understand the call stack.

When Java calls a method, it creates information associated with that invocation.

Conceptually, a method's stack frame contains information such as:

  • parameter values;
  • local variables;
  • intermediate calculations;
  • the place where execution should continue when the method returns.

Consider:

public static int factorial(int n) {
    if (n == 0) {
        return 1;
    }

    return n * factorial(n - 1);
}

Now call:

factorial(3);

The active calls eventually become:

factorial(3)
factorial(2)
factorial(1)
factorial(0)

At the deepest point, all four calls are active.

We can visualize the stack roughly as:

TOP
-------------------------
factorial(0), n = 0
-------------------------
factorial(1), n = 1
-------------------------
factorial(2), n = 2
-------------------------
factorial(3), n = 3
-------------------------
BOTTOM

The most recent method call is on top.

7. Descending and unwinding

Recursive execution is often easiest to understand as two phases.

Phase 1: Descending

The program repeatedly makes recursive calls:

factorial(3)
    factorial(2)
        factorial(1)
            factorial(0)

Each call waits for the next call to return.

Phase 2: Unwinding

Once the base case returns, calls complete in reverse order:

factorial(0) returns 1

factorial(1)
= 1 * 1
= 1

factorial(2)
= 2 * 1
= 2

factorial(3)
= 3 * 2
= 6

The stack follows a last-in, first-out pattern:

last call created → first call completed

8. Each call has its own parameters and local variables

Consider:

public static void show(int n) {
    int x = n * 10;

    if (n > 0) {
        show(n - 1);
    }

    System.out.println(x);
}

Calling:

show(3);

creates separate local variables:

show(3): n = 3, x = 30
show(2): n = 2, x = 20
show(1): n = 1, x = 10
show(0): n = 0, x = 0

The variables do not overwrite one another.

After reaching show(0), the calls return:

0
10
20
30

Why?

Because every invocation has its own stack frame and therefore its own x.

This idea is fundamental to understanding recursion.

9. Code before and after the recursive call

The position of a statement relative to the recursive call can dramatically change behavior.

Consider:

public static void printDown(int n) {
    if (n == 0) {
        return;
    }

    System.out.println(n);
    printDown(n - 1);
}

Calling:

printDown(3);

prints:

3
2
1

The printing happens while recursion is descending.

Now move the statement:

public static void printUp(int n) {
    if (n == 0) {
        return;
    }

    printUp(n - 1);
    System.out.println(n);
}

Calling:

printUp(3);

prints:

1
2
3

The printing happens during unwinding.

9.1 Before and after in the same method

Consider:

public static void demonstrate(int n) {
    if (n == 0) {
        return;
    }

    System.out.println("Before " + n);

    demonstrate(n - 1);

    System.out.println("After " + n);
}

Calling:

demonstrate(3);

prints:

Before 3
Before 2
Before 1
After 1
After 2
After 3

Trace:

demonstrate(3)
    print Before 3

    demonstrate(2)
        print Before 2

        demonstrate(1)
            print Before 1

            demonstrate(0)
            return

            print After 1
        return

        print After 2
    return

    print After 3
return

Statements after a recursive call cannot execute until the entire recursive call finishes.

10. A systematic way to trace recursion

Do not try to mentally execute every call simultaneously.

Instead, trace systematically.

Consider:

public static int mystery(int n) {
    if (n == 0) {
        return 0;
    }

    return 2 + mystery(n - 1);
}

What does:

mystery(4)

return?

Expand the calls:

mystery(4)
= 2 + mystery(3)

= 2 + 2 + mystery(2)

= 2 + 2 + 2 + mystery(1)

= 2 + 2 + 2 + 2 + mystery(0)

= 2 + 2 + 2 + 2 + 0

= 8

The method computes:

2n

for nonnegative n.

10.1 A good hand-tracing strategy

For each call, write:

method name
parameter values
what the call is waiting for
returned value

For example:

factorial(3)
needs: 3 * factorial(2)

factorial(2)
needs: 2 * factorial(1)

factorial(1)
needs: 1 * factorial(0)

factorial(0)
returns 1

factorial(1)
returns 1

factorial(2)
returns 2

factorial(3)
returns 6

11. Recursive thinking: The "leap of faith"

One of the biggest mistakes beginners make is trying to mentally solve every future recursive call while writing the method.

A better approach is:

Assume the recursive call correctly solves the smaller problem.

Then ask:

How can I use that answer to solve the current problem?

Consider:

factorial(n)

Assume:

factorial(n - 1)

correctly computes:

(n-1)!

Then:

n * factorial(n - 1)

must compute:

n!

This is sometimes called the recursive leap of faith.

It does not mean blindly assuming the algorithm works.

You still need to verify:

  1. the base case is correct;
  2. the recursive problem is truly smaller;
  3. recursion eventually reaches the base case;
  4. the smaller answer is combined correctly.

12. Define the meaning of the method first

A powerful recursive design technique is to precisely define what one invocation means.

Suppose we want to recursively sum an array.

Instead of vaguely thinking:

This method sums an array.

define:

sum(values, index)

to mean:

Return the sum of all elements in values beginning at index and continuing through the end of the array.

Now the algorithm almost writes itself.

If:

index == values.length

there are no values remaining, so:

return 0;

Otherwise:

values[index]

is the current value, and:

sum(values, index + 1)

is the sum of the remaining values.

Therefore:

return values[index] + sum(values, index + 1);

Complete method:

public static int sum(
        int[] values,
        int index) {

    if (index == values.length) {
        return 0;
    }

    return values[index]
            + sum(values, index + 1);
}

13. A five-step method for designing recursion

When writing a recursive algorithm from scratch, use this process.

Step 1: Define exactly what the method means

Example:

sum(values, index)

means:

Sum every array element from index through the last position.

Step 2: Identify the simplest problem

What happens when no values remain?

index == values.length

The sum is:

0

Step 3: Determine how the problem becomes smaller

Move one position forward:

index + 1

Step 4: Assume the recursive call works

Assume:

sum(values, index + 1)

correctly sums the rest.

Step 5: Combine the current piece with the smaller answer

return values[index]
        + sum(values, index + 1);

This five-step process is useful for almost every introductory recursive problem.

14. A general recursive template

Many value-returning recursive methods resemble:

public static ReturnType solve(Input input) {

    if (baseCaseCondition) {
        return baseCaseAnswer;
    }

    Input smallerInput =
            makeProblemSmaller(input);

    ReturnType smallerAnswer =
            solve(smallerInput);

    return combineCurrentPartWith(
            smallerAnswer);
}

A shorter form is often:

public static ReturnType solve(Input input) {
    if (baseCaseCondition) {
        return baseCaseAnswer;
    }

    return combine(
        currentPart,
        solve(smallerInput)
    );
}

For methods returning void:

public static void solve(Input input) {
    if (baseCaseCondition) {
        return;
    }

    // optional work before recursion

    solve(smallerInput);

    // optional work after recursion
}

15. Recursive sum from 1 to n

Suppose we want:

1 + 2 + 3 + ⋯ + n

We can define:

sum(0)=0

and:

sum(n)=n+sum(n-1)

Java:

public static int sumTo(int n) {
    if (n < 0) {
        throw new IllegalArgumentException(
            "n must be nonnegative");
    }

    if (n == 0) {
        return 0;
    }

    return n + sumTo(n - 1);
}

Trace:

sumTo(4)
= 4 + sumTo(3)

= 4 + 3 + sumTo(2)

= 4 + 3 + 2 + sumTo(1)

= 4 + 3 + 2 + 1 + sumTo(0)

= 4 + 3 + 2 + 1 + 0

= 10

16. Factorial with input validation

The simple implementation:

public static int factorial(int n) {
    if (n == 0) {
        return 1;
    }

    return n * factorial(n - 1);
}

assumes n >= 0.

What if we call:

factorial(-3);

Then:

factorial(-3)
factorial(-4)
factorial(-5)
...

The base case is never reached.

A safer implementation is:

public static int factorial(int n) {
    if (n < 0) {
        throw new IllegalArgumentException(
            "Factorial requires a nonnegative integer.");
    }

    if (n == 0) {
        return 1;
    }

    return n * factorial(n - 1);
}

This connects recursion to defensive programming from earlier weeks.

17. Recursion with digits

Integers can be made smaller using integer division.

Suppose:

472

Using:

472 % 10

gives:

2

the final digit.

Using:

472 / 10

gives:

47

which removes the final digit.

That gives us a natural recursive decomposition.

17.1 Sum of digits

We want:

472 → 4 + 7 + 2 → 13

Implementation:

public static int sumDigits(int n) {
    if (n < 0) {
        throw new IllegalArgumentException(
            "n must be nonnegative");
    }

    if (n < 10) {
        return n;
    }

    return n % 10 + sumDigits(n / 10);
}

Trace:

sumDigits(472)

= 2 + sumDigits(47)

= 2 + 7 + sumDigits(4)

= 2 + 7 + 4

= 13

The smaller problem is produced by:

n / 10

17.2 Count the digits

For a nonnegative integer:

public static int digitCount(int n) {
    if (n < 0) {
        throw new IllegalArgumentException(
            "n must be nonnegative");
    }

    if (n < 10) {
        return 1;
    }

    return 1 + digitCount(n / 10);
}

Example:

digitCount(5278)

= 1 + digitCount(527)
= 1 + 1 + digitCount(52)
= 1 + 1 + 1 + digitCount(5)
= 1 + 1 + 1 + 1
= 4

18. Recursive powers

For a nonnegative exponent:

x^0=1

and:

x^n=x× x^{n-1}

Java:

public static long power(
        long base,
        int exponent) {

    if (exponent < 0) {
        throw new IllegalArgumentException(
            "Exponent must be nonnegative");
    }

    if (exponent == 0) {
        return 1;
    }

    return base
            * power(base, exponent - 1);
}

For:

power(2, 4)

we get:

2 * power(2, 3)
2 * 2 * power(2, 2)
2 * 2 * 2 * power(2, 1)
2 * 2 * 2 * 2 * power(2, 0)
2 * 2 * 2 * 2 * 1
16

19. Making the problem much smaller

A recursive problem does not always need to shrink by exactly one unit.

Consider:

2^8

We know:

2^8 = 2^4 × 2^4

and:

2^4 = 2^2 × 2^2

This leads to:

public static long fastPower(
        long base,
        int exponent) {

    if (exponent < 0) {
        throw new IllegalArgumentException(
            "Exponent must be nonnegative");
    }

    if (exponent == 0) {
        return 1;
    }

    long half =
        fastPower(base, exponent / 2);

    if (exponent % 2 == 0) {
        return half * half;
    }

    return base * half * half;
}

Notice the important difference:

power(n)       → power(n - 1)
fastPower(n)   → fastPower(n / 2)

The second algorithm reduces the problem much more aggressively.

We will develop formal vocabulary for comparing algorithm growth in Week 11.

For now, remember:

How quickly an algorithm reduces its remaining problem can have a major effect on how much work it performs.

20. Recursion with strings

Strings offer several natural recursive decompositions.

For:

"CAT"

we can think of:

first character = 'C'
remaining string = "AT"

The recursive problem becomes smaller because the remaining string has fewer characters.

21. Printing characters recursively

public static void printChars(String s) {
    if (s.isEmpty()) {
        return;
    }

    System.out.println(s.charAt(0));

    printChars(s.substring(1));
}

Calling:

printChars("CAT");

produces:

C
A
T

Calls:

printChars("CAT")
printChars("AT")
printChars("T")
printChars("")

The empty string is the base case.

22. Reversing a string

Consider:

public static String reverse(String s) {
    if (s.length() <= 1) {
        return s;
    }

    return reverse(s.substring(1))
            + s.charAt(0);
}

For:

reverse("DOG")

descending:

reverse("DOG")
= reverse("OG") + "D"

reverse("OG")
= reverse("G") + "O"

reverse("G")
= "G"

unwinding:

reverse("G")
= "G"

reverse("OG")
= "G" + "O"
= "GO"

reverse("DOG")
= "GO" + "D"
= "GOD"

Notice that the important concatenation happens during unwinding.

Important implementation note

This version is excellent for learning recursive reasoning.

For large strings, repeatedly creating substrings and new String objects may be unnecessarily expensive. In production code, an indexed or iterative approach may be more appropriate.

The clearest teaching solution is not always the most efficient production solution.

23. Counting characters in a string

Suppose we want to count 'a' in:

"banana"

One implementation is:

public static int countChar(
        String text,
        char target,
        int index) {

    if (index == text.length()) {
        return 0;
    }

    int current =
        text.charAt(index) == target ? 1 : 0;

    return current
            + countChar(
                text,
                target,
                index + 1);
}

Call:

countChar("banana", 'a', 0)

The method meaning is:

Count occurrences of target from index through the end of text.

That method meaning is much more useful than simply saying:

This method counts characters.

24. Palindrome checking

A palindrome reads the same forward and backward.

Examples:

racecar
level
madam

Think recursively.

A string is a palindrome if:

  1. it contains zero or one characters; or
  2. its first and last characters match and its middle portion is a palindrome.

Implementation:

public static boolean isPalindrome(
        String s) {

    if (s.length() <= 1) {
        return true;
    }

    if (s.charAt(0)
            != s.charAt(s.length() - 1)) {
        return false;
    }

    return isPalindrome(
        s.substring(1, s.length() - 1)
    );
}

For:

racecar

the recursive decomposition is:

racecar
 aceca
  cec
   e

At every stage, the smaller problem has exactly the same form:

Is this smaller string a palindrome?

25. Recursion with arrays

Arrays require a different technique because passing an array does not make the array smaller.

Suppose:

int[] values = {5, 8, 2};

The same array object exists in every call.

Instead of creating new arrays, we usually introduce an index parameter.

The index describes which portion remains to be processed.

26. Summing an array recursively

Define:

sumArray(values, index)

to mean:

Return the sum of all elements from index through the final array position.

Implementation:

public static int sumArray(
        int[] values,
        int index) {

    if (index == values.length) {
        return 0;
    }

    return values[index]
            + sumArray(
                values,
                index + 1);
}

For:

int[] values = {5, 8, 2};

calling:

sumArray(values, 0)

gives:

5 + sumArray(values, 1)

5 + 8 + sumArray(values, 2)

5 + 8 + 2 + sumArray(values, 3)

5 + 8 + 2 + 0

15

The array does not become smaller.

The remaining logical problem becomes smaller.

27. Recursive array maximum

Suppose we want the maximum array element.

Define:

max(values, index)

as:

Return the maximum element from index through the end of the array.

Implementation:

public static int max(
        int[] values,
        int index) {

    if (index == values.length - 1) {
        return values[index];
    }

    int maxOfRest =
        max(values, index + 1);

    if (values[index] > maxOfRest) {
        return values[index];
    }

    return maxOfRest;
}

The critical line is:

int maxOfRest =
    max(values, index + 1);

Use the recursive leap of faith:

Assume max(values, index + 1) correctly tells us the largest element after the current position.

Then the current call only needs to compare:

values[index]

with:

maxOfRest

A shorter version is:

public static int max(
        int[] values,
        int index) {

    if (index == values.length - 1) {
        return values[index];
    }

    return Math.max(
        values[index],
        max(values, index + 1)
    );
}

28. Counting occurrences in an array

public static int countOccurrences(
        int[] values,
        int target,
        int index) {

    if (index == values.length) {
        return 0;
    }

    int countInRest =
        countOccurrences(
            values,
            target,
            index + 1);

    if (values[index] == target) {
        return 1 + countInRest;
    }

    return countInRest;
}

For:

int[] values = {4, 7, 4, 2, 4};

calling:

countOccurrences(values, 4, 0);

returns:

3

A more compact implementation is:

public static int countOccurrences(
        int[] values,
        int target,
        int index) {

    if (index == values.length) {
        return 0;
    }

    int current =
        values[index] == target ? 1 : 0;

    return current
        + countOccurrences(
            values,
            target,
            index + 1);
}

29. Recursive array search

Suppose we want to know whether an array contains a target.

public static boolean contains(
        int[] values,
        int target,
        int index) {

    if (index == values.length) {
        return false;
    }

    if (values[index] == target) {
        return true;
    }

    return contains(
        values,
        target,
        index + 1);
}

This method can return early.

If the target occurs at the current location:

return true;

There is no reason to process the remainder of the array.

30. Extra parameters represent recursive state

This pattern is extremely important.

Suppose the public problem is:

Sum an array.

But the recursive problem is better expressed as:

Sum the portion of the array beginning at a particular position.

The recursive implementation needs an extra parameter:

index

Similarly, binary search uses:

low
high

to describe the portion of the array still under consideration.

A major algorithm-design principle is:

We do not always need to physically create smaller data. Parameters can describe a smaller logical problem.

31. Using recursive helper methods

Callers usually should not need to know about recursive bookkeeping parameters.

For example, this public interface is natural:

sumArray(values);

This is less convenient:

sumArray(values, 0);

We can hide the index using a helper:

public static int sumArray(int[] values) {
    return sumArray(values, 0);
}

private static int sumArray(
        int[] values,
        int index) {

    if (index == values.length) {
        return 0;
    }

    return values[index]
            + sumArray(
                values,
                index + 1);
}

The public method provides the clean interface.

The private helper contains the internal recursive state.

This connects recursion to encapsulation.

32. Another helper example: Palindrome with indexes

Instead of constructing smaller substrings, we can represent the remaining string using two indexes.

public static boolean isPalindrome(
        String text) {

    return isPalindrome(
        text,
        0,
        text.length() - 1
    );
}

private static boolean isPalindrome(
        String text,
        int left,
        int right) {

    if (left >= right) {
        return true;
    }

    if (text.charAt(left)
            != text.charAt(right)) {
        return false;
    }

    return isPalindrome(
        text,
        left + 1,
        right - 1
    );
}

Now no substring needs to be constructed.

The recursive state is represented by:

left
right

Each call shrinks the interval:

0 ........ 6
  1 .... 5
    2 .. 4
      3

33. Searching: Linear search

Before studying binary search, consider ordinary linear search.

public static int linearSearch(
        int[] values,
        int target) {

    for (int i = 0;
         i < values.length;
         i++) {

        if (values[i] == target) {
            return i;
        }
    }

    return -1;
}

Linear search checks values sequentially.

For:

[3, 7, 12, 18, 25, 31, 42]

searching for 31 might examine:

3
7
12
18
25
31

This works whether or not the data is sorted.

34. Binary search

Binary search works differently.

It requires a sorted collection.

Suppose:

[3, 7, 12, 18, 25, 31, 42]

We want:

25

The middle value is:

18

Because:

25 > 18

and the array is sorted, the target cannot be anywhere to the left of 18.

We can discard that entire portion.

Now the problem becomes:

[25, 31, 42]

We have reduced the search problem dramatically.

35. Why must binary search use sorted data?

Suppose we have:

[20, 3, 50, 8, 1]

The middle value is:

50

If the target is 8, seeing 50 does not allow us to safely discard either side.

Ordering is what gives binary search its power.

If a sorted array's middle element is 50 and the target is 8, then we know:

target < middle

therefore the target, if present, must occur in the lower half.

Without ordering, that conclusion is invalid.

36. Recursive binary search

public static int binarySearch(
        int[] values,
        int target,
        int low,
        int high) {

    if (low > high) {
        return -1;
    }

    int mid =
        low + (high - low) / 2;

    if (values[mid] == target) {
        return mid;
    }

    if (target < values[mid]) {
        return binarySearch(
            values,
            target,
            low,
            mid - 1);
    }

    return binarySearch(
        values,
        target,
        mid + 1,
        high);
}

Initial call:

int index = binarySearch(
    values,
    target,
    0,
    values.length - 1
);

36.1 Base cases

Binary search has two important stopping situations.

Target found

if (values[mid] == target) {
    return mid;
}

Search interval is empty

if (low > high) {
    return -1;
}

The empty interval means:

There are no positions remaining where the target could occur.

37. Binary search trace

Suppose:

index:  0   1   2   3   4   5   6
value:  3   7  12  18  25  31  42

Search for:

31

Initial state:

low = 0
high = 6
mid = 3
values[3] = 18

Since:

31 > 18

search:

low = 4
high = 6

Now:

mid = 5
values[5] = 31

Target found.

Return:

5

Only two middle values were examined.

38. Binary search with a public helper interface

A cleaner design is:

public static int binarySearch(
        int[] values,
        int target) {

    return binarySearch(
        values,
        target,
        0,
        values.length - 1
    );
}

private static int binarySearch(
        int[] values,
        int target,
        int low,
        int high) {

    if (low > high) {
        return -1;
    }

    int mid =
        low + (high - low) / 2;

    if (values[mid] == target) {
        return mid;
    }

    if (target < values[mid]) {
        return binarySearch(
            values,
            target,
            low,
            mid - 1
        );
    }

    return binarySearch(
        values,
        target,
        mid + 1,
        high
    );
}

The caller simply writes:

int result =
    binarySearch(values, 25);

The private helper hides:

low
high

from the user of the method.

39. Why binary search is algorithmically important

Suppose there are approximately 1,000 sorted values.

Binary search reduces the search range approximately like this:

1000
500
250
125
62
31
15
7
3
1

That is only about ten reductions.

For approximately one million values:

1,000,000
500,000
250,000
125,000
...

only about twenty halvings are needed.

Compare this with examining values one by one.

The important Week 10 lesson is:

Different correct algorithms can require dramatically different amounts of work.

We will formalize this idea using algorithm analysis and Big-O notation in Week 11.

40. Recursion versus iteration

Many problems can be written both ways.

Consider factorial.

Iterative version

public static int factorialIterative(
        int n) {

    if (n < 0) {
        throw new IllegalArgumentException();
    }

    int result = 1;

    for (int i = 2; i <= n; i++) {
        result *= i;
    }

    return result;
}

Recursive version

public static int factorialRecursive(
        int n) {

    if (n < 0) {
        throw new IllegalArgumentException();
    }

    if (n == 0) {
        return 1;
    }

    return n
        * factorialRecursive(n - 1);
}

Both are correct.

The useful question is not:

Is recursion better than iteration?

Instead ask:

Which approach most clearly and appropriately represents this particular problem?

41. How iteration stores progress

A loop usually stores progress explicitly.

For factorial:

int result = 1;

for (int i = 2; i <= n; i++) {
    result *= i;
}

Progress is represented by variables such as:

i
result

42. How recursion stores progress

In recursion:

return n * factorial(n - 1);

progress is represented across separate method calls.

Conceptually:

factorial(4): n = 4
factorial(3): n = 3
factorial(2): n = 2
factorial(1): n = 1
factorial(0): n = 0

The call stack remembers the unfinished work.

43. When recursion is a good fit

Recursion is particularly useful when:

  • a problem is naturally defined using smaller instances of itself;
  • a structure contains smaller structures of the same form;
  • a problem repeatedly divides into smaller subproblems;
  • operations need to occur while calls unwind;
  • recursive code directly mirrors the conceptual definition of the problem.

Examples include:

  • binary search;
  • tree traversal;
  • directory traversal;
  • nested structures;
  • divide-and-conquer algorithms;
  • maze exploration;
  • backtracking;
  • expression processing.

Some of these appear in later courses or weeks.

44. When iteration may be better

Iteration is often preferable when:

  • the task is straightforward sequential repetition;
  • recursion adds no clarity;
  • the number of steps could be extremely large;
  • stack memory is a concern;
  • the recursive solution merely recreates a simple loop.

For example, summing:

1 + 2 + ... + 1,000,000

is usually more naturally implemented with a loop.

45. Recursion uses stack space

Every active recursive invocation needs a stack frame.

Consider:

factorial(5)

The call depth is roughly:

factorial(5)
factorial(4)
factorial(3)
factorial(2)
factorial(1)
factorial(0)

For a small input, this is not a problem.

For extremely large recursion depth, however, the program can exhaust the available call stack.

Java may then throw:

java.lang.StackOverflowError

46. Recursion depth

Recursion depth refers to the maximum number of recursive invocations active at the same time.

For:

factorial(n)

the depth grows roughly in proportion to n.

For binary search, the remaining problem is repeatedly cut approximately in half, so its recursive depth grows far more slowly.

There is no universal maximum safe recursion depth in Java.

It depends on factors including:

  • JVM configuration;
  • available stack memory;
  • the size of each stack frame;
  • the platform;
  • the method being executed.

Therefore:

A recursive algorithm may be logically correct and still be unsafe for extremely deep inputs.

47. Java and tail recursion

You may encounter the term tail recursion.

A method is tail-recursive when its recursive call is the final operation:

public static int factorialHelper(
        int n,
        int result) {

    if (n == 0) {
        return result;
    }

    return factorialHelper(
        n - 1,
        n * result
    );
}

Some programming language implementations can optimize certain tail calls and avoid creating new stack frames.

For Java, however:

Do not assume tail-recursive calls will be optimized away.

A deeply tail-recursive Java method can still produce a StackOverflowError.

Therefore, converting a simple Java loop into tail recursion does not automatically reduce memory usage.

48. Common error: No base case

Incorrect:

public static void countdown(int n) {
    System.out.println(n);
    countdown(n - 1);
}

Calls continue:

countdown(5)
countdown(4)
countdown(3)
...
countdown(0)
countdown(-1)
countdown(-2)
...

Eventually:

StackOverflowError

Correct:

public static void countdown(int n) {
    if (n == 0) {
        return;
    }

    System.out.println(n);
    countdown(n - 1);
}

49. Common error: A base case exists but is unreachable

Consider:

public static void countdown(int n) {
    if (n == 0) {
        return;
    }

    countdown(n + 1);
}

For:

countdown(5);

the sequence is:

5
6
7
8
9
...

The method technically contains a base case.

But the calls move away from it.

Therefore, do not ask only:

Does the method have a base case?

Also ask:

Does every recursive call make progress toward that base case?

50. Common error: The argument does not change

Incorrect:

public static int sumTo(int n) {
    if (n == 0) {
        return 0;
    }

    return n + sumTo(n);
}

If we call:

sumTo(5)

the next call is:

sumTo(5)

then:

sumTo(5)

again.

The problem never becomes smaller.

Correct:

return n + sumTo(n - 1);

51. Common error: Base-case test happens too late

Incorrect:

public static void countdown(int n) {
    countdown(n - 1);

    if (n == 0) {
        return;
    }

    System.out.println(n);
}

The recursive call occurs before the base-case test.

When n == 0, Java still calls:

countdown(-1);

before checking whether it should stop.

In most ordinary recursive methods, the base case needs to be checked before another recursive call occurs.

52. Common error: Using n-- in the recursive call

Avoid:

countdown(n--);

Post-decrement passes the current value first.

If:

n == 5

then:

countdown(n--);

passes 5 to the recursive call.

The current frame's local n is decremented afterward, but the recursive invocation already received 5.

This can prevent progress.

Prefer explicit code:

countdown(n - 1);

It is easier to read and reason about.

53. Common error: Ignoring the recursive return value

Consider:

public static int sumTo(int n) {
    if (n == 0) {
        return 0;
    }

    sumTo(n - 1);
    return n;
}

This recursive call:

sumTo(n - 1);

does return a value.

But that value is ignored.

Therefore, the method does not accumulate the smaller results.

Correct:

public static int sumTo(int n) {
    if (n == 0) {
        return 0;
    }

    return n + sumTo(n - 1);
}

For a value-returning recursive method, always ask:

What value does the recursive call give me, and what must the current invocation do with it?

54. Common error: Using static state unnecessarily

Avoid designs such as:

static int total = 0;

public static void sum(int[] values, int index) {
    if (index == values.length) {
        return;
    }

    total += values[index];
    sum(values, index + 1);
}

This creates shared state that persists between calls.

For example, calling the method multiple times may produce surprising results unless total is manually reset.

Prefer returning the recursive result:

public static int sum(
        int[] values,
        int index) {

    if (index == values.length) {
        return 0;
    }

    return values[index]
        + sum(values, index + 1);
}

This is easier to:

  • understand;
  • test;
  • reuse;
  • debug.

55. Multiple base cases

A recursive algorithm may have more than one base case.

The Fibonacci sequence is defined as:

F(0)=0
F(1)=1

and:

F(n)=F(n-1)+F(n-2)

Java:

public static long fibonacci(int n) {
    if (n < 0) {
        throw new IllegalArgumentException(
            "n must be nonnegative");
    }

    if (n == 0) {
        return 0;
    }

    if (n == 1) {
        return 1;
    }

    return fibonacci(n - 1)
            + fibonacci(n - 2);
}

The two base cases can also be written:

if (n <= 1) {
    return n;
}

There is no rule saying recursion must contain exactly one base case.

56. Linear recursion

In linear recursion, each invocation makes at most one recursive call.

Examples:

factorial(n - 1)
sum(values, index + 1)
reverse(smallerString)

The call structure resembles a chain:

factorial(4)
    factorial(3)
        factorial(2)
            factorial(1)
                factorial(0)

57. Branching recursion

In branching recursion, an invocation can make multiple recursive calls.

Fibonacci:

return fibonacci(n - 1)
        + fibonacci(n - 2);

creates something like:

                 fib(5)
               /        \
           fib(4)       fib(3)
          /     \       /    \
      fib(3)  fib(2) fib(2) fib(1)
      /   \
   fib(2) fib(1)

The call structure becomes a tree rather than a simple chain.

This distinction matters because the number of total calls can become much larger than the maximum recursion depth.

58. Fibonacci: Elegant but inefficient

The recursive Fibonacci implementation closely matches the mathematical definition:

public static long fibonacci(int n) {
    if (n <= 1) {
        return n;
    }

    return fibonacci(n - 1)
            + fibonacci(n - 2);
}

That makes it elegant.

But examine:

fib(5)

It calls:

fib(4)
fib(3)

But fib(4) itself calculates:

fib(3)
fib(2)

So:

fib(3)

is calculated repeatedly.

Larger inputs produce many repeated subproblems.

This teaches an important distinction:

Correctness and efficiency are different properties.

A recursive algorithm can be:

  • correct;
  • readable;
  • mathematically elegant;

and still perform unnecessary work.

59. Iterative Fibonacci

An iterative implementation avoids the repeated recursive calculations:

public static long fibonacciIterative(
        int n) {

    if (n < 0) {
        throw new IllegalArgumentException(
            "n must be nonnegative");
    }

    if (n == 0) {
        return 0;
    }

    long previous = 0;
    long current = 1;

    for (int i = 2; i <= n; i++) {
        long next = previous + current;

        previous = current;
        current = next;
    }

    return current;
}

For this particular problem, the iterative implementation is usually preferable in practical code.

The lesson is not:

Recursion is inefficient.

The lesson is:

The structure of a recursive algorithm determines how much work it performs.

60. Recursive patterns to recognize

Several recurring patterns appear across recursive algorithms.

Pattern 1: Reduce by one

solve(n)
    ↓
solve(n - 1)

Examples:

  • factorial;
  • sum 1...n;
  • digit processing;
  • array processing one element at a time.

Pattern 2: Move through a sequence

solve(data, index)
    ↓
solve(data, index + 1)

Examples:

  • array sum;
  • array search;
  • count occurrences;
  • string processing with indexes.

Pattern 3: Shrink both ends

solve(left, right)
    ↓
solve(left + 1, right - 1)

Example:

  • palindrome checking.

Pattern 4: Reduce dramatically

solve(n)
    ↓
solve(n / 2)

Examples:

  • fast exponentiation;
  • binary search-like reductions.

Pattern 5: Multiple recursive subproblems

solve(problem)
    ↓
solve(smaller1)
+
solve(smaller2)

Examples:

  • Fibonacci;
  • future tree algorithms;
  • many divide-and-conquer algorithms.

61. Direct and indirect recursion

Most examples in this course use direct recursion.

Direct recursion

A method directly calls itself:

public static int factorial(int n) {
    if (n == 0) {
        return 1;
    }

    return n * factorial(n - 1);
}

Indirect recursion

Two or more methods can form a recursive cycle:

public static void methodA(int n) {
    if (n <= 0) {
        return;
    }

    methodB(n - 1);
}

public static void methodB(int n) {
    if (n <= 0) {
        return;
    }

    methodA(n - 1);
}

methodA does not directly call itself.

However:

methodA → methodB → methodA

forms recursion.

Indirect recursion is less common in introductory problems, but the call-stack principles are the same.

62. Recursion and mathematical induction

Recursive reasoning resembles mathematical induction.

An induction proof commonly has two ideas:

  1. prove a base case;
  2. assume something is true for a smaller case and use that to establish a larger case.

Recursive programming often follows:

  1. solve the base case;
  2. assume the recursive call correctly solves a smaller problem;
  3. use its result to solve the current problem.

For factorial:

return n * factorial(n - 1);

Assume:

factorial(n - 1)

correctly computes:

(n-1)!

Then multiplying by n computes:

n!

You do not need formal induction proofs for every Week 10 program, but recognizing this similarity helps develop rigorous recursive reasoning.

63. Informally arguing that recursion terminates

A useful termination argument has two parts.

Part 1: Identify a changing quantity

For factorial:

n

decreases by one.

For an array:

index

increases toward:

values.length

For binary search:

size of the search interval

becomes smaller.

Part 2: Show that it must reach a base case

Factorial:

n → n - 1 → n - 2 → ... → 0

Array traversal:

index → index + 1 → ... → values.length

Binary search:

large interval → smaller interval → ... → empty interval

If you cannot explain why valid input must eventually reach a base case, you should be suspicious of the recursive method.

64. Informally reasoning about correctness

Ask three questions.

1. Are the base cases correct?

Do they return the right answer for the smallest problems?

2. Does the recursive call solve a smaller version of the same problem?

If not, the recursive decomposition may be wrong.

3. Assuming the recursive call is correct, does the current call produce the right answer?

Example:

return values[index]
        + sum(values, index + 1);

Assume:

sum(values, index + 1)

correctly sums everything after the current element.

Then adding:

values[index]

produces exactly the sum beginning at index.

65. Algorithmic thinking

This week is not only about writing methods that call themselves.

Recursion gives us practice with a larger set of algorithm-design questions.

When approaching a problem, ask:

  1. What is the input?
  2. What result should be produced?
  3. What special or boundary cases exist?
  4. Can the problem be expressed using a smaller version of itself?
  5. How will I represent the smaller problem?
  6. What state must be carried between calls?
  7. What guarantees termination?
  8. Can some cases stop early?
  9. Am I repeating the same work unnecessarily?
  10. Could a loop express this more clearly?
  11. Could a different algorithm reduce the problem faster?
  12. What tradeoffs exist among the possible solutions?

These questions extend far beyond recursion.

They are central to programming and computer science.

66. Problem representation matters

Sometimes a problem initially looks difficult to express recursively because we have not chosen the right method parameters.

Suppose we start with:

public static int sumArray(
        int[] values)

The array itself never gets smaller.

Instead, redefine the recursive problem:

private static int sumArray(
        int[] values,
        int index)

Now:

index

represents what remains.

Similarly:

binarySearch(
    values,
    target,
    low,
    high)

uses:

low
high

to describe the current search interval.

A major recursive design insight is:

Choosing the right representation of the remaining problem can make the solution much easier to see.

67. Divide and conquer: A preview

Divide and conquer is an algorithm-design strategy in which a problem is broken into smaller problems that are solved and combined.

Recursion is often used to implement divide-and-conquer algorithms.

Binary search provides a simple example of repeated problem reduction:

search large interval
        ↓
search roughly half
        ↓
search roughly half again
        ↓
...

However, recursion and divide-and-conquer are not identical.

Factorial is recursive:

factorial(n - 1)

but is not usually described as a divide-and-conquer algorithm.

More formal study of algorithm strategies and performance comes later.

68. Why recursion matters for future data structures

Consider a structure that can contain smaller structures of the same kind.

For example, conceptually:

tree
├── smaller tree
└── smaller tree

This naturally suggests:

process current part
process first smaller structure
process second smaller structure

That is why recursion becomes particularly useful for trees and other recursive data structures.

For Week 10, the important point is not to master tree algorithms yet.

The important idea is:

When the data itself has recursive structure, a recursive algorithm often mirrors that structure naturally.

69. A complete worked design example

Problem

Write a recursive method that counts the number of even values in an integer array.

Suppose:

int[] values = {
    7, 4, 12, 9, 6
};

The answer should be:

3

because:

4, 12, 6

are even.

Step 1: Define the recursive meaning

Let:

countEven(values, index)

mean:

Return the number of even values from index through the final position.

Step 2: Find the base case

When:

index == values.length

no values remain.

Therefore:

return 0;

Step 3: Make the problem smaller

The remaining problem is:

countEven(values, index + 1)

Step 4: Solve the current piece

Check:

values[index] % 2 == 0

If true, the current value contributes 1.

Otherwise, it contributes 0.

Step 5: Combine

public static int countEven(
        int[] values,
        int index) {

    if (index == values.length) {
        return 0;
    }

    int current =
        values[index] % 2 == 0 ? 1 : 0;

    return current
        + countEven(
            values,
            index + 1);
}

Step 6: Hide the implementation parameter

public static int countEven(
        int[] values) {

    return countEven(values, 0);
}

private static int countEven(
        int[] values,
        int index) {

    if (index == values.length) {
        return 0;
    }

    int current =
        values[index] % 2 == 0 ? 1 : 0;

    return current
        + countEven(
            values,
            index + 1);
}

The public interface is now:

int result = countEven(values);

70. A complete worked string example

Problem

Remove every occurrence of a particular character.

Example:

removeChar("banana", 'a')

should return:

"bnn"

Define:

removeChar(text, target)

recursively.

Base case:

text.isEmpty()

returns:

""

Recursive step:

  1. recursively process everything after the first character;
  2. decide whether the current character belongs in the answer.
public static String removeChar(
        String text,
        char target) {

    if (text.isEmpty()) {
        return "";
    }

    String rest =
        removeChar(
            text.substring(1),
            target);

    if (text.charAt(0) == target) {
        return rest;
    }

    return text.charAt(0) + rest;
}

Trace beginning:

removeChar("banana", 'a')

current = 'b'
rest = removeChar("anana", 'a')

Eventually, unwinding reconstructs the string without 'a'.

71. A recursive method can return void

Recursion does not require a returned value.

Example:

public static void printDown(int n) {
    if (n < 0) {
        return;
    }

    System.out.println(n);

    printDown(n - 1);
}

Or:

public static void printUp(int n) {
    if (n < 0) {
        return;
    }

    printUp(n - 1);

    System.out.println(n);
}

The important concepts remain the same:

  • base case;
  • smaller problem;
  • progress;
  • stack frames;
  • descending;
  • unwinding.

72. Recursive design checklist

Before considering a recursive method finished, ask the following.

Meaning

  • What exactly does one invocation promise to compute?
  • What does each parameter mean?

Base case

  • What is the smallest valid problem?
  • Is the base-case answer logically correct?
  • Are multiple base cases needed?

Progress

  • What changes in every recursive call?
  • Is the recursive problem strictly smaller or closer to completion?
  • Can every valid input eventually reach a base case?

Recursive result

  • What does the recursive call return?
  • How does the current call use that result?
  • Am I accidentally ignoring the returned value?

Safety

  • Are invalid inputs handled?
  • Could the recursion become extremely deep?
  • Could this produce StackOverflowError?

Clarity

  • Would a helper method make the public interface cleaner?
  • Would iteration be simpler?

Efficiency

  • How many recursive calls seem to occur?
  • Is the same subproblem being recomputed?
  • Does the problem shrink slowly or rapidly?

Formal efficiency analysis comes next week, but these questions can already guide good programming decisions.

73. Debugging recursive programs

When recursive code fails, do not simply stare at the entire method.

Use a systematic process.

73.1 Test a base case first

For factorial:

factorial(0)

Should return:

1

If the base case itself fails, deeper inputs cannot work correctly.

73.2 Test one step above the base case

Try:

factorial(1)

Expected:

1

Then:

factorial(2)

Expected:

2

Small inputs make tracing manageable.

73.3 Print the arguments temporarily

public static int factorial(int n) {
    System.out.println(
        "factorial(" + n + ")"
    );

    if (n == 0) {
        return 1;
    }

    return n * factorial(n - 1);
}

This makes progress visible.

If you see:

factorial(5)
factorial(5)
factorial(5)
factorial(5)
...

you immediately know the argument is not becoming smaller.

73.4 Trace return values

You can temporarily write:

public static int factorial(int n) {
    if (n == 0) {
        System.out.println(
            "factorial(0) = 1");
        return 1;
    }

    int smaller =
        factorial(n - 1);

    int result =
        n * smaller;

    System.out.println(
        "factorial(" + n + ") = "
        + result);

    return result;
}

For:

factorial(4)

you might see:

factorial(0) = 1
factorial(1) = 1
factorial(2) = 2
factorial(3) = 6
factorial(4) = 24

This clearly exposes unwinding.

74. Frequently asked questions

FAQ 1: Is recursion just another kind of loop?

Not exactly.

Both can express repetition, but they represent repetition differently.

Loops use constructs such as:

for
while

Recursion uses repeated method invocation.

Iteration usually stores state in loop variables.

Recursion stores unfinished work in method calls on the call stack.

FAQ 2: Why does the first recursive call not disappear?

Because it has not finished.

For:

return n * factorial(n - 1);

the current invocation still needs the result of:

factorial(n - 1)

before it can perform multiplication and return.

Therefore, its stack frame remains active.

FAQ 3: Why does recursive code sometimes look like it runs backward?

It does not actually run backward.

Statements after a recursive call are simply delayed until that call returns.

This produces the appearance of reverse processing during stack unwinding.

FAQ 4: Can recursion have several base cases?

Yes.

Fibonacci has two natural base cases:

fib(0)
fib(1)

A palindrome checker may conceptually stop either because:

  • zero or one characters remain; or
  • a mismatched pair has already been found.

FAQ 5: Can a recursive method return void?

Yes.

For example:

public static void print(int n) {
    if (n == 0) {
        return;
    }

    System.out.println(n);
    print(n - 1);
}

Recursion is about method invocation, not return type.

FAQ 6: Why do recursive array methods often need an index?

Because the array does not physically become smaller.

The index describes the remaining logical portion of the problem.

FAQ 7: Why not copy a smaller array each time?

You could, but that usually creates unnecessary arrays and copying.

Using:

index

or:

low
high

is generally cleaner and avoids creating new arrays.

FAQ 8: Why use a helper method?

The recursive implementation may require extra parameters that callers should not need to provide.

For example:

sum(values)

is a better public interface than:

sum(values, 0)

The helper method allows both clean interface design and convenient recursion.

FAQ 9: Is recursion always slower than iteration?

No universal rule says that recursion is always slower.

However, recursive method calls have overhead, and each active invocation consumes stack space.

For straightforward linear repetition, iteration is often more memory-efficient.

The more important question is whether the recursive formulation expresses the algorithm naturally and whether its depth and amount of work are reasonable.

FAQ 10: Why can correct recursion still cause StackOverflowError?

Because logical correctness and available memory are different issues.

A recursive method can make progress and terminate eventually, yet require more simultaneously active stack frames than the JVM can support.

FAQ 11: Does Java optimize tail recursion?

Do not rely on it.

Java does not generally guarantee tail-call optimization.

Deep tail recursion can therefore still overflow the call stack.

FAQ 12: Why is naive Fibonacci considered a bad algorithm?

Because it repeatedly solves the same subproblems.

For example:

fib(5)

needs:

fib(4)
fib(3)

but fib(4) itself needs fib(3) again.

Correctness does not imply efficiency.

FAQ 13: Should I always use recursion when possible?

No.

Use recursion when it helps express the structure of the problem.

Use iteration when it is clearer, simpler, or safer.

Good programming means choosing appropriately rather than automatically preferring one technique.

FAQ 14: How should I begin a recursion problem on an exam?

Write down four things before coding:

1. Meaning of the method
2. Base case
3. Smaller problem
4. How to combine the smaller result

This prevents many common errors.

75. Key vocabulary

You should be able to explain all of the following.

Recursion

A technique in which a method solves a problem using one or more smaller instances of the same problem.

Recursive method

A method that eventually invokes itself.

Base case

A situation solved directly without another recursive call.

Recursive case

The part that reduces the current problem and performs recursion.

Recursive call

An invocation of the method on a smaller problem.

Progress

Movement from the current problem toward a base case.

Call stack

The runtime structure used to manage active method calls.

Stack frame

The execution information associated with one active method invocation.

Recursion depth

The greatest number of recursive calls simultaneously active.

Unwinding

The process of recursive invocations returning in reverse order after a base case is reached.

Stack overflow

Failure caused when the program exhausts available call-stack space.

Iteration

Repetition implemented using loop constructs.

Subproblem

A smaller problem whose solution contributes to the larger solution.

Problem decomposition

Breaking a difficult problem into smaller problems.

Helper method

An internal method that carries recursive state while allowing a simpler public interface.

Linear recursion

Recursion in which each invocation makes at most one recursive call.

Branching recursion

Recursion in which an invocation can make multiple recursive calls.

Binary search

A search algorithm for sorted data that repeatedly eliminates approximately half of the remaining search range.

Algorithm

A precise sequence or strategy for solving a computational problem.

81. Week 10 summary

The most important concepts from this week are not particular Java syntax patterns.

They are ways of reasoning.

Recursion

A recursive method solves a problem using smaller instances of the same problem.

Base case

Every recursive process needs one or more situations that can be solved directly.

Progress

A recursive call must move toward a base case.

Call stack

Every active invocation has its own parameters, local variables, and unfinished work.

Descending

Recursive calls move toward the smallest problem.

Unwinding

After a base case returns, unfinished calls complete in reverse order.

Method meaning

Precisely defining what one recursive invocation promises to compute often reveals the solution.

Recursive leap of faith

Assume the smaller recursive call works, then determine how its answer solves the current problem.

Problem representation

Indexes, boundaries, and other parameters can describe smaller logical problems without constructing new data.

Helper methods

Private helpers can carry recursive state while preserving a simple public interface.

Recursion versus iteration

Neither technique is universally superior.

Choose the one that appropriately expresses the structure and constraints of the problem.

Correctness versus efficiency

A recursive method may be perfectly correct while doing unnecessary work.

Naive Fibonacci is a classic example.

Algorithmic thinking

The broader lesson is to ask:

How can I represent this problem?
What is its simplest case?
How can I make it smaller?
What information must be carried forward?
What work can be avoided?
Why does the process terminate?
How do alternative solutions differ?

Final takeaway

The deepest idea from Week 10 is:

A difficult problem can often be solved by reducing it to one or more smaller instances of the same problem.

Once you can identify:

the base case
        +
the smaller problem
        +
the progress rule
        +
how to use the smaller answer

recursive code becomes much less mysterious.

Recursion is valuable not because methods are allowed to call themselves, but because it teaches you to recognize structure, decompose problems, reason about execution, and design algorithms systematically.

Those habits will become increasingly important as we move into algorithm analysis and data structures.
