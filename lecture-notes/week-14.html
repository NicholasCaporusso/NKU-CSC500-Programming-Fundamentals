2. From linear data to hierarchical data

Most of the data structures we have studied so far are linear.

Examples include:

  • arrays,
  • ArrayList,
  • linked lists,
  • stacks,
  • queues.

A linear structure places elements into some sequence.

For example:

10 -> 20 -> 30 -> 40

There is a natural notion of one element coming before or after another.

But many problems do not naturally form a sequence.

Consider a file system:

Documents
├── CSC500
│   ├── assignments
│   ├── lectures
│   └── project
└── Personal
    ├── photos
    └── taxes

Or an organizational structure:

CEO
├── Engineering
│   ├── Backend Team
│   └── Frontend Team
└── Sales
    ├── Domestic
    └── International

These structures contain branching relationships.

They are better described as hierarchical rather than linear.

A tree is a data structure designed to represent these kinds of relationships.

3. What is a tree?

A tree is a hierarchical collection of connected objects called nodes.

A simple tree might look like this:

        A
       / \
      B   C
     / \   \
    D   E   F

Each letter represents a node.

The lines connecting nodes represent relationships between them.

Unlike a linked list, a node can lead to more than one other node.

This branching structure is the defining visual characteristic of trees.

4. Where trees appear

Trees are fundamental throughout computer science.

Examples include:

File systems

Directories contain files and other directories.

home
├── student
│   ├── documents
│   └── downloads
└── shared

Web pages

Browsers represent HTML documents using the Document Object Model (DOM).

Conceptually:

<body>
    <h1>Hello</h1>
    <p>Welcome</p>
</body>

can be viewed as:

body
├── h1
└── p

Compilers

Expressions and programs are represented using syntax trees.

For example:

3 + 4 * 5

can be represented conceptually as:

        +
       / \
      3   *
         / \
        4   5

Databases

Database indexes frequently use specialized tree structures.

Artificial intelligence

Trees appear in:

  • decision trees,
  • game search,
  • planning,
  • search algorithms.

Other examples

  • organization charts,
  • course prerequisite relationships,
  • product categories,
  • menus,
  • routing systems,
  • XML documents.

Trees are useful whenever parent-child relationships or hierarchical organization are important.

5. Tree terminology

Consider this tree:

          A
        /   \
       B     C
      / \     \
     D   E     F

We need precise vocabulary to describe its structure.

5.1 Node

Each element in a tree is a node.

The nodes above are:

A, B, C, D, E, F

A node normally stores:

  1. some data,
  2. references to other nodes.

5.2 Edge

An edge is a connection between two nodes.

For example:

A -> B
A -> C
B -> D
B -> E
C -> F

These are five edges.

5.3 Root

The topmost node is called the root.

In our example:

A

is the root.

A non-empty tree has one root.

In a Java implementation, a tree object commonly keeps a reference to this node:

private TreeNode root;

An empty tree can be represented by:

root == null

5.4 Parent

If a node connects directly downward to another node, it is the parent of that node.

For example:

B

is the parent of:

D and E

5.5 Child

A node directly below another node is its child.

For example:

B and C

are children of A.

5.6 Siblings

Nodes that share the same parent are called siblings.

Examples:

B and C

are siblings.

Likewise:

D and E

are siblings.

5.7 Leaf

A leaf is a node that has no children.

In the example:

D
E
F

are leaves.

A leaf represents the end of a downward path through the tree.

5.8 Internal node

A node with at least one child is an internal node.

In our example:

A
B
C

are internal nodes.

5.9 Ancestor

An ancestor of a node is any node above it on the path toward the root.

For node E:

A -> B -> E

both A and B are ancestors of E.

A parent is therefore an immediate ancestor.

5.10 Descendant

A descendant of a node is any node below it.

For node B:

D and E

are descendants.

For node A:

B, C, D, E, F

are descendants.

5.11 Path

A path is a sequence of connected nodes.

For example:

A -> B -> E

is a path.

Its length, when measured in edges, is 2.

6. Subtrees and the recursive nature of trees

Consider:

          A
        /   \
       B     C
      / \
     D   E

If we focus only on node B and everything below it, we get:

      B
     / \
    D   E

This is called the subtree rooted at B.

Likewise, the subtree rooted at C is:

C

because C has no children in this particular example.

The idea of a subtree leads to one of the most important observations of this week:

A tree contains smaller trees inside itself.

For a binary tree, we can think of every non-empty tree as:

current node
+ left subtree
+ right subtree

This recursive structure is why recursion works so naturally with trees.

7. Depth

The depth of a node is the number of edges from the root to that node.

Consider:

        A
       / \
      B   C
     /
    D

Then:

A: depth 0
B: depth 1
C: depth 1
D: depth 2

The root always has depth 0.

A useful question for remembering depth is:

How far is this node from the root?

8. Height

The height of a node is the number of edges on the longest downward path from that node to a leaf.

Consider:

        A
       / \
      B   C
     /
    D
   /
  E

The longest path from A to a leaf is:

A -> B -> D -> E

There are three edges.

Therefore:

height(A) = 3

Under the convention used in these notes:

height of a leaf = 0
height of an empty tree = -1

Therefore:

height(E) = 0
height(D) = 1
height(B) = 2
height(A) = 3

Depth versus height

A useful distinction is:

Depth: distance from root down to a node
Height: longest distance from a node down to a leaf

For the root:

depth = 0
height = depends on the tree

Different textbooks sometimes define height using the number of nodes rather than edges. Always check the convention being used.

9. Binary trees

A binary tree is a tree in which every node has at most two children.

These children are conventionally called:

  • the left child,
  • the right child.

Example:

        10
       /  \
      5    20

A node in a binary tree may have:

  • zero children,
  • one child,
  • two children.

All are valid.

For example:

10
  \
   20

is a valid binary tree.

So is:

   10
  /
 5

The term binary does not mean that every node must have exactly two children.

It means at most two.

10. Representing a binary tree in Java

Trees are naturally represented using objects and references.

A basic binary-tree node can be written as:

class TreeNode {
    int value;
    TreeNode left;
    TreeNode right;

    TreeNode(int value) {
        this.value = value;
        this.left = null;
        this.right = null;
    }
}

Each node contains:

int value;

which stores its data.

It also contains:

TreeNode left;
TreeNode right;

which store references to the left and right children.

11. Understanding tree references

Suppose we write:

TreeNode root = new TreeNode(50);

root.left = new TreeNode(30);
root.right = new TreeNode(70);

Conceptually:

         root
           |
           v
          50
         /  \
       30    70

The variable root does not contain the entire tree.

It contains a reference to the root object.

That object contains references to its children.

This is similar to linked lists from Week 12:

linked list node:
value + next reference

A binary-tree node instead contains:

value + left reference + right reference

11.1 What does node.left mean?

Suppose:

node.left = new TreeNode(5);

This means:

  1. Create a new TreeNode containing 5.
  2. Store its reference in the left field of node.

Conceptually:

 node
  |
  v
 10
 /
5

11.2 What does node.left == null mean?

It means that the node currently has no left child.

if (node.left == null) {
    System.out.println("No left child");
}

11.3 Changing references changes the tree

Suppose:

node.left = null;

This removes the connection between node and its previous left child.

Likewise:

node.right = new TreeNode(20);

attaches a new right child.

The references define the structure of the tree.

12. Binary tree vs. binary search tree

Students must distinguish these two terms carefully.

A binary tree requires only:

Every node has at most two children.

For example:

       50
      /  \
    100   12

This is a valid binary tree.

But it is not a binary search tree.

Why?

Because a binary search tree imposes an additional ordering rule.

13. Binary search trees

A binary search tree, usually abbreviated BST, is a binary tree with an ordering property.

For every node:

all values in left subtree  < node value
all values in right subtree > node value

For example:

           50
         /    \
       30      70
      /  \    /  \
    20   40  60   80

This is a BST.

For the root 50:

20, 30, 40 < 50
60, 70, 80 > 50

For node 30:

20 < 30
40 > 30

For node 70:

60 < 70
80 > 70

The property applies recursively throughout the tree.

14. A critical BST rule: It applies to entire subtrees

One of the most common BST mistakes is checking only immediate children.

Consider:

        10
       /  \
      5    15
       \
        12

A student might reason:

12 > 5

so perhaps 12 is correctly positioned as the right child of 5.

But the tree is not a valid BST.

Why?

Because 12 is still somewhere inside the left subtree of 10.

Every value in that subtree must satisfy:

value < 10

But:

12 > 10

Therefore the BST property is violated.

The BST rule is not:

left child < node < right child

It is:

EVERY value in left subtree < node
EVERY value in right subtree > node

15. Why BST ordering is useful

Suppose we want to find 60 in:

           50
         /    \
       30      70
      /  \    /  \
    20   40  60   80

Start at 50.

60 > 50

Therefore 60, if it exists, must be in the right subtree.

We immediately ignore:

20
30
40

Move to 70.

60 < 70

So move left.

We reach:

60

and the search succeeds.

Only three nodes were examined:

50 -> 70 -> 60

The ordering property allowed us to eliminate entire subtrees.

This is the source of the BST's efficiency.

16. Searching a BST recursively

A recursive implementation is:

public static boolean contains(TreeNode node, int target) {
    if (node == null) {
        return false;
    }

    if (target == node.value) {
        return true;
    }

    if (target < node.value) {
        return contains(node.left, target);
    } else {
        return contains(node.right, target);
    }
}

There are three fundamental cases.

16.1 Case 1: Empty subtree

if (node == null) {
    return false;
}

We have reached a point where no node exists.

Therefore the target is not in the tree along this path.

16.2 Case 2: Found the target

if (target == node.value) {
    return true;
}

The search is complete.

16.3 Case 3: Choose a subtree

If the target is smaller:

if (target < node.value) {
    return contains(node.left, target);
}

Otherwise it must be larger:

return contains(node.right, target);

Notice something important:

BST search does not recursively search both subtrees.

It uses the ordering property to choose exactly one.

17. Tracing recursive BST search

Consider:

           50
         /    \
       30      70
      /  \    /  \
    20   40  60   80

Search for 40.

Initial call:

contains(root, 40)

Suppose root.value == 50.

Since:

40 < 50

we call:

contains(node.left, 40)

Now the current value is 30.

Since:

40 > 30

we call:

contains(node.right, 40)

The current value is now 40.

Since:

40 == 40

we return true.

The recursive path was:

50
 \
decision: left
      30
        \
        40

Or more simply:

50 -> 30 -> 40

18. Iterative BST search

The same algorithm can be written without recursion.

public static boolean contains(TreeNode root, int target) {
    TreeNode current = root;

    while (current != null) {
        if (target == current.value) {
            return true;
        }

        if (target < current.value) {
            current = current.left;
        } else {
            current = current.right;
        }
    }

    return false;
}

The algorithm repeatedly moves one level down.

Conceptually:

current
   |
   v
  50

If the target is smaller:

current = current.left;

If larger:

current = current.right;

Eventually either:

  1. we find the target, or
  2. current becomes null.

Both recursive and iterative approaches are valid.

19. Recursive vs. iterative search

The recursive version is often easier to connect to the mathematical structure of the tree:

search this tree
    -> search one smaller subtree

The iterative version avoids recursive calls and follows references with a loop.

For introductory tree programming, learning both approaches is valuable.

However, recursive code becomes especially natural when an operation must work on both subtrees.

20. Inserting into a BST

BST insertion uses the same comparisons as searching.

Suppose the tree is:

        50
       /  \
      30   70

We want to insert 40.

Compare:

40 < 50

Move left to 30.

Then:

40 > 30

Move right.

There is no right child:

30
  \
 null

So we place the new node there:

        50
       /  \
      30   70
        \
         40

General rule:

Follow the BST search path until reaching an empty child reference, then attach the new node there.

21. Recursive BST insertion

A common recursive implementation is:

public static TreeNode insert(TreeNode node, int value) {
    if (node == null) {
        return new TreeNode(value);
    }

    if (value < node.value) {
        node.left = insert(node.left, value);
    } else if (value > node.value) {
        node.right = insert(node.right, value);
    }

    return node;
}

This implementation contains an important pattern.

22. Why does recursive insertion return TreeNode?

Consider:

node.left = insert(node.left, value);

Why do we not simply write:

insert(node.left, value);

Suppose node.left is currently null.

The recursive call reaches:

if (node == null) {
    return new TreeNode(value);
}

A new object is created.

The caller must connect that object to the parent.

That is what this assignment does:

node.left = insert(node.left, value);

The recursive method means:

Give me the root of the updated subtree.

Then the caller stores that root into the correct child reference.

This pattern appears repeatedly in tree algorithms.

23. What about duplicate values?

There is no single universal BST duplicate policy.

Possible policies include:

  1. Ignore duplicates.
  2. Reject duplicates.
  3. Always place duplicates on one chosen side.
  4. Store a frequency count in the node.
  5. Associate multiple records with one key.

Our simple implementation uses:

if (value < node.value) {
    ...
} else if (value > node.value) {
    ...
}

There is no branch for:

value == node.value

Therefore duplicates are ignored.

For example:

tree.add(30);
tree.add(30);

still stores only one 30.

The important lesson is not that this policy is always correct.

The important lesson is:

A data structure's duplicate policy must be defined explicitly.

24. Insertion order determines BST shape

Insert:

50, 30, 70, 20, 40, 60, 80

The result is:

           50
         /    \
       30      70
      /  \    /  \
    20   40  60   80

This tree has relatively small height.

Now insert exactly the same values in this order:

20, 30, 40, 50, 60, 70, 80

The result is:

20
  \
   30
     \
      40
        \
         50
           \
            60
              \
               70
                 \
                  80

Both trees contain the same values.

Both are valid BSTs.

But their shapes are dramatically different.

That difference has major performance consequences.

25. Balanced and unbalanced trees

A tree is informally balanced when its height remains reasonably small relative to its number of nodes.

Example:

           50
         /    \
       30      70
      /  \    /  \
    20   40  60   80

This is reasonably balanced.

Compare:

20
  \
   30
     \
      40
        \
         50
           \
            60

This tree is highly unbalanced.

It behaves structurally like a linked list.

26. Why height determines BST performance

BST search follows a path from the root downward.

The number of nodes visited is therefore related to the tree's height.

If tree height is h, search is approximately:

O(h)

The same general reasoning applies to insertion and deletion.

27. Balanced BST complexity

A balanced binary tree roughly doubles the number of available node positions at each level.

For example:

Level 0:   1 node
Level 1:   2 nodes
Level 2:   4 nodes
Level 3:   8 nodes
Level 4:  16 nodes
Level 5:  32 nodes

After height h, a full binary tree can contain approximately:

2^(h + 1) - 1

nodes.

We do not need to memorize that formula for programming purposes.

The important relationship is:

number of nodes grows exponentially with height

Therefore:

height grows logarithmically with number of nodes

For a reasonably balanced BST:

height ≈ log₂ n

Therefore:

search ≈ O(log n)
insert ≈ O(log n)
delete ≈ O(log n)

28. Example: Why O(log n) matters

Suppose a balanced search tree stores roughly:

1,000,000

values.

Since:

2^20 ≈ 1,000,000

a search path may require only around 20 comparisons.

Contrast that with linear searching, which in the worst case may examine approximately one million values.

This illustrates why logarithmic algorithms become so powerful at large input sizes.

29. Worst-case BST performance

A simple BST does not automatically remain balanced.

Suppose we insert:

10, 20, 30, 40, 50

We obtain:

10
  \
   20
     \
      30
        \
         40
           \
            50

To find 50, we visit:

10 -> 20 -> 30 -> 40 -> 50

The search examines every node.

For n values:

height ≈ n

and therefore:

search = O(n)
insert = O(n)

in the worst case.

A BST is therefore not automatically O(log n).

The correct statement is:

A reasonably balanced BST supports approximately O(log n) search and insertion.

30. Trees are not automatically faster

Students sometimes learn:

tree = fast

This is too simplistic.

A data structure's performance depends on:

  • its organization,
  • the operation being performed,
  • the input size,
  • its implementation,
  • how frequently values change.

For example:

  • Accessing array[i] is O(1).
  • Binary search on a sorted array is O(log n).
  • Searching a poorly balanced BST can be O(n).
  • Searching a HashSet is typically O(1) average.

Therefore:

The question is not "Which data structure is fastest?"

Instead ask:

"Fast for which operation?"

31. Tree traversal

Sometimes we do not want to find one particular value.

Instead, we want to visit every node.

Systematically visiting all nodes of a tree is called tree traversal.

For binary trees, three classic depth-first traversal orders are:

  1. Preorder
  2. Inorder
  3. Postorder

The names describe when we process the current node relative to its subtrees.

32. Inorder traversal

Inorder traversal follows:

LEFT
NODE
RIGHT

In words:

  1. Traverse the left subtree.
  2. Process the current node.
  3. Traverse the right subtree.

Consider:

           50
         /    \
       30      70
      /  \    /  \
    20   40  60   80

Inorder traversal produces:

20 30 40 50 60 70 80

33. Why inorder traversal sorts a BST

A BST guarantees:

left values < node value < right values

Inorder traversal performs:

left
node
right

Therefore it naturally visits:

  1. smaller values,
  2. the current value,
  3. larger values.

So:

Inorder traversal of a valid BST visits its values in sorted order.

This is a property of BSTs, not arbitrary binary trees.

34. Recursive inorder traversal

public static void inorder(TreeNode node) {
    if (node == null) {
        return;
    }

    inorder(node.left);

    System.out.println(node.value);

    inorder(node.right);
}

The base case:

if (node == null) {
    return;
}

means:

There is no subtree here, so there is nothing to visit.

35. Tracing inorder traversal

Consider:

      30
     /  \
    20   40

Call:

inorder(root);

The logic is:

inorder(20)
print 30
inorder(40)

For node 20:

inorder(null)
print 20
inorder(null)

So the final output is:

20
30
40

36. Preorder traversal

Preorder follows:

NODE
LEFT
RIGHT

In words:

  1. Process the current node.
  2. Traverse the left subtree.
  3. Traverse the right subtree.

For:

           50
         /    \
       30      70
      /  \    /  \
    20   40  60   80

preorder gives:

50 30 20 40 70 60 80

Java:

public static void preorder(TreeNode node) {
    if (node == null) {
        return;
    }

    System.out.println(node.value);

    preorder(node.left);
    preorder(node.right);
}

Preorder is useful when a parent should be processed before its descendants.

Examples include:

  • displaying a hierarchy from the root downward,
  • copying certain tree representations,
  • serializing tree structure,
  • prefix-expression representations.

37. Postorder traversal

Postorder follows:

LEFT
RIGHT
NODE

In words:

  1. Traverse the left subtree.
  2. Traverse the right subtree.
  3. Process the current node.

For our example:

           50
         /    \
       30      70
      /  \    /  \
    20   40  60   80

postorder gives:

20 40 30 60 80 70 50

Java:

public static void postorder(TreeNode node) {
    if (node == null) {
        return;
    }

    postorder(node.left);
    postorder(node.right);

    System.out.println(node.value);
}

Postorder is useful when children must be processed before their parent.

Examples include:

  • computing information derived from children,
  • evaluating expression trees,
  • computing directory sizes,
  • deleting hierarchical structures,
  • calculating tree properties.

38. Remembering traversal orders

A useful table is:

TraversalOrder
PreorderNode, Left, Right
InorderLeft, Node, Right
PostorderLeft, Right, Node

The easiest strategy is to focus on where NODE appears.

Preorder

NODE
left
right

Process the node before its subtrees.

Inorder

left
NODE
right

Process the node between its subtrees.

Postorder

left
right
NODE

Process the node after its subtrees.

39. Traversal practice

Consider:

        8
       / \
      4   12
     / \    \
    2   6    14

Preorder

Rule:

NODE LEFT RIGHT

Result:

8 4 2 6 12 14

Inorder

Rule:

LEFT NODE RIGHT

Result:

2 4 6 8 12 14

Postorder

Rule:

LEFT RIGHT NODE

Result:

2 6 4 14 12 8

Exam strategy

Before tracing a traversal, write the rule at the top of your work:

PRE:  N L R
IN:   L N R
POST: L R N

This reduces memory mistakes.

40. The general pattern of recursive tree algorithms

Many tree algorithms follow this pattern:

public static ReturnType solve(TreeNode node) {
    if (node == null) {
        return baseValue;
    }

    ReturnType leftResult = solve(node.left);
    ReturnType rightResult = solve(node.right);

    return combine(node, leftResult, rightResult);
}

Conceptually:

1. Handle the empty tree.
2. Solve the problem for the left subtree.
3. Solve the problem for the right subtree.
4. Combine those answers with information from the current node.

This pattern is one of the most important ideas in this week.

41. Why tree recursion is so natural

A binary tree can be defined recursively as:

A binary tree is either empty, or it consists of a node with a left binary tree and a right binary tree.

That definition directly suggests recursive algorithms.

Suppose we want to count every node.

We can say:

nodes in this tree
=
1 for current node
+ nodes in left subtree
+ nodes in right subtree

Notice that the smaller problems are exactly the same type of problem:

count nodes in a tree

That is the structure recursion requires.

42. The typical tree base case

Most recursive tree algorithms begin with:

if (node == null) {
    ...
}

Why?

Because null represents an empty subtree.

Different problems return different values for an empty subtree.

For counting nodes:

return 0;

For summing values:

return 0;

For height under our convention:

return -1;

Choosing the correct base-case value is part of designing the recursive algorithm.

43. Counting nodes

How many nodes exist in a tree?

Recursive reasoning:

count(tree)
=
1
+ count(left subtree)
+ count(right subtree)

Java:

public static int countNodes(TreeNode node) {
    if (node == null) {
        return 0;
    }

    return 1
         + countNodes(node.left)
         + countNodes(node.right);
}

Each non-null node contributes exactly 1.

44. Tracing countNodes

Consider:

      10
     /  \
    5    20

Calling:

countNodes(root)

conceptually becomes:

1
+ countNodes(node containing 5)
+ countNodes(node containing 20)

Each leaf contributes:

1 + 0 + 0

So:

count(5)  = 1
count(20) = 1

and:

count(10) = 1 + 1 + 1 = 3

45. Counting leaves

A leaf has no children:

node.left == null && node.right == null

Therefore:

public static int countLeaves(TreeNode node) {
    if (node == null) {
        return 0;
    }

    if (node.left == null && node.right == null) {
        return 1;
    }

    return countLeaves(node.left)
         + countLeaves(node.right);
}

Notice that the current node contributes 1 only if it is actually a leaf.

46. Summing all values

Suppose nodes contain integers.

The sum is:

current value
+ sum of left subtree
+ sum of right subtree

Java:

public static int sum(TreeNode node) {
    if (node == null) {
        return 0;
    }

    return node.value
         + sum(node.left)
         + sum(node.right);
}

For:

      10
     /  \
    5    20

the answer is:

10 + 5 + 20 = 35

47. Calculating tree height recursively

Using our convention:

empty tree height = -1
leaf height = 0

the recursive implementation is:

public static int height(TreeNode node) {
    if (node == null) {
        return -1;
    }

    int leftHeight = height(node.left);
    int rightHeight = height(node.right);

    return 1 + Math.max(leftHeight, rightHeight);
}

Why do we take the maximum?

Because height is defined using the longest root-to-leaf path.

48. Why is empty-tree height -1?

Suppose the node is a leaf:

  10
 /  \
null null

Both recursive calls return:

-1

So:

1 + Math.max(-1, -1)

equals:

0

Therefore the leaf has height 0, matching our edge-based definition.

If a course instead defines leaf height as 1, the empty-tree base case can be 0.

Neither convention is inherently wrong.

Consistency matters.

49. Recursive calls do not copy the tree

Suppose we write:

inorder(node.left);

Java does not create an entire copy of the left subtree.

It passes a reference to another TreeNode.

All recursive calls operate on the same collection of node objects.

For example:

        root
         |
         v
        10
       /  \
      5    20

Calling:

inorder(root.left);

passes the reference to the node containing 5.

It does not duplicate any nodes.

50. Recursion and the call stack

Although recursion does not copy the tree, every active recursive method call requires a stack frame.

For example, when traversing a deep path:

50
/
30
/
20
/
10

the call stack may temporarily contain:

inorder(50)
inorder(30)
inorder(20)
inorder(10)

Therefore recursive tree algorithms generally use:

O(h)

additional call-stack space, where h is the tree height.

For a balanced tree:

h ≈ log n

For a highly unbalanced tree:

h ≈ n

This is another way tree shape affects an algorithm.

51. Full tree traversal complexity

A traversal visits every node once.

If the tree has n nodes:

preorder  = O(n)
inorder   = O(n)
postorder = O(n)

Balancing does not reduce this to O(log n).

Why?

Because if the goal is to visit every element, all n nodes must still be processed.

Balanced trees help when an algorithm can eliminate subtrees, as in BST search.

They do not magically make a full traversal sublinear.

52. Finding the minimum in a BST

Because smaller values appear to the left:

The minimum value in a BST is found by following left-child references until no left child exists.

Example:

           50
         /    \
       30      70
      /
    20

The minimum is:

20

Implementation:

public static int findMin(TreeNode root) {
    if (root == null) {
        throw new IllegalArgumentException("Tree is empty");
    }

    TreeNode current = root;

    while (current.left != null) {
        current = current.left;
    }

    return current.value;
}

53. Finding the maximum in a BST

Similarly:

The maximum value is the rightmost node.

public static int findMax(TreeNode root) {
    if (root == null) {
        throw new IllegalArgumentException("Tree is empty");
    }

    TreeNode current = root;

    while (current.right != null) {
        current = current.right;
    }

    return current.value;
}

54. BST deletion

Deleting from a BST is more complicated than searching or insertion because we must preserve the ordering property.

There are three major cases.

For CSC 500, understanding these cases is more important than memorizing a deletion implementation.

55. Deletion Case 1: Leaf node

Suppose:

      30
     /  \
    20   40

Delete 20.

Since 20 has no children, we can simply disconnect it:

      30
        \
         40

Conceptually, the parent's reference becomes:

null

56. Deletion Case 2: One child

Suppose:

      30
        \
         40
           \
            50

Delete 40.

Node 40 has one child: 50.

Its parent can connect directly to that child:

      30
        \
         50

The child takes the deleted node's position in the structure.

57. Deletion Case 3: Two children

Suppose:

        50
       /  \
      30   70
          / \
         60 80

Delete 70.

We cannot simply remove it because doing so would disconnect two subtrees.

Instead, we choose a replacement that preserves BST ordering.

Two standard choices are:

  • the inorder predecessor,
  • the inorder successor.

Inorder predecessor

The largest value in the node's left subtree.

Inorder successor

The smallest value in the node's right subtree.

For node 70:

left subtree maximum  = 60
right subtree minimum = 80

Either may be used by an appropriate deletion algorithm.

58. Optional complete recursive BST deletion

You do not need to memorize this method, but studying it shows how the three cases translate into code.

private TreeNode remove(TreeNode node, int value) {
    if (node == null) {
        return null;
    }

    if (value < node.value) {
        node.left = remove(node.left, value);
    } else if (value > node.value) {
        node.right = remove(node.right, value);
    } else {
        // Found the node to delete.

        // Case 1 or part of Case 2:
        if (node.left == null) {
            return node.right;
        }

        // Case 2:
        if (node.right == null) {
            return node.left;
        }

        // Case 3: two children.
        int successor = findMin(node.right);
        node.value = successor;
        node.right = remove(node.right, successor);
    }

    return node;
}

The difficult case is:

int successor = findMin(node.right);
node.value = successor;
node.right = remove(node.right, successor);

We replace the current value with its inorder successor, then remove the original successor node from the right subtree.

59. Encapsulating a BST in a class

Instead of allowing other code to manipulate TreeNode objects directly, we can create a BinarySearchTree class.

public class BinarySearchTree {

    private TreeNode root;

    private static class TreeNode {
        int value;
        TreeNode left;
        TreeNode right;

        TreeNode(int value) {
            this.value = value;
        }
    }

    public BinarySearchTree() {
        root = null;
    }
}

Notice that root is private:

private TreeNode root;

And TreeNode itself can also be hidden inside the class.

This means clients do not need to understand the internal representation.

They can work with operations such as:

add()
contains()
size()
printInOrder()

This is encapsulation.

60. A more complete BST implementation

public class BinarySearchTree {

    private static class TreeNode {
        int value;
        TreeNode left;
        TreeNode right;

        TreeNode(int value) {
            this.value = value;
        }
    }

    private TreeNode root;

    public void add(int value) {
        root = add(root, value);
    }

    private TreeNode add(TreeNode node, int value) {
        if (node == null) {
            return new TreeNode(value);
        }

        if (value < node.value) {
            node.left = add(node.left, value);
        } else if (value > node.value) {
            node.right = add(node.right, value);
        }

        return node;
    }

    public boolean contains(int value) {
        return contains(root, value);
    }

    private boolean contains(TreeNode node, int value) {
        if (node == null) {
            return false;
        }

        if (value == node.value) {
            return true;
        }

        if (value < node.value) {
            return contains(node.left, value);
        }

        return contains(node.right, value);
    }

    public int size() {
        return size(root);
    }

    private int size(TreeNode node) {
        if (node == null) {
            return 0;
        }

        return 1 + size(node.left) + size(node.right);
    }

    public int height() {
        return height(root);
    }

    private int height(TreeNode node) {
        if (node == null) {
            return -1;
        }

        return 1 + Math.max(
            height(node.left),
            height(node.right)
        );
    }

    public void printInOrder() {
        printInOrder(root);
    }

    private void printInOrder(TreeNode node) {
        if (node == null) {
            return;
        }

        printInOrder(node.left);
        System.out.println(node.value);
        printInOrder(node.right);
    }

    public void printPreOrder() {
        printPreOrder(root);
    }

    private void printPreOrder(TreeNode node) {
        if (node == null) {
            return;
        }

        System.out.println(node.value);
        printPreOrder(node.left);
        printPreOrder(node.right);
    }

    public void printPostOrder() {
        printPostOrder(root);
    }

    private void printPostOrder(TreeNode node) {
        if (node == null) {
            return;
        }

        printPostOrder(node.left);
        printPostOrder(node.right);
        System.out.println(node.value);
    }
}

62. Abstract data types revisited

Recall the distinction between an abstract data type (ADT) and an implementation.

An ADT describes:

What operations should be available?

An implementation describes:

How are those operations performed internally?

For example, a set ADT might support:

add
remove
contains
size

Possible implementations include:

  • a list,
  • a hash table,
  • a balanced search tree.

A user of the set abstraction may not need to know which representation is being used.

Likewise, a priority queue describes operations and behavior; a heap is a common implementation technique.

This separation between what and how is a major idea in computer science.

63. Java's tree-based collections

Java provides tree-based collection classes such as:

TreeSet
TreeMap

They provide ordered collection behavior without requiring us to manually implement tree nodes.

64. TreeSet

A TreeSet stores unique values and maintains them in sorted order.

import java.util.TreeSet;

public class Main {
    public static void main(String[] args) {
        TreeSet<Integer> numbers = new TreeSet<>();

        numbers.add(50);
        numbers.add(20);
        numbers.add(70);
        numbers.add(30);

        System.out.println(numbers);
    }
}

Output:

[20, 30, 50, 70]

A TreeSet combines two important ideas:

set semantics
+
sorted ordering

Compare this with HashSet, where the main goal is fast membership testing rather than sorted iteration.

65. TreeMap

A TreeMap stores key-value pairs while keeping its keys sorted.

import java.util.TreeMap;

public class Main {
    public static void main(String[] args) {
        TreeMap<String, Integer> scores = new TreeMap<>();

        scores.put("Charlie", 88);
        scores.put("Alice", 95);
        scores.put("Bob", 91);

        System.out.println(scores);

}

Output will list the keys in sorted order:

{Alice=95, Bob=91, Charlie=88}

Compare:

HashMap  -> optimized for fast average key lookup
TreeMap  -> keeps keys ordered

Again, the best choice depends on the operations required by the problem.

66. Self-balancing trees

Our simple BST does not automatically keep itself balanced.

More advanced data structures solve this problem.

Examples include:

  • AVL trees,
  • red-black trees,
  • B-trees,
  • B+ trees.

You do not need to implement these in CSC 500.

The important idea is:

Some trees automatically reorganize themselves to maintain properties that keep important operations efficient.

Java's tree-based sorted collections use self-balancing techniques internally.

At this point, understanding why balancing matters is more important than understanding rotation algorithms.

67. Another tree structure: The heap

A heap is another tree-based data structure.

But a heap follows a very different ordering rule from a BST.

A common form is a min-heap.

In a min-heap:

Every parent is less than or equal to its children.

Example:

          10
        /    \
      20      15
     /  \    /
   40   30  25

We can verify:

10 <= 20
10 <= 15

20 <= 40
20 <= 30

15 <= 25

This satisfies the min-heap ordering property.

68. A heap is not a BST

Consider:

          10
        /    \
      20      15
     /  \
   40    30

This may be a valid min-heap.

But it is not a BST.

Why?

The two structures enforce different relationships.

BST rule

all left subtree values < node
all right subtree values > node

Min-heap rule

parent <= children

A heap only guarantees ordering between a parent and its children.

It does not fully order the left and right subtrees relative to each other.

69. Min-heaps and max-heaps

Min-heap

In a min-heap:

parent <= children

Therefore the smallest element is always at the root.

Example:

          5
        /   \
      10     8
     / \
   20   15

Minimum:

5

Max-heap

A max-heap reverses the property:

parent >= children

Therefore the largest element appears at the root.

70. What problem does a heap solve?

A heap is especially useful when we repeatedly need to answer questions such as:

What is the smallest item?

or:

What is the highest-priority item?

A heap does not attempt to completely sort every element.

It maintains only enough ordering to make priority operations efficient.

That distinction is extremely important.

71. Priority queues

A priority queue is an abstract data type in which elements are processed according to priority.

A normal queue uses:

FIFO
First In, First Out

Example:

A arrives
B arrives
C arrives

processing order:
A, B, C

A priority queue instead asks:

Which element currently has the highest priority?

Insertion order may not determine removal order.

72. Priority queue example

Suppose a scheduler contains jobs:

Job A: priority 4
Job B: priority 1
Job C: priority 3
Job D: priority 2

If smaller numbers represent higher priority, processing could occur as:

Job B
Job D
Job C
Job A

The exact interpretation of "priority" depends on the application.

Examples include:

  • task scheduling,
  • simulations,
  • event processing,
  • CPU scheduling,
  • shortest-path algorithms,
  • emergency-service systems,
  • best-first search.

73. Heap vs. priority queue

These terms describe different concepts.

A priority queue is an ADT:

What behavior do we want?

A heap is a data structure:

How might we implement that behavior efficiently?

A heap is a common implementation of a priority queue.

This is another example of the distinction between interface/behavior and implementation.

74. Java PriorityQueue

Java provides:

java.util.PriorityQueue

For numbers, Java's default PriorityQueue behaves as a min-priority queue.

Example:

import java.util.PriorityQueue;

40, 10, 30, 20

10, 20, 30, 40

75. Important PriorityQueue operations

Common methods include:

10

10

76. remove() vs. poll()

When the queue is empty:

pq.remove();

throws an exception.

By contrast:

pq.poll();

returns:

null

for an empty queue.

Similarly:

pq.element();

throws an exception if empty, whereas:

pq.peek();

returns null.

For many programs, peek() and poll() are convenient because they allow emptiness to be handled explicitly.

87. Common mistake: Binary tree = BST

Incorrect:

Every binary tree is a BST.

Correct:

Every BST is a binary tree, but not every binary tree is a BST.

Example:

       10
      /  \
     20   5

This is a binary tree because no node has more than two children.

It is not a BST because its ordering is wrong.

88. Common mistake: Checking only immediate children

Consider:

        10
       /
      5
       \
        12

Checking only:

5 < 10
12 > 5

is insufficient.

12 lies in the entire left subtree of 10.

Therefore it must satisfy:

12 < 10

which it does not.

BST constraints apply to entire subtrees.

89. Common mistake: Assuming inorder always sorts

Inorder traversal of:

       10
      /  \
     20   5

produces:

20 10 5

which is not sorted.

Therefore the statement is not:

Inorder traversal always produces sorted values.

The correct statement is:

Inorder traversal of a valid BST produces sorted values.

90. Common mistake: BST search visits both subtrees

A normal recursive traversal often performs:

visit(node.left);
visit(node.right);

BST search does not.

Instead:

if (target < node.value) {
    return contains(node.left, target);
} else {
    return contains(node.right, target);
}

The ordering property tells us which subtree could contain the target.

Searching both would waste the main advantage of a BST.

91. Common mistake: Recursive calls copy subtrees

This:

countNodes(node.left)

does not duplicate the left subtree.

It passes a reference to another node object.

The same tree remains in memory.

92. Common mistake: Forgetting the base case

This method is incorrect:

public static int count(TreeNode node) {
    return 1 + count(node.left) + count(node.right);
}

Eventually:

node == null

but the method continues trying to access:

node.left

leading to a NullPointerException.

Correct:

public static int count(TreeNode node) {
    if (node == null) {
        return 0;
    }

    return 1 + count(node.left) + count(node.right);
}

93. Common mistake: Thinking BSTs are always O(log n)

Incorrect:

BST search = O(log n)

with no qualification.

Correct:

balanced BST search ≈ O(log n)
worst-case unbalanced BST search = O(n)

Tree shape matters.

94. Common mistake: Confusing BSTs and heaps

A BST provides global subtree ordering:

left < node < right

A min-heap provides local parent-child ordering:

parent <= children

Therefore:

  • a BST is useful for arbitrary searches and sorted iteration,
  • a heap is useful for repeatedly obtaining the minimum or maximum.

95. Common mistake: Assuming a PriorityQueue is fully sorted internally

Suppose:

PriorityQueue<Integer> pq = new PriorityQueue<>();

pq.add(40);
pq.add(10);
pq.add(30);
pq.add(20);

The priority queue guarantees that repeated removal produces:

10
20
30
40

It does not mean that every internal position behaves like a fully sorted array.

The heap maintains only the ordering needed for priority operations.

Do not rely on arbitrary iteration over a PriorityQueue to produce sorted order.

96. Determining whether a tree is a valid BST

For simple examples, carefully inspect each subtree.

A more rigorous way to think is to give every node an allowed range.

Suppose the root is:

10

Initially it may occupy:

(-infinity, +infinity)

Its left subtree must then occupy:

(-infinity, 10)

Its right subtree must occupy:

(10, +infinity)

If the left child is 5, then 5's right subtree must satisfy both:

value > 5

and:

value < 10

so the valid range is:

(5, 10)

This range-based reasoning avoids the common error of checking only immediate parent-child relationships.

97. Optional recursive BST validation

A more advanced implementation follows that range idea:

public static boolean isValidBST(
        TreeNode node,
        long min,
        long max) {

    if (node == null) {
        return true;
    }

    if (node.value <= min || node.value >= max) {
        return false;
    }

    return isValidBST(node.left, min, node.value)
        && isValidBST(node.right, node.value, max);
}

Initial call:

boolean valid = isValidBST(
    root,
    Long.MIN_VALUE,
    Long.MAX_VALUE
);

You do not need to memorize this code.

The important concept is that each position in a BST has constraints inherited from all of its ancestors.

102. Another recursive reasoning problem

public static int mystery(TreeNode node) {
    if (node == null) {
        return 0;
    }

    return node.value
         + mystery(node.left)
         + mystery(node.right);
}

Now every node contributes:

node.value

Therefore the function computes:

the sum of all values in the tree.

When reading recursive tree code, ask:

What does the base case mean?
What does the current node contribute?
What do the left and right recursive calls compute?
How are those answers combined?

109. Frequently asked questions

FAQ 1: Is every binary tree a BST?

No.

A binary tree only requires at most two children per node.

A BST additionally requires ordered subtrees.

FAQ 2: Is every BST a binary tree?

Yes.

A BST is a particular kind of binary tree.

FAQ 3: Does the BST rule apply only to immediate children?

No.

It applies to every value in the entire left and right subtrees.

FAQ 4: Why is recursion common in trees?

Because each subtree is itself a tree.

Recursive algorithms therefore apply the same operation to smaller versions of the original structure.

FAQ 5: Why do tree methods often call themselves twice?

A binary node may have two subtrees:

node.left
node.right

A full-tree algorithm may need to solve the problem for both.

FAQ 6: Why does BST search call itself only once?

Because BST ordering tells us which subtree may contain the target.

The other subtree can be eliminated.

FAQ 7: Does recursion copy the subtree?

No.

Java passes a reference to a node.

The node objects are not duplicated.

FAQ 8: Why does recursive insertion return a node?

Because when an empty position is found, a new subtree root is created.

The returned reference allows the parent to connect to that new subtree.

FAQ 9: Why does inorder traversal produce sorted output?

Only for a valid BST.

The traversal processes:

smaller values
current value
larger values

because of the BST property.

FAQ 10: Are BST operations always O(log n)?

No.

They are approximately O(log n) when tree height is logarithmic.

A badly unbalanced BST can require O(n) operations.

FAQ 11: Why does insertion order matter?

Insertion order determines the shape of a simple BST.

Sorted insertion can produce a chain-like, inefficient tree.

FAQ 12: What is the difference between depth and height?

depth:
distance from root to node

height:
longest distance from node to a leaf

FAQ 13: Why is the empty-tree height -1?

With an edge-based height definition, this causes a leaf to have height 0:

1 + max(-1, -1) = 0

FAQ 14: Are heaps sorted trees?

No.

A heap has only enough ordering to guarantee that its highest-priority element appears at the root.

FAQ 15: Is a heap the same thing as a priority queue?

No.

A priority queue is an abstract behavior.

A heap is a common implementation of that behavior.

FAQ 16: Why not use a BST instead of a heap?

It depends on the required operations.

Use a BST when arbitrary ordered search is important.

Use a heap when repeated access to the highest- or lowest-priority item is most important.

FAQ 17: Is Java's PriorityQueue a min-queue or max-queue?

For values using natural ordering, it is a min-priority queue by default.

The smallest element is returned first.

FAQ 18: Does iterating through a PriorityQueue produce sorted values?

Do not assume so.

Priority order is guaranteed for priority-removal operations, not arbitrary iteration through the internal structure.

FAQ 19: When should I use TreeSet instead of HashSet?

Use TreeSet when sorted order matters.

Use HashSet when fast average membership testing matters and ordering is unnecessary.

FAQ 20: When should I use TreeMap instead of HashMap?

Use TreeMap when sorted keys matter.

Use HashMap when fast average key lookup is the primary concern.

112. Key takeaways

The most important ideas from Week 14 are:

1. Trees represent hierarchical relationships.

They allow data to branch instead of being stored only in a linear sequence.

2. Trees are naturally recursive.

Every subtree is itself a tree.

That observation explains why recursion works so naturally for traversal, counting, height calculations, insertion, searching, and deletion.

3. A binary tree is not necessarily a BST.

A binary tree only limits nodes to at most two children.

A BST adds an ordering property.

4. The BST property applies to entire subtrees.

left subtree < node < right subtree

Do not check only immediate children.

5. BST search eliminates possibilities.

A comparison at each node tells us which subtree can contain the target.

6. Inorder traversal of a BST produces sorted values.

Remember:

LEFT NODE RIGHT

7. Tree height strongly affects BST efficiency.

A balanced tree may provide:

O(log n)

search and insertion.

A highly unbalanced tree may degrade to:

O(n)

8. A heap and BST solve different problems.

A BST supports ordered searching.

A heap efficiently exposes a minimum or maximum priority element.

9. A priority queue is an ADT.

A heap is a common way to implement it.

Java provides:

PriorityQueue

for priority-based processing.

10. Data structures involve tradeoffs.

There is no universally best structure.

Always ask:

What operations does this program need most frequently, and which data structure supports those operations appropriately?

That shift—from memorizing structures to reasoning about their tradeoffs—is one of the central goals of studying data structures.
