1. From statements to programs

During the first three weeks, we learned the fundamental statements from which programs are built:

  • variables and expressions,
  • input and output,
  • if and else,
  • Boolean expressions,
  • while, for, and do-while loops.

These tools allow us to solve increasingly interesting problems.

For example, we could write a program that reads three exam scores, computes a weighted average, determines a letter grade, and prints the result:

import java.util.Scanner;

public class GradeCalculator {
    public static void main(String[] args) {
        Scanner input = new Scanner(System.in);

        System.out.print("Enter exam 1 score: ");
        double exam1 = input.nextDouble();

        System.out.print("Enter exam 2 score: ");
        double exam2 = input.nextDouble();

        System.out.print("Enter final exam score: ");
        double finalExam = input.nextDouble();

        double average =
                exam1 * 0.30 +
                exam2 * 0.30 +
                finalExam * 0.40;

        if (average >= 90) {
            System.out.println("Grade: A");
        } else if (average >= 80) {
            System.out.println("Grade: B");
        } else if (average >= 70) {
            System.out.println("Grade: C");
        } else if (average >= 60) {
            System.out.println("Grade: D");
        } else {
            System.out.println("Grade: F");
        }
    }
}

There is nothing fundamentally wrong with this program.

But notice that everything happens inside main.

Imagine that this program eventually needs to:

  • validate every score,
  • calculate several kinds of averages,
  • determine a letter grade,
  • determine pass/fail status,
  • print a formatted report,
  • process many students,
  • calculate statistics,
  • display menus.

A program containing hundreds of statements inside a single main method becomes increasingly difficult to understand.

This motivates one of the most important ideas in programming:

Program decomposition is the process of breaking a large problem into smaller, manageable subproblems.

In Java, one of our main tools for decomposition is the method.

2. What is a method?

A method is a named block of code that performs a particular task.

For example:

public static void printGreeting() {
    System.out.println("Welcome to CSC 500!");
}

This method has the name:

printGreeting

Its job is to print a greeting.

We execute it by calling it:

printGreeting();

A complete program might be:

public class GreetingExample {

    public static void printGreeting() {
        System.out.println("Welcome to CSC 500!");
        System.out.println("Let's learn Java.");
    }

    public static void main(String[] args) {
        printGreeting();
    }
}

Output:

Welcome to CSC 500!
Let's learn Java.

The important execution idea is:

main begins
    |
    | calls printGreeting()
    v
printGreeting executes
    |
    | finishes
    v
execution returns to main

When a method finishes, Java resumes execution at the statement immediately following the method call.

3. You have already been using methods

Although this week is our first systematic study of methods, you have already called many methods.

For example:

System.out.println("Hello");

println is a method.

Math.sqrt(25);

sqrt is a method.

input.nextInt();

nextInt is a method.

The important transition this week is:

Until now, we have mostly called methods written by other programmers.

Now we begin designing and writing our own methods.

4. Why methods matter

Methods are not merely a Java syntax feature. They are a major tool for organizing thought.

They provide several important benefits.

4.1 Decomposition

A large task can be broken into smaller tasks.

Instead of thinking:

Write the entire grade-processing program.

we can think:

read score
calculate average
determine grade
print report

Each smaller task can become a method.

4.2 Readability

Compare:

double subtotal = price * quantity;
double tax = subtotal * 0.06;
double total = subtotal + tax;
System.out.printf("$%.2f%n", total);

with:

double total = calculateTotal(price, quantity);
printTotal(total);

The second version communicates the meaning of the operations.

Good method names allow programs to read almost like a description of the solution.

4.3 Reuse

Suppose tax is calculated with:

double tax = amount * 0.06;

If this calculation appears ten times, we could repeat the expression ten times.

A better approach is:

public static double calculateTax(double amount) {
    return amount * 0.06;
}

Then:

double tax1 = calculateTax(100.0);
double tax2 = calculateTax(250.0);
double tax3 = calculateTax(37.50);

The calculation is defined once and reused.

4.4 Testing

A small method can often be tested independently.

Suppose:

public static int square(int number) {
    return number * number;
}

We can test several inputs:

System.out.println(square(3));   // expected: 9
System.out.println(square(0));   // expected: 0
System.out.println(square(-4));  // expected: 16

If these tests work, we gain confidence in that particular piece of the program.

4.5 Debugging

Suppose a 500-line program gives an incorrect result.

If the program is one giant method, we may have to search through hundreds of statements.

If it is decomposed into:

readScore
calculateAverage
determineGrade
printReport

we can ask more focused questions:

Are the scores being read correctly?

Does calculateAverage return the correct value?

Does determineGrade use the correct boundaries?

Is printReport displaying the correct information?

Methods help us isolate problems.

4.6 Abstraction

Consider:

double root = Math.sqrt(25);

To use Math.sqrt, we do not need to know the internal algorithm Java uses to calculate square roots.

We only need to know:

What information does sqrt need?
What result does sqrt produce?

Our own methods can provide the same kind of abstraction.

For example:

double average = calculateAverage(score1, score2, score3);

Someone reading that statement understands its purpose without immediately needing to study the formula.

Methods therefore allow us to give names to ideas.

5. Anatomy of a Java method

Consider:

public static int square(int number) {
    int result = number * number;
    return result;
}

We can view the method as:

public static int square(int number)
│      │     │   │       │
│      │     │   │       └── parameter
│      │     │   └────────── method name
│      │     └────────────── return type
│      └──────────────────── static modifier
└─────────────────────────── access modifier

The body is:

{
    int result = number * number;
    return result;
}

For this week, concentrate primarily on:

  • the method name,
  • parameter list,
  • return type,
  • method body,
  • return statement.

6. Why are we writing public static?

Our methods this week will commonly look like:

public static int square(int number) {
    return number * number;
}

For now, we will use public static so that methods can be called directly from the static main method:

public static void main(String[] args) {
    int result = square(5);
}

The deeper meaning of class-level versus object-level methods will become more important when we study classes and objects.

For Week 4, the useful pattern is:

public static returnType methodName(parameters) {
    // statements
}

7. Method names

Method names should describe what the method does.

Good examples include:

calculateAverage
calculateTax
printMenu
readScore
findMaximum
isValidScore
convertToCelsius
canRegister

Poor names include:

doStuff
thing
method1
abc
work
process

A method name is an opportunity to communicate meaning.

For Java, method names conventionally use lower camel case:

calculateAverage
findLargestValue
printStudentReport

The first word begins with a lowercase letter, while later words begin with uppercase letters.

8. Method definitions and method calls

These are two different concepts.

Method definition

A method definition describes what the method does.

public static int square(int number) {
    return number * number;
}

This defines square.

Method call

A method call asks Java to execute the method.

square(5);

or:

int result = square(5);

A useful distinction is:

definition → describes the operation

call       → performs the operation

9. Methods with no parameters

Some methods do not need any information from the caller.

Example:

public static void printSeparator() {
    System.out.println("--------------------");
}

The empty parentheses:

()

mean that the method receives no parameters.

We call it with:

printSeparator();

Example:

public static void main(String[] args) {
    printSeparator();
    System.out.println("CSC 500");
    printSeparator();
}

Output:

--------------------
CSC 500
--------------------

The same method can be called repeatedly.

10. void methods

A method that does not return a value uses the return type:

void

Example:

public static void printWelcome() {
    System.out.println("Welcome!");
}

The method performs an action, but it does not send a value back to the caller.

A common use of void methods is output:

public static void printMenu() {
    System.out.println("1. Deposit");
    System.out.println("2. Withdraw");
    System.out.println("3. Exit");
}

Call:

printMenu();

Another example:

public static void printStars(int count) {
    for (int i = 0; i < count; i++) {
        System.out.print("*");
    }

    System.out.println();
}

Calls:

printStars(3);
printStars(8);

Output:

***
********

11. Parameters: Giving information to a method

Many methods need information in order to perform their tasks.

That information is supplied using parameters.

Consider:

public static void greet(String name) {
    System.out.println("Hello, " + name + "!");
}

The method has one parameter:

String name

That parameter says:

"To perform my task, give me a String."

Now we can write:

greet("Maria");
greet("James");
greet("Aisha");

Output:

Hello, Maria!
Hello, James!
Hello, Aisha!

Without a parameter, we might need separate methods:

greetMaria();
greetJames();
greetAisha();

That would be unnecessarily repetitive.

Parameters make a method more general.

12. Parameters vs. arguments

These words are related but have different meanings.

Consider the definition:

public static int square(int number) {
    return number * number;
}

Here:

number

is a parameter.

Now consider the call:

square(5);

Here:

5

is an argument.

The easiest rule to remember is:

Parameters appear in method definitions. Arguments appear in method calls.

Another example:

public static void greet(String name) {
    System.out.println("Hello, " + name);
}

name is the parameter.

greet("Elena");

"Elena" is the argument.

13. Arguments can be expressions

An argument does not have to be a literal value.

Suppose:

public static int doubleValue(int number) {
    return number * 2;
}

We can call:

doubleValue(7);

But we can also write:

int age = 20;
int result = doubleValue(age + 1);

Java first evaluates:

age + 1

which produces:

21

Then it effectively performs:

doubleValue(21)

which returns:

42

Therefore:

result == 42

14. Multiple parameters

A method may have several parameters.

Example:

public static int multiply(int a, int b) {
    return a * b;
}

Call:

int result = multiply(4, 6);

Conceptually:

a receives 4
b receives 6

Then:

a * b
4 * 6
24

So result becomes 24.

15. Argument order matters

Arguments correspond to parameters by position.

Consider:

public static double divide(double numerator,
                            double denominator) {
    return numerator / denominator;
}

These are not equivalent:

divide(10, 2);   // 5.0
divide(2, 10);   // 0.2

The first call means:

numerator   = 10
denominator = 2

The second means:

numerator   = 2
denominator = 10

The names of variables in the caller are irrelevant to this matching.

For example:

double x = 10;
double y = 2;

double answer = divide(x, y);

Java matches:

x → numerator
y → denominator

because of their positions.

16. Number and types of arguments

Suppose a method is defined as:

public static void printPerson(String name, int age) {
    System.out.println(name + " is " + age + " years old.");
}

Correct:

printPerson("Aisha", 28);

Incorrect:

printPerson(28, "Aisha");

The argument types are in the wrong positions.

Also incorrect:

printPerson("Aisha");

There are too few arguments.

Also incorrect:

printPerson("Aisha", 28, 100);

There are too many arguments.

When debugging a method call, check:

  1. method name,
  2. number of arguments,
  3. argument types,
  4. argument order.

17. Methods that return values

Many methods compute an answer that the caller needs.

Example:

public static int square(int number) {
    return number * number;
}

The return type:

int

means:

This method produces an integer value.

If we call:

square(5)

the call produces:

25

We can save that value:

int result = square(5);

We can print it:

System.out.println(square(5));

We can use it in an expression:

int total = square(3) + square(4);

The expression can be understood as:

square(3) + square(4)

9 + 16

25

Therefore:

total == 25

18. Return types

Every method declares the type of result it produces.

Examples:

public static int getAge() {
    return 25;
}

returns an int.

public static double calculateAverage(
        double a,
        double b) {

    return (a + b) / 2.0;
}

returns a double.

public static boolean isPassing(double score) {
    return score >= 60;
}

returns a boolean.

public static String getMessage() {
    return "Welcome";
}

returns a String.

public static char determineGrade(double average) {
    return 'A';
}

returns a char.

And:

public static void printMessage() {
    System.out.println("Hello");
}

returns no value.

The return type is essentially a promise made by the method.

If a method says:

public static int ...

then it must return an integer-compatible value.

This is invalid:

public static int getNumber() {
    return "five";
}

A String is not an int.

19. The return statement

A return statement has two important effects:

  1. it sends a value back to the caller, and
  2. it immediately ends the current method.

Consider:

public static double calculateCircleArea(double radius) {
    double area = Math.PI * radius * radius;
    return area;
}

Call:

double result = calculateCircleArea(5.0);

Conceptually:

radius = 5.0

area = π × 5.0 × 5.0

return area

result receives the returned value

20. Returning an expression directly

A temporary variable is not always required.

This:

public static double calculateCircleArea(double radius) {
    double area = Math.PI * radius * radius;
    return area;
}

can also be written as:

public static double calculateCircleArea(double radius) {
    return Math.PI * radius * radius;
}

Both are correct.

Choose the version that makes the method easiest to understand.

Temporary variables can sometimes improve readability:

public static double calculateTotal(
        double price,
        int quantity,
        double taxRate) {

    double subtotal = price * quantity;
    double tax = subtotal * taxRate;
    double total = subtotal + tax;

    return total;
}

Even though this could be written as one expression, the intermediate names may make the computation clearer.

21. A method call is an expression when it returns a value

Suppose:

public static int cube(int n) {
    return n * n * n;
}

Then:

cube(4)

is an expression whose value is:

64

That means we can use it anywhere an int expression would be legal.

For example:

int x = cube(4);
System.out.println(cube(4));
int total = 10 + cube(3);
if (cube(2) > 5) {
    System.out.println("Large enough");
}

This is one reason value-returning methods are powerful: they compose naturally with the rest of the language.

22. Printing is not returning

This distinction is extremely important.

Consider:

public static void square(int n) {
    System.out.println(n * n);
}

Calling:

square(5);

prints:

25

But the caller does not receive the number 25.

Therefore this is invalid:

int result = square(5);

square has return type void.

Now compare:

public static int square(int n) {
    return n * n;
}

Now:

int result = square(5);

is valid.

The caller receives 25.

The difference is:

PrintingReturning
Sends information to the consoleSends information to the caller
Primarily an output actionProduces a value
Usually a side effectCan participate in expressions
Caller cannot directly reuse printed text as the method's resultCaller decides what to do with the result

A useful design principle is:

If a method computes a value that other code may need, usually return the value rather than printing it inside the calculation method.

For example, prefer:

public static double calculateTax(double amount) {
    return amount * 0.06;
}

Then the caller can choose to:

double tax = calculateTax(100);

or:

System.out.println(calculateTax(100));

or:

double total = 100 + calculateTax(100);

The calculation method remains flexible.

23. void vs. value-returning methods

A useful design question is:

Does the caller need an answer from this method?

If yes, the method should usually return a value.

Examples:

calculateAverage(...)
findMaximum(...)
isValidScore(...)
determineGrade(...)
convertToCelsius(...)

These naturally produce results.

If the method primarily performs an action, void may be appropriate.

Examples:

printMenu(...)
displayReport(...)
printSeparator(...)

A useful mental distinction is:

questions / calculations → usually return something

commands / actions        → often void

This is a guideline rather than an absolute rule.

24. Boolean methods

Methods returning boolean are especially useful because they can give names to conditions.

Suppose we repeatedly write:

score >= 0 && score <= 100

We could instead define:

public static boolean isValidScore(double score) {
    return score >= 0 && score <= 100;
}

Then:

if (isValidScore(score)) {
    System.out.println("Valid score.");
} else {
    System.out.println("Invalid score.");
}

The second version communicates the idea directly:

if the score is valid

rather than forcing the reader to interpret the Boolean expression every time.

Boolean method names often resemble questions:

isEven
isValid
isPassing
hasPermission
canRegister
containsValue

Example:

public static boolean isEven(int number) {
    return number % 2 == 0;
}

Usage:

if (isEven(10)) {
    System.out.println("Even");
}

25. Returning from conditional logic

Suppose we need the larger of two integers.

public static int max(int a, int b) {
    if (a > b) {
        return a;
    } else {
        return b;
    }
}

Every possible execution path returns an integer.

We can also write:

public static int max(int a, int b) {
    if (a > b) {
        return a;
    }

    return b;
}

Why is the else unnecessary?

Because if:

return a;

executes, the method ends immediately.

The later:

return b;

can only be reached when a > b was false.

26. Every required path must return a value

Consider:

public static int larger(int a, int b) {
    if (a > b) {
        return a;
    }
}

What happens when:

a <= b

?

The method reaches its closing brace without returning an int.

Java rejects this code.

A non-void method must return a compatible value along every possible path that can reach the end of the method.

Correct:

public static int larger(int a, int b) {
    if (a > b) {
        return a;
    } else {
        return b;
    }
}

27. Early return in a void method

A void method can use:

return;

without a value.

Example:

public static void printPositiveNumber(int n) {
    if (n <= 0) {
        return;
    }

    System.out.println(n);
}

If n <= 0, the method ends immediately.

If n > 0, execution continues to:

System.out.println(n);

This is sometimes called an early return.

Use it when it makes the logic clearer.

28. Methods can call other methods

Methods are not limited to being called from main.

A method can call another method.

Example:

public static double calculateSubtotal(
        double price,
        int quantity) {

    return price * quantity;
}

public static double calculateTax(double subtotal) {
    return subtotal * 0.06;
}

public static double calculateTotal(
        double price,
        int quantity) {

    double subtotal =
            calculateSubtotal(price, quantity);

    double tax =
            calculateTax(subtotal);

    return subtotal + tax;
}

Then:

double total = calculateTotal(20.0, 3);

Conceptually:

calculateTotal(20.0, 3)

    calculateSubtotal(20.0, 3)
        returns 60.0

    calculateTax(60.0)
        returns 3.6

    return 60.0 + 3.6

returns 63.6

Complex behavior is constructed from smaller operations.

29. Nested method calls

A method call can also be supplied as an argument to another method.

Suppose:

public static int doubleNumber(int x) {
    return x * 2;
}

public static int addFive(int x) {
    return x + 5;
}

Then:

int result = addFive(doubleNumber(4));

Evaluate from the inside outward.

First:

doubleNumber(4)

returns:

8

So the expression becomes:

addFive(8)

which returns:

13

Therefore:

result == 13

30. Another nested-call trace

Consider:

public static int square(int n) {
    return n * n;
}

public static int addSquares(int a, int b) {
    return square(a) + square(b);
}

Then:

int x = addSquares(2, 3);

Trace:

addSquares(2, 3)

    a = 2
    b = 3

    square(2)
        n = 2
        return 4

    square(3)
        n = 3
        return 9

    return 4 + 9

return 13

Therefore:

x = 13

This style of indentation is useful when tracing method calls manually.

31. Variable scope

A variable is not accessible everywhere in a Java program.

The region of the program in which a variable can be accessed is called its scope.

Consider:

public static void printNumber() {
    int number = 10;
    System.out.println(number);
}

The variable:

number

exists within printNumber.

This is invalid:

public static void main(String[] args) {
    printNumber();

    System.out.println(number);  // Error
}

Why?

Because number belongs to printNumber, not main.

Calling a method does not make its local variables visible to the caller.

32. Local variables

A variable declared inside a method is a local variable.

Example:

public static double calculateArea(double radius) {
    double area = Math.PI * radius * radius;
    return area;
}

Here:

area

is local to calculateArea.

The parameter:

radius

is also local to that method invocation.

Neither variable can simply be referenced from another method.

33. Parameters are local variables too

Consider:

public static int square(int number) {
    return number * number;
}

The parameter number belongs to a particular call of square.

Suppose:

int a = square(5);
int b = square(10);

Conceptually, the first call has:

number = 5

and the second call has:

number = 10

These are separate method invocations with separate local environments.

34. Different methods can use the same variable name

Because local variables belong to separate scopes, two methods may use identical variable names.

public static void methodA() {
    int x = 10;
    System.out.println(x);
}

public static void methodB() {
    int x = 20;
    System.out.println(x);
}

Calling:

methodA();
methodB();

prints:

10
20

The two variables named x are unrelated.

A useful mental model is:

methodA's x ≠ methodB's x

They happen to have the same name, but belong to different scopes.

35. Block scope

Scope can also be limited by blocks.

Consider:

if (score >= 60) {
    String message = "Pass";
    System.out.println(message);
}

The variable message was declared inside the if block.

After the closing brace:

System.out.println(message);

is invalid.

Similarly:

for (int i = 0; i < 10; i++) {
    System.out.println(i);
}

The loop variable i is scoped to the loop.

Afterward:

System.out.println(i);

is invalid.

This leads to a useful programming principle:

Keep variables in the smallest reasonable scope.

A variable should usually exist only where it is needed.

36. How do methods share information?

Suppose:

public static void main(String[] args) {
    int age = 25;
    printAge();
}

public static void printAge() {
    System.out.println(age);
}

This does not work because age belongs to main.

If printAge needs the age, pass it explicitly:

public static void main(String[] args) {
    int age = 25;
    printAge(age);
}

public static void printAge(int age) {
    System.out.println(age);
}

This is a fundamental pattern:

information going into a method
        ↓
     parameters

information coming out of a method
        ↓
   return values

Methods communicate through clearly defined inputs and outputs.

37. Data flow through methods

Consider:

double average =
        calculateAverage(exam1, exam2, exam3);

char grade =
        determineGrade(average);

printReport(average, grade);

The data flow is:

exam1
exam2 ─────► calculateAverage ─────► average
exam3

average ───► determineGrade ───────► grade

average ─┐
         ├──► printReport
grade ───┘

This is an extremely useful way to think about program design:

What information does each operation need, and what information does it produce?

38. Java uses pass-by-value

Java passes arguments to methods by value.

For primitive values, this is easiest to see directly.

Consider:

public static void changeNumber(int number) {
    number = 100;
}

Now:

public static void main(String[] args) {
    int x = 5;

    changeNumber(x);

    System.out.println(x);
}

What prints?

5

not:

100

Why?

Conceptually:

main:

x = 5

        copy the value 5
             |
             v

changeNumber:

number = 5

Inside the method:

number = 100;

changes the local parameter number.

It does not change x.

After the method returns:

main:
x = 5

still holds.

We will revisit parameter passing when we study objects and references. For now, remember that a primitive argument's value is copied into the parameter.

39. A common incorrect mental model

Students sometimes imagine this call:

changeNumber(x);

as though number becomes another name for x.

For primitive arguments, that is not the correct model.

Instead think:

x

5
│
│ copy
▼
number

5

After:

number = 100;

we have:

x       = 5
number  = 100

They are separate variables.

40. Returning a changed value

If you want a method to calculate a new value, return it.

For example:

public static int addOne(int number) {
    return number + 1;
}

Then:

int x = 5;
x = addOne(x);

Trace:

x = 5

addOne(5)
    number = 5
    return 6

x = 6

The original variable changes because main explicitly assigns the returned value back into x.

41. Execution flow between methods

Consider:

public static void methodA() {
    System.out.println("A1");
    methodB();
    System.out.println("A2");
}

public static void methodB() {
    System.out.println("B");
}

public static void main(String[] args) {
    System.out.println("Start");
    methodA();
    System.out.println("End");
}

Trace carefully.

main starts:

Start

Then:

methodA();

transfers execution into methodA.

It prints:

A1

Then methodA calls:

methodB();

methodB prints:

B

methodB finishes, so execution returns to methodA.

methodA continues:

A2

Then methodA finishes.

Execution returns to main, which prints:

End

Complete output:

Start
A1
B
A2
End

Notice that execution does not simply proceed down the source file from top to bottom.

Method calls change the execution path.

42. The call stack

Java must keep track of active method calls.

It does this using a structure called the call stack.

Suppose:

main calls methodA
methodA calls methodB
methodB calls methodC

At the deepest point, we can picture:

+-------------+
| methodC     |  ← current method
+-------------+
| methodB     |
+-------------+
| methodA     |
+-------------+
| main        |
+-------------+

methodC finishes first:

+-------------+
| methodB     |  ← resume here
+-------------+
| methodA     |
+-------------+
| main        |
+-------------+

Then methodB finishes:

+-------------+
| methodA     |
+-------------+
| main        |
+-------------+

Then methodA finishes:

+-------------+
| main        |
+-------------+

This behavior is often summarized as:

The most recently called method is the first one to finish and return.

43. Stack frames

Each active method call has its own conceptual region of the call stack, commonly called a stack frame.

A stack frame contains information associated with that particular call, including conceptually:

  • parameter values,
  • local variables,
  • where execution should return afterward.

Consider:

public static int addOne(int x) {
    int result = x + 1;
    return result;
}

When:

addOne(10)

runs, its frame might be pictured as:

+----------------------+
| addOne               |
| x = 10               |
| result = 11          |
| return location: ... |
+----------------------+

When the method finishes, that frame is removed.

44. Separate calls have separate local variables

Consider:

public static int doubleValue(int x) {
    int result = x * 2;
    return result;
}

Now:

int a = doubleValue(5);
int b = doubleValue(10);

The first call has conceptually:

doubleValue frame

x = 5
result = 10

That call finishes.

The second call gets a new frame:

doubleValue frame

x = 10
result = 20

The local variables are not shared between calls.

This explains an important property of methods:

Every method invocation has its own local execution environment.

45. Tracing with the call stack

Consider:

public static int calculate(int x) {

46. Why the call stack matters

You do not manually manage the call stack, but understanding it explains:

  • why local variables in different method calls do not interfere,
  • how Java remembers where execution should return,
  • how nested method calls work,
  • why each call has separate parameter values,
  • how error stack traces describe method-call history.

It will also become especially important when recursion is studied later.

For Week 4, the main goal is to understand ordinary method calls and returns.

47. A first look at stack traces

When a runtime error occurs, Java may display a stack trace.

For example:

Exception in thread "main"
java.lang.ArithmeticException: / by zero
    at Example.divide(Example.java:14)
    at Example.calculate(Example.java:9)
    at Example.main(Example.java:4)

This tells us that the execution path was approximately:

main
  called calculate
    called divide
      error occurred

The stack trace is therefore closely related to the call stack.

When investigating one, look for the first useful line referring to your own code near the exception.

48. Program decomposition

Suppose the problem is:

Read three exam scores, calculate the average, determine the letter grade, and print a report.

Rather than immediately writing code, identify the conceptual tasks:

readScore
calculateAverage
determineGrade
printReport

We can picture:

main
 |
 +-- readScore
 |
 +-- calculateAverage
 |
 +-- determineGrade
 |
 +-- printReport

Each method has one focused job.

49. The role of main

Beginning programmers often think:

Everything happens in main.

A better model is:

main coordinates the program.

For example:

public static void main(String[] args) {
    displayWelcome();
    readData();
    performCalculations();
    displayResults();
}

The details of those operations can live elsewhere.

A good main method often reads like the high-level story of the program.

50. Complete example: Decomposing a grade program

import java.util.Scanner;

public class GradeProgram {

    public static double readScore(
            Scanner input,
            String prompt) {

        System.out.print(prompt);
        return input.nextDouble();
    }

    public static double calculateAverage(
            double score1,
            double score2,
            double score3) {

        return (score1 + score2 + score3) / 3.0;
    }

    public static char determineGrade(double average) {
        if (average >= 90) {
            return 'A';
        } else if (average >= 80) {
            return 'B';
        } else if (average >= 70) {
            return 'C';
        } else if (average >= 60) {
            return 'D';
        } else {
            return 'F';
        }
    }

    public static void printReport(
            double average,
            char grade) {

        System.out.printf("Average: %.2f%n", average);
        System.out.println("Grade: " + grade);
    }

    public static void main(String[] args) {
        Scanner input = new Scanner(System.in);

        double exam1 =
                readScore(input, "Enter exam 1: ");

        double exam2 =
                readScore(input, "Enter exam 2: ");

        double exam3 =
                readScore(input, "Enter exam 3: ");

        double average =
                calculateAverage(exam1, exam2, exam3);

        char grade =
                determineGrade(average);

        printReport(average, grade);
    }
}

Look at main again:

public static void main(String[] args) {
    Scanner input = new Scanner(System.in);

    double exam1 =
            readScore(input, "Enter exam 1: ");

    double exam2 =
            readScore(input, "Enter exam 2: ");

    double exam3 =
            readScore(input, "Enter exam 3: ");

    double average =
            calculateAverage(exam1, exam2, exam3);

    char grade =
            determineGrade(average);

    printReport(average, grade);
}

Its structure tells the story:

read three scores

calculate the average

determine the grade

print the report

This is the purpose of decomposition.

51. One responsibility per method

A useful design principle is:

One method, one primary responsibility.

Good:

calculateAverage(...)

Good:

determineGrade(...)

Good:

printReport(...)

Less desirable:

readScoresCalculateAverageDetermineGradeAndPrintEverything(...)

That method contains several different conceptual jobs.

A good test is to ask:

Can I describe what this method does with one short phrase?

If the answer requires many unrelated verbs:

"reads input, validates it, calculates three things,
prints a report, displays a menu, and..."

the method probably has too many responsibilities.

52. How long should a method be?

There is no universal maximum number of lines.

The more important question is:

Does this method perform one coherent conceptual task?

A 5-line method can still be poorly designed.

A 25-line method may be perfectly reasonable if all 25 lines belong to one operation.

However, extremely long methods often indicate that decomposition may help.

Look for conceptual sections such as:

// read data

...

// validate data

...

// calculate average

...

// determine grade

...

// print report

Those comments may be clues that separate methods are appropriate.

53. Top-down design

One way to design a larger program is top-down design.

Start with the whole problem.

For example:

Run an ATM simulation

Ask what major tasks are needed:

display menu
read choice
process choice

Then perhaps break process choice into:

deposit
withdraw
check balance

The structure might be:

main
 |
 +-- displayMenu
 |
 +-- readChoice
 |
 +-- processChoice
       |
       +-- deposit
       |
       +-- withdraw
       |
       +-- checkBalance

The principle is:

Start with the large problem and repeatedly divide it into smaller problems until each piece is manageable.

54. Separating calculation from input and output

Suppose we need to convert Fahrenheit to Celsius.

Formula:

C = (F - 32) × 5 / 9

A good calculation method is:

public static double fahrenheitToCelsius(
        double fahrenheit) {

    return (fahrenheit - 32) * 5.0 / 9.0;
}

Notice what this method does not do.

It does not:

  • create a Scanner,
  • ask the user for input,
  • print the result.

It receives a number and returns a number.

Then main can handle interaction:

import java.util.Scanner;

public class TemperatureConverter {

    public static double fahrenheitToCelsius(
            double fahrenheit) {

        return (fahrenheit - 32) * 5.0 / 9.0;
    }

    public static void main(String[] args) {
        Scanner input = new Scanner(System.in);

        System.out.print(
                "Enter temperature in Fahrenheit: ");

        double fahrenheit = input.nextDouble();

        double celsius =
                fahrenheitToCelsius(fahrenheit);

        System.out.printf(
                "%.2f F = %.2f C%n",
                fahrenheit,
                celsius);
    }
}

The calculation is independent from the user interface.

That makes the calculation easier to understand, reuse, and test.

55. Calculation methods as inputs → outputs

A useful way to design a calculation method is:

inputs
   ↓
method
   ↓
output

For example:

weight, height
      ↓
 calculateBMI
      ↓
     BMI

Code:

public static double calculateBMI(
        double weight,
        double height) {

    return weight / (height * height);
}

The method's contract is easy to understand:

Give me:
    weight
    height

I will give you:
    BMI

56. Boolean methods as named questions

Suppose the rule for a valid exam score is:

0 <= score <= 100

In Java:

score >= 0 && score <= 100

Instead of repeatedly writing this condition, create:

public static boolean isValidScore(double score) {
    return score >= 0 && score <= 100;
}

Now:

while (!isValidScore(score)) {
    System.out.println("Invalid score.");
    score = input.nextDouble();
}

The condition communicates its meaning directly.

Methods are therefore useful not only for removing repetition but also for naming concepts.

57. Method signatures

Consider:

public static double calculateArea(double radius)

The method has:

  • name: calculateArea
  • one parameter of type double
  • return type: double

For identifying overloaded methods, Java considers the method name together with the parameter list.

For example:

max(int, int)

is distinct from:

max(double, double)

The parameter types differ.

Similarly:

calculate(int, double)

differs from:

calculate(double, int)

because parameter order is part of the distinction.

58. A brief introduction to method overloading

Java permits several methods with the same name when their parameter lists differ.

For example:

public static int max(int a, int b) {
    if (a > b) {
        return a;
    }

    return b;
}

public static double max(double a, double b) {
    if (a > b) {
        return a;
    }

    return b;
}

Then:

int x = max(3, 8);

uses the integer version.

double y = max(3.5, 8.2);

uses the double version.

This is called method overloading.

For Week 4, recognize the idea; the central focus remains designing and using ordinary methods correctly.

Two methods cannot be distinguished by return type alone.

This is not valid:

public static int getValue() {
    return 5;
}

public static double getValue() {
    return 5.0;
}

Both have the same name and the same parameter list.

59. Common error: Forgetting the return value

Incorrect:

public static int square(int number) {
    int result = number * number;
}

The method declares:

int

but never returns an int.

Correct:

public static int square(int number) {
    int result = number * number;
    return result;
}

Or:

public static int square(int number) {
    return number * number;
}

60. Common error: Returning the wrong type

Incorrect:

public static int getNumber() {
    return "hello";
}

The method promises an int, but returns a String.

Correct:

public static int getNumber() {
    return 5;
}

61. Common error: Using a void method as a value

Suppose:

public static void printHello() {
    System.out.println("Hello");
}

This is valid:

printHello();

This is not:

String message = printHello();

printHello() does not produce a value.

62. Common error: Printing instead of returning

Suppose the assignment says:

Write a method that returns the square of a number.

Incorrect:

public static void square(int n) {
    System.out.println(n * n);
}

That method prints the square.

Correct:

public static int square(int n) {
    return n * n;
}

Pay close attention to verbs in programming requirements:

print
display
return
calculate
read

They do not all mean the same thing.

63. Common error: Scope confusion

Incorrect:

public static void calculate() {
    int result = 25;
}

public static void main(String[] args) {
    calculate();
    System.out.println(result);
}

result belongs to calculate.

One solution is to return it:

public static int calculate() {
    return 25;
}

public static void main(String[] args) {
    int result = calculate();
    System.out.println(result);
}

Information crosses method boundaries through parameters and return values.

64. Common error: Uninitialized local variables

Local variables must receive values before being read.

Incorrect:

public static void example() {
    int result;
    System.out.println(result);
}

result has been declared, but no value has been assigned.

Correct:

public static void example() {
    int result = 0;
    System.out.println(result);
}

A subtler case is:

int result;

if (condition) {
    result = 10;
}

System.out.println(result);

If condition is false, result has never been assigned.

Java detects this possibility.

65. Common error: Correct syntax, wrong logic

A method can compile and still be wrong.

Consider:

public static double average(double a, double b) {
    return a + b / 2;
}

Because division occurs before addition, this calculates:

a + (b / 2)

not:

(a + b) / 2

Correct:

public static double average(double a, double b) {
    return (a + b) / 2.0;
}

Compilation tells us that the program follows Java's syntax and type rules.

It does not prove that the algorithm is correct.

66. Testing methods

Methods make testing easier because we can test one operation at a time.

Suppose:

public static boolean isPositive(int n) {
    return n > 0;
}

Useful tests include:

Input     Expected

  5       true
  1       true
  0       false
 -1       false
-20       false

Notice that we tested the important boundary around zero.

For:

public static boolean isPassing(double score) {
    return score >= 60;
}

important tests include:

59 → false
60 → true
61 → true

These values test the boundary.

A useful testing habit is:

  1. choose an input,
  2. predict the result by hand,
  3. run the method,
  4. compare actual and expected results.

67. Common syntax mistakes

Missing return type

Incorrect:

public static calculate(int x) {
    return x * 2;
}

Correct:

public static int calculate(int x) {
    return x * 2;
}

Missing parentheses

Incorrect:

public static void greet {
    System.out.println("Hello");
}

Correct:

public static void greet() {
    System.out.println("Hello");
}

Defining a method inside another method

This is not permitted:

public static void main(String[] args) {

    public static void greet() {
        System.out.println("Hello");
    }
}

Instead, place methods at the class level:

public class Example {

    public static void greet() {
        System.out.println("Hello");
    }

    public static void main(String[] args) {
        greet();
    }
}

Wrong argument count

Definition:

public static int add(int a, int b) {
    return a + b;
}

Wrong:

add(5);

Wrong:

add(5, 7, 10);

Correct:

add(5, 7);

Wrong argument types

Definition:

public static double calculateTax(double amount) {
    return amount * 0.06;
}

Reasonable:

calculateTax(100.0);

Incorrect:

calculateTax("one hundred");

68. A systematic way to design a method

When you believe a task should become a method, ask four questions.

Question 1: What is the method's responsibility?

Example:

Calculate the average of three scores.

This suggests the name:

calculateAverage

Question 2: What information does it need?

It needs:

score1
score2
score3

So the parameters may be:

double score1,
double score2,
double score3

Question 3: What result does it produce?

It produces an average.

The result is a double.

Therefore:

public static double calculateAverage(
        double score1,
        double score2,
        double score3)

Question 4: What computation performs the job?

return (score1 + score2 + score3) / 3.0;

The complete method becomes:

public static double calculateAverage(
        double score1,
        double score2,
        double score3) {

    return (score1 + score2 + score3) / 3.0;
}

This design process can be summarized as:

responsibility
     ↓
method name

required information
     ↓
parameters

produced information
     ↓
return type

algorithm
     ↓
method body

69. Complete worked example: Fitness calculator

The following program demonstrates several Week 4 principles.

import java.util.Scanner;

public class FitnessCalculator {

    public static double calculateBMI(
            double weightKg,
            double heightMeters) {

        return weightKg /
                (heightMeters * heightMeters);
    }

    public static String classifyBMI(double bmi) {
        if (bmi < 18.5) {
            return "Underweight";
        } else if (bmi < 25) {
            return "Normal";
        } else if (bmi < 30) {
            return "Overweight";
        } else {
            return "Obese";
        }
    }

    public static void displayResult(
            double bmi,
            String category) {

        System.out.printf("BMI: %.1f%n", bmi);
        System.out.println("Category: " + category);
    }

    public static void main(String[] args) {
        Scanner input = new Scanner(System.in);

        System.out.print("Weight in kilograms: ");
        double weight = input.nextDouble();

        System.out.print("Height in meters: ");
        double height = input.nextDouble();

        double bmi =
                calculateBMI(weight, height);

        String category =
                classifyBMI(bmi);

        displayResult(bmi, category);
    }
}

Notice the decomposition:

calculate BMI
     ↓
classify BMI
     ↓
display result

The responsibilities are separated.

calculateBMI performs a calculation:

double bmi = calculateBMI(weight, height);

classifyBMI performs a decision:

String category = classifyBMI(bmi);

displayResult handles output:

displayResult(bmi, category);

And main coordinates the overall workflow.

70. Following data through the complete example

Suppose the user enters:

weight = 80
height = 2

Then:

calculateBMI(80, 2)

runs.

Inside:

weightKg = 80
heightMeters = 2

BMI = 80 / (2 × 2)
    = 80 / 4
    = 20

The method returns:

20

Then:

classifyBMI(20)

runs.

Inside:

bmi = 20

The condition:

bmi < 18.5

is false.

The next condition:

bmi < 25

is true.

So:

return "Normal";

Finally:

displayResult(20, "Normal");

prints the result.

Notice how data moves from one method to another without one method needing access to another method's local variables.

71. Methods as contracts

It is useful to think of a method as making a contract.

Consider:

public static double calculateArea(
        double length,
        double width) {

    return length * width;
}

Its contract is approximately:

Name:
    calculateArea

Inputs:
    double length
    double width

Output:
    double

Responsibility:
    calculate rectangle area

A caller does not need to know about the local implementation details.

It can simply write:

double area = calculateArea(10, 5);

Thinking about methods through their contracts encourages clean program design.

72. Programming style guidelines for Week 4

From this point forward, use these guidelines when appropriate:

  1. Avoid putting the entire program inside main.
  2. Use methods for meaningful subtasks.
  3. Give methods descriptive names.
  4. Keep each method focused on one primary responsibility.
  5. Pass required information through parameters.
  6. Return calculated values when the caller needs them.
  7. Keep calculation logic separate from input/output when reasonable.
  8. Keep variables in the smallest reasonable scope.
  9. Avoid repeating substantial logic that belongs in a reusable method.
  10. Test methods with simple and boundary inputs.
  11. Make main communicate the high-level workflow of the program.
  12. Prefer explicit data flow over methods that depend on hidden information.

The goal is not to create as many methods as possible.

The goal is to create an understandable program.

73. Key distinctions to memorize

Method definition vs. method call

Definition:

public static int square(int x) {
    return x * x;
}

Call:

square(5);

Parameter vs. argument

Parameter:

int x

in:

public static int square(int x)

Argument:

5

in:

square(5)

return vs. println

return result;

sends a value back to the caller.

System.out.println(result);

displays information on the console.

void vs. value-returning

public static void printMenu()

returns no value.

public static double calculateAverage(...)

returns a double.

Local variable vs. parameter

Local variable:

double area = length * width;

Parameter:

double length

Both belong to the method's local execution environment.

Scope vs. value

A variable can have a perfectly valid value but still be inaccessible because it is outside the current scope.

Scope answers:

Can this variable name be used here?

not:

What value does this variable contain?

74. Common questions

Q1. Does every method need parameters?

No.

public static void printMenu() {
    ...
}

takes no parameters.

Use parameters only when the method needs information from its caller.

Q2. Does every method return a value?

No.

A void method returns no value:

public static void printGreeting() {
    System.out.println("Hello");
}

Q3. Can a method have several parameters?

Yes.

public static double area(
        double length,
        double width) {

    return length * width;
}

Q4. Can two methods use variables with the same names?

Yes, if those variables belong to different scopes.

public static void a() {
    int x = 5;
}

public static void b() {
    int x = 20;
}

The two x variables are separate.

Q5. Why can't one method see another method's local variables?

Because each method invocation has its own local execution environment.

Pass required data through parameters or return values.

Q6. Can I call a method more than once?

Yes.

printSeparator();
printSeparator();
printSeparator();

Every call executes the method again.

Q7. Can one method call another?

Yes.

public static int calculate(int x) {
    return square(x) + 1;
}

Q8. Can a method call be used inside another call?

Yes.

printNumber(square(5));

The inner call is evaluated first.

Q9. Why didn't changing a primitive parameter change the original variable?

Because the method receives a copy of the primitive value.

changeNumber(x);

does not make the method's parameter the same variable as x.

Q10. Should every calculation be a method?

Not necessarily.

Create a method when doing so provides meaningful structure, reuse, clarity, abstraction, or testability.

Avoid breaking programs into meaningless tiny fragments merely to increase the number of methods.

75. Debugging checklist for methods

When a method-related program does not compile, check:

Method definition

  • Is there a return type?
  • Is the method name spelled correctly?
  • Are parentheses present?
  • Are parameter types specified?
  • Is the method defined at the class level rather than inside another method?
  • Are braces balanced?

Method call

  • Is the method name correct?
  • Is the number of arguments correct?
  • Are argument types compatible?
  • Are arguments in the correct order?

Return values

  • Does a non-void method return something?
  • Does every reachable path return an appropriate value?
  • Is the returned value compatible with the declared return type?
  • Are you accidentally trying to assign a void method?

Scope

  • Is the variable visible at the location where it is being used?
  • Was it declared inside another method?
  • Was it declared inside an if or loop block?
  • Was it initialized before being read?

Logic

  • Are formulas parenthesized correctly?
  • Are conditional boundaries correct?
  • Are arguments supplied in the intended order?
  • Have you tested simple inputs by hand?

76. Manual tracing strategy

When tracing programs containing several methods, do not try to keep everything in your head.

Use a structured process.

Suppose:

public static int f(int x) {
    return x * 2;
}

public static int g(int x) {
    return f(x) + 1;
}

public static void main(String[] args) {
    int a = 3;
    int b = g(a);

    System.out.println(a);
    System.out.println(b);
}

Trace:

main starts

a = 3

call g(3)

    g:
    x = 3

80. Conceptual summary

Before Week 4, we could think of a program primarily as a sequence of statements:

variables
conditions
loops

Week 4 introduces another level of organization.

We can now group statements into named operations.

The central ideas are:

method
    =
a named operation

parameter
    =
information entering a method

argument
    =
the actual value supplied by the caller

return value
    =
information produced by a method

void
    =
the method produces no return value

scope
    =
where a variable can be accessed

local variable
    =
a variable belonging to a local method/block scope

call stack
    =
the structure that tracks active method calls

decomposition
    =
breaking a large problem into smaller problems

Perhaps the most important mindset change is:

Do not think of a program as one long sequence of instructions.

Instead, think of a program as:

a collection of smaller operations
        ↓
communicating through inputs and outputs
        ↓
cooperating to solve a larger problem

That way of thinking is foundational to writing larger programs.

Week 4 quick reference

Basic void method

public static void methodName() {
    // statements
}

Call:

methodName();

void method with parameters

public static void greet(String name) {
    System.out.println("Hello, " + name);
}

Call:

greet("Maria");

Value-returning method

public static int square(int number) {
    return number * number;
}

Call:

int result = square(5);

Multiple parameters

public static double area(
        double length,
        double width) {

    return length * width;
}

Call:

double result = area(10, 5);

Boolean method

public static boolean isEven(int number) {
    return number % 2 == 0;
}

Usage:

if (isEven(number)) {
    System.out.println("Even");
}

Remember

parameter → in the definition

argument  → in the call

return    → sends a value to the caller

println   → sends output to the console

void      → no return value

scope     → where a variable can be accessed
