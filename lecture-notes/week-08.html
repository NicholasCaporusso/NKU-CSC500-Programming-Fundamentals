Learning objectives

By the end of this week, students should be able to:

  • Explain the purpose of inheritance in object-oriented programming.
  • Distinguish between an is-a relationship and a has-a relationship.
  • Define subclasses using extends.
  • Use super to invoke superclass constructors and methods.
  • Explain method overriding and distinguish it from method overloading.
  • Use polymorphism through superclass references.

1. Why inheritance?

So far, we have designed programs using classes and objects.

For example:

public class Student {
    private String name;
    private int id;

    public Student(String name, int id) {
        this.name = name;
        this.id = id;
    }

    public String getName() {
        return name;
    }

    public int getId() {
        return id;
    }
}

Suppose our program also contains employees:

public class Employee {
    private String name;
    private int id;
    private double salary;

    public Employee(String name, int id, double salary) {
        this.name = name;
        this.id = id;
        this.salary = salary;
    }
}

There is duplication here.

Both Student and Employee have:

  • a name
  • an ID
  • behaviors associated with a person

Conceptually:

Student is a Person
Employee is a Person

We could capture the common behavior in a superclass:

public class Person {
    private String name;
    private int id;

    public Person(String name, int id) {
        this.name = name;
        this.id = id;
    }

    public String getName() {
        return name;
    }

    public int getId() {
        return id;
    }
}

Then:

public class Student extends Person {
}

and:

public class Employee extends Person {
}

This relationship is called inheritance.

2. Superclasses and subclasses

Inheritance creates a relationship between two classes.

The more general class is called the:

  • superclass
  • parent class
  • base class

The more specialized class is called the:

  • subclass
  • child class
  • derived class

Example:

public class Animal {
}
public class Dog extends Animal {
}

Here:

Animal = superclass
Dog    = subclass

We can say:

A Dog is an Animal.

Java expresses this relationship with the keyword:

extends

3. The "is-a" test

Inheritance should generally represent an is-a relationship.

For example:

Dog is an Animal
Car is a Vehicle
Professor is an Employee
SavingsAccount is a BankAccount
Circle is a Shape

These may be reasonable inheritance relationships.

But consider:

Car is an Engine
Student is a Course
Computer is a Processor

These are not valid.

Instead:

Car has an Engine
Student takes a Course
Computer has a Processor

These relationships usually require composition, not inheritance.

A useful rule is:

"is-a"  → consider inheritance
"has-a" → consider composition

4. A basic inheritance example

Consider a superclass representing bank accounts.

public class BankAccount {

    private String accountNumber;
    private double balance;

    public BankAccount(String accountNumber, double balance) {
        this.accountNumber = accountNumber;
        this.balance = balance;
    }

    public void deposit(double amount) {
        balance += amount;
    }

    public void withdraw(double amount) {
        balance -= amount;
    }

    public double getBalance() {
        return balance;
    }

    public String getAccountNumber() {
        return accountNumber;
    }
}

Now suppose we want a specialized account:

public class SavingsAccount extends BankAccount {

    private double interestRate;

    public SavingsAccount(
            String accountNumber,
            double balance,
            double interestRate) {

        super(accountNumber, balance);

        this.interestRate = interestRate;
    }

    public void addInterest() {
        double interest = getBalance() * interestRate;
        deposit(interest);
    }
}

The SavingsAccount class inherits accessible methods from BankAccount.

For example:

SavingsAccount account =
    new SavingsAccount("A123", 1000.0, 0.05);

account.deposit(200);
account.addInterest();

System.out.println(account.getBalance());

Although SavingsAccount does not explicitly define deposit() or getBalance(), those methods are inherited.

5. Constructors and super

Constructors are not inherited.

When a subclass object is created, the superclass portion of the object must also be initialized.

Consider:

public class Person {

    private String name;

    public Person(String name) {
        this.name = name;
    }
}

Then:

public class Student extends Person {

    private String major;

    public Student(String name, String major) {
        super(name);
        this.major = major;
    }
}

The statement:

super(name);

calls the constructor of the superclass.

Conceptually:

new Student("Alice", "Computer Science")
        |
        v
Person constructor initializes name
        |
        v
Student constructor initializes major

A call to a superclass constructor must occur before the subclass constructor finishes initializing the subclass.

If used explicitly, super(...) must be the first statement in the constructor.

6. What does a subclass inherit?

A subclass inherits accessible members of its superclass.

Suppose:

public class Animal {

    public void eat() {
        System.out.println("Eating...");
    }

    public void sleep() {
        System.out.println("Sleeping...");
    }
}

Then:

public class Dog extends Animal {

    public void bark() {
        System.out.println("Woof!");
    }
}

A Dog object can use:

Dog dog = new Dog();

dog.eat();
dog.sleep();
dog.bark();

The first two methods come from Animal.

The third comes from Dog.

7. Private fields and inheritance

A common misunderstanding is that subclasses can directly access private fields inherited from a superclass.

They cannot.

Consider:

public class Person {

    private String name;

    public Person(String name) {
        this.name = name;
    }
}

This will not compile:

public class Student extends Person {

    public void printName() {
        System.out.println(name);
    }
}

Because:

name

is private to the Person class.

Instead, the superclass should provide an appropriate method:

public String getName() {
    return name;
}

Then:

public class Student extends Person {

    public void printName() {
        System.out.println(getName());
    }
}

This preserves encapsulation.

8. protected

Java provides another access modifier:

protected

A protected member can be accessed by subclasses.

Example:

public class Person {

    protected String name;
}

Then:

public class Student extends Person {

    public void printName() {
        System.out.println(name);
    }
}

This compiles.

However, using protected fields can weaken encapsulation.

In many cases, this design is preferable:

private String name;

public String getName() {
    return name;
}

rather than:

protected String name;

9. Method overriding

A subclass can provide its own implementation of an inherited method.

This is called method overriding.

Consider:

public class Animal {

    public void makeSound() {
        System.out.println("Some animal sound");
    }
}

Now:

public class Dog extends Animal {

    @Override
    public void makeSound() {
        System.out.println("Woof!");
    }
}

And:

public class Cat extends Animal {

    @Override
    public void makeSound() {
        System.out.println("Meow!");
    }
}

Now:

Dog dog = new Dog();
dog.makeSound();

prints:

Woof!

The Dog implementation replaces the inherited behavior for Dog objects.

10. The @Override annotation

Java allows us to write:

@Override

before an overriding method.

Example:

@Override
public void makeSound() {
    System.out.println("Woof!");
}

Technically, the method may still override without the annotation.

However, you should almost always include it.

Why?

Suppose you accidentally write:

@Override
public void makesound() {
    System.out.println("Woof!");
}

Notice the lowercase s.

Java reports an error because no superclass method matches.

Without @Override, Java might interpret this as an entirely new method.

Therefore:

Use @Override whenever you intend to override a method.

11. Overriding vs. overloading

These concepts are frequently confused.

Overloading

Same method name, different parameter lists.

public void print(int x) {
}

public void print(double x) {
}

public void print(String x) {
}

The compiler decides which method to call based on the arguments.

Overriding

A subclass provides a new implementation of a method inherited from its superclass.

public class Animal {

    public void speak() {
        System.out.println("Animal speaks");
    }
}
public class Dog extends Animal {

    @Override
    public void speak() {
        System.out.println("Woof");
    }
}

A useful comparison:

ConceptMeaning
OverloadingSame method name, different parameters
OverridingSubclass replaces inherited method behavior

12. Calling a superclass method

Sometimes a subclass overrides a method but still wants to use the superclass implementation.

Use:

super.methodName()

Example:

public class Person {

    public void describe() {
        System.out.println("I am a person.");
    }
}
public class Student extends Person {

    @Override
    public void describe() {
        super.describe();
        System.out.println("I am also a student.");
    }
}

Calling:

Student s = new Student();
s.describe();

produces:

I am a person.
I am also a student.

13. Introducing polymorphism

Inheritance becomes particularly powerful when combined with polymorphism.

The word polymorphism roughly means:

many forms

Consider:

public class Animal {

    public void makeSound() {
        System.out.println("Animal sound");
    }
}
public class Dog extends Animal {

    @Override
    public void makeSound() {
        System.out.println("Woof!");
    }
}

Now observe:

Animal animal = new Dog();

This is legal.

Why?

Because:

Dog is an Animal

The variable type is:

Animal

but the actual object is:

Dog

14. Reference type vs. object type

This distinction is central to Java polymorphism.

Consider:

Animal a = new Dog();

There are two types involved.

Reference type

Animal

The variable a is declared as an Animal.

Runtime object type

Dog

The object created with new is a Dog.

We can visualize this as:

Animal a
   |
   v
+--------+
|  Dog   |
+--------+

15. Dynamic method dispatch

What happens here?

Animal a = new Dog();
a.makeSound();

Suppose:

public class Animal {

    public void makeSound() {
        System.out.println("Animal");
    }
}

and:

public class Dog extends Animal {

    @Override
    public void makeSound() {
        System.out.println("Dog");
    }
}

The output is:

Dog

Why?

Java determines the overriding method using the object's actual runtime type.

The object is a Dog.

Therefore:

Dog.makeSound()

runs.

This is known as:

dynamic method dispatch.

16. Why polymorphism matters

Suppose we have:

public class Dog extends Animal { ... }
public class Cat extends Animal { ... }
public class Cow extends Animal { ... }

Without polymorphism, we might write separate code for every animal.

With polymorphism:

Animal[] animals = new Animal[3];

animals[0] = new Dog();
animals[1] = new Cat();
animals[2] = new Cow();

Then:

for (Animal animal : animals) {
    animal.makeSound();
}

Output:

Woof!
Meow!
Moo!

The loop does not need to know which specific subtype it is processing.

Each object determines its own behavior.

This gives us:

  • extensibility
  • reduced duplication
  • simpler code
  • separation between general behavior and specific implementation

17. A more realistic example

Imagine a payroll system.

Superclass:

public class Employee {

    private String name;

    public Employee(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }

    public double calculatePay() {
        return 0;
    }
}

Subclass:

public class SalariedEmployee extends Employee {

    private double annualSalary;

    public SalariedEmployee(
            String name,
            double annualSalary) {

        super(name);
        this.annualSalary = annualSalary;
    }

    @Override
    public double calculatePay() {
        return annualSalary / 12.0;
    }
}

Another subclass:

public class HourlyEmployee extends Employee {

    private double hourlyRate;
    private double hoursWorked;

    public HourlyEmployee(
            String name,
            double hourlyRate,
            double hoursWorked) {

        super(name);
        this.hourlyRate = hourlyRate;
        this.hoursWorked = hoursWorked;
    }

    @Override
    public double calculatePay() {
        return hourlyRate * hoursWorked;
    }
}

Now:

Employee[] employees = {
    new SalariedEmployee("Alice", 120000),
    new HourlyEmployee("Bob", 30, 160)
};

We can process them uniformly:

for (Employee employee : employees) {

    System.out.println(
        employee.getName()
        + ": "
        + employee.calculatePay()
    );
}

Each employee calculates pay differently.

The calling code does not need to know how.

18. The power of programming to an abstraction

Notice what the payroll code does:

Employee employee

rather than:

SalariedEmployee employee

or:

HourlyEmployee employee

Whenever possible, code should depend on the general abstraction rather than a specific implementation.

This principle will become increasingly important when we study data structures.

For example, later we may write:

List<String> names = new ArrayList<>();

rather than:

ArrayList<String> names = new ArrayList<>();

The same design idea is at work.

19. Abstract classes

Our previous Employee superclass contained:

public double calculatePay() {
    return 0;
}

But does a generic employee really have a meaningful pay calculation?

Probably not.

Every particular kind of employee must decide how pay is calculated.

Java allows us to express this using an abstract method.

public abstract class Employee {

    private String name;

    public Employee(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }

    public abstract double calculatePay();
}

The method:

public abstract double calculatePay();

has no implementation.

It declares a requirement:

Every concrete subclass of Employee must provide this method.

20. Abstract classes cannot be instantiated

Because Employee is abstract:

Employee e = new Employee("Alice");

is illegal.

Java prevents us from creating an object whose behavior is incomplete.

But this is legal:

Employee e =
    new SalariedEmployee("Alice", 120000);

The variable has type:

Employee

but the object is a concrete subclass.

21. Concrete and abstract classes

A concrete class can be instantiated:

Dog dog = new Dog();

An abstract class cannot:

Animal animal = new Animal();

if Animal has been declared:

public abstract class Animal

Abstract classes are useful when:

  • several subclasses share state
  • several subclasses share some implementation
  • the superclass should define common behavior
  • some operations must be supplied by subclasses

22. Example: abstract shape class

public abstract class Shape {

    public abstract double area();

    public abstract double perimeter();
}

Circle:

public class Circle extends Shape {

    private double radius;

    public Circle(double radius) {
        this.radius = radius;
    }

    @Override
    public double area() {
        return Math.PI * radius * radius;
    }

    @Override
    public double perimeter() {
        return 2 * Math.PI * radius;
    }
}

Rectangle:

public class Rectangle extends Shape {

    private double width;
    private double height;

    public Rectangle(double width, double height) {
        this.width = width;
        this.height = height;
    }

    @Override
    public double area() {
        return width * height;
    }

    @Override
    public double perimeter() {
        return 2 * (width + height);
    }
}

Now:

Shape[] shapes = {
    new Circle(5),
    new Rectangle(4, 8),
    new Circle(2)
};

We can write:

double totalArea = 0;

for (Shape shape : shapes) {
    totalArea += shape.area();
}

The same code works with every kind of Shape.

23. Interfaces

An interface describes a set of behaviors that a class promises to provide.

Example:

public interface Printable {

    void print();
}

A class can implement the interface:

public class Report implements Printable {

    @Override
    public void print() {
        System.out.println("Printing report...");
    }
}

The keyword is:

implements

24. Interface as a contract

An interface can be viewed as a contract.

If a class says:

implements Printable

it promises:

Objects of this class can be printed.

The exact implementation is up to the class.

For example:

public class Invoice implements Printable {

    @Override
    public void print() {
        System.out.println("Printing invoice...");
    }
}

Another class:

public class Photo implements Printable {

    @Override
    public void print() {
        System.out.println("Printing photo...");
    }
}

Then:

Printable[] items = {
    new Invoice(),
    new Photo(),
    new Report()
};

We can write:

for (Printable item : items) {
    item.print();
}

This is polymorphism again.

25. Interface reference types

An interface can be used as a variable type.

Printable p = new Report();

The reference type is:

Printable

The actual object type is:

Report

Calling:

p.print();

uses the Report implementation.

26. Multiple interfaces

Java classes can extend only one class.

This is illegal:

public class C extends A, B {
}

Java does not support multiple class inheritance.

However, a class may implement multiple interfaces.

Example:

public class SmartPhone
        implements Printable, Comparable<SmartPhone> {
}

This allows a class to participate in several behavioral abstractions.

27. Abstract classes vs. interfaces

Both abstract classes and interfaces support abstraction and polymorphism.

A simplified comparison:

Abstract ClassInterface
Uses extendsUses implements
Can contain instance fieldsPrimarily defines capabilities/contracts
Can define constructorsHas no ordinary object constructor
Can contain implemented methodsCan contain abstract and certain implemented methods
Class can extend only oneClass can implement multiple
Often represents a shared type hierarchyOften represents a shared capability

Examples:

Dog is an Animal

suggests inheritance.

Report is Printable
Photo is Printable
Invoice is Printable

suggests an interface.

A useful intuition is:

abstract class → "what something fundamentally is"
interface      → "what something can do"

This is a guideline, not an absolute rule.

28. Composition vs. inheritance

Inheritance is powerful, but it is often overused.

Suppose we have:

public class Engine {
    public void start() {
    }
}

We should not write:

public class Car extends Engine {
}

because a car is not an engine.

Instead:

public class Car {

    private Engine engine;

    public Car() {
        engine = new Engine();
    }

    public void start() {
        engine.start();
    }
}

This is composition.

The relationship is:

Car has an Engine

rather than:

Car is an Engine

29. Prefer composition when appropriate

Inheritance creates a strong relationship between classes.

A subclass depends heavily on its superclass.

Therefore, use inheritance only when there is a genuine conceptual subtype relationship.

Ask:

Can every object of the subclass reasonably be treated as an object of the superclass?

If yes, inheritance may be appropriate.

For example:

Every Dog can be treated as an Animal.
Every Circle can be treated as a Shape.
Every SavingsAccount can be treated as a BankAccount.

But:

Every Car can be treated as an Engine.

does not make sense.

30. Polymorphic collections

One of the most useful applications of polymorphism is storing different subclasses in a single collection.

Consider:

ArrayList<Shape> shapes = new ArrayList<>();

Then:

shapes.add(new Circle(5));
shapes.add(new Rectangle(4, 8));
shapes.add(new Circle(2));

Later:

for (Shape shape : shapes) {
    System.out.println(shape.area());
}

This allows heterogeneous objects to be processed through a common abstraction.

31. Compile-time type checking

Suppose:

Animal a = new Dog();

and Dog has:

public void fetch() {
    System.out.println("Fetching...");
}

but Animal does not.

Can we write:

a.fetch();

No.

The compiler examines the reference type:

Animal

and asks:

Does Animal declare a method named fetch?

It does not.

Therefore the call does not compile.

Even though the actual object happens to be a Dog.

32. Casting

We could write:

Animal a = new Dog();

Dog d = (Dog) a;

d.fetch();

This is called downcasting.

However, casting must be used carefully.

Consider:

Animal a = new Cat();

Dog d = (Dog) a;

This compiles, but fails at runtime with:

ClassCastException

because the object is actually a Cat.

Excessive downcasting is often a sign that the object-oriented design could be improved.

33. instanceof

Java allows us to check an object's type:

if (a instanceof Dog) {
    Dog d = (Dog) a;
    d.fetch();
}

Modern Java also supports pattern matching syntax:

if (a instanceof Dog d) {
    d.fetch();
}

However, a large amount of code such as:

if (x instanceof Dog) {
    ...
} else if (x instanceof Cat) {
    ...
} else if (x instanceof Cow) {
    ...
}

may indicate that polymorphism should be used instead.

For example, instead of:

if (animal instanceof Dog) {
    System.out.println("Woof");
} else if (animal instanceof Cat) {
    System.out.println("Meow");
}

prefer:

animal.makeSound();

and let each subclass implement its own behavior.

34. Object: the root of Java classes

Every Java class ultimately inherits from:

Object

For example:

public class Student {
}

implicitly behaves as though it were:

public class Student extends Object {
}

This means every Java object inherits methods such as:

toString()
equals()
hashCode()

These methods are often overridden.

35. Overriding toString()

By default:

Student s = new Student(...);

System.out.println(s);

may produce something like:

Student@3fee733d

That is usually not useful.

We can override:

@Override
public String toString() {
    return "Student{name='" + name + "', id=" + id + "}";
}

Then:

System.out.println(s);

might print:

Student{name='Alice', id=123}

This makes objects easier to inspect and debug.

36. A complete design example

Suppose we are building a notification system.

Different notifications may be sent differently.

We begin with an interface:

public interface Notification {

    void send();
}

Email:

public class EmailNotification
        implements Notification {

    private String address;
    private String message;

    public EmailNotification(
            String address,
            String message) {

        this.address = address;
        this.message = message;
    }

    @Override
    public void send() {
        System.out.println(
            "Sending email to " + address
        );
    }
}

SMS:

public class SmsNotification
        implements Notification {

    private String phoneNumber;
    private String message;

    public SmsNotification(
            String phoneNumber,
            String message) {

        this.phoneNumber = phoneNumber;
        this.message = message;
    }

    @Override
    public void send() {
        System.out.println(
            "Sending SMS to " + phoneNumber
        );
    }
}

Application:

Notification[] notifications = {
    new EmailNotification(
        "alice@example.com",
        "Your order shipped"
    ),

    new SmsNotification(
        "555-1234",
        "Your order shipped"
    )
};

Now:

for (Notification n : notifications) {
    n.send();
}

Notice that the calling code knows nothing about how email or SMS works.

It knows only:

Every Notification can send().

That is abstraction and polymorphism working together.

37. Extensibility

Suppose later we add:

public class PushNotification
        implements Notification {

    @Override
    public void send() {
        System.out.println(
            "Sending push notification..."
        );
    }
}

The existing processing loop does not change:

for (Notification n : notifications) {
    n.send();
}

This is an important benefit of polymorphic design.

We can introduce new implementations without rewriting code that depends only on the abstraction.

38. A mental model for polymorphism

When you see:

Superclass variable = new Subclass();

ask two questions.

Question 1: what methods may I call?

Look at the declared reference type.

Example:

Animal a = new Dog();

The compiler allows methods declared by Animal.

Question 2: which overridden implementation runs?

Look at the actual object type.

Since the object is a Dog, an overridden method in Dog runs.

Therefore:

Compiler:
"What operations are allowed?"

Runtime:
"Which implementation should execute?"

This distinction is fundamental.

39. Example trace

Consider:

public class A {

    public void print() {
        System.out.println("A");
    }
}
public class B extends A {

    @Override
    public void print() {
        System.out.println("B");
    }
}

Then:

A x = new A();
A y = new B();
B z = new B();

x.print();
y.print();
z.print();

Output:

A
B
B

Why?

x refers to an A object → A.print()

y refers to a B object → B.print()

z refers to a B object → B.print()

The declared type of y does not force A.print() to run.

40. Common mistakes

Mistake 1: thinking private fields are directly accessible

Incorrect:

public class Student extends Person {

    public void test() {
        name = "Alice";
    }
}

if name is private in Person.

Use methods provided by the superclass.

Mistake 2: forgetting super(...)

If the superclass has no zero-argument constructor:

public Person(String name)

the subclass must explicitly call it.

Mistake 3: confusing overloading and overriding

Remember:

overloading → different parameters
overriding → new subclass implementation

Mistake 4: thinking reference type determines overridden behavior

Incorrect mental model:

Animal a = new Dog();

Since a is an Animal,
Animal.makeSound() runs.

Correct:

The actual object is a Dog,
so Dog.makeSound() runs.

Mistake 5: using inheritance only to reuse code

Code reuse alone does not justify inheritance.

The relationship should represent a meaningful subtype.

41. Design principle: depend on abstractions

Consider:

public void printReport(
    LaserPrinter printer) {
}

This function works only with LaserPrinter.

Suppose instead we define:

public interface Printer {
    void print(String text);
}

Then:

public void printReport(
    Printer printer) {
}

Now the method can work with:

LaserPrinter
InkjetPrinter
PdfPrinter
NetworkPrinter

provided each implements Printer.

This principle makes software easier to change.

42. Class hierarchy example

A possible hierarchy might be:

                  Shape
                    |
          +---------+---------+
          |                   |
        Circle             Rectangle
                              |
                            Square

We can interpret this as:

Circle is a Shape.
Rectangle is a Shape.
Square is a Rectangle.

However, class hierarchies should be designed carefully.

Mathematical relationships do not automatically translate into good software inheritance relationships.

We should ask whether subclass behavior truly satisfies the expectations of the superclass.

43. Inheritance hierarchies should usually be shallow

Very deep hierarchies can become difficult to understand.

For example:

Entity
  |
LivingThing
  |
Animal
  |
Mammal
  |
Canine
  |
DomesticCanine
  |
Dog
  |
WorkingDog
  |
PoliceDog

Such designs can become fragile.

In many applications, composition and interfaces produce simpler designs.

Prefer simple relationships unless a deeper hierarchy genuinely models the problem.

44. In-class example

Suppose we need to model different types of course assignments.

Every assignment has:

title
points possible

Different assignment types may calculate scores differently.

We might create:

public abstract class Assignment {

    private String title;
    private double pointsPossible;

    public Assignment(
            String title,
            double pointsPossible) {

        this.title = title;
        this.pointsPossible = pointsPossible;
    }

    public String getTitle() {
        return title;
    }

    public double getPointsPossible() {
        return pointsPossible;
    }

    public abstract double calculateScore();
}

Then:

public class Exam extends Assignment {

    private int correct;
    private int totalQuestions;

    public Exam(
            String title,
            double pointsPossible,
            int correct,
            int totalQuestions) {

        super(title, pointsPossible);

        this.correct = correct;
        this.totalQuestions = totalQuestions;
    }

    @Override
    public double calculateScore() {
        return ((double) correct / totalQuestions)
                * getPointsPossible();
    }
}

Another subclass might calculate a score differently.

The grading system can still process all assignments uniformly:

for (Assignment a : assignments) {
    System.out.println(
        a.getTitle()
        + ": "
        + a.calculateScore()
    );
}

46. In-class exercise 2: find the problem

Consider:

public class Animal {

    private String name;

    public Animal(String name) {
        this.name = name;
    }
}
public class Dog extends Animal {

    public Dog(String name) {
        this.name = name;
    }

Why does this not compile?

Because name is private to Animal.

A correct constructor is:

public Dog(String name) {
    super(name);
}

49. Key vocabulary

Students should be comfortable with the following terms:

Inheritance A mechanism by which one class derives behavior and characteristics from another.

Superclass The more general class in an inheritance relationship.

Subclass The more specialized class.

Overriding Providing a new implementation of an inherited method.

Polymorphism Treating objects of different concrete types through a common abstraction.

Dynamic method dispatch Selecting an overridden method at runtime based on the object's actual type.

Abstract class A class that cannot be directly instantiated and may contain abstract methods.

Abstract method A method declaration without an implementation that subclasses must implement.

Interface A type describing a behavioral contract that implementing classes agree to provide.

Composition Building an object from other objects through has-a relationships.

50. Conceptual summary

Inheritance allows us to express:

A specialized type is a more general type.

For example:

Dog is an Animal.

Method overriding allows subclasses to specialize behavior:

Animal.makeSound()
Dog.makeSound()
Cat.makeSound()

Polymorphism allows us to write:

Animal a = new Dog();

and later:

a.makeSound();

without knowing the exact subtype in the calling code.

Abstract classes allow us to define:

  • shared state
  • shared behavior
  • required subclass behavior

Interfaces allow unrelated classes to share a behavioral contract.

Together these concepts allow us to design programs around abstractions rather than individual concrete classes.

51. What students should be able to read

By the end of the week, students should be able to explain this program:

public abstract class Shape {

    public abstract double area();
}
public class Circle extends Shape {

    private double radius;

    public Circle(double radius) {
        this.radius = radius;
    }

    @Override
    public double area() {
        return Math.PI * radius * radius;
    }
}
public class Rectangle extends Shape {

    private double width;
    private double height;

    public Rectangle(
            double width,
            double height) {

        this.width = width;
        this.height = height;
    }

    @Override
    public double area() {
        return width * height;
    }
}
public class Main {

    public static void main(String[] args) {

        Shape[] shapes = {
            new Circle(5),
            new Rectangle(4, 6),
            new Circle(10)
        };

        for (Shape shape : shapes) {
            System.out.println(shape.area());
        }
    }
}

A student should be able to explain:

  1. Why Shape is abstract.
  2. Why new Shape() is illegal.
  3. Why a Circle can be stored in a Shape variable.
  4. Why the loop does not need instanceof.
  5. Which area() method executes for each element.
  6. How a new subtype such as Triangle could be added without changing the loop.

The key principle is:

The reference type determines which operations the compiler allows, while the runtime object type determines which overridden implementation executes.

Week 8 takeaways

The most important ideas from this week are:

  1. Inheritance models subtype relationships.

``text Dog is an Animal. ``

  1. A subclass can override superclass behavior.
  1. A superclass reference can refer to subclass objects.

``java Animal a = new Dog(); ``

  1. Overridden methods are selected according to the runtime object type.
  1. Abstract classes represent incomplete generalizations that subclasses complete.
  1. Interfaces represent behavioral contracts.
  1. Polymorphism lets us write code against abstractions rather than specific implementations.
  1. Inheritance should be used deliberately; composition is often the better design for has-a relationships.

The larger lesson is that object-oriented programming is not primarily about building complicated class hierarchies. It is about identifying useful abstractions and designing software so that different implementations can be used through stable, well-defined interfaces.
