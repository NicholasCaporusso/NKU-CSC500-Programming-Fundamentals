1. From classes to class hierarchies

In previous weeks, we learned how to create classes that bundle together:

  • state, represented by fields;
  • behavior, represented by methods;
  • constructors that initialize objects;
  • access modifiers that enforce encapsulation.

For example:

public class Student {

    private String name;
    private int id;

    public Student(String name, int id) {
        this.name = name;
        this.id = id;
    }

    public String getName() {
        return name;
    }

    public int getId() {
        return id;
    }
}

Suppose our program also needs an Employee class:

public class Employee {

    private String name;
    private int id;
    private double salary;

    public Employee(String name, int id, double salary) {
        this.name = name;
        this.id = id;
        this.salary = salary;
    }

    public String getName() {
        return name;
    }

    public int getId() {
        return id;
    }

    public double getSalary() {
        return salary;
    }
}

Notice the duplication.

Both a student and an employee have:

name
id

More importantly, both are conceptually kinds of people:

Student is a Person.
Employee is a Person.

Instead of defining the common characteristics independently in every class, we can define a more general class:

public class Person {

    private String name;
    private int id;

    public Person(String name, int id) {
        this.name = name;
        this.id = id;
    }

    public String getName() {
        return name;
    }

    public int getId() {
        return id;
    }
}

Then we can define specialized classes:

public class Student extends Person {

    private String major;

    public Student(String name, int id, String major) {
        super(name, id);
        this.major = major;
    }

    public String getMajor() {
        return major;
    }
}

and:

public class Employee extends Person {

    private double salary;

    public Employee(String name, int id, double salary) {
        super(name, id);
        this.salary = salary;
    }

    public double getSalary() {
        return salary;
    }
}

We have now created an inheritance hierarchy.

2. What is inheritance?

Inheritance is an object-oriented mechanism through which one class is defined as a more specialized form of another class.

Consider:

public class Animal {
}

and:

public class Dog extends Animal {
}

Animal is the more general class.

Dog is the more specialized class.

Several terms are used for these roles.

General classSpecialized class
superclasssubclass
parent classchild class
base classderived class

In this course, we will normally use superclass and subclass.

The Java syntax is:

class Subclass extends Superclass {
}

For example:

public class Dog extends Animal {
}

Conceptually:

Animal
  ↑
  |
 Dog

The arrow can be read as:

Dog is an Animal.

3. The most important test: Is-a

Inheritance should normally represent an is-a relationship.

Examples:

Dog is an Animal.
Cat is an Animal.
Professor is an Employee.
SavingsAccount is a BankAccount.
Circle is a Shape.
Truck is a Vehicle.

These relationships could reasonably be represented using inheritance.

For example:

public class Dog extends Animal {
}

or:

public class SavingsAccount extends BankAccount {
}

A useful question is:

Can every object of the subclass reasonably be treated as an object of the superclass?

For example:

Every Dog can be treated as an Animal.        Yes.
Every Circle can be treated as a Shape.       Yes.
Every SavingsAccount can be treated as a BankAccount. Yes.

Now consider:

Car is an Engine.
Computer is a Processor.
Student is a Course.
House is a Room.

These statements do not make conceptual sense.

The real relationships are closer to:

Car has an Engine.
Computer has a Processor.
House has Rooms.
Student takes Courses.

These are not normally inheritance relationships.

They are usually modeled through composition or other object relationships.

4. Is-a versus has-a

This distinction is one of the most important design decisions in object-oriented programming.

Is-a

An is-a relationship usually suggests inheritance.

Dog is an Animal.
public class Dog extends Animal {
}

Has-a

A has-a relationship usually suggests composition.

Car has an Engine.

We might write:

public class Engine {

    public void start() {
        System.out.println("Engine started.");
    }
}

and:

public class Car {

    private Engine engine;

    public Car() {
        engine = new Engine();
    }

    public void start() {
        engine.start();
    }
}

Here:

Car
 |
 | has an
 v
Engine

We should not write:

public class Car extends Engine {
}

A car is not a specialized kind of engine.

Useful rule

"is-a"  → consider inheritance
"has-a" → consider composition

The word consider matters. An is-a statement does not automatically guarantee that inheritance is the best software design, but it is an important first test.

5. A basic inheritance example

Consider a bank account:

public class BankAccount {

    private String accountNumber;
    private double balance;

    public BankAccount(String accountNumber, double balance) {
        this.accountNumber = accountNumber;
        this.balance = balance;
    }

    public void deposit(double amount) {
        balance += amount;
    }

    public void withdraw(double amount) {
        balance -= amount;
    }

    public String getAccountNumber() {
        return accountNumber;
    }

    public double getBalance() {
        return balance;
    }
}

Now suppose a savings account behaves like a bank account but also has an interest rate.

public class SavingsAccount extends BankAccount {

    private double interestRate;

    public SavingsAccount(
            String accountNumber,
            double balance,
            double interestRate) {

        super(accountNumber, balance);
        this.interestRate = interestRate;
    }

    public void addInterest() {
        double interest = getBalance() * interestRate;
        deposit(interest);
    }
}

Now:

SavingsAccount account =
    new SavingsAccount("A123", 1000.0, 0.05);

account.deposit(200.0);
account.addInterest();

System.out.println(account.getBalance());

SavingsAccount does not define:

deposit()
getBalance()
getAccountNumber()

Those behaviors come from BankAccount.

But SavingsAccount also introduces its own state and behavior:

interestRate
addInterest()

Conceptually, a SavingsAccount object contains both:

BankAccount characteristics
        +
SavingsAccount-specific characteristics

6. What does a subclass get from its superclass?

Suppose:

public class Animal {

    public void eat() {
        System.out.println("Eating...");
    }

    public void sleep() {
        System.out.println("Sleeping...");
    }
}

and:

public class Dog extends Animal {

    public void bark() {
        System.out.println("Woof!");
    }
}

Then:

Dog dog = new Dog();

dog.eat();
dog.sleep();
dog.bark();

is legal.

Dog can use:

  • eat() from Animal;
  • sleep() from Animal;
  • bark() from Dog.

This gives subclasses access to reusable superclass behavior.

However, the statement "a subclass inherits everything" is too simplistic.

Access control still matters.

7. Inheritance does not remove encapsulation

Consider:

public class Person {

    private String name;

    public Person(String name) {
        this.name = name;
    }
}

Now suppose we write:

public class Student extends Person {

    public Student(String name) {
        super(name);
    }

    public void printName() {
        System.out.println(name);  // ERROR
    }
}

This does not compile.

Why?

Because name is:

private

A private field may be accessed directly only inside the class that declares it.

Student is not allowed to manipulate Person's private field directly.

The object still contains the state associated with that field. The important point is that the field is controlled by the Person class.

A better design is:

public class Person {

    private String name;

    public Person(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }
}

Now the subclass can write:

public class Student extends Person {

    public Student(String name) {
        super(name);
    }

    public void printName() {
        System.out.println(getName());
    }
}

This preserves encapsulation.

Important principle

Inheritance does not mean that subclasses should freely manipulate the internal state of their superclasses.

The superclass should remain responsible for protecting its own representation.

9. Should fields be protected?

Java allows this:

public class Person {

    protected String name;
}

Then a subclass can write:

public class Student extends Person {

    public void printName() {
        System.out.println(name);
    }
}

This is convenient, but convenience is not always good design.

A subclass can now modify name directly:

name = null;

That weakens the superclass's control over its state.

Often this is preferable:

public class Person {

    private String name;

    public String getName() {
        return name;
    }
}

or, if controlled modification is appropriate:

protected void setName(String name) {
    this.name = name;
}

The main lesson is:

Do not make fields protected or public merely because subclasses need them.

Preserve encapsulation whenever practical.

10. Constructors and inheritance

A very important rule is:

Constructors are not inherited.

Consider:

public class Person {

    private String name;

    public Person(String name) {
        this.name = name;
    }
}

If Student extends Person, Student does not automatically acquire a Student(String) constructor.

We must define the subclass's constructor:

public class Student extends Person {

    private String major;

    public Student(String name, String major) {
        super(name);
        this.major = major;
    }
}

When we write:

Student s =
    new Student("Alice", "Mathematics");

construction conceptually happens in stages:

new Student(...)
      |
      v
Person portion must be initialized
      |
      v
Person constructor executes
      |
      v
Student-specific fields are initialized
      |
      v
Student constructor completes

11. The super(...) constructor call

Inside a subclass constructor:

super(...)

calls a superclass constructor.

Example:

public class Person {

    private String name;
    private int id;

    public Person(String name, int id) {
        this.name = name;
        this.id = id;
    }
}

Subclass:

public class Student extends Person {

    private String major;

    public Student(String name, int id, String major) {
        super(name, id);
        this.major = major;
    }
}

Here:

super(name, id);

calls:

Person(String name, int id)

The superclass is responsible for initializing its own fields.

The subclass initializes its own fields.

This is good object-oriented design.

12. super(...) must come first

If explicitly written, a superclass constructor call must be the first statement of a constructor.

Correct:

public Student(String name, String major) {
    super(name);
    this.major = major;
}

Incorrect:

public Student(String name, String major) {
    this.major = major;
    super(name);       // ERROR
}

Why is this rule useful?

Before the subclass-specific part of an object is initialized, Java ensures that the superclass part is constructed properly.

13. What happens if we do not write super(...)?

Suppose:

public Student() {
}

If there is no explicit constructor call, Java attempts to behave as though you wrote:

public Student() {
    super();
}

That is, Java attempts to call the superclass's no-argument constructor.

Suppose the superclass is:

public class Person {

    public Person() {
        System.out.println("Person()");
    }
}

Then:

public class Student extends Person {

    public Student() {
        System.out.println("Student()");
    }
}

works.

Creating:

new Student();

prints:

Person()
Student()

14. A common constructor error

Now suppose:

public class Person {

    private String name;

    public Person(String name) {
        this.name = name;
    }
}

There is no:

Person()

constructor.

This subclass will therefore fail:

public class Student extends Person {

    public Student() {
    }
}

Java tries to insert:

super();

but no matching superclass constructor exists.

We need something such as:

public class Student extends Person {

    public Student(String name) {
        super(name);
    }
}

Common debugging question

If Java gives an error involving a superclass constructor, ask:

  1. What superclass constructor is Java trying to call?
  2. Does that constructor exist?
  3. Did I explicitly supply the necessary arguments using super(...)?

Suppose:

16. Method overriding

Inheritance becomes much more powerful when subclasses can specialize behavior.

Suppose:

public class Animal {

    public void makeSound() {
        System.out.println("Some animal sound");
    }
}

A Dog may need a more specific implementation:

public class Dog extends Animal {

    @Override
    public void makeSound() {
        System.out.println("Woof!");
    }
}

A Cat may provide another:

public class Cat extends Animal {

    @Override
    public void makeSound() {
        System.out.println("Meow!");
    }
}

Now:

Dog dog = new Dog();
Cat cat = new Cat();

dog.makeSound();
cat.makeSound();

prints:

Woof!
Meow!

This is called method overriding.

Definition

Method overriding occurs when a subclass provides its own implementation of an inherited instance method.

17. Rules for overriding

At an introductory level, an overriding method should have:

  • the same method name;
  • the same parameter list;
  • a compatible return type;
  • an access level that does not improperly reduce visibility.

For example:

class Parent {

    public void display(int x) {
        System.out.println("Parent: " + x);
    }
}

Correct override:

class Child extends Parent {

    @Override
    public void display(int x) {
        System.out.println("Child: " + x);
    }
}

But:

public void display(double x)

does not override display(int).

It has a different parameter list.

That is an overload.

18. The @Override annotation

When overriding, write:

@Override

before the method.

Example:

@Override
public void makeSound() {
    System.out.println("Woof!");
}

The annotation communicates to Java:

I intend this method to override an inherited method.

Suppose the superclass contains:

public void makeSound() {
}

but we accidentally write:

@Override
public void makesound() {
    System.out.println("Woof!");
}

Notice:

makeSound
makesound

These are different names because Java is case-sensitive.

Because of @Override, the compiler tells us that the method does not actually override anything.

Without @Override, Java could interpret it as an unrelated new method.

Best practice

Use @Override whenever you intend to override a superclass method or implement an interface method.

19. Overriding versus overloading

These two terms are easily confused.

Method overloading

Overloading means using the same method name with different parameter lists.

public void print(int value) {
    System.out.println(value);
}

public void print(double value) {
    System.out.println(value);
}

public void print(String value) {
    System.out.println(value);
}

Which overload is selected depends on the arguments in the method call.

For example:

print(5);
print(2.5);
print("hello");

The compiler determines which overload applies.

Method overriding

Overriding involves inheritance.

class Animal {

    public void speak() {
        System.out.println("Animal");
    }
}
class Dog extends Animal {

    @Override
    public void speak() {
        System.out.println("Dog");
    }
}

Here Dog replaces the inherited implementation for Dog objects.

Comparison

FeatureOverloadingOverriding
Same method name?YesYes
Parameter listDifferentSame
Requires inheritance?NoYes
Main purposeMultiple forms of an operationSpecialized subclass behavior
SelectionPrimarily compile timeRuntime object matters

A useful memory aid:

OVERLOAD  → change the parameters
OVERRIDE  → change inherited behavior

20. Calling the superclass version of an overridden method

Sometimes a subclass wants to extend rather than completely replace superclass behavior.

Suppose:

public class Person {

    public void describe() {
        System.out.println("I am a person.");
    }
}

Then:

public class Student extends Person {

    @Override
    public void describe() {
        super.describe();
        System.out.println("I am also a student.");
    }
}

Calling:

Student s = new Student();
s.describe();

prints:

I am a person.
I am also a student.

The expression:

super.describe();

means:

Invoke the superclass implementation of describe() for this object.

21. Two different uses of super

Do not confuse:

super(...)

with:

super.methodName(...)

super(...)

Invokes a superclass constructor.

public Student(String name) {
    super(name);
}

super.methodName(...)

Invokes a superclass method.

@Override
public void describe() {
    super.describe();
    System.out.println("Student");
}

The same keyword is involved, but the purposes are different.

22. Introducing polymorphism

Inheritance gives us subtype relationships.

Polymorphism lets us take advantage of those relationships.

The word comes from roots meaning roughly:

poly  → many
morph → forms

In programming, polymorphism allows one general type to refer to objects of several more specific types.

Suppose:

public class Animal {

    public void makeSound() {
        System.out.println("Animal sound");
    }
}

and:

public class Dog extends Animal {

    @Override
    public void makeSound() {
        System.out.println("Woof!");
    }
}

We can write:

Animal animal = new Dog();

This is legal.

Why?

Because:

Dog is an Animal.

23. Reference type versus runtime object type

This is the most important mental model in this entire week.

Consider:

Animal animal = new Dog();

Two types appear.

Reference type

The variable is declared:

Animal animal

Therefore its reference type or declared type is:

Animal

Runtime object type

The expression:

new Dog()

creates a Dog.

Therefore the actual object's type is:

Dog

We can visualize this as:

reference variable

Animal animal
      |
      |
      v
+-------------+
| Dog object  |
+-------------+

The two types have different responsibilities.

24. The central polymorphism rule

For:

Animal animal = new Dog();

remember two questions.

Question 1: What operations may I call?

Look at the reference type.

Animal

The compiler asks:

Is this operation valid for an Animal?

Question 2: Which overridden method implementation executes?

Look at the actual runtime object.

Dog

If Dog overrides the method, the Dog version executes.

This gives us the key mental model:

REFERENCE TYPE
    |
    +---- determines what the compiler allows

RUNTIME OBJECT TYPE
    |
    +---- determines which overridden instance method executes

25. Dynamic method dispatch

Suppose:

public class Animal {

    public void makeSound() {
        System.out.println("Animal");
    }
}
public class Dog extends Animal {

    @Override
    public void makeSound() {
        System.out.println("Dog");
    }
}

Now:

Animal animal = new Dog();
animal.makeSound();

What prints?

Dog

At compile time Java verifies that:

makeSound()

is a valid operation for an Animal.

At runtime Java sees that the actual object is a Dog.

Therefore:

Dog.makeSound()

executes.

This runtime selection of an overriding implementation is called dynamic method dispatch.

Other terms you may encounter include:

  • runtime polymorphism;
  • dynamic binding;
  • virtual method dispatch.

For this course, dynamic method dispatch is the main term.

27. Why polymorphism is useful

Suppose we have:

class Dog extends Animal {
    ...
}
class Cat extends Animal {
    ...
}
class Cow extends Animal {
    ...
}

Without polymorphism we may be tempted to write special-case logic:

if (type.equals("dog")) {
    ...
} else if (type.equals("cat")) {
    ...
} else if (type.equals("cow")) {
    ...
}

Polymorphism lets the objects provide their own behavior.

For example:

Animal[] animals = {
    new Dog(),
    new Cat(),
    new Cow()
};

Then:

for (Animal animal : animals) {
    animal.makeSound();
}

might print:

Woof!
Meow!
Moo!

The loop contains no:

if
else if
instanceof

logic for individual animal types.

It simply asks every animal to perform an operation all animals support:

animal.makeSound();

Each object responds appropriately.

28. Polymorphism and extensibility

Suppose we later add:

public class Sheep extends Animal {

    @Override
    public void makeSound() {
        System.out.println("Baa!");
    }
}

Now we can place it into the same collection:

Animal[] animals = {
    new Dog(),
    new Cat(),
    new Cow(),
    new Sheep()
};

Our loop remains:

for (Animal animal : animals) {
    animal.makeSound();
}

No change is necessary.

That is one of the major advantages of good polymorphic design:

New implementations can often be added without rewriting code that depends only on the common abstraction.

29. A practical payroll example

Consider a payroll system.

Every employee has a name, but different kinds of employees calculate pay differently.

We could begin with:

public class Employee {

    private String name;

    public Employee(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }

    public double calculatePay() {
        return 0.0;
    }
}

A salaried employee:

public class SalariedEmployee extends Employee {

    private double annualSalary;

    public SalariedEmployee(
            String name,
            double annualSalary) {

        super(name);
        this.annualSalary = annualSalary;
    }

    @Override
    public double calculatePay() {
        return annualSalary / 12.0;
    }
}

An hourly employee:

public class HourlyEmployee extends Employee {

    private double hourlyRate;
    private double hoursWorked;

    public HourlyEmployee(
            String name,
            double hourlyRate,
            double hoursWorked) {

        super(name);
        this.hourlyRate = hourlyRate;
        this.hoursWorked = hoursWorked;
    }

    @Override
    public double calculatePay() {
        return hourlyRate * hoursWorked;
    }
}

Now:

Employee[] employees = {
    new SalariedEmployee("Alice", 120000),
    new HourlyEmployee("Bob", 30, 160)
};

We can process them uniformly:

for (Employee employee : employees) {
    System.out.println(
        employee.getName()
        + ": $"
        + employee.calculatePay()
    );
}

calculatePay() behaves differently depending on the actual employee object.

The caller does not need to know the formula.

That responsibility belongs to each subclass.

30. Why returning 0.0 is suspicious

Look again at:

public double calculatePay() {
    return 0.0;
}

What does it mean to calculate the pay of a generic employee?

There may be no meaningful answer.

A generic Employee may exist only as a common concept from which specific employee types are derived.

This motivates abstract classes.

31. Abstract classes

An abstract class is a class designed to serve as a base type but not to be instantiated directly.

We declare one using:

abstract

For example:

public abstract class Employee {

    private String name;

    public Employee(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }

    public abstract double calculatePay();
}

Notice:

public abstract double calculatePay();

There is no method body.

This method declares a requirement:

Every concrete subclass must supply an appropriate implementation of calculatePay().

32. Abstract methods

An abstract method specifies an operation without providing its implementation.

Syntax:

public abstract double calculatePay();

Notice the semicolon:

;

There is no:

{
    ...
}

body.

A concrete subclass must implement the method.

For example:

public class SalariedEmployee extends Employee {

    private double annualSalary;

    public SalariedEmployee(
            String name,
            double annualSalary) {

        super(name);
        this.annualSalary = annualSalary;
    }

    @Override
    public double calculatePay() {
        return annualSalary / 12.0;
    }
}

If a subclass does not implement all inherited abstract methods, then that subclass must itself remain abstract.

33. Abstract classes cannot be instantiated

If:

public abstract class Employee {
    ...
}

then this is illegal:

Employee employee = new Employee("Alice");

Why?

Employee represents an incomplete general concept.

However, this is legal:

Employee employee =
    new SalariedEmployee("Alice", 120000);

The reference type is:

Employee

but the runtime object type is:

SalariedEmployee

The actual object is concrete and fully implements the required behavior.

34. Abstract classes can still have constructors

A common misconception is:

If an abstract class cannot be instantiated, why would it need a constructor?

Because the superclass portion of subclass objects still needs to be initialized.

Example:

public abstract class Vehicle {

    private String manufacturer;

    public Vehicle(String manufacturer) {
        this.manufacturer = manufacturer;
    }

    public String getManufacturer() {
        return manufacturer;
    }
}

Subclass:

public class Car extends Vehicle {

    public Car(String manufacturer) {
        super(manufacturer);
    }
}

Creating:

Car car = new Car("Honda");

still invokes the Vehicle constructor.

The constructor is not used to create a standalone Vehicle.

It is used to initialize the Vehicle portion of a subclass object.

35. Abstract classes can mix concrete and abstract behavior

An abstract class is not simply an interface written with different syntax.

It can contain:

  • instance fields;
  • constructors;
  • concrete methods;
  • abstract methods;
  • static methods.

Example:

public abstract class Employee {

    private String name;
    private int id;

    public Employee(String name, int id) {
        this.name = name;
        this.id = id;
    }

    public String getName() {
        return name;
    }

    public int getId() {
        return id;
    }

    public void printIdentity() {
        System.out.println(id + ": " + name);
    }

    public abstract double calculatePay();
}

All employee subclasses share:

name
id
getName()
getId()
printIdentity()

but each must provide its own:

calculatePay()

36. Example: Abstract shape hierarchy

Suppose every shape has an area and perimeter, but the formulas differ.

public abstract class Shape {

    public abstract double area();

    public abstract double perimeter();
}

A circle:

public class Circle extends Shape {

    private double radius;

    public Circle(double radius) {
        this.radius = radius;
    }

    @Override
    public double area() {
        return Math.PI * radius * radius;
    }

    @Override
    public double perimeter() {
        return 2 * Math.PI * radius;
    }
}

A rectangle:

public class Rectangle extends Shape {

    private double width;
    private double height;

    public Rectangle(double width, double height) {
        this.width = width;
        this.height = height;
    }

    @Override
    public double area() {
        return width * height;
    }

    @Override
    public double perimeter() {
        return 2 * (width + height);
    }
}

Now:

Shape[] shapes = {
    new Circle(5),
    new Rectangle(4, 8),
    new Circle(2)
};

We can calculate a total:

double totalArea = 0.0;

for (Shape shape : shapes) {
    totalArea += shape.area();
}

System.out.println(totalArea);

The loop does not know or care which formula applies.

Each object provides its own implementation.

37. Concrete versus abstract classes

A concrete class can be instantiated:

Circle c = new Circle(5);

An abstract class cannot:

Shape s = new Shape(); // ERROR

A useful design question is:

Does this class represent objects that should meaningfully exist on their own?

If yes, a concrete class may be appropriate.

If the class represents an incomplete general category whose specialized subclasses supply important behavior, an abstract class may be appropriate.

38. Interfaces

Inheritance is useful when classes belong to a meaningful common family.

Sometimes, however, completely different kinds of objects need to support the same behavior.

Suppose we want to represent things that can be printed:

public interface Printable {

    void print();
}

An interface defines a behavioral contract.

It says:

Any class implementing Printable promises to provide a print() operation.

A class implements an interface using:

implements

For example:

public class Report implements Printable {

    @Override
    public void print() {
        System.out.println("Printing report...");
    }
}

Another class:

public class Photo implements Printable {

    @Override
    public void print() {
        System.out.println("Printing photo...");
    }
}

These classes may be otherwise unrelated.

But both satisfy the Printable contract.

39. Interface methods and public

Consider:

public interface Printable {
    void print();
}

An implementing class should write:

@Override
public void print() {
    ...
}

not:

void print() {
    ...
}

Why?

The interface method is part of a public contract. The implementing class cannot provide a less-accessible implementation.

For introductory Java programming, use:

@Override
public ...

for interface methods.

40. Interface references

An interface is also a Java reference type.

We can write:

Printable item = new Report();

The reference type is:

Printable

The object type is:

Report

Then:

item.print();

executes:

Report.print()

This is polymorphism.

We can also write:

Printable p1 = new Report();
Printable p2 = new Photo();

p1.print();
p2.print();

Possible output:

Printing report...
Printing photo...

41. Polymorphism does not require a common custom superclass

Suppose:

class Report implements Printable {
    ...
}

and:

class Photo implements Printable {
    ...
}

Report and Photo may have very different data and purposes.

Yet we can write:

Printable[] items = {
    new Report(),
    new Photo()
};

and:

for (Printable item : items) {
    item.print();
}

This is one major advantage of interfaces.

They allow otherwise unrelated classes to participate in the same behavioral abstraction.

42. Classes can implement multiple interfaces

Java permits a class to directly extend only one class.

This is legal:

public class Dog extends Animal {
}

This is not:

public class Dog extends Animal, Pet {
}

Java does not support this form of multiple class inheritance.

However, a class may implement multiple interfaces.

For example:

public interface Printable {
    void print();
}
public interface Saveable {
    void save();
}

A class may implement both:

public class Report
        implements Printable, Saveable {

    @Override
    public void print() {
        System.out.println("Printing report");
    }

    @Override
    public void save() {
        System.out.println("Saving report");
    }
}

Conceptually:

Report can be treated as Printable.
Report can be treated as Saveable.

43. Extending a class and implementing interfaces

A class can also extend one superclass while implementing interfaces.

For example:

public class OnlineReport
        extends Report
        implements Saveable {

    @Override
    public void save() {
        System.out.println("Saving online report.");
    }
}

The general syntax is:

class Child extends Parent implements Interface1, Interface2 {
}

44. Abstract class versus interface

Both abstract classes and interfaces support abstraction and polymorphism, but they play somewhat different design roles.

Abstract classInterface
Often represents a shared familyOften represents a capability/contract
Uses extendsUses implements
Can contain instance fieldsDoes not normally represent ordinary per-object instance state
Can have constructorsNo ordinary object constructor
Can contain concrete methodsCan define required behavior and certain implemented behaviors
Can contain abstract methodsCommonly declares required operations
Class extends only one classClass may implement multiple interfaces
Good for shared implementation/stateGood for shared behavioral requirements

A useful intuition is:

abstract class → what something fundamentally is

interface      → what something can do

Examples:

Dog is an Animal.
Circle is a Shape.
HourlyEmployee is an Employee.

These suggest a class hierarchy.

But:

Report is Printable.
Photo is Printable.
Invoice is Printable.

These suggest a shared capability.

This is a design guideline, not a mechanical law.

45. Choosing between a regular class, abstract class, and interface

Use a regular class when

Objects of the class should be created directly.

Example:

Student student =
    new Student("Alice", 1001);

Use an abstract class when

There is a meaningful common family with shared state or implementation, but the general type should not normally exist by itself.

Example:

Shape
 ├── Circle
 ├── Rectangle
 └── Triangle

Use an interface when

You primarily want to express a capability that multiple classes can satisfy.

Example:

Printable
 ├── Report
 ├── Invoice
 └── Photo

46. Programming to an abstraction

Consider:

public void printReport(LaserPrinter printer) {
    ...
}

This method requires exactly:

LaserPrinter

What if we later want to use:

InkjetPrinter
PdfPrinter
NetworkPrinter

Instead, we might define:

public interface Printer {

    void print(String text);
}

Then:

public void printReport(
        Printer printer,
        String reportText) {

    printer.print(reportText);
}

Now any object satisfying Printer can be used.

For example:

class LaserPrinter implements Printer {

    @Override
    public void print(String text) {
        System.out.println("Laser: " + text);
    }
}
class PdfPrinter implements Printer {

    @Override
    public void print(String text) {
        System.out.println("PDF: " + text);
    }
}

The method depends on the behavior it requires, not on one specific implementation.

This idea is often summarized as:

Program to abstractions rather than unnecessarily depending on concrete implementations.

47. Connecting this idea to Java collections

You may eventually see code such as:

List<String> names = new ArrayList<>();

instead of:

ArrayList<String> names = new ArrayList<>();

The idea is similar.

The program says:

I need something that behaves like a List.

It does not unnecessarily say:

My entire design depends specifically on ArrayList.

The same principle applies to our own class hierarchies and interfaces.

48. Polymorphic arrays

We can store different subclass objects in an array whose element type is the superclass.

For example:

Animal[] animals = new Animal[4];

animals[0] = new Dog();
animals[1] = new Cat();
animals[2] = new Cow();
animals[3] = new Dog();

Then:

for (Animal animal : animals) {
    animal.makeSound();
}

The array contains references whose declared abstraction is:

Animal

but the individual runtime objects may have different types.

49. Polymorphic ArrayLists

We can use the same idea with an ArrayList.

ArrayList<Shape> shapes = new ArrayList<>();

shapes.add(new Circle(5));
shapes.add(new Rectangle(4, 8));
shapes.add(new Circle(2));

Then:

for (Shape shape : shapes) {
    System.out.println(shape.area());
}

This pattern is extremely important:

collection
    +
shared abstraction
    +
polymorphism

It allows heterogeneous objects to be processed uniformly.

50. Compile-time type checking

Consider:

Animal animal = new Dog();

Suppose Animal contains:

public void makeSound() {
}

and Dog contains:

@Override
public void makeSound() {
    System.out.println("Woof");
}

public void fetch() {
    System.out.println("Fetching...");
}

This works:

animal.makeSound();

But this does not:

animal.fetch();   // ERROR

Why?

The compiler sees the variable as:

Animal

It asks:

Does Animal guarantee that fetch() exists?

No.

A different possible Animal object could be a Cat, and a cat may not support fetch().

Therefore the compiler rejects the operation.

51. Method call: Two-step reasoning

Whenever you see:

animal.someMethod();

and inheritance is involved, reason in two stages.

Stage 1: Compile-time legality

Look at the declared reference type.

For:

Animal animal = new Dog();

ask:

Does Animal provide someMethod()?

If not, the call does not compile.

Stage 2: Runtime implementation

If the call is legal, ask:

What is the actual object's type?

If the method is overridden, that runtime type determines which implementation executes.

This is one of the most important problem-solving strategies for Week 8.

52. Upcasting

Consider:

Dog dog = new Dog();
Animal animal = dog;

The conversion:

Dog → Animal

moves from a more specific type to a more general type.

This is called upcasting.

Java performs it automatically.

We can simply write:

Animal animal = new Dog();

No explicit cast is required because every Dog is an Animal.

Upcasting is the normal foundation of polymorphism.

53. Downcasting

Suppose:

Animal animal = new Dog();

Because the reference type is Animal, this does not compile:

animal.fetch();

If we know that the runtime object really is a Dog, we can perform a downcast:

Dog dog = (Dog) animal;
dog.fetch();

or:

((Dog) animal).fetch();

The cast:

(Dog)

tells Java:

Treat this reference as a Dog.

But downcasting must be used carefully.

54. Unsafe downcasting

Consider:

Animal animal = new Cat();

Dog dog = (Dog) animal;

The compiler may permit the cast because Dog and Animal are related types.

However, at runtime the actual object is a Cat, not a Dog.

The cast is invalid.

Therefore downcasting may fail at runtime.

The important conceptual point is:

A cast does not change the object.

This:

(Dog) animal

does not transform a Cat into a Dog.

It only tells Java how you intend to treat the reference.

55. instanceof

Java provides the instanceof operator for testing whether an object is compatible with a particular type.

Example:

Animal animal = new Dog();

if (animal instanceof Dog) {
    Dog dog = (Dog) animal;
    dog.fetch();
}

The condition asks whether the runtime object referenced by animal can be treated as a Dog.

Another example:

if (animal instanceof Cat) {
    System.out.println("This is a cat.");
}

56. Do not use instanceof to replace polymorphism

Suppose we write:

if (animal instanceof Dog) {
    System.out.println("Woof");
} else if (animal instanceof Cat) {
    System.out.println("Meow");
} else if (animal instanceof Cow) {
    System.out.println("Moo");
}

This may be a sign that the design should instead use:

animal.makeSound();

with overriding.

Why?

Each object should often know how to perform its own behavior.

Compare:

if (animal instanceof Dog) {
    ((Dog) animal).makeSound();
} else if (animal instanceof Cat) {
    ((Cat) animal).makeSound();
}

with:

animal.makeSound();

The polymorphic version is:

  • shorter;
  • easier to extend;
  • less coupled to concrete types;
  • usually easier to maintain.

instanceof is useful when actual type-specific logic is truly required, but frequent type checking can indicate that you are not taking full advantage of polymorphism.

57. Polymorphism is about asking objects to behave

A weak design often asks:

What kind of object are you?

then performs the behavior externally.

For example:

if (employee instanceof HourlyEmployee) {
    ...
} else if (employee instanceof SalariedEmployee) {
    ...
}

A more polymorphic design says:

double pay = employee.calculatePay();

Each employee object knows how it calculates its own pay.

This leads to a central object-oriented principle:

Ask objects to perform operations through a shared abstraction rather than repeatedly asking what concrete type they are.

58. Object: The root of Java class hierarchies

Every Java class ultimately derives from:

java.lang.Object

Suppose we define:

public class Student {
}

Conceptually:

Object
  ↑
Student

Suppose:

public class Person {
}

and:

public class Student extends Person {
}

Then:

Object
  ↑
Person
  ↑
Student

This is why all Java objects have methods associated with Object, including methods such as:

toString()
equals()
hashCode()
getClass()

You may override some of these methods when appropriate.

59. Overriding toString()

One especially useful inherited method is:

toString()

Suppose:

public class Student {

    private String name;
    private int id;

    public Student(String name, int id) {
        this.name = name;
        this.id = id;
    }
}

If we write:

Student student =
    new Student("Alice", 1001);

System.out.println(student);

Java implicitly asks for a string representation of the object.

The default representation is often not useful to a human reader.

We can override toString():

public class Student {

    private String name;
    private int id;

    public Student(String name, int id) {
        this.name = name;
        this.id = id;
    }

    @Override
    public String toString() {
        return "Student{name='" + name
            + "', id=" + id + "}";
    }
}

Now:

System.out.println(student);

might print:

Student{name='Alice', id=1001}

60. toString() is also polymorphic

Because toString() is an instance method, normal overriding rules apply.

Consider:

Object item = new Student("Alice", 1001);

System.out.println(item.toString());

The reference type is:

Object

The runtime object type is:

Student

If Student overrides toString(), the Student implementation executes.

Once again:

reference type → what calls are legal
runtime type   → which override runs

61. Can private methods be overridden?

No.

A private method is not accessible to the subclass as an overridable inherited method.

Suppose:

class Parent {

    private void display() {
        System.out.println("Parent");
    }
}

and:

class Child extends Parent {

    public void display() {
        System.out.println("Child");
    }
}

Child.display() is not an override of Parent.display().

It is a different method.

This is another reason @Override is valuable. If you incorrectly write:

@Override
public void display() {
    ...
}

Java will tell you that no valid inherited method is being overridden.

62. Can static methods be overridden?

Static methods do not participate in runtime overriding in the same way instance methods do.

Consider:

class Parent {

    public static void identify() {
        System.out.println("Parent");
    }
}
class Child extends Parent {

    public static void identify() {
        System.out.println("Child");
    }
}

This is generally described as method hiding, not overriding.

For Week 8, remember:

Dynamic method dispatch applies to overridden instance methods, not static methods.

Therefore, when reasoning about polymorphism, focus primarily on instance methods.

63. Fields are not polymorphic methods

Suppose:

class Parent {
    public String label = "Parent";
}

and:

class Child extends Parent {
    public String label = "Child";
}

Then:

Parent x = new Child();

System.out.println(x.label);

does not behave like an overridden method.

Field access is resolved according to the reference expression rather than dynamic method dispatch.

This is one reason why hiding fields with the same name in a subclass is usually confusing.

Prefer:

  • private fields;
  • appropriately named methods;
  • method overriding when behavior needs specialization.

64. Constructors cannot be overridden

Constructors are not inherited methods.

Therefore they cannot be overridden.

These are simply constructors for different classes:

class Person {

    public Person() {
    }
}
class Student extends Person {

    public Student() {
    }
}

The subclass constructor may call the superclass constructor, but it does not override it.

Remember:

methods      → may be inherited and overridden
constructors → not inherited, not overridden

65. final and inheritance

The keyword final can restrict inheritance-related behavior.

Final class

public final class Utility {
}

A final class cannot be subclassed.

This is illegal:

public class SpecialUtility extends Utility {
}

Final method

public class Parent {

    public final void display() {
        System.out.println("Parent");
    }
}

A subclass cannot override display().

public class Child extends Parent {

    // ERROR
    @Override
    public void display() {
        System.out.println("Child");
    }
}

The superclass is stating that this particular behavior must not be replaced by subclasses.

66. Composition versus inheritance revisited

Inheritance creates a strong relationship between classes.

A subclass depends on its superclass's:

  • behavior;
  • design;
  • assumptions;
  • public and protected API.

Therefore inheritance should not be used merely because two classes share some code.

Consider:

class Bird {
    public void eat() {
        ...
    }
}

You should not automatically make every class that needs an eat() method extend Bird.

Code reuse alone is not enough.

The relationship must also make conceptual sense.

Ask:

Is the subclass genuinely substitutable for the superclass?

If the answer is no, composition or an interface may be a better design.

67. Why composition is often safer

Consider:

public class Engine {

    public void start() {
        System.out.println("Engine started.");
    }
}

Composition:

public class Car {

    private Engine engine;

    public Car(Engine engine) {
        this.engine = engine;
    }

    public void start() {
        engine.start();
    }
}

This design says:

Car has an Engine.

The Car can delegate engine-related work to the Engine.

This relationship is usually more accurate and less tightly coupled than pretending:

Car is an Engine.

68. A useful design decision process

When deciding among inheritance, interfaces, and composition, ask the following questions.

Question 1

Is one type genuinely a specialized version of another?

Dog is an Animal?

If yes, inheritance may make sense.

Question 2

Do several possibly unrelated classes need to guarantee the same behavior?

Report can print.
Photo can print.
Invoice can print.

An interface may make sense.

Question 3

Does one object contain or use another object?

Car has an Engine.
Course has Students.
Computer has a Processor.

Composition may make sense.

Question 4

Am I using inheritance only because I want to reuse a few lines of code?

If yes, reconsider the design.

69. Keep inheritance hierarchies understandable

It is possible to construct very deep hierarchies:

Entity
  |
LivingThing
  |
Animal
  |
Mammal
  |
Canine
  |
DomesticCanine
  |
Dog
  |
WorkingDog
  |
PoliceDog

A hierarchy like this may become difficult to reason about.

Questions become harder:

  • Where was this method defined?
  • Which class owns this field?
  • Which constructor runs?
  • Which behavior has been overridden?
  • Which assumptions must every subclass satisfy?

More inheritance does not automatically produce better object-oriented design.

Prefer simple, meaningful hierarchies unless the problem genuinely requires more depth.

70. Complete example: Notifications

Consider a system that sends different kinds of notifications.

We begin with an interface:

public interface Notification {

    void send();
}

Email implementation:

public class EmailNotification
        implements Notification {

    private String emailAddress;

    public EmailNotification(String emailAddress) {
        this.emailAddress = emailAddress;
    }

    @Override
    public void send() {
        System.out.println(
            "Sending email to " + emailAddress
        );
    }
}

SMS implementation:

public class SmsNotification
        implements Notification {

    private String phoneNumber;

    public SmsNotification(String phoneNumber) {
        this.phoneNumber = phoneNumber;
    }

    @Override
    public void send() {
        System.out.println(
            "Sending SMS to " + phoneNumber
        );
    }
}

Now:

ArrayList<Notification> notifications =
    new ArrayList<>();

notifications.add(
    new EmailNotification("alice@example.com")
);

notifications.add(
    new SmsNotification("555-0100")
);

Processing:

for (Notification notification : notifications) {
    notification.send();
}

The loop knows only:

Every Notification supports send().

It does not need to know exactly how each notification is delivered.

71. Extending the notification example

Suppose later we introduce:

public class PushNotification
        implements Notification {

    @Override
    public void send() {
        System.out.println(
            "Sending push notification..."
        );
    }
}

We can add:

notifications.add(new PushNotification());

The loop remains:

for (Notification notification : notifications) {
    notification.send();
}

This demonstrates extensibility through abstraction.

72. Complete example: Course assignments

Suppose a course has several assignment types.

Every assignment has:

  • a title;
  • points possible.

But different assignments may calculate grades differently.

We can define:

public abstract class Assignment {

    private String title;
    private double pointsPossible;

    public Assignment(
            String title,
            double pointsPossible) {

        this.title = title;
        this.pointsPossible = pointsPossible;
    }

    public String getTitle() {
        return title;
    }

    public double getPointsPossible() {
        return pointsPossible;
    }

    public abstract double calculateScore();
}

A quiz:

public class Quiz extends Assignment {

    private int correctAnswers;
    private int totalQuestions;

    public Quiz(
            String title,
            double pointsPossible,
            int correctAnswers,
            int totalQuestions) {

        super(title, pointsPossible);

        this.correctAnswers = correctAnswers;
        this.totalQuestions = totalQuestions;
    }

    @Override
    public double calculateScore() {
        double fraction =
            (double) correctAnswers / totalQuestions;

        return fraction * getPointsPossible();
    }
}

A project:

public class Project extends Assignment {

    private double earnedPoints;

    public Project(
            String title,
            double pointsPossible,
            double earnedPoints) {

        super(title, pointsPossible);
        this.earnedPoints = earnedPoints;
    }

    @Override
    public double calculateScore() {
        return earnedPoints;
    }
}

Now:

Assignment[] assignments = {
    new Quiz("Quiz 1", 20, 8, 10),
    new Project("Project 1", 100, 92),
    new Quiz("Quiz 2", 20, 9, 10)
};

Then:

for (Assignment assignment : assignments) {

    System.out.println(
        assignment.getTitle()
        + ": "
        + assignment.calculateScore()
    );
}

No type-checking logic is necessary.

73. A detailed polymorphism trace

Consider:

abstract class Shape {

    public abstract double area();

    public void describe() {
        System.out.println("I am a shape.");
    }
}
class Circle extends Shape {

    private double radius;

    public Circle(double radius) {
        this.radius = radius;
    }

    @Override
    public double area() {
        return Math.PI * radius * radius;
    }

    @Override
    public void describe() {
        System.out.println("I am a circle.");
    }

    public double getRadius() {
        return radius;
    }
}

Now:

Shape s = new Circle(5);

Let's reason carefully.

Can we write this?

s.area();

Yes.

Shape declares area().

Which implementation runs?

Circle.area()

because the object is a Circle.

Can we write this?

s.describe();

Yes.

Shape declares describe().

Which version runs?

Circle.describe()

because Circle overrides it.

Can we write this?

s.getRadius();

No.

getRadius() is not part of the Shape reference type.

Could we downcast?

If we know the object is a circle:

Circle c = (Circle) s;
System.out.println(c.getRadius());

Yes.

But if a large amount of code needs to downcast repeatedly, reconsider whether the abstraction exposes the behavior the program actually needs.

74. A common exam-style example

What does this print?

class A {

    public void f() {
        System.out.println("A");
    }
}
class B extends A {

    @Override
    public void f() {
        System.out.println("B");
    }
}
class C extends B {

    @Override
    public void f() {
        System.out.println("C");
    }
}

Main code:

A x = new A();
A y = new B();
A z = new C();

x.f();
y.f();
z.f();

Output:

A
B
C

Reason:

x refers to A object → A.f()
y refers to B object → B.f()
z refers to C object → C.f()

The reference type of all three variables is A.

But that does not force A.f() to execute.

The runtime object determines the overriding implementation.

75. Another trace: What is legal?

Suppose:

class Animal {

    public void eat() {
        System.out.println("eat");
    }
}
class Dog extends Animal {

    @Override
    public void eat() {
        System.out.println("dog eats");
    }

    public void fetch() {
        System.out.println("fetch");
    }
}

Now:

Animal a = new Dog();

Analyze each statement.

Statement 1

a.eat();

Legal?

Yes.

Animal declares eat().

Output?

dog eats

because the runtime object is a Dog.

Statement 2

a.fetch();

Legal?

No.

Animal does not declare fetch().

Statement 3

Legal?

Yes, provided the actual object is a Dog.

76. Common Mistake 1: Directly accessing private superclass fields

Incorrect:

public class Student extends Person {

    public void test() {
        name = "Alice";
    }
}

if Person contains:

private String name;

Better:

public String getName() {
    return name;
}

and use the superclass's methods.

77. Common Mistake 2: Making superclass fields public

Students sometimes "fix" the previous problem by writing:

public String name;

This removes much of the protection provided by encapsulation.

Inheritance does not justify making all state public.

Prefer:

private String name;

with controlled methods.

78. Common Mistake 3: Forgetting super(...)

Suppose:

class Person {

    public Person(String name) {
    }
}

This subclass is incomplete:

class Student extends Person {

    public Student() {
    }
}

because Java attempts:

super();

and no no-argument Person constructor exists.

Use an appropriate call:

public Student(String name) {
    super(name);
}

79. Common Mistake 4: Confusing overloading with overriding

Remember:

overloading → different parameter list
overriding  → subclass replaces inherited behavior

Example overload:

print(int x)
print(String x)

Example override:

Animal.makeSound()
Dog.makeSound()

80. Common Mistake 5: Thinking the reference type chooses the override

Incorrect mental model:

Animal a = new Dog();

a is declared Animal,
therefore Animal.makeSound() runs.

Correct mental model:

The reference type confirms that makeSound() is legal.

The actual Dog object determines that
Dog.makeSound() executes.

81. Common Mistake 6: Assuming the runtime type makes every method callable

Incorrect:

Animal a = new Dog();

a.fetch(); // "But the object is a Dog!"

The compiler still reasons from the reference type.

Ask:

Does Animal guarantee fetch()?

If not, the call fails at compile time.

82. Common Mistake 7: Excessive downcasting

Code such as:

if (animal instanceof Dog) {
    ((Dog) animal).makeSound();
} else if (animal instanceof Cat) {
    ((Cat) animal).makeSound();
}

should cause you to ask:

Should makeSound() simply belong to Animal and be overridden?

Frequent downcasting may indicate that the abstraction is not designed around the behavior the program actually needs.

83. Common Mistake 8: Using inheritance only for code reuse

Suppose two classes both contain:

public void printName() {
    ...
}

That fact alone does not mean one should extend the other.

Inheritance says more than:

"These classes share code."

It says:

"The subclass is a specialized kind of the superclass."

Code reuse is a possible benefit of inheritance, not sufficient justification for inheritance.

84. Common Mistake 9: Building very deep hierarchies

Deep inheritance trees can make programs hard to understand.

Before adding another inheritance level, ask:

  • Does this represent a meaningful subtype?
  • Does the new abstraction improve the design?
  • Would composition be simpler?
  • Would an interface express the requirement better?

Prefer clarity over hierarchy depth.

85. Common Mistake 10: Replacing behavior with type codes

Suppose:

class Employee {

    private String type;

    public double calculatePay() {

        if (type.equals("hourly")) {
            ...
        } else if (type.equals("salary")) {
            ...
        }

        return 0;
    }
}

An object-oriented alternative may be:

Employee
 ├── HourlyEmployee
 └── SalariedEmployee

with:

public abstract double calculatePay();

and overriding in subclasses.

This places behavior with the objects responsible for it.

Consider:

                 Shape

          +--------+--------+
          |                 |
       Circle           Rectangle

94. Vocabulary

Inheritance

A mechanism for defining a specialized class from a more general class.

Superclass

The more general class in an inheritance relationship.

Subclass

A more specialized class derived from a superclass.

Is-a relationship

A subtype relationship suitable for considering inheritance.

Dog is an Animal.

Has-a relationship

A composition relationship.

Car has an Engine.

Method overriding

Providing a subclass implementation of an inherited instance method.

Method overloading

Using the same method name with different parameter lists.

super

A keyword used to access superclass constructors or superclass behavior.

Polymorphism

The ability to work through a common type while objects provide type-specific behavior.

Reference type

The declared type of a variable.

Animal a

Runtime object type

The actual class of the object created.

new Dog()

Dynamic method dispatch

Runtime selection of an overridden instance method based on the actual object type.

Abstract class

A class intended as an incomplete/general base type that cannot be directly instantiated.

Abstract method

A method declaration without a concrete implementation.

Interface

A type representing a behavioral contract.

Upcasting

Treating a subtype reference as a more general supertype reference.

Downcasting

Explicitly treating a supertype reference as a more specific subtype reference.

Composition

Building classes using other objects in has-a relationships.

96. A final mental model for polymorphism

Whenever you encounter:

Animal animal = new Dog();

animal.makeSound();

remember three ideas.

1. Inheritance establishes the relationship

Dog IS-A Animal

That is why this assignment is legal:

Animal animal = new Dog();

2. The reference type determines which operations the compiler permits

Reference type:

Animal

The compiler checks whether:

makeSound()

belongs to the Animal abstraction.

3. The runtime object determines which override executes

Runtime type:

Dog

Therefore, if Dog overrides makeSound():

Dog.makeSound()

executes.

Memorize the distinction conceptually rather than memorizing isolated examples:

COMPILE TIME:
"What operations are guaranteed by the reference type?"

RUNTIME:
"Which overridden implementation belongs to the actual object?"

        this.id = id;

    public String getName() {
        return name;
    }

        return id;
    }

    @Override

public class HourlyEmployee
        extends Employee {

    private double hoursWorked;

    public HourlyEmployee(
            String name,
            int id,
            double hourlyRate,
            double hoursWorked) {

        super(name, id);

        this.hourlyRate = hourlyRate;
        this.hoursWorked = hoursWorked;
    }

    @Override
    public double calculatePay() {
        return hourlyRate * hoursWorked;
    }
}

public class SalariedEmployee
        extends Employee {

    private double annualSalary;

    public SalariedEmployee(
            String name,
            int id,
            double annualSalary) {

        super(name, id);
        this.annualSalary = annualSalary;
    }

    public double calculatePay() {

            String name,

            double sales,
            double commissionRate) {

        super(name, id);

        this.sales = sales;
        this.commissionRate = commissionRate;
    }

    @Override
    public double calculatePay() {
        return sales * commissionRate;
    }
}

103. Week 8 takeaways

The most important ideas from Week 8 are:

  1. Inheritance models subtype relationships.
   Dog is an Animal.
  1. Inheritance should represent more than mere code reuse.
  1. Has-a relationships are usually modeled using composition.
   Car has an Engine.
  1. A subclass can specialize inherited behavior through overriding.
  1. Use @Override whenever you intend to override a method.
  1. Overriding and overloading are different concepts.
   overriding  → new subclass implementation
   overloading → different parameter list
  1. Constructors are not inherited.
  1. super(...) initializes the superclass portion of a subclass object.
  1. Private superclass state remains encapsulated.
  1. A superclass or interface reference can refer to objects of more specific types.
    Animal animal = new Dog();
  1. The reference type controls what operations are permitted at compile time.
  1. The runtime object type controls which overridden instance-method implementation executes.
  1. Dynamic method dispatch is the mechanism that makes runtime polymorphism work.
  1. Abstract classes represent general types that may contain shared state and behavior while requiring subclasses to complete certain operations.
  1. Interfaces represent behavioral contracts.
  1. A class can extend only one class but may implement multiple interfaces.
  1. Polymorphic collections let one collection contain multiple concrete object types through a shared abstraction.
  1. Casting can expose subtype-specific operations but should be used deliberately.
  1. Repeated casting and instanceof checks may indicate that behavior belongs in the common abstraction.
  1. Every Java class ultimately derives from Object.
  1. Methods such as toString() can be overridden polymorphically.
  1. Good object-oriented design often depends on abstractions rather than concrete implementations.

The larger lesson is not that object-oriented programming requires complicated class hierarchies.

The larger lesson is:

Identify meaningful abstractions, place behavior with the objects responsible for it, and write code that can work with different implementations through stable common types.
