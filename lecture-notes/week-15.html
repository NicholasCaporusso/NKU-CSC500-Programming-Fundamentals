1. Where we are in the course

During the semester, we have learned many individual programming concepts:

  • variables and expressions
  • conditionals
  • loops

  • arrays
  • classes and objects
  • inheritance
  • interfaces
  • polymorphism
  • exceptions
  • file I/O
  • recursion
  • algorithm analysis
  • searching and sorting
  • lists
  • stacks
  • queues
  • maps
  • sets
  • trees

Knowing these concepts individually is important.

However, real programming problems rarely tell us:

"Use a loop here."

or

"This problem requires a HashMap."

Instead, we are given a problem and must decide:

  1. What information does the program need to represent?
  2. What objects should exist?
  3. What responsibilities should each object have?
  4. What data structures should we use?
  5. What algorithms should we use?
  6. How should the different pieces communicate?
  7. How can we test whether the program works?
  8. How can we design the program so that it can be modified later?

These questions are the subject of software design.

2. Programming vs. software design

Programming is the process of expressing instructions in a programming language.

Software design is the process of deciding:

  • what components should exist,
  • how those components should be organized,
  • what responsibilities they should have,
  • and how they should interact.

Consider the following problem:

Create a program that manages student registrations for university courses.

A beginning programmer may immediately start writing code.

A stronger programmer first asks questions.

For example:

  • What is a student?
  • What is a course?
  • What information belongs to a student?
  • What information belongs to a course?
  • Who is responsible for registration?
  • How are enrolled students stored?
  • Can a student register twice?
  • Does a course have a maximum capacity?
  • Should the program prevent registration when the course is full?
  • How will the system find students?
  • How will the system find courses?

Before writing code, we need a model.

3. A running example: course registration system

Suppose we want to build a simplified university registration system.

The system should support the following operations:

  • add a student
  • add a course
  • enroll a student in a course
  • drop a student from a course
  • display students enrolled in a course
  • display the courses taken by a student
  • find students by ID
  • find courses by course code

A poor implementation might put everything inside one class:

public class RegistrationProgram {
    public static void main(String[] args) {
        // all data
        // all input
        // all registration logic
        // all searching
        // all output
        // all file handling
    }
}

This might work for a tiny program.

But as the program grows, it becomes difficult to:

  • understand,
  • test,
  • modify,
  • reuse,
  • and debug.

Instead, we should identify the major concepts in the problem.

Possible classes include:

Student
Course
RegistrationSystem

We might assign responsibilities as follows.

Student

Responsible for representing one student.

Possible fields:

private String id;
private String name;

Possible methods:

getId()
getName()

Course

Responsible for representing one course.

Possible fields:

private String courseCode;
private String title;
private int capacity;

Possible methods:

getCourseCode()
getTitle()
getCapacity()

Registrationsystem

Responsible for coordinating students and courses.

Possible operations:

addStudent(...)
addCourse(...)
enrollStudent(...)
dropStudent(...)
findStudent(...)
findCourse(...)

This is an example of decomposition.

4. Decomposition

A large problem should usually be divided into smaller problems.

This process is called decomposition.

Instead of asking:

How do I build the entire registration system?

we ask:

How do I represent a student?

Then:

How do I represent a course?

Then:

How do I store students?

Then:

How do I find a student by ID?

Then:

How do I enroll a student?

Each smaller problem is easier to reason about.

Good decomposition usually produces components with clear responsibilities.

5. The single responsibility principle

A useful design guideline is:

A class should have one clear primary responsibility.

This does not mean that a class can only contain one method.

It means that the methods should generally belong to the same conceptual responsibility.

Consider this class:

public class Student {

    private String id;
    private String name;

    public Student(String id, String name) {
        this.id = id;
        this.name = name;
    }

    public void registerForCourse(Course c) {
        // ...
    }

    public void saveDatabase() {
        // ...
    }

    public void printUniversityReport() {
        // ...
    }

    public void sendEmail() {
        // ...
    }
}

The Student class is now responsible for:

  • representing a student,
  • course registration,
  • database persistence,
  • reports,
  • and email.

These are unrelated responsibilities.

A better design might separate them:

Student
RegistrationSystem
StudentRepository
ReportGenerator
EmailService

For CSC500, we do not need to create elaborate enterprise architectures.

The important question is:

Does this responsibility naturally belong to this object?

6. Abstraction

Abstraction means focusing on what something does while hiding unnecessary details about how it does it.

Consider Java's ArrayList.

We can write:

ArrayList<String> names = new ArrayList<>();

names.add("Alice");
names.add("Bob");

System.out.println(names.get(0));

We do not need to know:

  • exactly how much internal memory was allocated,
  • when the backing array is resized,
  • how elements are copied during resizing.

Those details are hidden.

We use the abstraction:

a resizable list

The ability to ignore irrelevant implementation details is one of the most important ideas in computer science.

7. Interfaces and implementations

Consider:

ArrayList<String> names = new ArrayList<>();

This works.

But often this version is preferable:

List<String> names = new ArrayList<>();

Why?

Because List describes the behavior that the program requires.

ArrayList describes one particular implementation.

The declaration:

List<String> names

says:

I need something that behaves like a list.

The declaration:

ArrayList<String> names

says:

I specifically require an ArrayList.

Usually we should depend on the more general abstraction when possible.

8. Programming to an interface

Suppose we write:

List<Student> students = new ArrayList<>();

Later, we might decide that another list implementation is preferable.

For example:

List<Student> students = new LinkedList<>();

Much of the program may continue working without changes.

This is one advantage of programming to an interface rather than an implementation.

Compare:

public void printStudents(ArrayList<Student> students)

with:

public void printStudents(List<Student> students)

The second version is more flexible.

It accepts:

  • ArrayList
  • LinkedList
  • or another class implementing List

when appropriate.

9. Choosing a data structure

One of the most important design decisions is choosing how to represent collections of data.

We should not ask:

Which data structure is best?

There is no universally best data structure.

Instead ask:

Which data structure is appropriate for the operations this program performs?

10. Arrays

Use an array when:

  • the number of elements is fixed or predictable,
  • indexed access is important,
  • simple storage is sufficient.

Example:

double[] temperatures = new double[365];

Advantages:

  • simple
  • fast indexed access
  • low overhead

Disadvantages:

  • fixed size
  • insertion/removal may be inconvenient

11. ArrayList

Use an ArrayList when:

  • the collection changes size,
  • order matters,
  • indexed access is useful,
  • most insertions occur near the end.

Example:

List<Student> students = new ArrayList<>();

Typical operations:

students.add(student);
students.get(i);
students.remove(i);

Accessing an element by index is typically efficient.

Searching for an arbitrary student is generally linear:

O(n)

12. LinkedList

A linked list stores elements using nodes connected by references.

Conceptually:

[A] -> [B] -> [C] -> [D]

A linked structure can be useful when frequent insertion and removal occur at known positions.

However, Java programmers should not automatically choose LinkedList simply because insertions are theoretically efficient.

The entire access pattern matters.

For many general-purpose list operations, ArrayList is an excellent default.

13. Stack

A stack follows:

Last In, First Out

or:

LIFO

Operations typically include:

push
pop
peek

Stacks are useful for:

  • undo operations
  • expression processing
  • depth-first search
  • tracking nested structures
  • function-call behavior

Example:

Browser back history

The most recently visited page is often the first one revisited.

14. Queue

A queue follows:

First In, First Out

or:

FIFO

Queues are useful for:

  • task scheduling
  • print jobs
  • customer service simulations
  • breadth-first search
  • event processing

Example:

Printer jobs

The first submitted job is normally processed first.

15. Set

A set represents a collection in which duplicate elements are not allowed.

Example:

Set<String> registeredIds = new HashSet<>();

A set is useful when the main question is:

Is this item already present?

Example:

if (registeredIds.contains(studentId)) {
    System.out.println("Already registered");
}

A HashSet usually provides very efficient membership checking.

16. Map

A map stores associations between keys and values.

Example:

Map<String, Student> studentsById = new HashMap<>();

We might store:

"S1001" -> Student object
"S1002" -> Student object
"S1003" -> Student object

Then:

Student student = studentsById.get("S1002");

This can be much more appropriate than scanning through a list.

17. List vs. map

Suppose we store 50,000 students.

With a list:

List<Student> students;

to find student "S48172", we might need to inspect many students.

The operation is approximately:

O(n)

With a hash map:

Map<String, Student> studentsById;

we can write:

studentsById.get("S48172");

The average lookup time is approximately:

O(1)

This illustrates an important design principle:

Data structures should reflect how the data will be used.

18. Choose based on operations

Suppose we need to store students.

Ask what operations matter.

Requirement a

"We frequently display all students in registration order."

A list may be appropriate.

Requirement b

"We constantly retrieve students by ID."

A map may be better.

Requirement C

"We only care whether a student ID has appeared."

A set may be sufficient.

Requirement D

"We need both ordering and fast ID lookup."

We may maintain more than one structure if the complexity is justified.

For example:

List<Student> students;
Map<String, Student> studentsById;

However, maintaining multiple structures also creates additional responsibility:

both structures must remain consistent.

Every design choice introduces tradeoffs.

19. A useful data structure decision table

RequirementPossible Structure
Fixed sequence of valuesArray

LIFO processingStack / Deque

Key-value lookupHashMap
Hierarchical dataTree

Do not memorize the table as a rigid rule.

Instead, connect each structure to its operations.

20. Designing around responsibilities

Suppose our registration system has:

public class RegistrationSystem {

    private Map<String, Student> students;
    private Map<String, Course> courses;

}

Why maps?

Because common operations are:

find student using student ID
find course using course code

We might initialize them as:

public RegistrationSystem() {
    students = new HashMap<>();
    courses = new HashMap<>();
}

Then:

public Student findStudent(String id) {
    return students.get(id);
}

and:

public Course findCourse(String courseCode) {
    return courses.get(courseCode);
}

The data structure supports the behavior of the system.

21. Encapsulation revisited

Suppose we have:

public class Course {

    public List<Student> students;

}

Any part of the program can now modify the list:

course.students.clear();

or:

course.students.add(student);

This means the Course object cannot control its own state.

A better design is:

public class Course {

    private List<Student> students;

}

and expose controlled operations:

public boolean enroll(Student student) {
    // validation
}

Now the Course class can enforce rules such as:

  • maximum enrollment
  • duplicate prevention
  • prerequisite rules

This is encapsulation.

22. Preserve class invariants

An invariant is a condition that should always be true for an object.

For a course, possible invariants include:

number of enrolled students <= capacity
capacity >= 0
course code is not null
course code is not empty

Suppose we allow this:

course.setCapacity(-100);

The object may enter an invalid state.

A better class protects its invariants.

For example:

public Course(String code, String title, int capacity) {

    if (capacity < 0) {
        throw new IllegalArgumentException(
            "Capacity cannot be negative"
        );
    }

    this.code = code;
    this.title = title;
    this.capacity = capacity;
}

Objects should protect themselves from invalid states when practical.

23. Cohesion

Cohesion describes how closely related the responsibilities inside a component are.

High cohesion is generally desirable.

Consider:

public class GradeCalculator {

    public double calculateAverage(...) { ... }

    public double calculateMedian(...) { ... }

    public char determineLetterGrade(...) { ... }

}

These operations are closely related.

This class has relatively high cohesion.

Now consider:

public class Utility {

    public double calculateGrade(...) { ... }

    public void sendEmail(...) { ... }

    public void sortStudents(...) { ... }

    public void saveImage(...) { ... }

    public boolean validatePassword(...) { ... }

}

These methods have little relationship.

The class has low cohesion.

Large Utility classes can become a warning sign that responsibilities have not been designed carefully.

24. Coupling

Coupling describes how strongly components depend on each other.

Suppose:

public class ReportGenerator {

    private RegistrationSystem system;

}

This is a reasonable dependency.

Now imagine that ReportGenerator directly modifies:

  • internal student arrays,
  • internal course arrays,
  • private enrollment information,
  • file storage details,
  • user interface state.

The components have become tightly coupled.

Tight coupling makes change difficult.

A useful goal is:

high cohesion
low coupling

That means:

  • each component has a clear purpose,
  • components interact through clear boundaries.

25. Information hiding

A class should expose what other classes need while hiding unnecessary details.

For example:

public class Course {

    private List<Student> students;

    public int getEnrollmentCount() {
        return students.size();
    }
}

A caller can ask:

course.getEnrollmentCount();

The caller does not need to know whether students are stored using:

  • an array,
  • an ArrayList,
  • a HashSet,
  • a database,
  • or something else.

That implementation could change later.

The public interface remains stable.

26. Public apis

The public methods of a class form an API.

API means:

Application Programming Interface

It is the interface through which other code uses a class.

For example, a Course API might include:

public String getCode()

public String getTitle()

public boolean enroll(Student student)

public boolean drop(Student student)

public int getEnrollmentCount()

public boolean isFull()

The caller should not need to know how these methods are implemented.

This is similar to how we use Java library classes.

27. Separate "what" from "how"

Consider:

public Student findStudent(String id)

This describes what the operation does.

The implementation determines how.

Version 1 might scan a list:

for (Student student : students) {
    if (student.getId().equals(id)) {
        return student;
    }
}

Version 2 might use:

return studentsById.get(id);

The public method does not have to change.

That is one of the benefits of abstraction.

28. Avoid long methods

Consider:

public void processRegistration() {

    // read user input

    // validate student

    // find course

    // verify capacity

    // enroll student

    // save data

    // update statistics

    // display messages

    // print report
}

Even if this method works, it contains too many conceptual steps.

A better version may delegate responsibilities:

public void processRegistration() {

    Student student = readStudent();

    Course course = selectCourse();

    validateRegistration(student, course);

    enroll(student, course);

    save();

    displayConfirmation(student, course);
}

Now the high-level algorithm is visible.

29. Methods should express intent

Compare:

if (course.getStudents().size() < course.getCapacity()) {

with:

if (!course.isFull()) {

The second version expresses the intent more clearly.

The details belong inside Course.

For example:

public boolean isFull() {
    return students.size() >= capacity;
}

Readable programs often use well-named methods to express concepts.

30. Naming matters

Compare:

int x;
int n;
ArrayList<String> a;

with:

int enrollmentCount;
int maximumCapacity;
List<String> studentIds;

Good names reduce the amount of mental effort required to understand code.

Names should usually communicate purpose.

Bad names:

data
thing
value
temp
stuff
obj
x

These names are sometimes appropriate for extremely local calculations, but descriptive names are preferable in most program logic.

31. Avoid magic numbers

Consider:

if (score >= 93) {

Why 93?

The meaning is not obvious.

Instead:

private static final int MINIMUM_A_SCORE = 93;

Then:

if (score >= MINIMUM_A_SCORE) {

Named constants make assumptions visible.

32. Refactoring

Refactoring means improving the internal structure of code without changing its externally observable behavior.

For example, suppose we have:

if (students.size() >= capacity) {
    System.out.println("Course full");
}

in several different places.

We might refactor this into:

public boolean isFull() {
    return students.size() >= capacity;
}

Then use:

if (course.isFull()) {

The behavior has not changed.

The design has improved.

33. Why refactor?

Programs usually evolve.

You may first write code that works.

Then you realize:

  • logic is duplicated,
  • methods are too long,
  • names are unclear,
  • responsibilities are misplaced,
  • data structures are inappropriate.

Refactoring improves the code after we understand the problem better.

Good programmers rarely produce perfect designs on the first attempt.

Design is iterative.

34. Common refactorings

Extract method

Before:

public void printReport() {

    double total = 0;

    for (Student s : students) {
        total += s.getGrade();
    }

    double average = total / students.size();

    // many more lines
}

After:

public void printReport() {

    double average = calculateAverage();

    // ...
}

Rename

Before:

int n;

After:

int enrollmentCount;

Remove duplication

Before:

if (student.getId() == null ||
    student.getId().isEmpty()) {
    // ...
}

appears in five locations.

After:

private boolean hasValidId(Student student) {
    return student.getId() != null &&
           !student.getId().isEmpty();
}

Move responsibility

Suppose registration validation appears in the user-interface class.

Move it into:

RegistrationSystem

if registration is a business rule rather than a display concern.

35. Duplication is a warning sign

Suppose you repeatedly write:

if (students.size() >= capacity) {

in many places.

If the definition of "full" changes, every copy must be updated.

For example, perhaps later five seats are reserved.

Then the rule becomes:

students.size() >= capacity - RESERVED_SEATS

If the logic exists in one place:

course.isFull()

only one method needs to change.

36. Testing larger programs

Testing a 20-line program is relatively easy.

Testing a 1,000-line program is not.

The solution is not to test the entire program only at the end.

Instead, test components independently.

For example:

Student
Course
RegistrationSystem

should each be tested separately when possible.

37. Unit testing

A unit test tests a small component of a program.

Usually the component is:

  • a method,
  • a class,
  • or a small group of related classes.

Consider:

public boolean isFull() {
    return students.size() >= capacity;
}

Possible tests include:

empty course -> not full
one seat remaining -> not full
exactly capacity students -> full

We care particularly about boundary cases.

38. Boundary testing

Errors often occur near boundaries.

Suppose capacity is:

30

Test enrollment counts:

0
1
29
30
31

Why test 29, 30, and 31?

Because bugs often occur due to confusion between:

<

and:

<=

Boundary testing is especially important for:

  • array indexes
  • capacities
  • numeric ranges
  • empty collections
  • loop endpoints

39. Testing normal, boundary, and invalid cases

For most methods, consider three categories.

Normal cases

Typical expected input.

Example:

course has 15 out of 30 students

Boundary cases

Values near limits.

Example:

course has 29, 30, or 31 students

Invalid cases

Values that should not occur.

Example:

negative capacity
null student
empty course code

Thinking systematically about these categories improves test quality.

40. Testing a registration method

Suppose:

public boolean enroll(Student student)

What should we test?

Possible cases:

  1. enroll a valid student
  2. verify enrollment count increases
  3. enroll when one seat remains
  4. attempt enrollment when course is full
  5. attempt duplicate enrollment
  6. attempt to enroll null
  7. verify failed enrollment does not modify state

Testing is not simply:

Run the program and see whether it crashes.

Testing means intentionally constructing situations that challenge our assumptions.

41. Test behavior, not implementation

Suppose Course stores students internally using:

ArrayList<Student>

A test generally should not care about that.

Instead test behavior:

Can a student enroll?
Can a student drop?
Does the course recognize when it is full?

Then if the implementation changes to:

HashSet<Student>

the tests may still remain valid.

This is another benefit of abstraction.

42. Debugging larger programs

When a large program fails, random changes are rarely productive.

A useful debugging process is:

  1. reproduce the error,
  2. determine what should have happened,
  3. determine what actually happened,
  4. identify where the states first diverged,
  5. form a hypothesis,
  6. test the hypothesis,
  7. fix the underlying cause,
  8. run tests again.

Debugging should be systematic.

43. Reproduce the bug

A vague report such as:

Registration does not work.

is difficult to debug.

A useful bug report looks like:

1. Create course CSC500 with capacity 2.
2. Enroll student S1.
3. Enroll student S2.
4. Attempt to enroll student S3.
5. S3 is incorrectly accepted.

Now we have a reproducible case.

Reproducibility dramatically simplifies debugging.

44. Observe program state

Suppose enrollment fails unexpectedly.

Relevant state might include:

course.capacity
course.students.size()
student.id
course.code

We want to determine where our assumptions stop matching reality.

For example:

System.out.println(
    "students = " + students.size()
);

can help.

A debugger is even better because it lets us inspect program state without constantly adding print statements.

45. Debuggers

Modern IDEs provide debuggers.

Important debugger concepts include:

Breakpoint

Pause execution at a particular line.

Step over

Execute the current line and move to the next line.

Step into

Enter a method being called.

Step out

Complete the current method and return to its caller.

Variable inspection

View current values of local variables, fields, and objects.

Learning to use a debugger is one of the highest-value practical programming skills.

46. Do not debug by guessing

A common beginner debugging strategy is:

change code
run
change something else
run
add random condition
run

This can occasionally work, but it does not teach us why the program failed.

Instead ask:

What evidence do I have?

For example:

Hypothesis:

The course allows too many students because isFull() uses > instead of >=.

Then inspect:

public boolean isFull() {
    return students.size() > capacity;
}

Indeed, when size equals capacity:

30 > 30

is false.

Therefore one additional student can enroll.

The correct expression is:

students.size() >= capacity

This is evidence-based debugging.

47. Exceptions and failure

Exceptions should communicate exceptional situations.

Suppose:

public Course(
    String code,
    String title,
    int capacity
)

receives:

capacity = -4

One approach is:

throw new IllegalArgumentException(
    "Capacity must be nonnegative"
);

This is better than silently constructing an invalid object.

However, exceptions should not replace normal control flow.

For example, checking whether a course is full is usually a normal condition:

if (course.isFull()) {

rather than an unexpected exceptional event.

48. Reading documentation

Professional programmers do not memorize every library class and method.

Instead, they learn to read documentation efficiently.

For Java, an important resource is the Java API documentation.

Suppose you encounter:

HashMap

You should be able to determine:

  • what it represents,
  • how to construct it,
  • what interfaces it implements,
  • what put() does,
  • what get() does,
  • what containsKey() does,
  • what remove() does,
  • what happens when a key does not exist.

You are not expected to memorize the entire Java library.

You are expected to know how to learn from documentation.

49. Reading a method signature

Consider:

V put(K key, V value)

The generic types mean:

K = key type
V = value type

If we declare:

Map<String, Student> students;

then:

K = String
V = Student

Therefore:

Student put(String key, Student value)

conceptually describes the specific types in this map.

50. Read more than the method name

Suppose you see:

get(Object key)

Do not assume its behavior.

Read the documentation.

Questions include:

  • What is returned when the key exists?
  • What is returned when it does not?
  • Can null be returned?
  • Does this operation modify the map?
  • What complexity should we expect?

Correct use of APIs requires understanding their contracts.

51. Documentation as a programming skill

As you advance in computer science, you will constantly encounter technologies you have never used.

The specific technology changes.

The learning process remains similar:

  1. identify the abstraction,
  2. read examples,
  3. read method signatures,
  4. understand the contract,
  5. experiment with a small program,
  6. integrate it into the larger system.

Independent technical learning is part of programming competence.

52. An integrated design example

Consider a simplified library system.

Requirements:

  • add books
  • register users
  • borrow books
  • return books
  • find books by ISBN
  • display books currently borrowed by a user

Before coding, identify concepts:

Book
User
Library

Possible representation:

public class Book {

    private String isbn;
    private String title;
    private String author;
    private boolean borrowed;

}
public class User {

    private String id;
    private String name;
    private List<Book> borrowedBooks;

}
public class Library {

    private Map<String, Book> booksByIsbn;
    private Map<String, User> usersById;

}

53. Why these data structures?

Books are frequently located using ISBN:

Map<String, Book>

Users are frequently located using ID:

Map<String, User>

Each user's borrowed books form a relatively small ordered collection:

List<Book>

These are not arbitrary choices.

They follow from the required operations.

54. Library API

A possible API:

public void addBook(Book book)

public void addUser(User user)

public Book findBook(String isbn)

public User findUser(String id)

public boolean borrowBook(
    String userId,
    String isbn
)

public boolean returnBook(
    String userId,
    String isbn
)

Notice that outside code does not directly manipulate the internal maps.

The Library object controls its state.

55. Borrowing a book

Conceptually:

borrowBook(userId, isbn)

1. Find user.
2. Find book.
3. Verify user exists.
4. Verify book exists.
5. Verify book is available.
6. Mark book borrowed.
7. Add book to user's borrowed books.
8. Return success.

The implementation follows the algorithm.

public boolean borrowBook(
        String userId,
        String isbn) {

    User user = usersById.get(userId);
    Book book = booksByIsbn.get(isbn);

    if (user == null || book == null) {
        return false;
    }

    if (book.isBorrowed()) {
        return false;
    }

    book.setBorrowed(true);
    user.borrowBook(book);

    return true;
}

56. Think about failure before coding

What can go wrong?

Possible cases:

unknown user
unknown ISBN
book already borrowed
user already borrowed the same book
user reached borrowing limit
null arguments

A strong programmer considers these cases while designing the method rather than discovering all of them after deployment.

57. Complexity of the design

Suppose we have:

Map<String, Book> booksByIsbn;

Finding a book is approximately:

O(1)

on average.

If we instead used:

List<Book> books;

finding a book might require:

O(n)

search.

The choice matters increasingly as the data grows.

58. Software design is about tradeoffs

There is rarely one perfect design.

Suppose we store borrowed status in:

Book

That is simple.

But suppose the system later needs:

loan date
due date
renewal count
fine amount

Now a boolean is insufficient.

We may introduce:

Loan

with fields such as:

private Book book;
private User user;
private LocalDate borrowedDate;
private LocalDate dueDate;

The design changes as requirements become more sophisticated.

This is normal.

59. Do not overdesign

There is an opposite danger.

A simple 300-line student project does not require:

17 interfaces
14 abstract classes
8 factories
5 manager classes

Good design is not the same as maximum complexity.

We want enough structure to make the program understandable and maintainable.

A good principle is:

Use the simplest design that cleanly solves the current problem while leaving reasonable room for change.

60. Design smells

A design smell is a sign that code may need improvement.

Common examples include:

Very long methods

A method contains many unrelated operations.

Very large classes

One class seems responsible for almost everything.

Duplicate code

The same logic appears repeatedly.

Excessive public fields

Outside code can directly manipulate internal state.

Excessive if statements based on type

This may indicate that polymorphism could be useful.

Unclear names

Variables and methods do not communicate their purpose.

Excessive dependencies

Changing one class requires modifying many unrelated classes.

These are not absolute rules.

They are signals worth investigating.

61. Example: type-based logic

Suppose:

if (employee.getType().equals("FULL_TIME")) {
    pay = employee.getHours() * 40;
} else if (
    employee.getType().equals("PART_TIME")
) {
    pay = employee.getHours() * 25;
} else if (
    employee.getType().equals("CONTRACTOR")
) {
    pay = employee.getHours() * 60;
}

If each employee type has different behavior, we might instead use polymorphism:

public interface Employee {
    double calculatePay();
}

Then:

employee.calculatePay();

Each class implements its own rule.

This removes centralized type-checking logic.

62. But do not use inheritance automatically

Inheritance is useful when there is a genuine:

is-a

relationship.

For example:

GraduateStudent is a Student

may sometimes make sense.

Composition is often better when the relationship is:

has-a

For example:

Course has a List<Student>

not:

Course extends ArrayList<Student>

Ask what conceptual relationship actually exists.

63. Composition

Composition means building objects using other objects.

Example:

public class Course {

    private Instructor instructor;
    private List<Student> students;

}

A course:

has an instructor
has students

Composition is one of the most common relationships in object-oriented programs.

64. Designing before coding

A practical process for a medium-sized assignment is:

Step 1: understand the requirements

Write down exactly what the system must do.

Step 2: identify important nouns

Nouns often suggest classes or data.

Example:

student
course
registration
instructor

This technique is useful but not mechanical.

Not every noun should become a class.

Step 3: identify important verbs

Verbs often suggest operations.

Example:

enroll
drop
find
add
remove

Step 4: assign responsibilities

Ask:

Which class should be responsible for each operation?

Step 5: choose data structures

Ask:

What operations do we perform most frequently?

Step 6: define public interfaces

Determine which methods other classes need.

Step 7: implement incrementally

Build small pieces.

Step 8: test continuously

Do not wait until the entire program is finished.

Step 9: refactor

Improve the structure after it works.

65. Incremental development

Do not attempt to write 800 lines and then run the program for the first time.

Instead:

Create Student
test Student

Create Course
test Course

Create RegistrationSystem
test addStudent

test addCourse

test findStudent

test enrollment

add file loading

test file loading

At each stage, the program should remain relatively stable.

This makes bugs easier to isolate.

66. Version 1 does not need every feature

Suppose the final application requires:

add student
add course
register
drop
save
load
search
report

Do not implement everything simultaneously.

A possible sequence is:

Version 1:
add student and course

Version 2:
registration

Version 3:
dropping

Version 4:
search

Version 5:
file persistence

Version 6:
reports

Incremental development reduces risk.

67. Separate user interface from program logic

Suppose your program uses a menu:

1. Add student
2. Add course
3. Register student
4. Exit

Avoid placing all business logic inside the menu code.

Bad approach:

if (choice == 3) {

    // search students
    // search courses
    // verify capacity
    // modify course
    // update student
    // save file
}

Better:

if (choice == 3) {
    registerStudentUI();
}

which eventually calls:

registrationSystem.enroll(studentId, courseCode);

The user interface handles interaction.

The domain classes handle the underlying logic.

68. Why separation helps

Later we might replace:

console interface

with:

graphical interface
web interface
mobile application

If business logic is separated, much of it can remain unchanged.

This demonstrates the value of modularity.

69. Data structure vs. domain model

Do not confuse the data structure with the conceptual object.

A student is not:

HashMap<String, String>

A student is a conceptual entity.

Prefer:

Student student;

where appropriate.

The collection of students might be represented using:

Map<String, Student>

Data structures organize objects.

Classes model concepts.

70. Readability is a design goal

Programs are read far more often than they are originally written.

A correct but incomprehensible program is difficult to maintain.

Compare:

for (int i = 0; i < x.size(); i++) {
    if (x.get(i).g() >= y) {
        z++;
    }
}

with:

for (Student student : students) {
    if (student.getGrade() >= passingGrade) {
        passingStudentCount++;
    }
}

Both may perform the same computation.

The second communicates meaning.

71. Comments

Comments should explain things that are not obvious from the code.

Poor comment:

// increase i by 1
i++;

The code already tells us this.

More useful:

// Students who withdraw remain in the enrollment
// history, so do not remove this entry.

That comment explains a design decision.

72. Avoid comments that compensate for bad code

Instead of:

// Check whether the course has enough space
if (students.size() < capacity) {

we might write:

if (!isFull()) {

The method name communicates the idea.

Readable code reduces the need for explanatory comments.

73. Defensive programming

Programs should anticipate invalid states and inputs.

For example:

public void addStudent(Student student) {

    if (student == null) {
        throw new IllegalArgumentException(
            "Student cannot be null"
        );
    }

    if (students.containsKey(student.getId())) {
        throw new IllegalArgumentException(
            "Duplicate student ID"
        );
    }

    students.put(student.getId(), student);
}

The method protects the system's assumptions.

74. Preconditions and postconditions

A precondition is something that must be true before an operation.

Example:

Student ID must not already exist.

A postcondition is something that should be true afterward.

Example:

After addStudent succeeds, the student can be found using the ID.

Thinking in terms of preconditions and postconditions helps us reason about methods.

75. Example method contract

Suppose:

public boolean enroll(
    String studentId,
    String courseCode
)

Possible contract:

Preconditions

studentId is not null
courseCode is not null

Success

student exists
course exists
course has capacity
student is not already enrolled

Postcondition after success

student appears in course enrollment
method returns true

Failure

system remains unchanged
method returns false

This contract clarifies expected behavior.

76. Consistency matters

Suppose enrollment information is stored in both:

Course.students
Student.courses

When a student enrolls, both structures must change.

If one changes and the other does not, the program becomes inconsistent.

For example:

Course says Alice is enrolled.
Student says Alice is not enrolled.

When data is duplicated, consistency becomes a design concern.

Sometimes it is better to store the relationship once.

Other times duplicating it improves performance or convenience.

Again, design involves tradeoffs.

77. Avoid invalid intermediate states

Consider:

course.addStudent(student);
student.addCourse(course);

What happens if the first succeeds and the second fails?

The program may become inconsistent.

Centralizing the operation in one responsible class can help:

registrationSystem.enroll(
    studentId,
    courseCode
);

The method coordinates the entire operation.

78. Think in terms of invariants

Ask:

What must always be true?

For a registration system:

No duplicate student IDs.
No duplicate course codes.
Enrollment never exceeds capacity.
A student cannot be enrolled twice.
All registrations reference valid students.
All registrations reference valid courses.

These invariants guide both implementation and testing.

79. Complexity is part of design

Suppose a method works correctly.

That does not necessarily mean it is appropriate.

Consider:

for (Student s : students) {
    for (Course c : courses) {
        // ...
    }
}

If there are:

10,000 students
5,000 courses

the nested loop may perform:

50,000,000 comparisons

Understanding complexity helps us identify designs that work at realistic scales.

80. But do not optimize everything

Another common mistake is premature optimization.

A student may spend hours replacing:

ArrayList

with a complicated structure to improve an operation that runs five times.

Before optimizing ask:

  1. Is there a performance problem?
  2. Which operation causes it?
  3. How large is the input?
  4. Will the more complex design actually matter?

Correctness and clarity are usually the first priorities.

81. Appropriate efficiency

For CSC500, develop the habit of asking:

What is n?
How does the runtime grow as n grows?
Which operations dominate?
Is there a better data structure?

You do not need to perform advanced mathematical analysis for every method.

But you should recognize obvious differences such as:

O(1)
O(log n)
O(n)
O(n log n)
O(n²)

82. Putting everything together

For a medium-sized Java program, you should now be able to reason at several levels.

Syntax level

Is the Java code legal?

Execution level

What does each statement do?

Algorithm level

What sequence of steps solves the problem?

Data structure level

How should information be organized?

Object-oriented level

What classes and relationships represent the domain?

Design level

How should components interact?

Complexity level

How does the solution scale?

Testing level

How do we know the program is correct?

Strong programmers move between all of these levels.

83. A design checklist

Before implementing a substantial program, ask:

Requirements

  • What must the program do?
  • What inputs exist?
  • What outputs are required?
  • What invalid situations can occur?

Classes

  • What concepts should become classes?
  • What responsibility does each class have?
  • Are responsibilities clearly separated?

Data

  • What information does each class store?
  • Which fields should be private?
  • What invariants must hold?

Data structures

  • Do I need ordering?
  • Do I need indexed access?
  • Do I need unique elements?
  • Do I need fast lookup by key?
  • Do I need FIFO or LIFO processing?

Methods

  • What operations should each class provide?

Dependencies

  • Which classes need to know about each other?
  • Can unnecessary dependencies be removed?

Testing

  • What are the normal cases?
  • What are the boundary cases?
  • What are the invalid cases?

Complexity

  • What operations happen most often?
  • What are their approximate costs?

87. Example design exercise

Consider the following problem:

Design a package delivery system. Each package has a tracking number, recipient, address, weight, and status. The system must allow users to add packages, locate a package by tracking number, update its status, and display all packages having a particular status.

Before coding, answer the following.

What classes might exist?

Possible answer:

Package
DeliverySystem

Possibly:

Address

if address behavior becomes sufficiently complex.

88. What data structure should store packages?

A primary operation is:

find package by tracking number

Therefore:

Map<String, Package> packagesByTrackingNumber;

is a natural choice.

Lookup is approximately:

O(1)

on average.

89. How do we find all packages with a status?

One simple solution is to scan the map:

for (Package p : packages.values()) {
    if (p.getStatus() == status) {
        // ...
    }
}

Runtime:

O(n)

If status searches become extremely frequent, we might later maintain additional indexing.

But that creates more complexity.

The simple O(n) solution may be completely appropriate.

This is an example of choosing a solution based on actual requirements.

90. Possible package status representation

Instead of storing:

String status;

we might define:

public enum PackageStatus {
    CREATED,
    IN_TRANSIT,
    OUT_FOR_DELIVERY,
    DELIVERED
}

Why might this be better?

A string permits invalid values:

"deleverd"
"shipping"
"????"

An enum restricts the program to known states.

This improves correctness.

91. Design exercise: social network

Suppose we want a tiny social network.

Requirements:

  • register users
  • find a user by username
  • add friendships
  • list a user's friends
  • determine whether two users are friends

What structures might be useful?

One possibility:

Map<String, User> users;

Inside User:

Set<User> friends;

Why a set?

Because:

  • duplicate friendships should not exist,
  • membership testing is important.

This illustrates how problem requirements suggest data structures.

92. Design exercise: task scheduler

Requirements:

  • add tasks
  • each task has priority
  • always process the highest-priority task next

Which structure is appropriate?

A:

ArrayList

could work.

But a:

PriorityQueue

better represents the required behavior.

Again:

Choose a structure based on operations.

94. Key takeaways

1. Design before coding.

Understand the problem before writing large amounts of Java.

2. Decompose large problems.

Divide systems into components with clear responsibilities.

3. Favor high cohesion.

Keep closely related responsibilities together.

4. Reduce unnecessary coupling.

Components should interact through clear interfaces.

5. Use encapsulation.

Protect internal state and class invariants.

6. Choose data structures based on operations.

A List, Set, Map, stack, queue, or tree represents different needs.

7. Program to abstractions when appropriate.

For example:

List<Student>

rather than unnecessarily requiring:

ArrayList<Student>

8. Refactor.

Working code can still be improved.

9. Test components systematically.

Include normal, boundary, and invalid cases.

10. Debug using evidence.

Reproduce problems and inspect program state rather than guessing.

11. Learn to read documentation.

Professional programming requires continuously learning unfamiliar APIs.

12. Software design involves tradeoffs.

There is rarely one universally correct solution.
