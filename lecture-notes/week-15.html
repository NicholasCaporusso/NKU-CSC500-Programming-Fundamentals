1. From programming to software design

Throughout CSC 500, we have studied individual programming ideas:

  • variables and expressions;
  • decisions and Boolean logic;
  • loops;
  • methods;
  • arrays and strings;
  • classes and objects;
  • encapsulation;
  • inheritance;
  • interfaces and polymorphism;
  • exceptions;
  • file I/O;
  • testing;
  • recursion;
  • algorithm analysis;
  • searching and sorting;
  • lists and linked structures;
  • stacks;
  • queues;
  • sets;
  • maps;
  • trees.

When studying each topic separately, exercises often tell us what technique to use.

For example:

Write a loop that calculates the average.

or:

Store these objects in an ArrayList.

Real software problems usually do not work that way.

Instead, we might receive a requirement such as:

Build an application that manages student registration for university courses.

Nothing in that statement tells us:

  • which classes to create;
  • which objects should store which information;
  • which data structures to use;
  • where validation should occur;
  • whether an interface is useful;
  • what algorithms are appropriate;
  • how errors should be reported;
  • or how the system should be tested.

Those decisions are part of software design.

2. Programming vs. software design

Programming

Programming is the process of expressing instructions in a programming language.

For example:

if (score >= 70) {
    System.out.println("Pass");
}

Programming requires knowing Java syntax and understanding how statements execute.

Software design

Software design operates at a higher level.

It asks questions such as:

  • What components should exist?
  • What should each component be responsible for?
  • What information should each object store?
  • Which information should remain private?
  • Which methods should be public?
  • Which data structures fit the required operations?
  • Which classes should depend on which other classes?
  • How can the system be tested?
  • How easy will it be to modify later?

A program can produce the correct result while still being poorly designed.

For example, a 2,000-line main method might eventually work.

That does not mean it is easy to:

  • understand;
  • test;
  • debug;
  • reuse;
  • modify;
  • or extend.

Good software design considers both the computer and the programmers who must understand the program.

3. What makes software well designed?

There is no single formula for perfect software design.

However, well-designed software is generally:

Correct

It performs the required behavior.

Readable

Another programmer can understand what the code means.

Modular

The program is divided into meaningful pieces.

Maintainable

A reasonable change does not require rewriting the entire application.

Testable

Important components can be tested independently.

Robust

Invalid input and unusual situations are handled sensibly.

Appropriately efficient

The program uses algorithms and data structures suitable for the expected workload.

Reusable

Useful components can potentially be used in more than one context.

Adaptable

The design does not unnecessarily prevent likely future changes.

These goals sometimes conflict.

A highly optimized solution may be harder to understand.

A highly flexible solution may require more classes.

A very simple solution may not scale.

Therefore:

Software design is the process of making informed tradeoffs.

There is rarely one universally best design independent of requirements.

4. Do not begin every large problem by coding

A common beginner strategy is:

read problem
    ↓
open editor
    ↓
start writing Java

For small exercises, this may work.

For larger programs, it often leads to:

  • duplicated code;
  • unclear responsibilities;
  • inappropriate data structures;
  • huge methods;
  • unnecessary dependencies;
  • inconsistent validation;
  • and difficult debugging.

A better process is:

requirements
    ↓
data
    ↓
responsibilities
    ↓
classes and methods
    ↓
data structures
    ↓
algorithms
    ↓
implementation
    ↓
testing
    ↓
refactoring

This process is iterative.

You may discover during implementation that your original design was not ideal.

That is normal.

The goal is not to predict everything perfectly before writing code.

The goal is to think before writing large amounts of code.

5. Start with requirements

Suppose we receive the following problem.

Create a simplified university course-registration system.

Requirements:

  • students can be added;
  • courses can be added;
  • students can enroll in courses;
  • students can drop courses;
  • courses have capacities;
  • a student cannot register twice for the same course;
  • students can be found by student ID;
  • courses can be found by course code;
  • the program can display the students in a course;
  • the program can display the courses taken by a student.

Before designing classes, make sure the requirements are understood.

Ask questions.

For example:

  • Are student IDs unique?
  • Are course codes unique?
  • Can course capacity be zero?
  • Can a student register for an unknown course?
  • What happens if a course is full?
  • Can a student drop a course they are not taking?
  • Does enrollment order matter?
  • Should duplicate registrations be rejected?
  • How will data be saved?
  • What should the program do with invalid input?

These questions expose hidden assumptions.

A large percentage of programming difficulty comes from misunderstanding the problem rather than misunderstanding Java syntax.

6. Identify the important concepts

One useful first step is to look for important nouns in the problem description.

For our registration system, obvious concepts include:

Student
Course
Registration
RegistrationSystem

Not every noun must become a class.

But nouns often identify candidate objects.

Then look for important actions:

add
find
enroll
drop
display

These may suggest methods.

We can begin forming a model.

7. Decomposition

Decomposition means dividing a large problem into smaller, more manageable problems.

Instead of asking:

How do I implement an entire registration system?

ask:

  1. How do I represent one student?
  2. How do I represent one course?
  3. How do I store all students?
  4. How do I find a student by ID?
  5. How do I store enrolled students?
  6. How do I determine whether a course is full?
  7. How do I prevent duplicate registration?
  8. How do I enroll a student?
  9. How do I drop a student?
  10. How do I display information?

Each smaller problem is easier to reason about.

This is the same principle we first encountered when learning methods:

readInput();
validateInput();
calculateResult();
displayResult();

Now we apply decomposition at a larger scale using classes and collaborating objects.

8. Responsibilities

After identifying candidate classes, ask:

What should each class know?

and:

What should each class do?

For example:

Student

Represents one student.

Possible state:

private String id;
private String name;

Possible behavior:

getId()
getName()

Course

Represents one course.

Possible state:

private String code;
private String title;
private int capacity;
private Set<Student> students;

Possible behavior:

getCode()
getTitle()
isFull()
enroll(...)
drop(...)
getEnrollmentCount()

RegistrationSystem

Coordinates the overall collection of students and courses.

Possible state:

private Map<String, Student> studentsById;
private Map<String, Course> coursesByCode;

Possible behavior:

addStudent(...)
addCourse(...)
findStudent(...)
findCourse(...)
register(...)
unregister(...)

This division is not the only possible design.

The important issue is whether responsibilities are placed where they make sense.

9. The Single Responsibility Principle

A useful software-design guideline is the Single Responsibility Principle, often abbreviated SRP.

At an introductory level:

A class should have one clear primary responsibility.

This does not mean:

A class should have exactly one method.

For example, this class can contain many methods:

public class Stack<E> {

    public void push(E value) { ... }

    public E pop() { ... }

    public E peek() { ... }

    public boolean isEmpty() { ... }

    public int size() { ... }
}

All of those methods support the same conceptual responsibility:

Represent and manage a stack.

That is cohesive.

Now consider:

public class Student {

    public void enrollInCourse(...) { ... }

    public void saveEntireDatabase(...) { ... }

    public void sendEmail(...) { ... }

    public void calculateUniversityBudget(...) { ... }

    public void generatePDFReport(...) { ... }
}

This class is doing many unrelated things.

A useful design question is:

Can I describe the responsibility of this class in one short sentence?

For example:

Course represents one university course and manages its enrollment.

That is reasonably focused.

If your description becomes:

SystemManager handles students, courses, files, reports, menus, validation, sorting, email, and statistics...

the class is probably doing too much.

10. Cohesion

Cohesion describes how closely related the responsibilities inside a component are.

High cohesion

Consider:

public class GradeCalculator {

    public double calculateAverage(...) { ... }

    public double calculateMedian(...) { ... }

    public char calculateLetterGrade(...) { ... }
}

The methods are strongly related.

This class has high cohesion.

Low cohesion

Consider:

public class Utility {

    public double calculateAverage(...) { ... }

    public void sendEmail(...) { ... }

    public void resizeImage(...) { ... }

    public void saveStudent(...) { ... }

    public boolean validatePassword(...) { ... }
}

These methods do not represent one clear responsibility.

The class has low cohesion.

As a general guideline:

Prefer high cohesion.

High cohesion tends to improve:

  • readability;
  • testability;
  • maintainability;
  • reuse;
  • and understanding.

11. Coupling

Coupling describes how strongly one part of a program depends on another.

Objects must interact, so some coupling is necessary.

The goal is to avoid unnecessary tight coupling.

Suppose we write:

public class ReportGenerator {

    private RegistrationSystem system;

    public ReportGenerator(RegistrationSystem system) {
        this.system = system;
    }
}

That dependency may be reasonable because the report requires registration information.

However, suppose ReportGenerator directly manipulates:

  • the internal student map;
  • the course's private participant collection;
  • file-storage implementation;
  • console-menu state;
  • and internal validation flags.

Now ReportGenerator knows far too much about other components.

Small implementation changes can break it.

A useful design goal is:

high cohesion
low unnecessary coupling

That means:

  • each component has a focused responsibility;
  • components interact through small, clear interfaces.

12. Abstraction

Abstraction means focusing on the important behavior while hiding unnecessary implementation details.

Consider:

List<String> names = new ArrayList<>();

names.add("Alice");
names.add("Bob");

System.out.println(names.get(0));

We can use ArrayList without understanding:

  • exactly how large its internal array currently is;
  • precisely when resizing happens;
  • how elements are copied during resizing;
  • or how memory is allocated internally.

The abstraction we care about is:

a resizable ordered collection.

Abstraction allows programmers to reason at a higher level.

Instead of thinking:

move memory
resize array
copy element
update capacity

we think:

names.add("Alice");

That reduction in mental complexity is essential in large programs.

13. Encapsulation

Encapsulation means grouping related state and behavior together and controlling access to internal state.

Consider this poor design:

public class Course {

    public List<Student> students = new ArrayList<>();
}

Outside code can now write:

course.students.clear();

or:

course.students.add(student);

The Course class has lost control over its own state.

Suppose the course must enforce:

  • maximum capacity;
  • no duplicate students;
  • no null students.

Direct external modification can bypass all of those rules.

A better design is:

public class Course {

    private Set<Student> students = new HashSet<>();

    public boolean enroll(Student student) {
        // enforce rules here
    }

    public boolean drop(Student student) {
        // enforce rules here
    }
}

Now state changes occur through controlled operations.

14. Getters and setters are not automatically good design

Beginning Java courses often introduce getters and setters:

public String getName() {
    return name;
}

public void setName(String name) {
    this.name = name;
}

This does not mean every field should automatically receive both.

Consider:

private double balance;

A method such as:

public void setBalance(double balance) {
    this.balance = balance;
}

allows callers to assign arbitrary values:

account.setBalance(-1000000);

Better methods may be:

public void deposit(double amount) { ... }

public boolean withdraw(double amount) { ... }

These express meaningful operations and enforce rules.

Therefore:

Expose behavior appropriate to the abstraction, not simply direct access to every field.

15. Class invariants

An invariant is a condition that should remain true whenever an object is in a valid state.

For a Course, possible invariants include:

capacity >= 0

code is not null

code is not empty

number of students <= capacity

the same student does not appear twice

A class should protect important invariants.

Consider:

public Course(String code, String title, int capacity) {

    if (code == null || code.isBlank()) {
        throw new IllegalArgumentException(
            "Course code cannot be empty"
        );
    }

    if (capacity < 0) {
        throw new IllegalArgumentException(
            "Capacity cannot be negative"
        );
    }

    this.code = code;
    this.title = title;
    this.capacity = capacity;
}

Now an invalid object cannot easily be constructed.

This is much safer than:

Course course =
    new Course("", "Programming", -500);

being silently accepted.

16. Designing the Student class

Here is a simple version:

import java.util.Objects;

public class Student {

    private final String id;
    private String name;

    public Student(String id, String name) {

        if (id == null || id.isBlank()) {
            throw new IllegalArgumentException(
                "Student ID cannot be empty"
            );
        }

        if (name == null || name.isBlank()) {
            throw new IllegalArgumentException(
                "Student name cannot be empty"
            );
        }

        this.id = id;
        this.name = name;
    }

    public String getId() {
        return id;
    }

    public String getName() {
        return name;
    }

    public void rename(String newName) {

        if (newName == null || newName.isBlank()) {
            throw new IllegalArgumentException(
                "Student name cannot be empty"
            );
        }

        name = newName;
    }

    @Override
    public boolean equals(Object obj) {

        if (this == obj) {
            return true;
        }

        if (!(obj instanceof Student other)) {
            return false;
        }

        return id.equals(other.id);
    }

    @Override
    public int hashCode() {
        return Objects.hash(id);
    }

    @Override
    public String toString() {
        return id + " - " + name;
    }
}

Notice several design decisions.

Student ID is immutable

private final String id;

If IDs define student identity, allowing arbitrary ID changes could cause problems.

Validation happens at the boundary

The constructor prevents obviously invalid students.

Behavior is meaningful

Rather than exposing:

setId(...)

we make the identity stable.

17. Designing the Course class

import java.util.Collections;
import java.util.HashSet;
import java.util.Set;

public class Course {

    private final String code;
    private String title;
    private final int capacity;

    private final Set<Student> students;

    public Course(
            String code,
            String title,
            int capacity) {

        if (code == null || code.isBlank()) {
            throw new IllegalArgumentException(
                "Course code cannot be empty"
            );
        }

        if (title == null || title.isBlank()) {
            throw new IllegalArgumentException(
                "Course title cannot be empty"
            );
        }

        if (capacity < 0) {
            throw new IllegalArgumentException(
                "Capacity cannot be negative"
            );
        }

        this.code = code;
        this.title = title;
        this.capacity = capacity;
        this.students = new HashSet<>();
    }

    public String getCode() {
        return code;
    }

    public String getTitle() {
        return title;
    }

    public int getCapacity() {
        return capacity;
    }

    public int getEnrollmentCount() {
        return students.size();
    }

    public boolean isFull() {
        return students.size() >= capacity;
    }

    public boolean containsStudent(Student student) {
        return students.contains(student);
    }

    public boolean enroll(Student student) {

        if (student == null) {
            throw new IllegalArgumentException(
                "Student cannot be null"
            );
        }

        if (isFull()) {
            return false;
        }

        return students.add(student);
    }

    public boolean drop(Student student) {

        if (student == null) {
            return false;
        }

        return students.remove(student);
    }

    public Set<Student> getStudents() {
        return Collections.unmodifiableSet(students);
    }
}

This class demonstrates several Week 15 ideas simultaneously:

  • encapsulation;
  • meaningful methods;
  • invariants;
  • set semantics;
  • information hiding;
  • decomposition;
  • high cohesion.

18. Why use a Set<Student> here?

A set does not allow duplicate elements.

One requirement says:

A student cannot enroll twice in the same course.

That immediately suggests set-like behavior.

We could use:

List<Student>

and manually check:

if (!students.contains(student)) {
    students.add(student);
}

But:

Set<Student>

communicates the design more directly:

This collection represents unique students.

The data structure itself helps enforce the requirement.

This demonstrates an important rule:

Choose data structures based on the operations and constraints of the problem.

19. Choosing data structures

There is no universally best data structure.

Instead ask:

What operations does this part of the program need to perform frequently?

A useful summary:

RequirementTypical Choice
Fixed-size indexed collectionArray
Resizable ordered collectionArrayList
LIFO processingStack / Deque
FIFO processingQueue / Deque
Unique valuesHashSet
Fast lookup using a keyHashMap
Hierarchical relationshipsTree
Ordered hierarchical searchingBST when appropriate
Priority-based processingPriorityQueue

Do not memorize this as a rigid rule.

Use it as a starting point for reasoning.

20. Arrays

Use an array when:

  • size is fixed or predictable;
  • indexed access is important;
  • simple storage is sufficient.

Example:

double[] dailyTemperatures = new double[365];

Advantages:

  • simple representation;
  • direct indexing;
  • low overhead;
  • array[i] is O(1).

Disadvantages:

  • fixed length;
  • insertions/removals may require shifting data;
  • resizing requires creating another array.

21. ArrayList

Use an ArrayList when:

  • the collection grows or shrinks;
  • order matters;
  • indexed access matters;
  • appending elements is common.

Example:

List<Student> students = new ArrayList<>();

Typical operations:

students.add(student);
students.get(index);
students.remove(index);

Typical complexity intuition:

OperationTypical Cost
get(i)O(1)
appendO(1) amortized
searchO(n)
insert/remove near beginningO(n)

For many ordinary list problems, ArrayList is an excellent default.

22. Linked lists

A linked list conceptually stores connected nodes:

[A] -> [B] -> [C] -> [D]

Linked structures can support efficient insertion or removal once the correct location is already known.

However:

Do not automatically select LinkedList merely because you learned that insertion can be O(1).

You must consider the full access pattern.

If finding the insertion location requires traversing the list first, the overall operation may still be O(n).

For many practical Java applications, ArrayList remains simpler and often appropriate.

23. Stacks

A stack follows:

Last In, First Out

or:

LIFO

Typical operations:

push
pop
peek

Useful for:

  • undo behavior;
  • parsing nested structures;
  • depth-first search;
  • expression processing;
  • tracking call-like behavior.

Conceptually:

push A
push B
push C

top
 ↓
[C]
[B]
[A]

C is removed first.

24. Queues

A queue follows:

First In, First Out

or:

FIFO

Useful for:

  • jobs waiting to be processed;
  • simulations;
  • breadth-first search;
  • event processing;
  • print queues.

Example:

Alice arrives
Bob arrives
Carol arrives

The service order is normally:

Alice
Bob
Carol

25. Sets

A set represents unique values.

Set<String> registeredIds =
    new HashSet<>();

Typical operations:

registeredIds.add("S1001");

boolean exists =
    registeredIds.contains("S1001");

Use a set when an important question is:

Is this value already present?

Common applications include:

  • duplicate prevention;
  • membership testing;
  • tracking visited nodes;
  • storing unique identifiers.

26. Maps

A map stores:

key → value

For example:

Map<String, Student> studentsById =
    new HashMap<>();

We might store:

"S1001" → Student object
"S1002" → Student object
"S1003" → Student object

Lookup:

Student student =
    studentsById.get("S1002");

A map is especially useful when the requirement says:

Find an object using its unique identifier.

Examples:

student ID → Student
username → User
ISBN → Book
tracking number → Package
product code → Product

Hash-map lookup is typically approximately O(1) average time.

27. List vs. Map: Requirements matter

Suppose the system stores 100,000 students.

List design

List<Student> students;

Finding an ID might require:

for (Student student : students) {
    if (student.getId().equals(targetId)) {
        return student;
    }
}

Worst-case work grows linearly:

O(n)

Map design

Map<String, Student> studentsById;

Lookup becomes:

return studentsById.get(targetId);

Average expected lookup:

O(1)

The lesson is not:

Maps are better than lists.

The lesson is:

The best representation depends on how the data is used.

28. Sometimes more than one structure is useful

Suppose requirements say:

  • frequently display students in registration order;
  • frequently retrieve students by ID.

A list supports order:

List<Student> students;

A map supports ID lookup:

Map<String, Student> studentsById;

You could maintain both.

But now a new problem appears:

Both representations must remain consistent.

If you add a student to one but not the other, the program becomes incorrect.

Therefore every improvement has a cost.

Maintaining multiple structures may be worthwhile—but only when the requirements justify the added complexity.

29. Interface vs. implementation

An interface describes available behavior.

An implementation describes how that behavior is provided.

Consider:

List<Student> students =
    new ArrayList<>();

Here:

List<Student>

describes the abstraction we require.

new ArrayList<>()

chooses one implementation.

We could later write:

List<Student> students =
    new LinkedList<>();

The declared type remains List<Student>.

30. Programming to an interface

Compare:

public void printStudents(
        ArrayList<Student> students) {
    ...
}

with:

public void printStudents(
        List<Student> students) {
    ...
}

The second version says:

I need something with list behavior.

It does not unnecessarily require one particular implementation.

It can accept:

new ArrayList<Student>()

or:

new LinkedList<Student>()

when appropriate.

This reduces coupling.

A common Java design style is therefore:

List<Student> students =
    new ArrayList<>();

Set<String> ids =
    new HashSet<>();

Map<String, Course> courses =
    new HashMap<>();

Queue<Job> jobs =
    new ArrayDeque<>();

The left side names the abstraction.

The right side selects an implementation.

31. Public APIs

The public methods of a class form its API:

Application Programming Interface

For a Course, the public API might include:

public String getCode()

public String getTitle()

public int getCapacity()

public int getEnrollmentCount()

public boolean isFull()

public boolean enroll(Student student)

public boolean drop(Student student)

Other classes should ideally use this API rather than manipulating Course internals.

Think of the public API as a contract.

It tells other programmers:

These are the operations you may rely on.

32. Separate "what" from "how"

Suppose the system offers:

public Student findStudent(String id)

This method communicates what happens:

Find a student using an ID.

Its implementation may change.

Version 1

for (Student student : students) {

    if (student.getId().equals(id)) {
        return student;
    }
}

return null;

Version 2

return studentsById.get(id);

The caller still writes:

system.findStudent("S1001");

The implementation changed.

The interface did not.

That is a major benefit of abstraction and information hiding.

33. Information hiding

Imagine that Course exposes:

public Set<Student> getStudents() {
    return students;
}

Then a caller could write:

course.getStudents().clear();

The caller has modified internal state without going through Course.

One alternative is:

public Set<Student> getStudents() {
    return Collections.unmodifiableSet(students);
}

Now callers may inspect the students but cannot directly modify the collection through the returned reference.

Another possibility is to return a copy:

public Set<Student> getStudents() {
    return new HashSet<>(students);
}

The exact design depends on the requirements.

The principle is:

Do not expose more implementation detail than callers need.

34. Designing RegistrationSystem

import java.util.HashMap;
import java.util.Map;

public class RegistrationSystem {

    private final Map<String, Student> studentsById;
    private final Map<String, Course> coursesByCode;

    public RegistrationSystem() {
        studentsById = new HashMap<>();
        coursesByCode = new HashMap<>();
    }

    public boolean addStudent(Student student) {

        if (student == null) {
            throw new IllegalArgumentException(
                "Student cannot be null"
            );
        }

        if (studentsById.containsKey(student.getId())) {
            return false;
        }

        studentsById.put(student.getId(), student);
        return true;
    }

    public boolean addCourse(Course course) {

        if (course == null) {
            throw new IllegalArgumentException(
                "Course cannot be null"
            );
        }

        if (coursesByCode.containsKey(course.getCode())) {
            return false;
        }

        coursesByCode.put(course.getCode(), course);
        return true;
    }

    public Student findStudent(String id) {
        return studentsById.get(id);
    }

    public Course findCourse(String code) {
        return coursesByCode.get(code);
    }

    public boolean register(
            String studentId,
            String courseCode) {

        Student student =
            findStudent(studentId);

        Course course =
            findCourse(courseCode);

        if (student == null || course == null) {
            return false;
        }

        return course.enroll(student);
    }

    public boolean unregister(
            String studentId,
            String courseCode) {

        Student student =
            findStudent(studentId);

        Course course =
            findCourse(courseCode);

        if (student == null || course == null) {
            return false;
        }

        return course.drop(student);
    }
}

Notice that RegistrationSystem coordinates the operation, but the Course object remains responsible for its enrollment rules.

That produces a useful division:

RegistrationSystem
    coordinates objects

Course
    protects course-specific enrollment rules

Student
    represents one student

35. Should enrollment live in Course or RegistrationSystem?

This is an example of a real design decision.

Two reasonable designs might exist.

Option A

course.enroll(student);

This makes Course responsible for its own participant collection and capacity.

Option B

registrationSystem.register(
    studentId,
    courseCode
);

This lets the system coordinate lookup and registration.

Often both are useful:

RegistrationSystem.register(...)

performs high-level coordination and eventually calls:

Course.enroll(...)

This demonstrates an important idea:

Different abstraction levels can cooperate.

The high-level object coordinates.

The lower-level object protects its own rules.

36. Composition vs. inheritance

Inheritance represents an is-a relationship.

Examples:

Dog is an Animal

Circle is a Shape

SavingsAccount is a BankAccount

Composition represents a has-a relationship.

Examples:

Course has Students

Car has an Engine

Order has OrderItems

University has Courses

For the registration system:

public class RegistrationSystem {

    private Map<String, Student> students;
    private Map<String, Course> courses;
}

This is composition.

The system has students and courses.

There is no reason for:

class Course extends Student

because a course is not a type of student.

A useful guideline is:

Use inheritance when the subclass genuinely represents a specialized form of the superclass.

and:

Prefer composition when the relationship is naturally “has-a.”

Do not use inheritance simply because two classes happen to share some code.

37. Methods should perform coherent tasks

There is no universal maximum method length.

A better rule is:

A method should perform one coherent conceptual task.

Consider:

public void processRegistration() {

    // read console input

    // validate user input

    // find student

    // find course

    // verify capacity

    // enroll student

    // save file

    // update statistics

    // print confirmation

    // print report
}

This method has too many responsibilities.

We might refactor:

public void processRegistration() {

    String studentId = readStudentId();
    String courseCode = readCourseCode();

    boolean registered =
        system.register(studentId, courseCode);

    displayResult(registered);
}

Now the high-level intent is visible.

38. Names should express intent

Compare:

int x;
int n;
List<String> a;

with:

int enrollmentCount;
int maximumCapacity;
List<String> studentIds;

Good names reduce mental effort.

Useful method names:

calculateAverage()
findStudentById()
isValidPassword()
removeExpiredAccounts()
saveRecords()

Weak names:

doStuff()
thing()
process2()
handle()
data()
runIt()

Boolean methods are often especially readable as questions:

isFull()
isEmpty()
hasPermission()
containsStudent()
isValid()

Then client code becomes almost English:

if (!course.isFull()) {
    ...
}

39. Magic numbers and named constants

Consider:

if (score >= 70) {
    ...
}

Why 70?

If 70 means the passing score, make the concept visible:

private static final int PASSING_SCORE = 70;

Then:

if (score >= PASSING_SCORE) {
    ...
}

Other common magic values include:

  • capacity limits;
  • timeout durations;
  • tax rates;
  • number of retries;
  • grade thresholds;
  • file-size limits.

Named constants improve both readability and maintainability.

40. Duplicate logic

Suppose this rule appears five times:

if (students.size() >= capacity) {
    ...
}

Later, the rule changes.

Perhaps five seats are reserved:

students.size() >= capacity - RESERVED_SEATS

Now every copied condition must be found and updated.

A better design is:

public boolean isFull() {
    return students.size() >= capacity;
}

Callers write:

if (course.isFull()) {
    ...
}

There is now one authoritative definition of the concept.

41. DRY

DRY stands for:

Don't Repeat Yourself.

It does not mean that two lines of code may never look similar.

The deeper principle is:

Important knowledge or rules should not have many independent representations.

If the same business rule is copied in six places, those copies can disagree.

Centralizing the rule makes modification safer.

However, do not combine unrelated code simply because it happens to look similar.

Ask:

Do these duplicated sections represent the same concept?

42. Refactoring

Refactoring means improving the internal structure of code without intentionally changing its externally observable behavior.

You often first produce:

working code

Then improve it into:

working + understandable code

Common reasons to refactor:

  • duplicated logic;
  • long methods;
  • unclear names;
  • inappropriate data structures;
  • classes doing too much;
  • misplaced responsibilities;
  • excessive dependencies.

Design is iterative.

The first working version is rarely the final possible design.

43. Common refactoring: Extract method

Before

public void printReport() {

    double total = 0;

    for (Student student : students) {
        total += student.getGrade();
    }

    double average =
        total / students.size();

    // another 80 lines...
}

After

public void printReport() {

    double average =
        calculateAverage();

    // reporting logic
}

private double calculateAverage() {

    double total = 0;

    for (Student student : students) {
        total += student.getGrade();
    }

    return total / students.size();
}

The extracted method names the concept.

44. Common refactoring: Rename

Before:

int n;

After:

int enrollmentCount;

Before:

void doThing() {
    ...
}

After:

void removeExpiredRegistrations() {
    ...
}

Renaming can dramatically improve readability without changing behavior.

45. Common refactoring: Move responsibility

Suppose a console user-interface class contains:

if (course.getEnrollmentCount()
        >= course.getCapacity()) {

    System.out.println("Course full");
}

The UI now knows the internal rule for fullness.

A better design is:

if (course.isFull()) {
    System.out.println("Course full");
}

The rule belongs to Course.

The UI simply displays the result.

This reduces coupling.

46. Can software be too modular?

Yes.

Imagine a 100-line homework program containing:

15 interfaces
20 classes
6 factory classes
5 layers
several design patterns

That is probably excessive.

More abstractions do not automatically mean better design.

Overengineering increases:

  • code volume;
  • conceptual complexity;
  • debugging difficulty;
  • number of dependencies.

A useful principle is:

Make the design as simple as possible while still supporting the requirements clearly.

Do not design an imaginary enterprise system when solving a small assignment.

47. Separation of concerns

Larger programs often benefit from separating different kinds of responsibilities.

For example:

User Interface
     |
     v
Registration Logic
     |
     v
Domain Objects
     |
     v
Data Storage

Possible classes:

ConsoleUI
RegistrationSystem
Student
Course
StudentRepository
CourseRepository

CSC 500 projects do not require sophisticated enterprise architecture.

The principle is simply:

Do not place unrelated concerns into the same method or class without a reason.

Changing how information is displayed should ideally not require rewriting enrollment logic.

Changing how records are stored should ideally not require rewriting every menu.

48. Keep main small

A common beginner program looks like:

public static void main(String[] args) {

    // 500 lines
}

A stronger design often makes main responsible for:

  1. creating major objects;
  2. connecting them;
  3. starting the application.

For example:

public class Main {

    public static void main(String[] args) {

        RegistrationSystem system =
            new RegistrationSystem();

        ConsoleUI ui =
            new ConsoleUI(system);

        ui.run();
    }
}

This is sometimes called the composition root informally: the place where major components are assembled.

For CSC 500, the important idea is simply:

main should coordinate rather than contain the entire program.

49. Organizing a larger Java project

One possible project structure is:

src/
    model/
        Student.java
        Course.java

    service/
        RegistrationSystem.java

    ui/
        ConsoleUI.java

    repository/
        StudentRepository.java

    util/
        FileUtils.java

    app/
        Main.java

You do not need this exact organization.

The important principle is that the project structure should help a reader understand responsibilities.

50. Complexity is a design concern

Big-O analysis is not separate from software design.

Suppose we frequently execute:

for (Student student : students) {

    if (student.getId().equals(targetId)) {
        return student;
    }
}

If there are n students, lookup is:

O(n)

One lookup may be fine.

Ten million repeated lookups may not be.

A map might reduce the average lookup to:

O(1)

Therefore a data structure can change the performance characteristics of the entire system.

51. But do not optimize everything prematurely

Suppose your application contains only 15 settings.

A linear search through:

List<Setting>

may be perfectly reasonable.

Building a complicated custom tree structure would probably make the program harder to understand with no meaningful benefit.

A useful development sequence is:

1. make it correct
2. make it clear
3. understand or measure performance
4. optimize meaningful bottlenecks

This does not mean you should ignore obviously poor algorithms.

It means:

Optimization should respond to requirements, not fear.

52. Complexity questions to ask

When reviewing a program, ask:

  • What does n represent?
  • Which operations happen most frequently?
  • Which loops depend on n?
  • Are loops nested?
  • Are we repeatedly performing linear searches?
  • Are we sorting repeatedly?
  • Can a better data structure remove repeated work?
  • How large can the input realistically become?

Recognize broad growth patterns:

O(1)
O(log n)
O(n)
O(n log n)
O(n²)

The goal is not merely memorizing symbols.

You should be able to explain why the program behaves that way.

53. Example complexity analysis

For:

public Student findStudent(String id) {
    return studentsById.get(id);
}

Average expected complexity:

O(1)

For:

public void printAllStudents() {

    for (Student student :
            studentsById.values()) {

        System.out.println(student);
    }
}

If there are n students:

O(n)

For:

for (Student a : students) {
    for (Student b : students) {
        compare(a, b);
    }
}

approximately:

O(n²)

Always identify what input size n means.

54. Testing larger programs

A 20-line program can sometimes be tested manually from beginning to end.

A 2,000-line application cannot be reliably tested that way.

Instead, test at multiple levels.

Individual methods

Does isFull() return the correct value?

Individual classes

Can Course correctly enroll and remove students?

Component interactions

Does RegistrationSystem correctly find a Course and enroll a Student?

Whole application

Can a user complete a realistic registration workflow?

Testing should happen while the program is being developed—not only after everything is finished.

55. Unit testing

A unit test checks a small piece of program behavior.

Usually:

  • one method;
  • one class;
  • or a small group of tightly related classes.

Example using JUnit:

import static org.junit.jupiter.api.Assertions.*;
import org.junit.jupiter.api.Test;

public class CourseTest {

    @Test
    void newCourseIsNotFull() {

        Course course =
            new Course(
                "CSC500",
                "Programming Fundamentals",
                2
            );

        assertFalse(course.isFull());
    }
}

A useful unit test should be:

  • focused;
  • repeatable;
  • automatic;
  • predictable;
  • independent from unrelated functionality.

56. Arrange — Act — Assert

A helpful testing structure is:

Arrange
Act
Assert

Arrange

Create the test state.

Course course =
    new Course("CSC500", "Programming", 2);

Student alice =
    new Student("S1", "Alice");

Act

Perform the behavior.

boolean result =
    course.enroll(alice);

Assert

Check the result.

assertTrue(result);
assertEquals(1, course.getEnrollmentCount());

Full example:

@Test
void enrollingStudentIncreasesCount() {

    // Arrange
    Course course =
        new Course("CSC500", "Programming", 2);

    Student alice =
        new Student("S1", "Alice");

    // Act
    boolean result =
        course.enroll(alice);

    // Assert
    assertTrue(result);
    assertEquals(
        1,
        course.getEnrollmentCount()
    );
}

57. Normal, boundary, and invalid tests

For most operations, think in three categories.

Normal cases

Typical valid behavior.

Example:

Course capacity = 30
Current enrollment = 15

Boundary cases

Values close to important limits.

Example:

enrollment = 0
enrollment = 1
enrollment = 29
enrollment = 30

for capacity 30.

Invalid cases

Values or operations that should not be allowed.

Examples:

capacity = -1
student = null
course code = ""
duplicate student ID
unknown course

Systematic categories help uncover cases we might otherwise forget.

58. Why boundaries matter

Consider:

public boolean isFull() {
    return students.size() > capacity;
}

Suppose:

size = 30
capacity = 30

Then:

30 > 30

is false.

The program incorrectly believes there is another seat.

Correct:

public boolean isFull() {
    return students.size() >= capacity;
}

A test at exactly the capacity would expose the error.

This is why test values around boundaries are so valuable.

59. Testing Course.enroll

For:

public boolean enroll(Student student)

we should consider at least:

  1. valid enrollment;
  2. enrollment count increases;
  3. last available seat;
  4. course already full;
  5. duplicate student;
  6. null student;
  7. failed enrollment leaves the object unchanged.

Example:

@Test
void duplicateEnrollmentFails() {

    Course course =
        new Course("CSC500", "Programming", 5);

    Student alice =
        new Student("S1", "Alice");

    assertTrue(course.enroll(alice));
    assertFalse(course.enroll(alice));

    assertEquals(
        1,
        course.getEnrollmentCount()
    );
}

Testing is not simply:

Run the application and make sure it does not crash.

Testing means constructing cases that challenge the program's assumptions.

60. Test behavior, not private implementation

Suppose today Course stores students using:

HashSet<Student>

Later we change the implementation.

Tests should generally ask:

Can students enroll?

Are duplicates rejected?

Does isFull() work?

Can students drop?

They should not unnecessarily ask:

Is the private field exactly a HashSet?

Why?

Because if behavior remains correct, changing the private representation should not require rewriting every test.

That is another advantage of abstraction.

61. Example integration test

We can test several collaborating objects:

@Test
void systemRegistersKnownStudentInKnownCourse() {

    RegistrationSystem system =
        new RegistrationSystem();

    Student alice =
        new Student("S1", "Alice");

    Course course =
        new Course(
            "CSC500",
            "Programming Fundamentals",
            2
        );

    system.addStudent(alice);
    system.addCourse(course);

    boolean result =
        system.register(
            "S1",
            "CSC500"
        );

    assertTrue(result);
    assertTrue(
        course.containsStudent(alice)
    );
}

This test checks collaboration among:

Student
Course
RegistrationSystem

62. Bugs vs. exceptions

A bug is any defect in a program.

Examples:

  • wrong calculation;
  • incorrect condition;
  • infinite loop;
  • off-by-one error;
  • incorrect state change;
  • wrong data structure;
  • failure to enforce a rule.

An exception is a Java mechanism for representing exceptional execution conditions.

Example:

Integer.parseInt("hello");

causes a NumberFormatException.

An exception may reveal a bug.

But not every exception means the software design is wrong.

For example, a missing file or malformed user input may be an expected situation that the application should handle.

63. Exceptions should not replace ordinary decisions

Suppose a course being full is a normal possibility.

This is appropriate:

if (course.isFull()) {
    System.out.println("Course is full.");
}

It would generally be unnecessary to treat ordinary capacity checking as a surprising exceptional event.

On the other hand:

new Course(
    "CSC500",
    "Programming",
    -20
);

represents invalid construction.

Throwing:

throw new IllegalArgumentException(
    "Capacity must be nonnegative"
);

is reasonable.

Use exceptions to communicate invalid or exceptional situations—not as a replacement for every Boolean condition.

64. Debugging larger programs

When a large program fails, random modifications are rarely efficient.

A systematic debugging process is:

  1. reproduce the problem;
  2. identify the smallest example that causes it;
  3. determine what should have happened;
  4. determine what actually happened;
  5. find the first point where program state differs from expectation;
  6. form a hypothesis;
  7. test the hypothesis;
  8. fix the underlying cause;
  9. rerun existing tests.

The key question is:

At what point does the state first become incorrect?

This is usually more productive than:

Which line looks suspicious?

65. Make bugs reproducible

Bad bug description:

Registration is broken.

Useful bug description:

1. Create CSC500 with capacity 2.
2. Register S1.
3. Register S2.
4. Attempt to register S3.
5. S3 is incorrectly accepted.

Now we know:

  • exact initial state;
  • exact actions;
  • expected result;
  • actual result.

Reproducibility turns a vague problem into an experiment.

66. Observe program state

If registration fails unexpectedly, inspect relevant state.

For example:

course.capacity
course.getEnrollmentCount()
student.id
course.code

Temporary diagnostic output may help:

System.out.println(
    "capacity = " + course.getCapacity()
);

System.out.println(
    "count = " +
    course.getEnrollmentCount()
);

The goal is not to print everything.

The goal is to test a specific hypothesis.

67. Debuggers

Modern IDEs provide debuggers.

Important concepts include:

Breakpoint

Pause execution at a selected line.

Step over

Execute the current line without entering a called method.

Step into

Enter the method currently being called.

Step out

Finish the current method and return to its caller.

Variable inspection

View:

  • local variables;
  • fields;
  • object contents.

Call stack

See which sequence of method calls led to the current execution point.

A debugger is especially valuable when several objects interact.

68. Evidence-based debugging example

Suppose the program allows one student too many.

Hypothesis:

isFull() uses > instead of >=.

Inspect:

public boolean isFull() {
    return students.size() > capacity;
}

If:

students.size() = 30
capacity = 30

then:

30 > 30

is false.

The program believes the course is not full.

The evidence supports our hypothesis.

Fix:

public boolean isFull() {
    return students.size() >= capacity;
}

Then rerun tests.

That is debugging by reasoning rather than guessing.

69. Off-by-one errors revisited

Incorrect:

for (int i = 0;
     i <= array.length;
     i++) {

    System.out.println(array[i]);
}

Valid array indices are:

0 through array.length - 1

Eventually the loop attempts:

array[array.length]

which is invalid.

Correct:

for (int i = 0;
     i < array.length;
     i++) {

    System.out.println(array[i]);
}

Off-by-one errors frequently appear in:

  • loops;
  • arrays;
  • strings;
  • binary search;
  • range calculations;
  • substring operations.

Always explicitly identify the valid boundaries.

70. Debugging recursive code

When debugging recursion, ask:

  1. What is the base case?
  2. Does every recursive call move closer to the base case?
  3. What should each call return?
  4. How is the recursive result combined?

Example:

int factorial(int n) {

    if (n == 0) {
        return 1;
    }

    return n * factorial(n - 1);
}

Trace a small input:

factorial(3)

= 3 * factorial(2)

= 3 * 2 * factorial(1)

= 3 * 2 * 1 * factorial(0)

= 3 * 2 * 1 * 1

= 6

Small examples make recursive behavior easier to inspect.

71. Reading Java API documentation

Professional programmers do not memorize the entire Java library.

Instead, they know how to learn from documentation.

Suppose you encounter:

PriorityQueue

You should be able to investigate:

  1. Which package contains it?
  2. What interfaces does it implement?
  3. What ordering does it use?
  4. Which constructors are available?
  5. How do I add an element?
  6. How do I inspect the next element?
  7. How do I remove the next element?
  8. What happens when it is empty?
  9. Can it contain null?
  10. What exceptions might operations throw?

The important skill is not memorization.

It is information retrieval from technical documentation.

72. Reading a method signature

Suppose documentation contains:

V put(K key, V value)

For:

Map<String, Student> students;

we have:

K = String
V = Student

So conceptually:

Student put(
    String key,
    Student value
)

The return type matters.

Do not stop reading documentation after finding the method name.

Check:

  • parameter types;
  • return type;
  • exceptions;
  • special behavior;
  • null behavior when relevant.

73. Documentation vs. tutorials

A tutorial primarily teaches you how to accomplish something.

A tutorial may say:

Here is how to create a HashMap and store values.

API documentation precisely describes the programming interface.

It tells you things such as:

method name
parameter types
return type
exceptions
interfaces implemented
behavioral guarantees

Both are useful.

Tutorials help you begin.

Documentation helps you determine exact behavior.

74. A complete design walkthrough

Consider a new requirement.

Design a package-delivery application. Each package has a tracking number, recipient name, address, weight, and delivery status. The system can add packages, retrieve a package by tracking number, update its status, and list packages having a particular status.

Do not begin with Java.

First analyze.

75. Step 1 — Identify domain concepts

Possible classes:

Package
DeliverySystem

Possibly:

Address

if addresses need enough behavior to justify a separate object.

Potential status values:

CREATED
IN_TRANSIT
OUT_FOR_DELIVERY
DELIVERED

An enum may be appropriate:

public enum PackageStatus {
    CREATED,
    IN_TRANSIT,
    OUT_FOR_DELIVERY,
    DELIVERED
}

Why not strings?

Because:

"delivered"
"Delivered"
"DELIVERD"

could otherwise become inconsistent values.

An enum limits the program to known states.

76. Step 2 — Identify important operations

Requirements include:

add package

find by tracking number

update status

display packages with a status

The important phrase is:

find by tracking number

This suggests:

Map<String, Package>

because a tracking number acts as a key.

77. Step 3 — Design the domain class

public class Package {

    private final String trackingNumber;
    private final String recipient;
    private final double weight;

    private PackageStatus status;

    public Package(
            String trackingNumber,
            String recipient,
            double weight) {

        if (trackingNumber == null ||
            trackingNumber.isBlank()) {

            throw new IllegalArgumentException(
                "Tracking number required"
            );
        }

        if (weight < 0) {
            throw new IllegalArgumentException(
                "Weight cannot be negative"
            );
        }

        this.trackingNumber =
            trackingNumber;

        this.recipient =
            recipient;

        this.weight =
            weight;

        this.status =
            PackageStatus.CREATED;
    }

    public String getTrackingNumber() {
        return trackingNumber;
    }

    public PackageStatus getStatus() {
        return status;
    }

    public void updateStatus(
            PackageStatus status) {

        if (status == null) {
            throw new IllegalArgumentException(
                "Status cannot be null"
            );
        }

        this.status = status;
    }
}

78. Step 4 — Design the system class

import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

public class DeliverySystem {

    private final Map<String, Package>
        packagesByTrackingNumber;

    public DeliverySystem() {

        packagesByTrackingNumber =
            new HashMap<>();
    }

    public boolean addPackage(Package pkg) {

        String number =
            pkg.getTrackingNumber();

        if (packagesByTrackingNumber
                .containsKey(number)) {

            return false;
        }

        packagesByTrackingNumber
            .put(number, pkg);

        return true;
    }

    public Package findPackage(
            String trackingNumber) {

        return packagesByTrackingNumber
            .get(trackingNumber);
    }

    public List<Package> findByStatus(
            PackageStatus status) {

        List<Package> result =
            new ArrayList<>();

        for (Package pkg :
                packagesByTrackingNumber.values()) {

            if (pkg.getStatus() == status) {
                result.add(pkg);
            }
        }

        return result;
    }
}

79. Step 5 — Analyze complexity

Suppose there are n packages.

Find by tracking number

findPackage(...)

uses a HashMap.

Average expected:

O(1)

Add package

Average expected:

O(1)

Find all packages by status

for (Package pkg :
        packagesByTrackingNumber.values()) {
    ...
}

must inspect every package:

O(n)

Is O(n) acceptable?

That depends on requirements.

If the operation happens occasionally with 500 packages, probably.

If the system contains 100 million packages and constantly queries status, another structure may be justified.

Design decisions depend on scale and use.

80. Step 6 — Identify invariants

Possible invariants:

tracking numbers are unique

tracking number is nonempty

weight is nonnegative

status is not null

Where should those rules be enforced?

Prefer to enforce them close to the state they protect.

81. Step 7 — Design tests

For addPackage(...):

Normal

add a valid package

Boundary

weight = 0

Invalid

duplicate tracking number
empty tracking number
negative weight

For findPackage(...):

existing tracking number
unknown tracking number
only package in system
many packages

For status queries:

zero matching packages
one matching package
many matching packages
all packages match

This thinking should happen before or during implementation—not only after failure.

82. A second design exercise: Tiny social network

Requirements:

  • register users;
  • find a user by username;
  • create friendships;
  • list a user's friends;
  • determine whether two users are friends;
  • duplicate friendships are not allowed.

Useful structures might include:

Map<String, User> usersByUsername;

and inside User:

Set<User> friends;

Why a map?

username → user

is key-value lookup.

Why a set?

Because:

  • friendships should not be duplicated;
  • membership testing matters.

Again:

Requirements suggest operations, and operations suggest data structures.

83. A third design exercise: Task scheduler

Requirements:

  • tasks are submitted;
  • every task has a priority;
  • the highest-priority task should be processed next.

An ArrayList could store tasks.

But then repeatedly finding the highest-priority task might require searching.

A more appropriate abstraction may be:

PriorityQueue<Task>

because the required behavior is:

repeatedly remove the next highest-priority item.

This is a design question—not merely a syntax question.

By Week 15, you should be able to reason about a program at several levels.

What sequence of operations solves the problem?

Data-structure level

How should the information be organized?

Object-oriented level

Which classes and relationships model the problem?

Strong programmers move among all of these levels.

85. Design before implementation: A practical checklist

Before implementing a substantial program, ask the following.

Requirements

  • What must the program do?
  • What are the inputs?
  • What are the outputs?
  • What rules must be enforced?
  • What invalid situations can occur?

Classes

  • What concepts belong in classes?
  • What is each class responsible for?
  • Can I describe each responsibility clearly?
  • Does any class appear to be doing too much?

Data

  • What information must each object store?
  • Which fields should be private?
  • What values should never change?
  • What invariants must remain true?

Relationships

  • Which objects contain other objects?
  • Which relationships are composition?
  • Is inheritance truly appropriate anywhere?

Data structures

  • Does order matter?
  • Is indexed access required?
  • Must values be unique?
  • Is fast key lookup important?
  • Is processing FIFO?
  • Is processing LIFO?
  • Is hierarchy important?
  • Is priority important?

Methods

  • What operations should each class expose?
  • Do method names communicate intent?
  • Is any method doing several unrelated tasks?

Dependencies

  • Which objects need to communicate?
  • Does a class know more about another class than necessary?
  • Can an interface reduce unnecessary dependence?

Complexity

  • Which operations happen most frequently?
  • What is their approximate Big-O cost?
  • Is the design reasonable for the expected amount of data?

Error handling

  • Which invalid conditions can be prevented?
  • Which conditions should return false?
  • Which situations justify exceptions?

Testing

  • What are the normal cases?
  • What are the boundaries?
  • What invalid cases should be rejected?
  • Can important components be tested independently?

86. Code review checklist

Before submitting a project, review the code systematically.

Correctness

  • Does every requirement work?
  • Are invalid operations handled?
  • Have important boundary cases been tested?

Readability

  • Are names meaningful?
  • Is formatting consistent?
  • Can the high-level algorithm be understood?
  • Are comments used for non-obvious reasoning rather than obvious syntax?

Modularity

  • Does every class have a clear purpose?
  • Are methods reasonably focused?
  • Is too much logic inside main?

Encapsulation

  • Are fields private where appropriate?
  • Can outside code modify internal collections directly?
  • Are class invariants protected?

Data structures

  • Can you explain why each major structure was chosen?
  • Are you repeatedly scanning data that should be keyed?
  • Are duplicate values possible where they should not be?

Coupling and cohesion

  • Are closely related responsibilities together?
  • Are unrelated responsibilities separated?
  • Does one class know too much about another?

Duplication

  • Is important logic repeated?
  • Is the same constant copied in several places?
  • Could a meaningful method or abstraction centralize a rule?

Complexity

  • Are there unnecessary nested loops?
  • Are expensive operations repeated?
  • Is optimization actually required?

Testing

  • Do tests include normal, boundary, and invalid cases?
  • Can failures be reproduced?
  • Do tests verify behavior rather than private implementation?

Documentation

  • Are non-obvious assumptions explained?
  • Can another programmer understand the public API?

89. Common software-design mistakes

Mistake 1 — Coding before understanding

Problem statement → immediately write classes

Better:

understand requirements first

Mistake 2 — One giant class

public class Program {
    // every field
    // every method
    // all file I/O
    // all UI
    // all business logic
}

Better:

identify meaningful responsibilities

Mistake 3 — Making every field public

public int capacity;
public List<Student> students;

Better:

private int capacity;
private Set<Student> students;

with controlled operations.

Mistake 4 — Automatically creating setters

setBalance(...)
setStudentId(...)
setEnrollmentCount(...)

Ask whether arbitrary assignment makes sense.

Mistake 5 — Selecting a data structure by habit

"I always use ArrayList."

Better:

What operations must this structure support?

Mistake 6 — Using inheritance for code reuse alone

Ask:

Is this genuinely an is-a relationship?

Mistake 7 — Duplicating business rules

if (students.size() >= capacity)

copied throughout the application.

Better:

course.isFull()

Mistake 8 — Overengineering

Do not introduce unnecessary abstractions merely because they sound sophisticated.

Mistake 9 — Testing only successful cases

Testing:

valid input works

is not enough.

Also test boundaries and failure conditions.

Mistake 10 — Debugging by random editing

Use hypotheses and program-state evidence.

90. Frequently asked questions

FAQ 1 — How do I know what should become a class?

A class should usually represent a meaningful concept that has state, behavior, or both.

Ask:

Does this concept have information that must be remembered and operations that naturally belong to that information?

Examples:

Student
Course
BankAccount
Package
Order

Do not create classes merely because you can.

FAQ 2 — How many methods should a class have?

There is no correct maximum.

Ask whether the methods support the same general responsibility.

A Stack can have many methods and still have excellent cohesion.

FAQ 3 — Should every field be private?

Fields should generally be private unless there is a clear reason otherwise.

Private fields allow the class to control its own state and protect invariants.

FAQ 4 — Should every private field have a getter?

No.

Expose information that callers genuinely need.

FAQ 5 — Should every private field have a setter?

Definitely not automatically.

A setter may allow callers to create invalid states.

Prefer meaningful operations when possible.

FAQ 6 — Which data structure is best?

There is no universally best one.

The right question is:

Which structure supports the operations required by this problem?

FAQ 7 — Should I always use the structure with the best Big-O complexity?

No.

Also consider:

  • expected data size;
  • code complexity;
  • readability;
  • memory use;
  • frequency of operations;
  • maintenance cost.

For 15 values, an O(n) operation may be entirely acceptable.

FAQ 8 — Why write List instead of ArrayList?

Because:

List<Student>

states the abstraction the code requires.

The code does not unnecessarily depend on one implementation.

FAQ 9 — When should I use inheritance?

Use inheritance when one class is genuinely a specialized kind of another:

SavingsAccount is a BankAccount

Do not use inheritance solely because two classes share some code.

FAQ 10 — When should I prefer composition?

When the relationship is naturally:

has-a

Examples:

Course has Students
Car has Engine
Order has OrderItems

FAQ 11 — How long should a method be?

There is no universal line-count rule.

It should represent one coherent task.

If a method contains several conceptually different sections, consider extracting methods.

FAQ 12 — What does high cohesion mean?

It means that the responsibilities inside a component are closely related.

Aim for high cohesion.

FAQ 13 — What does low coupling mean?

It means components have few unnecessary dependencies on each other's internal details.

Low unnecessary coupling makes changes safer.

FAQ 14 — What is refactoring?

Refactoring improves code structure without intentionally changing externally observable behavior.

FAQ 15 — Should I refactor before the program works?

Usually establish correct behavior first.

Then improve structure while running tests to ensure behavior remains correct.

FAQ 16 — When should I optimize?

First understand correctness and clarity.

Then identify meaningful performance issues.

Do not spend large amounts of effort optimizing operations that do not matter.

FAQ 17 — How do I know whether my program is efficient enough?

Ask:

  • How large can the input become?
  • Which operations dominate runtime?
  • Are repeated linear searches occurring?
  • Are nested loops processing the same large data?
  • Would another structure significantly reduce cost?

FAQ 18 — How should I test a large program?

Test:

  • individual methods;
  • individual classes;
  • interactions;
  • and finally realistic whole-system scenarios.

Do not rely only on end-to-end manual testing.

FAQ 19 — What should I test besides normal behavior?

Always think about:

normal
boundary
invalid

Also consider:

  • empty collections;
  • one-element collections;
  • duplicate values;
  • missing values;
  • maximum values;
  • zero;
  • null, where relevant.

FAQ 20 — What is the most useful debugging question?

Ask:

Where does the program state first differ from what I expected?

That directs debugging toward evidence.

FAQ 21 — Should I use print statements for debugging?

They can be useful for small investigations.

For larger programs, learn to use a debugger so you can:

  • pause execution;
  • step through code;
  • inspect values;
  • inspect objects;
  • inspect the call stack.

FAQ 22 — Do professional programmers memorize Java's APIs?

No.

An important programming skill is knowing how to search and read API documentation efficiently.

FAQ 23 — Can two different software designs both be correct?

Absolutely.

For many problems there are several reasonable designs.

Compare designs based on requirements such as:

  • correctness;
  • readability;
  • performance;
  • memory;
  • flexibility;
  • testability;
  • complexity.

91. In-class design activity

Design a campus event-registration system.

Requirements:

  • students can register for events;
  • each student has a unique ID;
  • each event has a unique ID;
  • events have capacities;
  • students cannot register twice;
  • the system can find students by ID;
  • the system can find events by ID;
  • the system can list students registered for an event;
  • the system can list events registered by a student.

Part A — Identify candidate classes

Possible candidates:

Student
Event
RegistrationSystem

Would a separate:

Registration

class be useful?

Perhaps not initially.

But suppose later a registration contains:

registration date
wait-list position
payment status
attendance status

Now the relationship itself contains important state.

A Registration class may become worthwhile.

This illustrates how designs evolve as requirements change.

92. Activity — Select data structures

Choose structures for:

all students
all events
event participants
events selected by one student

Possible design:

Map<String, Student> studentsById;

Map<String, Event> eventsById;

For participants:

Set<Student> participants;

Questions:

  1. Why is a map suitable for students?
  2. Why is a map suitable for events?
  3. Why might a set be preferable for participants?
  4. When might a list be preferable?
  5. What consistency problems arise if registrations are stored in both Student and Event?

93. Activity — Design the API before the implementation

Write only method signatures.

For example:

    Student student
)

    Event event
)

    String studentId,
    String eventId

    String studentId,
    String eventId

    String studentId

    String eventId

Ask:

  • Are method names clear?
  • Are return values useful?

Designing the API before writing code forces us to think about responsibilities.

94. Activity — Identify invariants

Possible invariants:

Student IDs are unique.

Event IDs are unique.

Participant count never exceeds capacity.

A student cannot register twice.

Registrations refer only to existing students.

Registrations refer only to existing events.

For each invariant, ask:

Which class should enforce this rule?

For:

design cases such as:

unknown student

unknown event

event exactly at capacity

duplicate registration

For each case, specify:

operation
expected result
expected final state

96. Suggested refactoring lab

Start with a working program containing:

  • one enormous class;
  • public mutable fields;
  • poorly named variables;
  • duplicated validation;
  • long methods;
  • mixed UI and business logic;
  • repeated linear searches.

For example:

public class App {

    public ArrayList<String> a =
        new ArrayList<>();

    public ArrayList<String> b =
        new ArrayList<>();

    public void doStuff() {

        // 150 lines
    }
}

Refactoring objectives:

  1. identify domain classes;
  2. give each class a clear responsibility;
  3. make fields private where appropriate;
  4. rename vague fields and methods;
  5. extract coherent methods;
  6. centralize duplicated rules;
  7. replace inappropriate data structures;
  8. separate UI from core application logic;
  9. preserve observable behavior;
  10. create tests to protect behavior during refactoring.

The goal is not to add new features.

The goal is to improve the structure.

Suppose two solutions both satisfy the requirements.

There is rarely a meaningful definition of "best" without knowing which qualities matter most.

Improving the internal structure of code without intentionally changing its externally observable behavior.

99. Week 15 summary

The most important transition this week is from thinking:

How do I write this Java statement?

to thinking:

How should this software be organized?

A mature development process moves approximately through:

problem
    ↓
requirements
    ↓
model
    ↓
responsibilities
    ↓
classes
    ↓
data structures
    ↓
algorithms
    ↓
implementation
    ↓
testing
    ↓
debugging
    ↓
refactoring

Software development is iterative.

You may discover that:

  • a class has too many responsibilities;
  • a method is too large;
  • a list should really be a map;
  • an internal collection should not be exposed;
  • duplicated logic needs a method;
  • an API needs to be simplified;
  • a test reveals an incorrect assumption.

That is not a failure of the design process.

That is the design process.

The important concepts from the course now work together:

Object-oriented programming
    organizes responsibilities.

Data structures
    organize information.

Algorithms
    process information.

Big-O analysis
    helps us reason about scalability.

Interfaces
    separate required behavior
    from implementation details.

Encapsulation
    protects state and invariants.

Testing
    establishes confidence.

Debugging
    helps locate faults systematically.

Documentation
    lets us learn unfamiliar APIs.

Refactoring
    improves structure as our
    understanding develops.

The goal is no longer merely:

Write Java code that produces the correct output.

The broader goal is:

Design software that is correct, understandable, testable, maintainable, appropriately efficient, and suited to the problem being solved.
