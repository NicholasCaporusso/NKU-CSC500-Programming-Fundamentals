CSC500 - Programming fundamentals

Week 6: classes and objects

1. Overview

Until now, most of the programs we have written have been organized primarily around methods.

A typical program might contain:

  • variables,
  • arrays,
  • loops,
  • conditionals,
  • and several methods.

This style of programming works well for small programs. However, as programs become larger, it becomes increasingly difficult to organize all of the data and operations in a clear way.

Object-oriented programming gives us another way to structure programs.

Instead of thinking only in terms of:

What functions should my program perform?

we also begin asking:

What objects exist in the problem, what information do those objects store, and what can those objects do?

In Java, object-oriented programming is built around classes and objects.

This week introduces the central concepts behind object-oriented programming:

  • classes,
  • objects,
  • fields,
  • methods,
  • constructors,
  • references,
  • encapsulation,
  • access modifiers,
  • and the this keyword.

These ideas will form the foundation for most of the Java programming we do for the rest of the course.

2. Learning objectives

By the end of this week, you should be able to:

  1. Explain the difference between a class and an object.
  2. Define a Java class containing fields and methods.
  3. Create objects using the new operator.
  4. Access and modify object state through methods.
  5. Write constructors that initialize objects.
  6. Explain the role of object references.
  7. Distinguish between primitive variables and reference variables.
  8. Use private and public appropriately.
  9. Explain the purpose of encapsulation.
  10. Use the this keyword to refer to the current object.
  11. Write getter and setter methods when appropriate.
  12. Design a small program consisting of multiple interacting objects.

3. Motivation: why objects?

Suppose we want to write a program that stores information about students.

For each student we want to store:

  • name,
  • student ID,
  • number of credits,
  • GPA.

Without classes, we might use several arrays:

String[] names = new String[100];
int[] ids = new int[100];
int[] credits = new int[100];
double[] gpas = new double[100];

This works, but it creates a problem.

The information for a single student is spread across several arrays.

For example:

names[5]
ids[5]
credits[5]
gpas[5]

all describe the same student.

The relationship between those pieces of information exists only because the programmer remembers that index 5 refers to the same student in every array.

Object-oriented programming allows us to group related data together.

We could instead define a Student class.

public class Student {
    String name;
    int id;
    int credits;
    double gpa;
}

Then one object can represent one student.

Conceptually:

Student object
-----------------
name: "Alice"
id: 12345
credits: 18
gpa: 3.72

Now the data belonging to one student stays together.

This idea-combining related data and behavior-is one of the central motivations for object-oriented programming.

4. Classes and objects

A class is a definition or blueprint for a type of object.

An object is a particular instance of a class.

For example:

public class Dog {
    String name;
    int age;
}

Dog is a class.

We can create individual Dog objects:

Dog dog1 = new Dog();
Dog dog2 = new Dog();

Now dog1 and dog2 refer to two separate objects.

We can store different information in each one.

dog1.name = "Buddy";
dog1.age = 5;

dog2.name = "Luna";
dog2.age = 2;

Conceptually:

dog1
  |
  v
+----------------+
| Dog object     |
| name = Buddy   |
| age = 5        |
+----------------+

dog2
  |
  v
+----------------+
| Dog object     |
| name = Luna    |
| age = 2        |
+----------------+

The important distinction is:

Class = definition

Object = one particular instance created from that definition

Another analogy is a house blueprint.

The blueprint describes:

  • number of rooms,
  • layout,
  • dimensions.

But the blueprint is not itself a house.

You can construct many different houses from the same blueprint.

Similarly:

Class → blueprint

Object → constructed instance

5. Defining a class

Consider a simple bank account.

public class BankAccount {

    double balance;

}

The class contains one variable:

double balance;

A variable declared inside a class but outside a method is called a field.

Fields represent the state of an object.

We could create two accounts:

BankAccount account1 = new BankAccount();
BankAccount account2 = new BankAccount();

and give them different balances.

account1.balance = 500.0;
account2.balance = 1250.0;

Although both objects belong to the same class, they contain independent state.

6. Fields

A field is a variable that belongs to an object.

For example:

public class Rectangle {

    double width;
    double height;

}

Each Rectangle object has its own width and height.

Example:

Rectangle r1 = new Rectangle();
Rectangle r2 = new Rectangle();

r1.width = 5;
r1.height = 3;

r2.width = 10;
r2.height = 7;

Conceptually:

r1
 |
 v
+------------+
| width = 5  |
| height = 3 |
+------------+

r2
 |
 v
+-------------+
| width = 10  |
| height = 7  |
+-------------+

Changing r1.width does not affect r2.width.

Each object has its own state.

7. Objects can also have behavior

Objects do not only store information.

They can also perform operations.

These operations are represented by methods.

For example:

public class Rectangle {

    double width;
    double height;

    public double area() {
        return width * height;
    }

}

Now we can write:

Rectangle r = new Rectangle();

r.width = 5;
r.height = 3;

System.out.println(r.area());

Output:

15.0

The method operates using the object's own fields.

When we call:

r.area();

Java executes the area() method using the values stored inside the object referenced by r.

8. Instance methods

A method that operates on a particular object is called an instance method.

Example:

public class BankAccount {

    double balance;

    public void deposit(double amount) {
        balance = balance + amount;
    }

    public void withdraw(double amount) {
        balance = balance - amount;
    }

}

Usage:

BankAccount account = new BankAccount();

account.balance = 1000;

account.deposit(200);
account.withdraw(50);

System.out.println(account.balance);

Output:

1150.0

Notice that the methods do not need a balance parameter.

Why?

Because the method already belongs to a particular object.

When we write:

account.deposit(200);

the deposit method operates on account's balance.

9. Object state

The collection of values stored in an object's fields is called the object's state.

Consider:

public class LightBulb {

    boolean on;

    public void turnOn() {
        on = true;
    }

    public void turnOff() {
        on = false;
    }

}

Initially:

on = false

After:

bulb.turnOn();

the object's state changes:

on = true

Objects often represent entities whose state changes over time.

Examples include:

BankAccount
    balance

Student
    credits
    gpa

GameCharacter
    health
    position

ShoppingCart
    items
    total

Thermostat
    temperature

Object methods often cause controlled changes to object state.

10. Creating objects with new

Objects are normally created using the new operator.

Example:

Rectangle rect = new Rectangle();

This statement has several parts.

Rectangle rect = new Rectangle();

Rectangle

is the variable's type.

rect

is the reference variable.

new Rectangle()

creates a new object.

Conceptually:

rect
 |
 v
+-------------------+
| Rectangle object  |
| width = 0.0       |
| height = 0.0      |
+-------------------+

The variable rect does not contain the entire object.

Instead, it stores a reference to the object.

11. Primitive variables vs. reference variables

This distinction is extremely important in Java.

Consider:

int x = 10;

Here, x directly stores the value 10.

Now consider:

Rectangle r = new Rectangle();

Here, r stores a reference to a Rectangle object.

We can think of the two situations like this.

Primitive:

x
+----+
| 10 |
+----+

Reference:

r
+-----------+
| reference | --------+
+-----------+         |
                      v
               +-------------+
               | Rectangle   |
               | width       |
               | height      |
               +-------------+

Primitive types include:

int
double
boolean
char
long
float
short
byte

Most other types in Java are reference types.

Examples:

String
Scanner
ArrayList
Student
BankAccount
Rectangle

Arrays are also reference types.

12. Reference assignment

Consider:

BankAccount a = new BankAccount();
a.balance = 100;

BankAccount b = a;

A common misconception is that Java creates a second account.

It does not.

Both variables now refer to the same object.

a --------+
          |
          v
     +-------------+
     | BankAccount |
     | balance=100 |
     +-------------+
          ^
          |
b --------+

Now suppose we write:

b.balance = 500;

Then:

System.out.println(a.balance);

prints:

500.0

Why?

Because a and b refer to the same object.

This behavior is fundamentally different from primitive assignment.

Consider:

int x = 10;
int y = x;

y = 20;

System.out.println(x);

Output:

10

The value was copied.

With references, the reference itself is copied.

The underlying object is not automatically copied.

13. The null reference

A reference variable can also contain the special value:

null

Example:

BankAccount account = null;

This means that account currently refers to no object.

If we write:

account.deposit(100);

Java will generate a:

NullPointerException

because there is no object on which to execute the method.

A NullPointerException is one of the most common errors in Java.

Whenever one occurs, ask:

Which reference was null?

14. Constructors

So far, we have been creating objects like this:

BankAccount account = new BankAccount();

account.balance = 1000;

A better approach is often to initialize an object when it is created.

Java uses constructors for this purpose.

Example:

public class BankAccount {

    double balance;

    public BankAccount(double initialBalance) {
        balance = initialBalance;
    }

}

Now we can write:

BankAccount account = new BankAccount(1000);

The constructor initializes the object.

Conceptually:

new BankAccount(1000)

        |
        v

+------------------+
| BankAccount      |
| balance = 1000   |
+------------------+

15. Constructor syntax

A constructor looks similar to a method, but there are two important differences.

First, its name must match the class name.

Second, it does not have a return type.

Correct:

public BankAccount(double initialBalance) {
    balance = initialBalance;
}

Incorrect:

public void BankAccount(double initialBalance) {
    balance = initialBalance;
}

Adding void turns it into a normal method rather than a constructor.

16. Constructors with multiple parameters

Suppose we create a Student class.

public class Student {

    String name;
    int id;
    double gpa;

    public Student(String studentName,
                   int studentId,
                   double studentGpa) {

        name = studentName;
        id = studentId;
        gpa = studentGpa;
    }

}

Usage:

Student s1 =
    new Student("Maria", 12345, 3.8);

Student s2 =
    new Student("Ahmed", 98765, 3.4);

Each object is initialized with different values.

17. Multiple constructors

A class can have more than one constructor.

Example:

public class BankAccount {

    double balance;

    public BankAccount() {
        balance = 0;
    }

    public BankAccount(double initialBalance) {
        balance = initialBalance;
    }

}

Now both of the following are legal:

BankAccount account1 =
    new BankAccount();

BankAccount account2 =
    new BankAccount(500);

This is an example of overloading.

Two constructors may have the same name if they have different parameter lists.

18. The this keyword

Suppose we write:

public class Student {

    String name;

    public Student(String name) {
        name = name;
    }

}

What does:

name = name;

mean?

Both uses of name refer to the constructor parameter.

The field does not get assigned.

To distinguish the object's field from the parameter, Java provides the keyword:

this

We write:

public class Student {

    String name;

    public Student(String name) {
        this.name = name;
    }

}

Here:

this.name

means:

the name field belonging to this object.

while:

name

means:

the constructor parameter named name.

This pattern is extremely common in Java.

19. this refers to the current object

Consider:

public class BankAccount {

    double balance;

    public void deposit(double amount) {
        this.balance += amount;
    }

}

When we call:

account1.deposit(100);

inside the method:

this

refers to:

account1

If we instead call:

account2.deposit(100);

then:

this

refers to:

account2

The same method can therefore operate on different objects.

20. Encapsulation

So far, our fields have been accessible directly.

For example:

account.balance = -1000000;

Java allows this if the field is publicly accessible.

But should a bank account allow arbitrary code to assign any value directly to its balance?

Usually not.

Object-oriented programming encourages a principle called encapsulation.

Encapsulation means:

An object should control access to its own internal state.

Instead of allowing arbitrary direct modification, the class provides methods that define valid operations.

For example:

public class BankAccount {

    private double balance;

    public BankAccount(double initialBalance) {
        balance = initialBalance;
    }

    public void deposit(double amount) {
        if (amount > 0) {
            balance += amount;
        }
    }

    public void withdraw(double amount) {
        if (amount > 0 && amount <= balance) {
            balance -= amount;
        }
    }

    public double getBalance() {
        return balance;
    }

}

Outside code cannot now write:

account.balance = -10000;

because balance is private.

Instead, outside code must use the public interface:

account.deposit(500);

account.withdraw(100);

System.out.println(account.getBalance());

21. Access modifiers

Java provides access modifiers that control visibility.

For now, the two most important are:

public
private

A public member can generally be accessed from outside the class.

A private member can only be accessed from within the class itself.

Example:

public class Student {

    private String name;
    private double gpa;

    public String getName() {
        return name;
    }

}

From another class:

Student s = new Student();

This is legal:

s.getName();

This is not:

s.name

because name is private.

22. Why make fields private?

Consider a Person class:

public class Person {

    public int age;

}

Another part of the program can write:

person.age = -37;

That value makes no sense.

If the field is private, we can control how changes happen.

public class Person {

    private int age;

    public void setAge(int age) {
        if (age >= 0) {
            this.age = age;
        }
    }

}

Now the class can enforce its rules.

This is one benefit of encapsulation.

The class protects its internal state from invalid changes.

23. Getters

A method that returns the value of a private field is commonly called a getter.

Example:

public String getName() {
    return name;
}

Usage:

System.out.println(student.getName());

A common naming convention is:

field           getter

name            getName()
balance         getBalance()
age             getAge()
temperature     getTemperature()

For boolean fields, methods are often named:

isActive()
isEmpty()
isValid()

24. Setters

A method that modifies a private field is often called a setter.

Example:

public void setName(String name) {
    this.name = name;
}

However, not every field should automatically have a setter.

For example, consider:

private double balance;

Providing:

public void setBalance(double balance)

would allow outside code to arbitrarily replace the balance.

It might be better to expose:

deposit()
withdraw()

because those operations describe the behavior of a bank account more accurately.

A key design principle is:

Do not automatically write getters and setters for every field.

Instead ask:

What operations should users of this class actually be allowed to perform?

25. Example: a complete BankAccount class

public class BankAccount {

    private String owner;
    private double balance;

    public BankAccount(String owner,
                       double initialBalance) {

        this.owner = owner;

        if (initialBalance >= 0) {
            this.balance = initialBalance;
        } else {
            this.balance = 0;
        }
    }

    public String getOwner() {
        return owner;
    }

    public double getBalance() {
        return balance;
    }

    public void deposit(double amount) {

        if (amount > 0) {
            balance += amount;
        }
    }

    public boolean withdraw(double amount) {

        if (amount > 0 &&
            amount <= balance) {

            balance -= amount;
            return true;
        }

        return false;
    }

}

A separate program can use the class.

public class BankDemo {

    public static void main(String[] args) {

        BankAccount account =
            new BankAccount("Alice", 1000);

        account.deposit(250);

        boolean success =
            account.withdraw(400);

        System.out.println(
            account.getOwner()
        );

        System.out.println(
            account.getBalance()
        );

        System.out.println(
            "Withdrawal successful: "
            + success
        );
    }

}

Output:

Alice
850.0
Withdrawal successful: true

26. Public interface vs. internal implementation

A useful way to think about a class is to separate two ideas.

Public interface

The public interface describes what other code is allowed to do.

For BankAccount:

getOwner()
getBalance()
deposit()
withdraw()

These methods define how other code interacts with the object.

Internal implementation

The internal implementation describes how the class accomplishes its work.

For example:

private String owner;
private double balance;

Outside code should not need to know the details.

This separation is extremely important in software engineering.

If the internal implementation changes but the public interface stays the same, code using the class may not need to change.

27. Abstraction

Encapsulation is closely related to another concept: abstraction.

Abstraction means focusing on what something does without requiring the user to understand every implementation detail.

You already use abstraction frequently.

Consider:

String text = "hello";

text.toUpperCase();

You know what toUpperCase() does.

You probably do not know exactly how Java's String class implements the operation internally.

You do not need to know.

The method provides an abstraction.

Similarly, when someone uses:

account.withdraw(100);

they should not need to understand every detail of how the account stores its balance.

The class provides a useful abstraction.

28. Objects interacting with objects

Real object-oriented programs rarely contain only one type of object.

Objects interact.

Consider a Course class that contains students.

public class Course {

    private String courseCode;
    private Student[] students;
    private int studentCount;

    public Course(String courseCode,
                  int capacity) {

        this.courseCode = courseCode;
        students = new Student[capacity];
        studentCount = 0;
    }

    public void addStudent(Student student) {

        if (studentCount < students.length) {

            students[studentCount] = student;
            studentCount++;
        }
    }

}

Notice:

Student[] students;

A field can itself contain references to other objects.

We can write:

Student s1 =
    new Student("Alice", 101, 3.7);

Student s2 =
    new Student("Bob", 102, 3.4);

Course course =
    new Course("CSC500", 30);

course.addStudent(s1);
course.addStudent(s2);

Now the Course object contains references to Student objects.

This is one way that complex programs are constructed from interacting objects.

30. Equality and objects

Consider:

BankAccount a =
    new BankAccount("Alice", 100);

BankAccount b =
    new BankAccount("Alice", 100);

Are a and b the same object?

No.

Two separate objects were created.

Conceptually:

a ---> BankAccount object #1

b ---> BankAccount object #2

Even if their fields contain identical values, they are different objects.

Now consider:

BankAccount c = a;

Then:

a ---> BankAccount object #1
          ^
          |
c --------+

a and c refer to the same object.

This distinction becomes important when comparing objects.

31. The == operator and references

For primitive types:

int x = 5;
int y = 5;

System.out.println(x == y);

prints:

true

For object references, == asks whether the references point to the exact same object.

Example:

BankAccount a =
    new BankAccount("Alice", 100);

BankAccount b =
    new BankAccount("Alice", 100);

System.out.println(a == b);

Output:

false

because two separate objects were created.

But:

BankAccount c = a;

System.out.println(a == c);

prints:

true

because both references point to the same object.

Later we will discuss more sophisticated approaches for comparing object contents.

32. Strings are objects too

You have already been working with objects.

A String is an object.

Example:

String name = "Alice";

We call methods on it:

name.length();

name.toUpperCase();

name.substring(1, 3);

The expression:

name.length()

has the same general object-method structure as:

account.getBalance()

or:

rectangle.area()

The difference is that Java provides the String class for us, while we write classes such as BankAccount ourselves.

33. Instance variables vs. local variables

Consider:

public class Counter {

    private int count;

    public void increment() {

        int amount = 1;

        count = count + amount;
    }
}

There are two kinds of variables here.

count is a field, or instance variable.

It belongs to the object.

amount is a local variable.

It exists only while the method is running.

Conceptually:

Counter object
+----------------+
| count = 5      |
+----------------+

increment() call
+----------------+
| amount = 1     |
+----------------+

When the method finishes, the local variable disappears.

The object's fields remain as long as the object exists.

34. Object lifetime

Objects are created using new.

Example:

BankAccount account =
    new BankAccount("Alice", 100);

Eventually, an object may no longer have any references pointing to it.

For example:

account = null;

If no other reference points to the object, the program can no longer access it.

Java contains a system called garbage collection that automatically reclaims memory occupied by unreachable objects.

Unlike languages such as C and C++, Java programmers generally do not manually free object memory.

For this course, the important idea is:

Objects remain accessible while references to them exist.

35. Designing a class

When designing a class, ask several questions.

Question 1: what entity does the class represent?

Examples:

Student
Book
Employee
Rectangle
BankAccount
Course
Appointment
GameCharacter

Question 2: what state does each object need?

For a book:

title
author
ISBN
numberOfPages
checkedOut

Question 3: what behavior should the object provide?

For a book:

checkout()
returnBook()
isCheckedOut()
getTitle()

Question 4: which information should be private?

Usually the fields.

Question 5: what rules must the class enforce?

For example:

A bank balance should not become negative.

A person's age should not be negative.

A course enrollment should not exceed capacity.

A rectangle's width should not be negative.

A well-designed class makes invalid states difficult or impossible to create.

36. Example design: Rectangle

Suppose we want a rectangle abstraction.

Possible state:

width
height

Possible behavior:

area
perimeter
resize

Implementation:

public class Rectangle {

    private double width;
    private double height;

    public Rectangle(double width,
                     double height) {

        if (width >= 0) {
            this.width = width;
        }

        if (height >= 0) {
            this.height = height;
        }
    }

    public double getWidth() {
        return width;
    }

    public double getHeight() {
        return height;
    }

    public double getArea() {
        return width * height;
    }

    public double getPerimeter() {
        return 2 * width +
               2 * height;
    }

}

Usage:

Rectangle room =
    new Rectangle(12, 10);

System.out.println(
    room.getArea()
);

Output:

120.0

37. Example design: Counter

A simple counter is useful for understanding state.

public class Counter {

    private int count;

    public Counter() {
        count = 0;
    }

    public void increment() {
        count++;
    }

    public void decrement() {
        count--;
    }

    public void reset() {
        count = 0;
    }

    public int getCount() {
        return count;
    }

}

Usage:

Counter counter =
    new Counter();

counter.increment();
counter.increment();
counter.increment();

System.out.println(
    counter.getCount()
);

Output:

3

Notice that every call changes the same object's state.

38. Example design: Temperature

public class Temperature {

    private double celsius;

    public Temperature(double celsius) {
        this.celsius = celsius;
    }

    public double getCelsius() {
        return celsius;
    }

    public double getFahrenheit() {
        return celsius * 9.0 / 5.0 + 32;
    }

}

This example illustrates an important design concept.

We do not necessarily need fields for both Celsius and Fahrenheit.

If Fahrenheit can be calculated from Celsius, storing both could create inconsistencies.

For example:

celsius = 0
fahrenheit = 100

would be contradictory.

Instead, store the essential state and calculate derived information when needed.

39. Common mistake: forgetting new

Incorrect:

BankAccount account;

account.deposit(100);

The variable has been declared, but no object has been created.

Correct:

BankAccount account =
    new BankAccount("Alice", 0);

account.deposit(100);

40. Common mistake: directly exposing fields

Less desirable:

public class Student {

    public String name;
    public double gpa;

}

Better:

public class Student {

    private String name;
    private double gpa;

    public String getName() {
        return name;
    }

    public double getGpa() {
        return gpa;
    }

}

Private fields give the class control over its internal state.

41. Common mistake: confusing class and object

Incorrect conceptual statement:

Student is a student.

Better:

Student is a class that defines what Student objects contain and can do.

An individual object such as:

Student alice;

may represent a particular student.

42. Common mistake: confusing references with objects

Consider:

Student s1 =
    new Student("Alice", 1, 3.5);

Student s2 = s1;

There are:

2 reference variables

but only

1 Student object

This distinction is critical.

43. Common mistake: accidentally shadowing fields

Incorrect:

public Student(String name) {
    name = name;
}

Correct:

public Student(String name) {
    this.name = name;
}

The first version assigns the parameter to itself.

The second assigns the parameter value to the object's field.

44. Common mistake: writing unnecessary setters

Suppose we have:

public class BankAccount {

    private double balance;

}

It may be tempting to write:

public void setBalance(double balance) {
    this.balance = balance;
}

But ask whether callers should really be able to directly replace the account balance.

Usually:

deposit()
withdraw()

better represent the legal operations.

Good object-oriented design is not simply:

Make everything private and create getters and setters.

Instead:

Define a meaningful public interface that protects the object's rules.

48. Worked example: Book

Suppose we want to represent books in a library.

Requirements:

Each book has:

title
author
ISBN
checkout status

A user should be able to:

check out a book
return a book
determine whether it is checked out
retrieve its title and author

A possible design is:

public class Book {

    private String title;
    private String author;
    private String isbn;
    private boolean checkedOut;

    public Book(String title,
                String author,
                String isbn) {

        this.title = title;
        this.author = author;
        this.isbn = isbn;
        checkedOut = false;
    }

    public String getTitle() {
        return title;
    }

    public String getAuthor() {
        return author;
    }

    public String getIsbn() {
        return isbn;
    }

    public boolean isCheckedOut() {
        return checkedOut;
    }

    public boolean checkout() {

        if (checkedOut) {
            return false;
        }

        checkedOut = true;
        return true;
    }

    public void returnBook() {
        checkedOut = false;
    }

}

Notice that we do not provide:

setCheckedOut()

Instead, the class exposes meaningful operations:

checkout()
returnBook()

This is a more expressive design.

50. Multi-class programs

In Java, larger programs usually contain many classes.

For example:

Library
Book
Patron
Loan
LibraryApplication

Each class has a responsibility.

A useful design principle is:

A class should have one clear conceptual responsibility.

For example:

Book
    represents one book

Patron
    represents one library patron

Loan
    represents a borrowing transaction

Library
    manages collections of books and patrons

The goal is not simply to create many classes.

The goal is to organize the program into meaningful abstractions.

53. Concept check

For each statement, determine whether it is true or false.

1.

A class and an object are the same thing.

False.

A class defines a type of object. An object is an instance of that class.

2.

Two variables can refer to the same object.

True.

3.

Every field should have a setter.

False.

The public interface should expose only operations that make sense.

4.

A constructor has a return type.

False.

Constructors do not specify a return type.

5.

Private fields cannot be accessed directly from unrelated classes.

True.

6.

this refers to the current object.

True.

7.

Assigning one object reference variable to another automatically copies the object.

False.

It copies the reference.

59. Important design principle: protect invariants

An invariant is a condition that should always remain true for an object.

Examples:

For a bank account:

balance >= 0

For a course:

0 <= enrollment <= capacity

For a rectangle:

width >= 0

height >= 0

For an inventory item:

quantity >= 0

price >= 0

One purpose of encapsulation is to protect these invariants.

If external code can directly modify every field, maintaining invariants becomes much harder.

60. From procedural thinking to object-oriented thinking

Earlier in the course, you might have written:

double calculateArea(
    double width,
    double height) {

    return width * height;
}

This is procedural thinking.

The operation receives all required information through parameters.

With objects:

Rectangle rect =
    new Rectangle(5, 3);

double area =
    rect.getArea();

The data belongs to the object.

The object's method operates on its own state.

Neither approach is universally correct.

Object-oriented programming becomes particularly useful when:

  • many related values belong together,
  • the program models entities,
  • state changes over time,
  • operations depend on that state,
  • programs become large,
  • multiple components interact.

61. Reading object-oriented code

When you encounter an unfamiliar class, ask:

1. What does one object represent?

2. What fields define its state?

3. What constructors can create it?

4. What public methods can outside code call?

5. What private details are hidden?

6. Which methods modify object state?

7. Which methods simply return information?

This approach will become increasingly important as you begin reading larger Java programs.

63. End-of-week takeaways

The most important ideas from this week are:

1. Classes define new types.

class Student
class BankAccount
class Rectangle

2. Objects are instances of classes.

new Student(...)
new BankAccount(...)

3. Fields represent object state.

private double balance;

4. Methods represent object behavior.

deposit()
withdraw()

5. Constructors initialize new objects.

public Student(String name)

6. Variables of class types hold references.

Student student;

7. Multiple references can point to the same object.

This can cause changes through one variable to appear through another.

8. private fields support encapsulation.

Classes should control their own internal state.

9. this refers to the current object.

this.name = name;

10. Good classes protect their invariants.

An object's public methods should make invalid states difficult to create.
