1. Overview

Up to this point, most of our programs have been organized primarily around statements and methods.

A typical program might contain:

  • variables,
  • expressions,
  • conditionals,
  • loops,
  • arrays,
  • strings,
  • and several methods.

This works well for relatively small programs. We can divide a larger task into methods and pass the information those methods need through parameters.

For example, suppose we want to calculate the area of a rectangle:

public static double calculateArea(
        double width,
        double height) {

    return width * height;
}

The method receives the information it needs as parameters.

As programs become larger, however, we frequently encounter a different organizational problem:

Several pieces of data belong together, and several operations naturally act on that data.

For example, a bank account has information such as:

owner
balance
account number

and operations such as:

deposit
withdraw
get balance

A student has information such as:

name
student ID
credits
GPA

and operations such as:

add a completed course
calculate GPA
get credits

Object-oriented programming gives us a way to organize such information.

Instead of thinking only:

What functions should my program perform?

we also begin asking:

What objects exist in the problem?

What information does each object need to remember?

What operations should each object be able to perform?

In Java, these ideas are expressed primarily through classes and objects.

This week introduces the foundations of object-oriented programming:

  • classes,
  • objects,
  • fields,
  • object state,
  • instance methods,
  • constructors,
  • references,
  • null,
  • object identity,
  • aliasing,
  • encapsulation,
  • access modifiers,
  • getters and setters,
  • class invariants,
  • the this keyword,
  • and simple programs containing multiple interacting objects.

These concepts form the foundation for most of the Java programming we will do during the remainder of the course.

3. From procedural thinking to object-oriented thinking

Consider a rectangle.

A procedural solution might look like this:

public static double area(
        double width,
        double height) {

    return width * height;
}

public static double perimeter(
        double width,
        double height) {

    return 2 * width + 2 * height;
}

Every method receives the rectangle's data through parameters.

Usage might look like:

double width = 5.0;
double height = 3.0;

System.out.println(area(width, height));
System.out.println(perimeter(width, height));

There is nothing inherently wrong with this design.

But notice that:

width
height

belong together conceptually.

They describe one rectangle.

An object-oriented version groups the data and operations:

public class Rectangle {

    private double width;
    private double height;

    public Rectangle(double width, double height) {
        this.width = width;
        this.height = height;
    }

    public double getArea() {
        return width * height;
    }

    public double getPerimeter() {
        return 2 * width + 2 * height;
    }
}

Now we can write:

Rectangle room =
    new Rectangle(5.0, 3.0);

System.out.println(room.getArea());
System.out.println(room.getPerimeter());

The important change is conceptual.

In the procedural version:

operation + parameters

In the object-oriented version:

object containing state
        +
methods operating on that state

Neither style is universally better.

Object-oriented organization becomes especially useful when:

  • several values naturally belong together,
  • we need many instances of the same kind of entity,
  • an entity's state changes over time,
  • operations depend on that state,
  • multiple entities interact,
  • or a program becomes large enough that organization becomes difficult.

4. Motivation: Why classes?

Suppose we want to represent students.

For every student, we need to remember:

  • name,
  • student ID,
  • credits completed,
  • GPA.

Without classes, we might use parallel arrays:

String[] names = new String[100];
int[] ids = new int[100];
int[] credits = new int[100];
double[] gpas = new double[100];

The information for student number 5 is spread across four arrays:

names[5]
ids[5]
credits[5]
gpas[5]

The programmer must remember that all four values refer to the same student.

This becomes increasingly difficult as programs grow.

With a class, we can group the information:

public class Student {

    String name;
    int id;
    int credits;
    double gpa;
}

One object can now represent one student.

Conceptually:

Student object
+----------------------+
| name    = "Alice"    |
| id      = 12345      |
| credits = 18         |
| gpa     = 3.72       |
+----------------------+

The values that belong to Alice remain grouped together.

This is one of the central ideas of object-oriented programming:

Related data and related behavior can be grouped into an object.

5. Classes and objects

A class defines a type of object.

An object is one particular instance of that class.

Consider:

public class Dog {

    String name;
    int age;
}

Dog is a class.

It describes what every Dog object contains.

Now create two dogs:

Dog dog1 = new Dog();
Dog dog2 = new Dog();

These are two separate objects.

We might store:

dog1.name = "Buddy";
dog1.age = 5;

dog2.name = "Luna";
dog2.age = 2;

Conceptually:

dog1
 |
 v
+----------------+
| Dog object     |
| name = Buddy   |
| age = 5        |
+----------------+


dog2
 |
 v
+----------------+
| Dog object     |
| name = Luna    |
| age = 2        |
+----------------+

Both objects were created from the same class, but each object has its own state.

A useful first analogy is:

class  → blueprint
object → one thing built from that blueprint

Another useful analogy is:

class  → a new type
object → one value of that type

The second analogy is especially important in Java because a class literally defines a new type that you can use when declaring variables.

6. A class defines a new type

You already know Java's built-in types:

int
double
boolean
char

When we write:

public class Student {
}

we have defined another type:

Student

We can therefore declare variables of that type:

Student s1;
Student s2;
Student advisor;

Similarly:

public class BankAccount {
}

defines a type named:

BankAccount

and we may write:

BankAccount checking;
BankAccount savings;

This is one reason classes are so powerful.

Programmers can create types that represent concepts relevant to their programs.

7. Fields

A variable declared inside a class but outside a method or constructor is called a field.

Example:

public class Rectangle {

    double width;
    double height;
}

Here:

width
height

are fields.

Fields represent the state of an object.

Every Rectangle object gets its own values for these instance fields.

Consider:

Rectangle r1 = new Rectangle();
Rectangle r2 = new Rectangle();

r1.width = 5;
r1.height = 3;

r2.width = 10;
r2.height = 7;

Conceptually:

r1
 |
 v
+--------------+
| width = 5    |
| height = 3   |
+--------------+

r2
 |
 v
+--------------+
| width = 10   |
| height = 7   |
+--------------+

Changing:

r1.width = 12;

does not change r2.width.

Each object has its own state.

8. Object state

An object's state is the collection of values currently stored in its fields.

Consider:

public class LightBulb {

    private boolean on;

    public void turnOn() {
        on = true;
    }

    public void turnOff() {
        on = false;
    }
}

Suppose we create:

LightBulb bulb = new LightBulb();

Initially the field is:

on = false

After:

bulb.turnOn();

the object has changed state:

on = true

Many objects represent things whose state changes over time.

Examples:

BankAccount
    balance

Student
    credits
    totalGradePoints

GameCharacter
    health
    position

ShoppingCart
    items
    total

Thermostat
    temperature

LibraryBook
    checkedOut

A central responsibility of many methods is to change object state in a controlled way.

9. Objects have behavior

Objects do not merely store information.

They can also perform operations.

Those operations are represented by methods.

Example:

public class Rectangle {

    double width;
    double height;

    public double area() {
        return width * height;
    }
}

Now:

Rectangle r = new Rectangle();

r.width = 5;
r.height = 3;

System.out.println(r.area());

prints:

15.0

Notice something important.

The method does not receive width and height as parameters.

It already has access to the fields of the particular object on which the method is called.

When we write:

r.area();

Java runs area() for the object referenced by r.

10. Instance methods

A method that operates on a particular object is called an instance method.

Example:

public class BankAccount {

    double balance;

    public void deposit(double amount) {
        balance = balance + amount;
    }

    public void withdraw(double amount) {
        balance = balance - amount;
    }
}

Usage:

BankAccount account =
    new BankAccount();

account.balance = 1000;

account.deposit(200);
account.withdraw(50);

System.out.println(account.balance);

Output:

1150.0

Why does deposit not need a balance parameter?

Because the method runs on a particular account.

When Java sees:

account.deposit(200);

we can mentally read it as:

Ask the object referenced by account to deposit 200 into itself.

11. The receiving object

Consider:

BankAccount alice =
    new BankAccount();

BankAccount bob =
    new BankAccount();

alice.balance = 1000;
bob.balance = 500;

alice.deposit(100);

Only Alice's account changes.

Afterward:

alice.balance = 1100
bob.balance   = 500

The same deposit method exists for both objects, but the result depends on which object receives the method call.

Compare:

alice.deposit(100);

with:

bob.deposit(100);

The object before the dot is sometimes called the receiver of the method call.

This is useful when reading object-oriented code:

object.method(arguments)

means roughly:

Execute this method on this object.

12. Creating objects with new

Objects are normally created using the new operator.

Example:

Rectangle rect =
    new Rectangle();

Break the statement into pieces:

Rectangle       rect       =       new Rectangle();
   type       variable             create object

The expression:

new Rectangle()

creates a new Rectangle object.

The result of that expression is a reference to the newly created object.

That reference is stored in:

rect

Conceptually:

rect
 |
 v
+-------------------+
| Rectangle object  |
| width = 0.0       |
| height = 0.0      |
+-------------------+

The important point is:

rect is not the object itself.

rect stores a reference to the object.

13. What conceptually happens during new?

Consider:

Student s =
    new Student("Alice", 12);

Conceptually, Java performs several steps:

  1. Memory is allocated for a new Student object.
  2. The object's fields receive their initial default values.
  3. The selected constructor runs.
  4. The constructor establishes the intended initial state.
  5. A reference to the object is produced.
  6. That reference is stored in s.

A simplified diagram:

new Student("Alice", 12)
           |
           v
+---------------------+
| Student object      |
| name = "Alice"      |
| credits = 12        |
+---------------------+
           ^
           |
           s

14. Primitive variables vs. reference variables

This is one of the most important distinctions in Java.

Consider:

int x = 10;

x directly stores the primitive value 10.

Conceptually:

x
+----+
| 10 |
+----+

Now consider:

Student s =
    new Student("Alice");

s stores a reference to a Student object.

Conceptually:

s
+-----------+
| reference | --------+
+-----------+         |
                      v
                +-------------+
                | Student     |
                | name=Alice  |

Primitive types include:

byte

Examples:

15. Assignment with primitive values

Consider:

int x = 10;
int y = x;

The value in x is copied into y.

Conceptually:

x = 10
y = 10

Now:

y = 20;

produces:

x = 10
y = 20

Changing y does not change x.

16. Assignment with references

Now compare:

BankAccount a =
    new BankAccount();

a.balance = 100;

BankAccount b = a;

This does not create a second bank account.

The reference stored in a is copied into b.

Now both variables refer to the same object.

a --------\
           \
            v
       +----------------+
       | BankAccount    |
       | balance = 100  |
       +----------------+
            ^
           /
b --------/

Suppose:

b.balance = 500;

Then:

System.out.println(a.balance);

prints:

500.0

Why?

Because there is still only one BankAccount object.

Both references lead to that object.

17. Aliasing

When multiple reference variables point to the same object, we say that the object has aliases.

Example:

Student s1 =
    new Student("Alice");

Student s2 = s1;

Now:

s1 ----\
        \
         ---> Student object
        /     name = "Alice"
s2 ----/

If the object can change:

s2.setName("Alicia");

then:

System.out.println(
    s1.getName()
);

prints:

Alicia

because both references access the same object.

Aliasing is not automatically an error.

It is extremely common in object-oriented programs.

The important skill is to recognize when it exists.

18. Object identity

Two objects can contain identical data while still being different objects.

Consider:

Student a =
    new Student("Alice");

Student b =
    new Student("Alice");

Two separate uses of new created two separate objects.

Conceptually:

a ------> Student object #1
          name = "Alice"

b ------> Student object #2
          name = "Alice"

Even though the fields contain the same information:

object #1 != object #2

in terms of identity.

Now compare:

Student c = a;

Then:

a ----\
       ---> Student object #1
c ----/

b --------> Student object #2

a and c refer to the same object.

b refers to a different object.

19. == with object references

For primitive values:

int x = 5;
int y = 5;

System.out.println(x == y);

prints:

true

For object references, == asks a different question:

Do these two references refer to the exact same object?

Example:

Student a =
    new Student("Alice");

Student b =
    new Student("Alice");

System.out.println(a == b);

Output:

false

because two different objects were created.

But:

Student c = a;

System.out.println(a == c);

prints:

true

because both references point to the same object.

20. == vs. .equals()

Students often confuse object identity and logical equality.

For reference variables:

a == b

asks:

Are these the same object?

Logical equality asks something more like:

Should these two objects be considered equivalent based on their contents?

For strings:

String x =
    new String("hello");

String y =
    new String("hello");

System.out.println(x == y);
System.out.println(x.equals(y));

The first expression compares identity.

The second compares string contents.

For classes we write ourselves, meaningful .equals() behavior requires additional implementation.

For Week 6, the essential distinction is:

==          → same object?
.equals()   → logically equal?

Do not assume that .equals() automatically compares all fields of every class you create.

21. null

A reference variable does not always refer to an object.

It can contain the special value:

null

Example:

Student student = null;

Conceptually:

student ----> nothing

This does not mean that a special empty Student object exists.

It means:

student currently refers to no object.

22. NullPointerException

Consider:

Student student = null;

System.out.println(
    student.getName()
);

There is no Student object on which Java can execute getName().

The program therefore throws a:

NullPointerException

Another example:

private Student advisor;

Fields that hold object references default to null.

If no object has ever been assigned to advisor, then:

advisor.getName();

may cause a NullPointerException.

A useful debugging question is:

Which reference was null?

Then ask:

Why did I expect that reference to point to an object?

23. Declaring a reference is not the same as creating an object

This declares a variable:

BankAccount account;

It does not create an account.

To create an object:

account =
    new BankAccount();

A common beginner mistake is conceptually:

BankAccount account;

// use account as though an object exists
account.deposit(100);

The declaration creates a variable capable of storing a BankAccount reference.

The new expression creates the object.

Keep the distinction clear:

BankAccount account;

means:

Declare a variable.

while:

new BankAccount()

means:

Create an object.

24. Constructors

Objects often need meaningful initial values.

Instead of:

BankAccount account =
    new BankAccount();

account.balance = 1000;

we would prefer the object to be initialized when it is created.

Java uses a constructor for this purpose.

public class BankAccount {

    private double balance;

    public BankAccount(
            double initialBalance) {

        balance = initialBalance;
    }
}

Now:

BankAccount account =
    new BankAccount(1000);

creates the account and initializes its balance immediately.

25. Constructor syntax

A constructor resembles a method, but two features distinguish it.

Rule 1: Its name matches the class name

For:

public class Student {

a constructor is named:

Student

Rule 2: It has no return type

Correct:

public Student(String name) {
    this.name = name;
}

Incorrect:

public void Student(String name) {
    this.name = name;
}

The second version is a normal method named Student.

It is not a constructor.

The presence of void changes its meaning completely.

26. Constructors with multiple parameters

Example:

public class Student {

    private String name;
    private int id;
    private double gpa;

    public Student(
            String studentName,
            int studentId,
            double studentGpa) {

        name = studentName;
        id = studentId;
        gpa = studentGpa;
    }
}

Usage:

Student s1 =
    new Student(
        "Maria",
        12345,
        3.8);

Student s2 =
    new Student(
        "Ahmed",
        98765,
        3.4);

The same class creates objects with different state.

27. Constructor overloading

A class may contain multiple constructors.

Example:

public class BankAccount {

    private double balance;

    public BankAccount() {
        balance = 0;
    }

    public BankAccount(
            double initialBalance) {

        balance = initialBalance;
    }
}

Both are valid:

BankAccount a =
    new BankAccount();

BankAccount b =
    new BankAccount(500);

Java determines which constructor to use from the arguments.

This is called constructor overloading.

The constructors must have different parameter lists.

28. The compiler-generated default constructor

The phrase default constructor is often used imprecisely.

Consider:

public class Student {

    private String name;
}

If you write no constructors at all, Java automatically provides a no-argument constructor.

Therefore:

Student s =
    new Student();

works.

However, once you explicitly write a constructor:

public Student(String name) {
    this.name = name;
}

Java no longer automatically gives you a zero-argument constructor.

Therefore:

Student s =
    new Student();

will not compile unless you explicitly add:

public Student() {
}

A useful rule:

Java supplies the compiler-generated no-argument constructor only when you have written no constructors yourself.

29. Field default values

Instance fields receive default values automatically.

Some common defaults are:

TypeDefault field value
int0
long0L
double0.0
float0.0f
booleanfalse
charzero character
object referencenull

For example:

public class Student {

    private int credits;
    private String name;
}

A newly created object initially has approximately:

credits = 0
name = null

before any constructor assignments change those fields.

Even though Java provides defaults, good class design usually initializes fields deliberately when meaningful initialization is required.

30. Local variables do not receive the same automatic initialization

Compare fields with local variables.

This will not compile:

public void example() {

    int x;

    System.out.println(x);
}

The local variable x must be assigned before use.

So remember:

instance field → automatically receives a default value

local variable → must be definitely assigned before use

31. Fields vs. local variables

Consider:

public class Counter {

    private int count;

    public void increment() {

        int amount = 1;

        count =
            count + amount;
    }
}

Here:

count

is a field.

It belongs to the object.

amount

is a local variable.

It exists only while increment() is executing.

Conceptually:

Counter object
+----------------+
| count = 5      |
+----------------+

temporary method call
+----------------+
| amount = 1     |
+----------------+

After the method finishes:

amount disappears

count remains part of the object's state

32. Parameters vs. fields

Parameters are another kind of local variable.

Consider:

public void deposit(
        double amount) {

    balance += amount;
}

amount exists only during that method call.

balance belongs to the object.

For:

account.deposit(50);

we can imagine:

object state:
balance = 100

temporary parameter:
amount = 50

After the method:

balance = 150

The parameter is gone, but the modified field remains.

33. The this keyword

Consider:

public class Student {

    private String name;

    public Student(String name) {
        name = name;
    }
}

This contains a problem.

Inside the constructor, the parameter named name hides or shadows the field named name.

Therefore:

name = name;

assigns the parameter to itself.

The field remains unchanged.

Java provides the keyword:

this

to refer to the current object.

Correct version:

public class Student {

    private String name;

    public Student(String name) {
        this.name = name;
    }
}

Now:

this.name

means:

the field named name belonging to the current object

while:

name

means:

the parameter named name

Thus:

this.name = name;

means:

Store the parameter value in this object's field.

34. this means the current object

Suppose we have:

public class BankAccount {

    private double balance;

    public void deposit(
            double amount) {

        this.balance += amount;
    }
}

If we call:

alice.deposit(100);

then inside the method:

this

refers to Alice's account.

If we call:

bob.deposit(100);

then inside the same method code:

this

refers to Bob's account.

This is why one method definition can operate on many different objects.

35. Do we always need this?

No.

Inside an instance method:

public void deposit(double amount) {
    balance += amount;
}

is normally equivalent to:

public void deposit(double amount) {
    this.balance += amount;
}

this becomes necessary when a local name or parameter hides the field.

For example:

public void setName(String name) {
    this.name = name;
}

A common Java style is:

  • use this.field in constructors and setters when parameter names match field names,
  • omit this elsewhere unless it improves clarity.

36. Encapsulation

So far, we have occasionally accessed fields directly:

account.balance = 1000;

But consider what happens if the field is publicly accessible:

account.balance = -1000000;

Should arbitrary code be allowed to give a bank account an impossible balance?

Usually not.

Object-oriented programming encourages encapsulation.

A useful definition is:

Encapsulation groups state and behavior together while controlling access to an object's internal representation.

Instead of allowing outside code to change fields arbitrarily, the object exposes carefully designed operations.

37. private fields

Consider:

public class BankAccount {

    private double balance;
}

Because balance is private, another class cannot write:

account.balance = 500;

Instead, the class might expose:

public void deposit(double amount) {
    ...
}

public boolean withdraw(double amount) {
    ...
}

public double getBalance() {
    ...
}

Now the class controls how its state is used.

38. public and private

The two most important access modifiers for Week 6 are:

public
private

A public member is intended to be accessible by code outside the class.

A private member is accessible only from within the class itself.

Example:

public class Student {

    private String name;

    public String getName() {
        return name;
    }
}

Another class may write:

Student s = ...;

System.out.println(
    s.getName()
);

but not:

System.out.println(
    s.name
);

because name is private.

For now, a useful default guideline is:

fields                  → usually private
publicly useful methods → usually public
implementation helpers → possibly private

39. Why keep fields private?

Consider:

public class Person {

    public int age;
}

Then outside code can write:

person.age = -37;

That may violate the meaning of the object.

Instead:

public class Person {

    private int age;

    public void setAge(int age) {

        if (age >= 0) {
            this.age = age;
        }
    }
}

Now the class can enforce its own rules.

Private fields also reduce the amount of code that depends directly on the class's internal representation.

That makes future changes easier.

40. Class invariants

An invariant is a condition that should remain true for every valid object.

Examples:

For a bank account:

balance >= 0

For a rectangle:

width >= 0
height >= 0

For a course:

0 <= enrollment <= capacity

For an inventory item:

quantity >= 0
price >= 0

A well-designed class protects its invariants.

For example:

public boolean withdraw(
        double amount) {

    if (amount > 0 &&
        amount <= balance) {

        balance -= amount;
        return true;
    }

    return false;
}

The method refuses operations that would violate the account's rules.

41. Constructors should establish valid state

Encapsulation begins when the object is created.

Consider:

public BankAccount(
        String owner,
        double initialBalance) {

    this.owner = owner;

    if (initialBalance >= 0) {
        this.balance =
            initialBalance;
    } else {
        this.balance = 0;
    }
}

Even when invalid data is supplied, the constructor avoids creating an account with a negative balance.

In larger programs, another strategy might be to reject invalid arguments using an exception:

if (initialBalance < 0) {
    throw new IllegalArgumentException(
        "Initial balance cannot be negative");
}

We will study exception handling later.

For this week, focus on the design principle:

A constructor should establish a valid initial object state.

42. Getters

A method that returns information stored in an object is commonly called a getter or accessor.

Example:

public String getName() {
    return name;
}

Usage:

System.out.println(
    student.getName()
);

Common naming patterns:

FieldGetter
namegetName()
agegetAge()
balancegetBalance()
temperaturegetTemperature()

Boolean getters often use names such as:

isActive()
isEmpty()
isValid()
isCheckedOut()

43. Setters

A method that changes a field directly is often called a setter or mutator.

Example:

public void setName(String name) {
    this.name = name;
}

Sometimes a setter is appropriate.

For example, perhaps a person's display name can legitimately change.

But an important design rule is:

Do not automatically provide a setter for every field.

44. Why “private + getter + setter” is not automatically good encapsulation

Suppose we write:

private double balance;

but then add:

public void setBalance(
        double balance) {

    this.balance = balance;
}

Now outside code can still write:

account.setBalance(
    -1000000
);

We changed the syntax but did not meaningfully protect the object.

Better operations might be:

deposit(amount)
withdraw(amount)
transferTo(other, amount)

Those operations correspond to what bank accounts actually do.

Encapsulation is therefore not merely:

make every field private
+
write a getter and setter for everything

Instead:

Design a meaningful public interface that protects the object's rules.

45. Public interface and internal implementation

A class can be understood as having two sides.

Public interface

The public interface describes what other code is allowed to do.

For a bank account:

getOwner()
getBalance()
deposit(...)
withdraw(...)

Internal implementation

The implementation contains the details used to make those operations work.

For example:

private String owner;
private double balance;

Outside code should generally not depend on those details.

This separation allows us to change the implementation without necessarily changing code that uses the class.

46. Abstraction

Encapsulation is closely related to abstraction.

Abstraction means focusing on what something does without requiring the user to understand all of its implementation details.

You have already used abstractions.

Example:

String name = "alice";

String upper =
    name.toUpperCase();

You know what toUpperCase() does.

You do not need to know how Java internally processes every character.

Similarly:

account.withdraw(100);

should allow another programmer to think:

Attempt to withdraw 100.

They should not need to manually manipulate internal balance variables.

This is one of the goals of good class design.

47. Complete example: BankAccount

public class BankAccount {

    private String owner;
    private double balance;

    public BankAccount(
            String owner,
            double initialBalance) {

        this.owner = owner;

        if (initialBalance >= 0) {
            this.balance =
                initialBalance;
        } else {
            this.balance = 0;
        }
    }

    public String getOwner() {
        return owner;
    }

    public double getBalance() {
        return balance;
    }

    public void deposit(
            double amount) {

        if (amount > 0) {
            balance += amount;
        }
    }

    public boolean withdraw(
            double amount) {

        if (amount > 0 &&
            amount <= balance) {

            balance -= amount;
            return true;
        }

        return false;
    }
}

A separate class can use it:

public class BankDemo {

    public static void main(
            String[] args) {

        BankAccount account =
            new BankAccount(
                "Alice",
                1000);

        account.deposit(250);

        boolean success =
            account.withdraw(400);

        System.out.println(
            "Owner: "
            + account.getOwner());

        System.out.println(
            "Balance: "
            + account.getBalance());

        System.out.println(
            "Withdrawal successful: "
            + success);
    }
}

Output:

Owner: Alice
Balance: 850.0
Withdrawal successful: true

Notice what BankDemo does not do:

account.balance = ...

The account manages its own state.

48. Returning a value vs. printing a value

Students sometimes confuse:

System.out.println(...)

with:

return

Consider:

public void printBalance() {
    System.out.println(balance);
}

This displays the balance.

It does not give the value back to the caller.

Compare:

public double getBalance() {
    return balance;
}

Now another method can use the value:

double total =
    account1.getBalance()
    + account2.getBalance();

Returning a value is often more reusable than printing it directly.

A well-designed domain class usually provides information through return values and allows another part of the program to decide how to display it.

49. Should domain objects ask the user for input?

Usually not.

This design mixes user-interface logic with bank-account logic:

public void deposit() {

    Scanner input =
        new Scanner(System.in);

    System.out.print(
        "Amount: ");

    double amount =
        input.nextDouble();

    balance += amount;
}

A more reusable method is:

public void deposit(
        double amount) {

    if (amount > 0) {
        balance += amount;
    }
}

Then main can perform input:

System.out.print(
    "Deposit amount: ");

double amount =
    input.nextDouble();

account.deposit(amount);

This separation helps because the account can now be used:

  • from a console program,
  • from a graphical interface,
  • from a web application,
  • or from automated tests

without changing the account class.

50. Private helper methods

Not every method must be public.

Suppose a calculation is only needed internally:

public class Student {

    private double examAverage;
    private double homeworkAverage;

    public double calculateGrade() {
        return weightedAverage();
    }

    private double weightedAverage() {

        return 0.6 * examAverage
             + 0.4 * homeworkAverage;
    }
}

calculateGrade() is part of the public interface.

weightedAverage() is an implementation detail.

Outside code cannot call it directly.

This helps keep the public interface small and understandable.

51. Methods can call other methods on the same object

Consider:

public class Rectangle {

    private double width;
    private double height;

    public double getArea() {
        return width * height;
    }

    public boolean isLarge() {
        return getArea() > 100;
    }
}

Inside isLarge():

getArea()

calls another instance method on the same object.

We could also write:

return this.getArea() > 100;

but this is unnecessary here.

52. Objects can interact with other objects

Methods can receive other objects as parameters.

Example:

public class BankAccount {

    private double balance;

    public BankAccount(
            double balance) {

        this.balance = balance;
    }

    public void deposit(
            double amount) {

        if (amount > 0) {
            balance += amount;
        }
    }

    public boolean transferTo(
            BankAccount other,
            double amount) {

        if (amount <= 0 ||
            amount > balance) {

            return false;
        }

        balance -= amount;
        other.deposit(amount);

        return true;
    }
}

Usage:

BankAccount checking =
    new BankAccount(1000);

BankAccount savings =
    new BankAccount(500);

checking.transferTo(
    savings,
    200);

Afterward:

checking = 800
savings  = 700

One object has interacted with another object.

This is the beginning of multi-object program design.

53. Java is always pass-by-value

This statement is important:

Java is always pass-by-value.

Suppose:

public static void change(
        int x) {

    x = 100;
}

Then:

int number = 5;

change(number);

System.out.println(number);

prints:

5

The primitive value was copied into the parameter.

54. Pass-by-value with object references

Now consider:

public static void addMoney(
        BankAccount account) {

    account.deposit(100);
}

Suppose:

BankAccount savings =
    new BankAccount(500);

addMoney(savings);

The value stored in savings is a reference.

Java copies that reference value into the parameter account.

Conceptually:

savings -----\
              \
               ---> BankAccount
              /     balance = 500
account -----/

Both references point to the same object.

Therefore:

account.deposit(100);

changes the object.

After the method returns:

savings balance = 600

This sometimes causes people to say:

Java passes objects by reference.

That statement is inaccurate.

The precise explanation is:

Java passes the reference value by value.

55. Reassigning a parameter does not reassign the caller's variable

Consider:

public static void replace(
        BankAccount account) {

    account =
        new BankAccount(0);
}

Now:

BankAccount savings =
    new BankAccount(500);

replace(savings);

Inside replace, the parameter is changed to refer to a new object.

But the caller's variable still refers to the original account.

Conceptually before reassignment:

savings ----\
             ---> account object #1
parameter --/

Inside the method after reassignment:

savings --------> account object #1

parameter ------> account object #2

When the method ends, the local parameter disappears.

savings still refers to object #1.

This distinction is important:

modify shared object       → caller can observe change

reassign local parameter   → caller's variable is unchanged

56. Arrays of objects

Because a class defines a type, we can create arrays whose elements are references to objects.

Example:

Student[] students =
    new Student[3];

This creates an array capable of storing three Student references.

It does not automatically create three Student objects.

Initially:

students[0] = null
students[1] = null
students[2] = null

We must create objects separately:

students[0] =
    new Student("Alice");

students[1] =
    new Student("Bob");

students[2] =
    new Student("Carlos");

Conceptually:

students
+---------+
| [0] ----+----> Student("Alice")
| [1] ----+----> Student("Bob")
| [2] ----+----> Student("Carlos")
+---------+

This combines ideas from Week 5 and Week 6.

57. Traversing an array of objects

Suppose Student has:

public String getName()

Then:

for (int i = 0;
     i < students.length;
     i++) {

    System.out.println(
        students[i].getName());
}

prints each student's name.

Notice the expression:

students[i].getName()

Step by step:

  1. students[i] retrieves a reference.
  2. That reference points to a Student.
  3. getName() is called on that object.

If an array element contains null, then calling a method on it will cause a NullPointerException.

58. Objects can contain references to other objects

Fields can also have class types.

For example:

public class Course {

    private String courseCode;
    private Student[] students;
    private int studentCount;

    public Course(
            String courseCode,
            int capacity) {

        this.courseCode =
            courseCode;

        students =
            new Student[capacity];

        studentCount = 0;
    }

    public boolean addStudent(
            Student student) {

        if (studentCount >=
            students.length) {

            return false;
        }

        students[studentCount] =
            student;

        studentCount++;

        return true;
    }
}

Usage:

Student alice =
    new Student("Alice");

Student bob =
    new Student("Bob");

Course course =
    new Course(
        "CSC500",
        30);

course.addStudent(alice);
course.addStudent(bob);

The Course object now stores references to Student objects.

Drawing diagrams is one of the best ways to reason about references.

Suppose:

60. A systematic way to trace object code

When tracing object-oriented code by hand:

Step 1: Draw every reference variable

For:

Student a;
Student b;

draw:

a
b

Step 2: Create a box for each use of new

Student a =
    new Student("Alice");

creates one object:

a ----> Student #1

Step 3: Treat reference assignment as copying an arrow

Student b = a;

means:

a ----\
       ---> Student #1
b ----/

Do not draw a second object.

Step 4: Update fields when methods mutate objects

If:

b.setName("Alicia");

update Student #1.

Step 5: Track null

If:

a = null;

remove a's arrow.

Do not automatically delete the object if another reference still points to it.

61. Object lifetime and garbage collection

Objects are created with:

new

They remain accessible as long as the program has a way to reach them through references.

Example:

BankAccount account =
    new BankAccount(100);

Later:

account = null;

If no other reference points to that object, the program can no longer access it.

Java eventually reclaims memory used by unreachable objects through garbage collection.

For Week 6, the key idea is not the details of garbage collection.

It is:

References determine how your program can access objects.

62. Strings are objects too

You have already been using objects.

A String is an object.

Example:

String name = "Alice";

You call instance methods on strings:

name.length();
name.toUpperCase();
name.substring(1, 3);

Compare:

name.length()

with:

account.getBalance()

and:

rectangle.getArea()

All have the same general structure:

object.method(...)

The difference is that Java provides the String class, while we write classes such as Rectangle and BankAccount.

63. Mutability

An object is mutable if its state can change after construction.

Example:

BankAccount account =
    new BankAccount(100);

account.deposit(50);

The same object now contains a different balance.

A mutable object can therefore produce important effects when several references point to it.

Example:

BankAccount a =
    new BankAccount(100);

BankAccount b = a;

b.deposit(50);

Now both:

a.getBalance()
b.getBalance()

observe:

150

because there is only one mutable object.

64. Immutable objects

An immutable object's state cannot be changed after the object is created.

String is a familiar example.

Consider:

String s = "hello";

s.toUpperCase();

This does not modify the original string object.

If we want the result, we write:

s = s.toUpperCase();

A new string value is produced, and s is reassigned.

For Week 6, the main reason to understand mutability is that aliasing matters most when shared objects can change.

65. Avoid storing redundant derived state

Suppose we represent temperature.

Poor design might store:

private double celsius;
private double fahrenheit;

But these two fields describe the same quantity.

If one changes without the other:

celsius = 0
fahrenheit = 100

the object becomes inconsistent.

Instead:

public class Temperature {

    private double celsius;

    public Temperature(
            double celsius) {

        this.celsius =
            celsius;
    }

    public double getCelsius() {
        return celsius;
    }

    public double getFahrenheit() {

        return celsius
             * 9.0 / 5.0
             + 32;
    }
}

Now Fahrenheit is calculated when needed.

General principle:

Store essential state. Calculate derived information when practical.

This reduces the number of values that must remain synchronized.

66. Example: Designing a Counter

A counter has one clear piece of state:

count

and operations:

increment
decrement
reset
get count

Implementation:

public class Counter {

    private int count;

    public Counter() {
        count = 0;
    }

    public void increment() {
        count++;
    }

    public void decrement() {
        count--;
    }

    public void reset() {
        count = 0;
    }

    public int getCount() {
        return count;
    }
}

Usage:

Counter counter =
    new Counter();

counter.increment();
counter.increment();
counter.increment();

System.out.println(
    counter.getCount());

Output:

3

Every method call operates on the same object's state.

67. Example: Designing a Rectangle

Possible state:

width
height

Possible behavior:

get area
get perimeter
get width
get height

Implementation:

public class Rectangle {

    private double width;
    private double height;

    public Rectangle(
            double width,
            double height) {

        if (width >= 0) {
            this.width = width;
        }

        if (height >= 0) {
            this.height = height;
        }
    }

    public double getWidth() {
        return width;
    }

    public double getHeight() {
        return height;
    }

    public double getArea() {
        return width * height;
    }

    public double getPerimeter() {

        return 2 * width
             + 2 * height;
    }
}

Usage:

Rectangle room =
    new Rectangle(12, 10);

System.out.println(
    room.getArea());

Output:

120.0

68. Example: Designing a LibraryBook

Suppose a library book should remember:

title
author
checked-out status

It should support:

get title
get author
check whether it is checked out
check out the book
return the book

Implementation:

public class LibraryBook {

    private String title;
    private String author;
    private boolean checkedOut;

    public LibraryBook(
            String title,
            String author) {

        this.title = title;
        this.author = author;
        this.checkedOut = false;
    }

    public String getTitle() {
        return title;
    }

    public String getAuthor() {
        return author;
    }

    public boolean isCheckedOut() {
        return checkedOut;
    }

    public boolean checkOut() {

        if (checkedOut) {
            return false;
        }

        checkedOut = true;
        return true;
    }

    public boolean returnBook() {

        if (!checkedOut) {
            return false;
        }

        checkedOut = false;
        return true;
    }
}

Notice that we do not provide:

public void setCheckedOut(
        boolean checkedOut)

The public operations:

checkOut()
returnBook()

better express the object's behavior.

69. toString()

It is often useful to provide a readable text representation of an object.

For example:

@Override
public String toString() {

    return title
        + " by "
        + author;
}

Then:

System.out.println(book);

can print something meaningful such as:

The Hobbit by J. R. R. Tolkien

Without an appropriate toString() implementation, you may see output resembling:

LibraryBook@5acf9800

That is Java's default object representation and generally does not show the object's useful field values.

We will study overriding more formally later.

For now, you may treat toString() as a useful convenience for displaying and debugging objects.

70. Designing a class from a problem description

Suppose the problem says:

Design a program that represents library books. Each book has a title and author. A book starts available. It can be checked out unless it is already checked out, and it can be returned only if it is currently checked out.

A useful design process follows.

Step 1: Identify the concept

Possible class:

LibraryBook

Step 2: Identify essential state

title
author
checkedOut

Step 3: Identify meaningful behavior

getTitle()
getAuthor()
isCheckedOut()
checkOut()
returnBook()

Step 4: Identify invariants

For example:

checkedOut is either true or false

More importantly:

A book that is already checked out
cannot be checked out successfully again.

Step 5: Decide what should be private

Usually:

all fields

Step 6: Design constructors

Ask:

What information is required to create a meaningful object?

Probably:

title
author

The checked-out state can start as false.

Step 7: Decide which operations should return information

For example:

boolean checkOut()

can tell the caller whether the operation succeeded.

Step 8: Write small tests

Create objects and exercise the public interface.

71. Questions to ask when designing any class

When you are unsure how to begin, ask:

  1. What does one object represent?
  2. What state must one object remember?
  3. Which values can be calculated instead of stored?
  4. What operations naturally belong to this object?
  5. Which fields should be private?
  6. What should outside code be allowed to do?
  7. What should outside code not be allowed to do?
  8. What conditions must always remain true?
  9. What information must a constructor receive?
  10. What should methods return?
  11. Which methods change state?
  12. Which methods only inspect state?
  13. Do I really need a setter for this field?
  14. Does this class have one coherent responsibility?

There is not always one unique correct class design.

Design improves with practice.

72. What makes a reasonable Week 6 class?

At this point in CSC 500, a reasonably designed class usually has:

  • one clear purpose,
  • descriptive field names,
  • mostly private fields,
  • constructors that create meaningful objects,
  • public methods representing sensible operations,
  • protection against obviously invalid state,
  • minimal direct exposure of implementation details,
  • methods that are reasonably short,
  • and little duplicated logic.

Perfect software architecture is not expected.

The goal is to begin developing the habit of thinking about:

state
behavior
responsibility
interface
invariants

73. A complete multi-class example

Consider a small student-management application.

Student.java

public class Student {

    private String name;
    private int studentId;
    private int credits;
    private double totalGradePoints;

    public Student(
            String name,
            int studentId) {

        this.name = name;
        this.studentId =
            studentId;

        this.credits = 0;
        this.totalGradePoints = 0;
    }

    public String getName() {
        return name;
    }

    public int getStudentId() {
        return studentId;
    }

    public int getCredits() {
        return credits;
    }

    public double getGpa() {

        if (credits == 0) {
            return 0.0;
        }

        return totalGradePoints
             / credits;
    }

    public boolean addCourse(
            int courseCredits,
            double gradePointValue) {

        if (courseCredits <= 0) {
            return false;
        }

        if (gradePointValue < 0.0 ||
            gradePointValue > 4.0) {

            return false;
        }

        credits += courseCredits;

        totalGradePoints +=
            courseCredits
            * gradePointValue;

        return true;
    }

    @Override
    public String toString() {

        return name
            + " ("
            + studentId
            + "), credits="
            + credits
            + ", GPA="
            + getGpa();
    }
}

Important design decision:

We store:

credits
totalGradePoints

but not:

gpa

because GPA can be calculated:

GPA = totalGradePoints / credits

This prevents duplicated state from becoming inconsistent.

76. Finding the student with the highest GPA

Student best = students[0];

77. Common mistake: Confusing the class with an object

Incorrect conceptual statement:

Student is Alice.

Better:

Student is a class defining a type of object.

An individual object:

Student alice =
    new Student(
        "Alice",
        1001);

may represent Alice.

Remember:

Student → class/type

alice → variable holding a reference

new Student(...) → object creation

78. Common mistake: Assuming reference assignment copies an object

Consider:

Student a =
    new Student(
        "Alice",
        1001);

Student b = a;

How many reference variables?

2

How many Student objects?

1

A common incorrect mental model is:

a → object #1
b → copied object #2

Correct:

a ----\
       ---> object #1
b ----/

79. Common mistake: Forgetting new

Incorrect:

BankAccount account;

account.deposit(100);

No account object has been created.

Correct:

BankAccount account =
    new BankAccount(0);

account.deposit(100);

Keep declaration and object creation conceptually separate.

80. Common mistake: Adding a return type to a constructor

Incorrect:

public void Student(
        String name) {

    this.name = name;
}

This defines a method.

Correct:

public Student(
        String name) {

    this.name = name;
}

Constructors do not have return types.

81. Common mistake: Shadowing a field

Incorrect:

public Student(String name) {
    name = name;
}

Correct:

public Student(String name) {
    this.name = name;
}

The first version assigns the parameter to itself.

82. Common mistake: Assuming a no-argument constructor still exists

Suppose:

public class Student {

    public Student(String name) {
        ...
    }
}

Now this is invalid:

new Student();

unless you explicitly provide:

public Student() {
}

83. Common mistake: Making every field public

Poor design:

public class BankAccount {

    public double balance;
}

Outside code can now bypass every rule.

Prefer:

private double balance;

with meaningful operations.

84. Common mistake: Writing setters for everything

Potentially poor:

public void setBalance(
        double balance) {

    this.balance = balance;
}

Ask instead:

What legitimate actions change a balance?

Likely:

deposit(...)
withdraw(...)
transferTo(...)

Design methods around valid behavior rather than mechanically exposing fields.

85. Common mistake: Using == for logical object comparison

Remember:

a == b

means:

Do these references refer to the same object?

That is not automatically the same as asking:

Do these objects contain equivalent information?

For strings, use:

s1.equals(s2)

when comparing string contents.

For our own classes, meaningful .equals() behavior requires additional class design that will be discussed later.

86. Common mistake: Forgetting about null

Suppose:

Student[] students =
    new Student[100];

The array exists.

But its elements initially contain:

null

Therefore:

students[0].getName();

will fail until an object has been assigned:

students[0] =
    new Student(
        "Alice",
        1001);

87. Common mistake: Printing instead of returning

Less reusable:

public void printGpa() {
    System.out.println(getGpa());
}

More flexible:

public double getGpa() {
    ...
}

The caller may then:

System.out.println(
    student.getGpa());

or:

if (student.getGpa() >= 3.5) {
    ...
}

or:

double difference =
    s1.getGpa()
    - s2.getGpa();

Returning information allows more uses.

88. Common mistake: Storing information that can easily be derived

Suppose a student stores:

credits
totalGradePoints
gpa

Then every update must keep all three synchronized.

Instead, if:

GPA =
totalGradePoints / credits

we can calculate GPA when needed.

Fewer independent fields often mean fewer opportunities for inconsistent state.

89. Common mistake: Mixing input/output with domain logic

A BankAccount should usually know how to:

deposit
withdraw
report its balance

It usually should not be responsible for:

asking a console user for an amount
printing menus
reading Scanner input

Keep domain behavior and user-interface behavior separated when practical.

    new Student("Alice");

Changed

96. Reading an unfamiliar class

When you encounter a class you did not write, use this process.

1. What does one object represent?

Example:

Student?
Book?
BankAccount?
Rectangle?

2. What fields represent its state?

Look for declarations outside methods.

3. Which constructors exist?

Ask what information is required to create an object.

4. What is the public interface?

Look for public methods.

5. Which methods inspect state?

Examples:

getBalance()
getName()
isCheckedOut()

6. Which methods modify state?

Examples:

deposit()
withdraw()
checkOut()

7. What implementation details are hidden?

Look for private fields and helper methods.

This reading strategy will become increasingly useful as Java programs grow.

97. Testing a class

Testing an object means checking both:

  1. returned results,
  2. resulting object state.

For a bank account:

Create account with 100.
Expected balance: 100.

Deposit 50.
Expected balance: 150.

Withdraw 40.
Expected success: true.
Expected balance: 110.

Try to withdraw 500.
Expected success: false.
Expected balance: still 110.

Try to deposit -20.
Expected operation to be rejected.
Expected balance: still 110.

Notice that we test:

  • normal cases,
  • invalid cases,
  • and boundary cases.

More systematic testing will appear later in the course.

98. Debugging incorrect object state

If an object's state is wrong, ask:

  1. Which object contains the wrong value?
  2. Which field is incorrect?
  3. What should the field contain?
  4. Which constructor initialized it?
  5. Which methods can modify it?
  6. When was it last modified?
  7. Are multiple references pointing to the same object?
  8. Did I accidentally update a different object?
  9. Did a parameter shadow a field?
  10. Is a reference unexpectedly null?
  11. Did I assume assignment copied an object?
  12. Am I confusing identity with logical equality?

Drawing an object-reference diagram often exposes the problem quickly.

100. Frequently asked questions

Q1. Is a class an object?

No.

A class defines a type.

An object is one instance created from that class.

Q2. Does declaring a variable create an object?

No.

Student s;

declares a reference variable.

new Student(...)

creates an object.

Q3. What exactly is stored in an object variable?

A reference value.

For:

Student s =
    new Student("Alice");

s stores a reference to the object.

Q4. Does Student b = a; create a second student?

No.

It copies the reference.

Both variables then refer to the same object.

Q5. How can I tell how many objects were created?

Count the relevant new expressions.

Example:

Student a =
    new Student("A");

Student b = a;

Student c =
    new Student("C");

Two Student objects were created.

Q6. Why can changing b change what I observe through a?

Because a and b may refer to the same mutable object.

Q7. What does null mean?

The reference currently refers to no object.

Q8. What usually causes a NullPointerException?

Calling a method or accessing an object through a reference whose value is null.

Q9. Why doesn't a constructor have void?

Because constructors are not ordinary methods.

Adding void creates a method instead.

Q10. Do constructors return objects?

A constructor initializes a newly created object. The overall new expression produces the reference to that object.

You do not declare a constructor return type.

Q11. Can a class have multiple constructors?

Yes, if their parameter lists differ.

This is constructor overloading.

Q12. Does Java always provide a zero-argument constructor?

No.

Java provides a compiler-generated no-argument constructor only if you write no constructors yourself.

Q13. Why do fields sometimes seem initialized even though I never assigned them?

Instance fields receive default values.

For example:

int       → 0
double    → 0.0
boolean   → false
reference → null

Q14. Do local variables receive those defaults?

No.

Local variables must be assigned before they are used.

Q15. What does this refer to?

The current object on which the instance method or constructor is executing.

Q16. Why do we write this.name = name?

Because:

this.name

refers to the field, while:

name

refers to the parameter.

Q17. Do I need this every time I use a field?

No.

Use it when required to resolve a naming conflict or when it improves clarity.

Q18. Why should fields usually be private?

So the class can control access to its internal state and protect its invariants.

Q19. Does encapsulation mean creating getters and setters for every field?

No.

Encapsulation means designing a controlled interface.

Some fields should not have setters at all.

Q20. What is a class invariant?

A condition that should remain true for every valid object.

Example:

balance >= 0

Q21. Should methods print values or return values?

It depends on the responsibility of the method.

Domain classes generally become more reusable when they return information and allow other code to decide how to display it.

Q22. Can methods accept objects as parameters?

Yes.

Example:

public void transferTo(
        BankAccount other,
        double amount)

Q23. Is Java pass-by-reference for objects?

No.

Java is always pass-by-value.

For object variables, the value being copied is the reference.

Q24. Why can a method still modify my object?

Because the copied reference points to the same object.

Q25. Why can't a method reassign my variable?

Reassigning a parameter changes only the method's local copy of the reference.

Q26. What does == compare for objects?

Object identity: whether two references point to the exact same object.

Q27. Is == the correct way to compare strings?

Usually not when you mean string contents.

Use:

s1.equals(s2)

for content equality.

Q28. Can one object contain another object?

More precisely, one object can contain a field that stores a reference to another object.

For example:

private Student advisor;

or:

private Student[] students;

Q29. Can an object call another object's methods?

Yes.

For example:

other.deposit(amount);

Q30. How should I trace object code?

Draw reference variables as arrows and created objects as boxes.

Update the boxes when methods modify state.

103. End-of-week takeaways

The most important ideas from Week 6 are:

1. A class defines a type

public class Student {
    ...
}

2. An object is one instance of a class

new Student(...)

3. Fields represent object state

private int credits;

4. Instance methods represent object behavior

student.addCourse(...);

5. Constructors establish initial state

public Student(
        String name,
        int studentId) {
    ...
}

6. Variables of class types hold references

Student student;

7. Reference assignment does not copy an object

Student b = a;

may cause both variables to refer to one object.

8. null means no object is referenced

Student s = null;

9. this refers to the current object

this.name = name;

10. Fields should usually be private

private double balance;

11. Encapsulation is about controlling an object's interface

It is not simply about generating getters and setters.

12. Good classes protect their invariants

Invalid states should be difficult to create.

13. Java is always pass-by-value

When an object variable is passed to a method, the copied value is a reference.

14. Objects can interact

One object may receive references to other objects and invoke their methods.

15. Drawing reference diagrams is an important debugging skill

Whenever object behavior seems surprising, draw:

variables → objects → fields

105. The central idea of Week 6

If there is one idea to retain from this week, it is this:

An object combines state and behavior behind a carefully designed interface.

A class defines what objects of that type know and what they can do.

Objects hold state.

Methods operate on that state.

References allow objects to be found, shared, stored, and connected.

Encapsulation lets each object protect its own rules.

These ideas are the foundation on which more advanced object-oriented programming is built.
