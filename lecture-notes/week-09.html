1. Why this week matters

So far, most of our programs have assumed that everything goes according to plan.

For example:

int age = scanner.nextInt();

We assume the user enters an integer.

Or:

double result = total / count;

We assume count is not zero.

Or:

Scanner file = new Scanner(new File("students.txt"));

We assume the file exists.

Real programs cannot make these assumptions.

Users enter invalid input.

Files disappear.

Network connections fail.

Data may be incomplete.

Programmers make mistakes.

One of the differences between a small classroom program and production-quality software is how the program behaves when something goes wrong.

This week focuses on three closely related ideas:

  1. Detecting and responding to errors
  2. Working with external data
  3. Testing programs systematically

Together, these concepts help us write software that is more reliable.

2. Three categories of programming errors

Before discussing exceptions, we need to distinguish several kinds of errors.

2.1 syntax errors

A syntax error means that the program violates Java's grammatical rules.

Example:

int x = 10
System.out.println(x);

The semicolon is missing.

The Java compiler detects this problem.

Another example:

if (x > 5 {
    System.out.println("Large");
}

This code cannot compile.

Syntax errors are generally discovered before the program runs.

2.2 logic errors

A logic error occurs when the program runs, but produces the wrong answer.

Example:

double average = total / 2;

Suppose there are actually 10 values.

The program may compile.

It may run.

It may never crash.

But the result is incorrect.

Logic errors can be especially difficult because Java cannot automatically determine what the programmer intended.

Testing is one of our main tools for detecting logic errors.

2.3 runtime errors

A runtime error occurs while the program is executing.

Example:

int[] numbers = new int[5];

System.out.println(numbers[10]);

This program compiles.

But when it runs, Java detects that index 10 is outside the array.

The result is an exception.

3. What is an exception?

An exception is an object representing an abnormal situation that occurs while a program is running.

Consider:

int x = 10;
int y = 0;

int result = x / y;

When Java attempts to divide by zero, it creates an exception object.

Specifically:

ArithmeticException

If the program does not handle the exception, the program terminates.

A message similar to this appears:

Exception in thread "main" java.lang.ArithmeticException: / by zero

The exception mechanism allows us to separate:

  • normal program logic
  • error-handling logic

4. Exception hierarchy

Exceptions are objects.

Therefore, exception types are organized using inheritance.

A simplified Java hierarchy looks like this:

Object
   |
Throwable
   |
   +-- Error
   |
   +-- Exception
          |
          +-- RuntimeException

We will mainly work with classes below Exception.

Some common exception classes include:

ArithmeticException
NullPointerException
ArrayIndexOutOfBoundsException
NumberFormatException
IllegalArgumentException
IOException
FileNotFoundException

5. Common runtime exceptions

5.1 arithmeticexception

int x = 10 / 0;

Produces:

ArithmeticException

5.2 arrayindexoutofboundsexception

int[] values = {10, 20, 30};

System.out.println(values[5]);

Valid indices are:

0
1
2

Index 5 is invalid.

5.3 nullpointerexception

Consider:

String name = null;

System.out.println(name.length());

The variable exists.

But it does not refer to a String object.

Calling a method through a null reference causes:

NullPointerException

This is one of the most common exceptions in Java programs.

5.4 numberformatexception

String value = "hello";

int x = Integer.parseInt(value);

Java cannot interpret "hello" as an integer.

Therefore:

NumberFormatException

6. Handling exceptions with try and catch

We handle exceptions using a try-catch statement.

Basic structure:

try {
    // code that might throw an exception
}
catch (ExceptionType e) {
    // code that handles the exception
}

Example:

try {
    int result = 10 / 0;
    System.out.println(result);
}
catch (ArithmeticException e) {
    System.out.println("Cannot divide by zero.");
}

Output:

Cannot divide by zero.

The program does not terminate unexpectedly.

7. Control flow in try-catch

Consider:

try {
    System.out.println("A");

    int x = 10 / 0;

    System.out.println("B");
}
catch (ArithmeticException e) {
    System.out.println("C");
}

System.out.println("D");

What is printed?

A
C
D

B is never printed.

As soon as the exception occurs, Java stops executing the remaining statements in the try block.

Control immediately transfers to the matching catch.

8. The exception object

In:

catch (ArithmeticException e)

e is a reference to the exception object.

We can examine it.

Example:

catch (ArithmeticException e) {
    System.out.println(e.getMessage());
}

For division by zero, this may print:

/ by zero

Another useful method is:

e.printStackTrace();

Example:

catch (Exception e) {
    e.printStackTrace();
}

The stack trace shows where the exception occurred and how the program reached that point.

Stack traces are extremely useful for debugging.

9. Multiple catch blocks

A block of code may cause several different exceptions.

Example:

try {
    String text = "abc";
    int value = Integer.parseInt(text);

    int result = 100 / value;

    System.out.println(result);
}
catch (NumberFormatException e) {
    System.out.println("The string is not a valid integer.");
}
catch (ArithmeticException e) {
    System.out.println("Cannot divide by zero.");
}

Java chooses the first compatible catch.

10. Catching general exceptions

We could write:

catch (Exception e) {
    System.out.println("Something went wrong.");
}

This works because many exception classes inherit from Exception.

However, catching Exception everywhere is usually poor design.

Compare:

catch (Exception e) {
    System.out.println("Error.");
}

with:

catch (NumberFormatException e) {
    System.out.println("Please enter a valid integer.");
}

The second provides more meaningful handling.

General principle

Catch the most specific exception that you can meaningfully handle.

11. Catch ordering

Because exceptions participate in inheritance, catch order matters.

Incorrect:

try {
    // ...
}
catch (Exception e) {
    // ...
}
catch (NumberFormatException e) {
    // ...
}

This will not compile.

Why?

Because NumberFormatException is already covered by Exception.

The specific exception should appear first:

try {
    // ...
}
catch (NumberFormatException e) {
    // ...
}
catch (Exception e) {
    // ...
}

12. Finally

Java provides an optional finally block.

try {
    // risky code
}
catch (Exception e) {
    // handle error
}
finally {
    // cleanup
}

The finally block executes whether or not an exception occurred.

Example:

try {
    System.out.println("Trying operation...");
}
catch (Exception e) {
    System.out.println("Error.");
}
finally {
    System.out.println("Finished.");
}

Historically, finally was commonly used to close files, database connections, and other resources.

Modern Java usually uses try-with-resources for that purpose, which we will see later.

13. Checked vs. unchecked exceptions

Java distinguishes between two important categories.

Unchecked exceptions

Unchecked exceptions generally represent programming errors or invalid operations.

Examples:

NullPointerException
ArithmeticException
ArrayIndexOutOfBoundsException
IllegalArgumentException
NumberFormatException

These typically inherit from:

RuntimeException

The compiler does not require us to handle them.

Checked exceptions

Checked exceptions usually represent external conditions that a program may reasonably need to recover from.

Examples include:

IOException
FileNotFoundException

Java requires the programmer either to:

  • handle the exception

or

  • declare that the method may throw it

14. The throws keyword

Suppose a method might cause a checked exception.

We can declare this using throws.

Example:

public static void readFile() throws FileNotFoundException {
    Scanner file = new Scanner(new File("data.txt"));
}

This means:

This method may fail with a FileNotFoundException. The caller is responsible for dealing with that possibility.

Notice the difference:

throw

versus:

throws

They are different keywords.

15. The throw keyword

We use throw when we intentionally create an exception.

Example:

public static void setAge(int age) {

    if (age < 0) {
        throw new IllegalArgumentException("Age cannot be negative.");
    }
}

Usage:

setAge(-5);

produces an exception.

This is useful when a method detects that its contract has been violated.

16. Defensive programming

Defensive programming means anticipating possible errors instead of assuming valid input.

Consider:

public static double calculateAverage(double total, int count) {
    return total / count;
}

What happens when:

count == 0

A safer method would be:

public static double calculateAverage(double total, int count) {

    if (count <= 0) {
        throw new IllegalArgumentException(
            "count must be greater than zero"
        );
    }

    return total / count;
}

Now the method explicitly defines acceptable input.

17. Validate at the boundary

A useful software engineering rule is:

Validate data when it enters your system.

Suppose a class represents a bank account.

public class BankAccount {

    private double balance;

    public BankAccount(double initialBalance) {

        if (initialBalance < 0) {
            throw new IllegalArgumentException(
                "Initial balance cannot be negative."
            );
        }

        balance = initialBalance;
    }
}

This prevents the object from entering an invalid state.

18. Exception handling is not a substitute for good logic

Do not write:

try {
    System.out.println(array[index]);
}
catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("Bad index.");
}

when you could simply validate:

if (index >= 0 && index < array.length) {
    System.out.println(array[index]);
}
else {
    System.out.println("Bad index.");
}

Exceptions should normally represent exceptional situations.

They should not replace ordinary conditional logic.

19. File input and output

So far, many programs have received input from:

keyboard

and sent output to:

screen

But useful programs frequently need persistent data.

Examples:

students.txt
grades.csv
configuration.txt
transactions.txt

A file allows data to survive after the program terminates.

20. Reading text files with Scanner

We have already used:

Scanner

for keyboard input.

We can also use Scanner to read files.

First import:

import java.io.File;
import java.io.FileNotFoundException;
import java.util.Scanner;

Example:

public static void main(String[] args)
        throws FileNotFoundException {

    File file = new File("students.txt");

    Scanner input = new Scanner(file);

    while (input.hasNextLine()) {
        String line = input.nextLine();
        System.out.println(line);
    }

    input.close();
}

21. Reading line by line

Suppose students.txt contains:

Alice
Bob
Charlie
David

Code:

while (input.hasNextLine()) {
    String name = input.nextLine();
    System.out.println(name);
}

Output:

Alice
Bob

David

22. Reading structured data

Suppose the file contains:

Alice 92
Bob 85
Charlie 78

We can write:

while (input.hasNext()) {

    String name = input.next();
    int grade = input.nextInt();

    System.out.println(name + ": " + grade);

23. Reading csv-style data

Suppose:

Alice,92
Bob,85
Charlie,78

One approach is to read each line:

while (input.hasNextLine()) {

    String line = input.nextLine();

    String[] parts = line.split(",");

    String name = parts[0];
    int grade = Integer.parseInt(parts[1]);

    System.out.println(name + " -> " + grade);
}

This example combines:

  • file I/O
  • arrays
  • strings
  • parsing
  • exceptions

24. What can go wrong?

Consider:

Scanner input = new Scanner(new File("students.txt"));

The file may not exist.

Java therefore requires us to handle:

FileNotFoundException

Option 1:

public static void main(String[] args)
        throws FileNotFoundException {

Option 2:

try {
    Scanner input =
        new Scanner(new File("students.txt"));
}
catch (FileNotFoundException e) {
    System.out.println("File not found.");
}

For user-facing applications, handling the error is often preferable.

25. Writing to files

A convenient class for writing text is:

PrintWriter

Example:

import java.io.PrintWriter;
import java.io.FileNotFoundException;

Then:

PrintWriter output =
    new PrintWriter("results.txt");

output.println("Alice,92");
output.println("Bob,85");
output.println("Charlie,78");

output.close();

The resulting file contains:

Alice,92
Bob,85
Charlie,78

26. The importance of closing files

When a program opens a file, the operating system allocates resources.

We should release those resources when we are finished.

Old style:

Scanner input = new Scanner(new File("data.txt"));

try {
    // use input
}
finally {
    input.close();
}

Modern Java provides a cleaner solution.

27. Try-with-resources

Use:

try (Scanner input =
        new Scanner(new File("data.txt"))) {

    while (input.hasNextLine()) {
        System.out.println(input.nextLine());
    }

}
catch (FileNotFoundException e) {
    System.out.println("File not found.");
}

Java automatically closes the Scanner.

This is called:

try-with-resources

The general form is:

try (Resource resource = ...) {

    // use resource

}

When the block finishes, Java closes the resource automatically.

This is the preferred approach.

28. Example: reading student grades

Suppose the file is:

Alice,92
Bob,85
Charlie,78
David,95

We want to calculate the average.

import java.io.File;
import java.io.FileNotFoundException;
import java.util.Scanner;

public class GradeReader {

    public static void main(String[] args) {

        double total = 0;
        int count = 0;

        try (Scanner input =
                new Scanner(new File("grades.txt"))) {

            while (input.hasNextLine()) {

                String line = input.nextLine();

                String[] parts = line.split(",");

                String name = parts[0];
                double grade =
                    Double.parseDouble(parts[1]);

                System.out.println(
                    name + ": " + grade
                );

                total += grade;
                count++;
            }

            if (count > 0) {
                System.out.println(
                    "Average: " + total / count
                );
            }

        }
        catch (FileNotFoundException e) {

            System.out.println(
                "Could not locate grades.txt"
            );

        }
    }
}

29. A more difficult problem: malformed data

Suppose the file contains:

Alice,92
Bob,eighty
Charlie,78

This statement:

Double.parseDouble(parts[1]);

will throw:

NumberFormatException

We can handle malformed records.

while (input.hasNextLine()) {

    String line = input.nextLine();

    try {

        String[] parts = line.split(",");

        String name = parts[0];

        double grade =
            Double.parseDouble(parts[1]);

        System.out.println(
            name + ": " + grade
        );

    }
    catch (NumberFormatException e) {

        System.out.println(
            "Skipping invalid record: " + line
        );

    }
}

Notice something important.

The try-catch is inside the loop.

Why?

Because one bad record should not necessarily prevent us from processing the remaining file.

30. Designing error policies

There is not always one correct way to handle an error.

Suppose we encounter:

Bob,eighty

Possible policies include:

  • terminate immediately
  • skip the record
  • substitute a default value
  • ask the user for correction
  • log the error
  • throw the exception to another part of the program

The correct strategy depends on the application.

A payroll application may need to stop.

A data-analysis program may skip malformed rows.

A GUI application may display an error message.

Software design includes deciding how failure should behave.

31. Testing

Now we shift from handling known error conditions to detecting mistakes in our own programs.

Consider:

public static int max(int a, int b) {
    return a;
}

The program compiles.

It runs.

No exception occurs.

But the method is incorrect.

How do we detect the problem?

Testing.

32. What is software testing?

Software testing is the systematic process of evaluating whether software behaves as expected.

The key word is:

systematic

Testing is not simply running the program once and seeing whether it appears to work.

33. Manual testing

Suppose we write:

public static int max(int a, int b) {

    if (a > b) {
        return a;
    }

    return b;
}

We could manually test:

System.out.println(max(10, 5));
System.out.println(max(5, 10));
System.out.println(max(10, 10));

Expected output:

10
10
10

This is useful, but manual testing becomes difficult as programs grow.

34. Test cases

A test case consists of:

input
expected result
actual result

For max():

InputExpected
max(10, 5)10
max(5, 10)10
max(10, 10)10
max(-5, -10)-5

Good testing requires us to deliberately choose different kinds of inputs.

35. Normal cases

Normal cases represent typical inputs.

Example:

max(10, 5)

For a method calculating an average:

average({80, 90, 100})

Normal cases are important, but they are not enough.

36. Boundary cases

Boundary cases occur near limits.

Suppose:

public static boolean isValidAge(int age) {
    return age >= 0 && age <= 120;
}

Important tests include:

-1
0
1
119
120
121

Why?

Because programming errors frequently occur at boundaries.

Examples:

< instead of <=
index 0
index length - 1
empty array
exact threshold values

37. Exceptional cases

Exceptional cases deliberately test invalid or unusual inputs.

Examples:

null
empty file
missing file
negative values
zero
incorrect data format

Good programmers do not merely ask:

Does this work when everything is correct?

They also ask:

What happens when something goes wrong?

38. Unit testing

A unit test tests a small, isolated component of a program.

Usually that component is:

  • a method
  • a class

Suppose:

public class MathUtils {

    public static int square(int x) {
        return x * x;
    }
}

We want to test square() independently.

39. Junit

A common Java testing framework is:

JUnit

A basic JUnit test might look like:

import static org.junit.jupiter.api.Assertions.*;
import org.junit.jupiter.api.Test;

public class MathUtilsTest {

    @Test
    public void testSquarePositive() {

        assertEquals(
            25,
            MathUtils.square(5)
        );
    }

assertEquals compares:

expected value
actual value

public class MathUtilsTest {

Each test examines a different situation.

Suppose:

public static boolean isEven(int x) {
    return x % 2 == 0;

assertEquals(...)

42. Testing exceptions

Suppose:

public static double divide(
        double a,
        double b) {

    if (b == 0) {
        throw new IllegalArgumentException(
            "Denominator cannot be zero."
        );
    }

    return a / b;
}

We should test normal behavior:

@Test
public void testDivide() {

    assertEquals(
        5.0,
        MathUtils.divide(10, 2)
    );
}

But we should also test the exception:

@Test
public void testDivideByZero() {

    assertThrows(
        IllegalArgumentException.class,
        () -> MathUtils.divide(10, 0)
    );
}

This confirms that invalid input produces the intended failure.

43. Tests are executable specifications

Suppose we write:

assertThrows(
    IllegalArgumentException.class,
    () -> account.withdraw(-100)
);

This does more than check implementation.

It documents expected behavior.

The test says:

Withdrawing a negative amount is invalid and should produce an IllegalArgumentException.

This is why tests can serve as a form of documentation.

44. Testing classes

Suppose:

public class BankAccount {

    private double balance;

    public BankAccount(double balance) {

        if (balance < 0) {
            throw new IllegalArgumentException();
        }

        this.balance = balance;
    }

    public void deposit(double amount) {

        if (amount <= 0) {
            throw new IllegalArgumentException();
        }

        balance += amount;
    }

    public double getBalance() {
        return balance;
    }
}

Possible tests:

@Test
public void testInitialBalance() {

    BankAccount account =
        new BankAccount(100);

    assertEquals(
        100,
        account.getBalance()
    );
}

Another:

@Test
public void testDeposit() {

    BankAccount account =
        new BankAccount(100);

    account.deposit(50);

    assertEquals(
        150,
        account.getBalance()
    );
}

Invalid input:

@Test
public void testNegativeDeposit() {

    BankAccount account =
        new BankAccount(100);

    assertThrows(
        IllegalArgumentException.class,
        () -> account.deposit(-20)
    );
}

45. Arrange - act - assert

A useful structure for tests is:

Arrange
Act
Assert

Example:

@Test
public void testDeposit() {

    // Arrange
    BankAccount account =
        new BankAccount(100);

    // Act
    account.deposit(50);

    // Assert
    assertEquals(
        150,
        account.getBalance()
    );
}

This makes tests easier to read.

46. Testing is not proof

Passing tests does not prove that a program is correct.

Suppose a program passes:

10 tests

There may still be an input we forgot to test.

Testing gives us evidence of correctness.

It does not provide mathematical proof of correctness.

That distinction becomes increasingly important in algorithms and advanced computer science.

47. Writing testable code

Some code is easier to test than other code.

Consider:

public static void process() {

    Scanner input =
        new Scanner(System.in);

    System.out.println(
        "Enter two numbers:"
    );

    int a = input.nextInt();
    int b = input.nextInt();

    System.out.println(a + b);
}

This method combines:

  • input
  • computation
  • output

It is difficult to test automatically.

A better design separates responsibilities.

public static int add(int a, int b) {
    return a + b;
}

Then another method handles input/output.

This method is easy to test:

assertEquals(7, add(3, 4));

48. Separation of concerns

This illustrates an important software design principle:

Separate computation from input/output whenever practical.

Instead of:

read data
calculate result
print result

all in one method, prefer:

input layer
    ↓
processing layer
    ↓
output layer

This improves:

  • readability
  • reuse
  • testing
  • debugging

49. Example: a better grade program

Instead of writing everything in main, separate responsibilities.

public static double average(
        double[] grades) {

    if (grades.length == 0) {
        throw new IllegalArgumentException(
            "No grades provided."
        );
    }

    double total = 0;

    for (double grade : grades) {
        total += grade;
    }

    return total / grades.length;
}

Now we can test:

@Test
public void testAverage() {

    double[] grades =
        {80, 90, 100};

    assertEquals(
        90,
        GradeUtils.average(grades)
    );
}

And:

@Test
public void testEmptyGrades() {

    double[] grades = {};

    assertThrows(
        IllegalArgumentException.class,
        () -> GradeUtils.average(grades)
    );
}

50. Robustness vs. correctness

These terms are related but different.

Correctness

Does the program give the right answer for valid inputs?

Example:

average(80, 90, 100) → 90

Robustness

Does the program behave sensibly when something unexpected happens?

Examples:

missing file
invalid number
empty array
null reference
incorrect user input

Good software should strive for both.

51. Common beginner mistakes with exceptions

Mistake 1: catching everything

catch (Exception e) {
}

This hides problems.

The program may fail silently.

Mistake 2: empty catch blocks

Bad:

catch (FileNotFoundException e) {
}

The exception disappears and the programmer may not know something went wrong.

Mistake 3: using exceptions instead of validation

Bad:

try {
    array[index] = value;
}
catch (ArrayIndexOutOfBoundsException e) {
}

Better:

if (index >= 0 &&
    index < array.length) {

    array[index] = value;
}

Mistake 4: catching an exception too early

Sometimes the method that detects the problem does not know how to recover.

In that case, propagating the exception can be better than catching it immediately.

Mistake 5: treating stack traces as useless noise

When debugging, read:

exception type
message
first line referring to your code
line number
method call sequence

The stack trace often tells you exactly where to start investigating.

52. Reading a stack trace

Suppose Java prints:

Exception in thread "main"
java.lang.NullPointerException
    at Student.getName(Student.java:18)
    at Course.printRoster(Course.java:42)
    at Main.main(Main.java:10)

Read from the top.

The error occurred at:

Student.java:18

That method was called by:

Course.java:42

which was called by:

Main.java:10

The stack trace represents the active method calls when the exception occurred.

53. Debugging strategy

When an exception occurs:

  1. Read the exception type.
  2. Read the exception message.
  3. Find the first stack-trace line referring to your code.
  4. Inspect the values involved.
  5. Determine why an invalid state was possible.
  6. Fix the underlying cause rather than merely suppressing the exception.

Example:

NullPointerException

Do not immediately add:

if (x != null)

Ask:

Why is x null?

The deeper bug may be somewhere else.

Consider a small student-grade application.

The file:

Alice,90
Bob,83
Charlie,not-a-number
David,95

We want to:

  1. read each record
  2. parse the grade
  3. reject malformed records
  4. validate grade range
  5. calculate an average

A helper method:

public static double parseGrade(
        String text) {

    double grade =
        Double.parseDouble(text);

    if (grade < 0 || grade > 100) {

        throw new IllegalArgumentException(
            "Grade must be between 0 and 100."
        );
    }

    return grade;
}

File processing:

try (Scanner input =
        new Scanner(new File("grades.txt"))) {

    while (input.hasNextLine()) {

        String line = input.nextLine();

        try {

            String[] parts =
                line.split(",");

            if (parts.length != 2) {
                throw new IllegalArgumentException(
                    "Invalid record format."
                );
            }

            String name = parts[0];

            double grade =
                parseGrade(parts[1]);

            System.out.println(
                name + " -> " + grade
            );

        }
        catch (NumberFormatException e) {

            System.out.println(
                "Invalid number: " + line
            );

        }
        catch (IllegalArgumentException e) {

            System.out.println(
                "Invalid record: " + line
            );

        }

    }

}
catch (FileNotFoundException e) {

    System.out.println(
        "Unable to open grades.txt"
    );
}

This example demonstrates several concepts together:

file input

validation

59. Exceptions and method contracts

Every method has an implicit or explicit contract.

Consider:

public static double sqrt(double x)

A possible contract is:

Precondition:
x >= 0

Postcondition:
returns the nonnegative square root of x

If a caller violates the precondition, we might throw:

IllegalArgumentException

Example:

if (x < 0) {
    throw new IllegalArgumentException(
        "x must be nonnegative"
    );
}

Exceptions therefore help enforce contracts between different parts of a program.

60. Key design principle: fail fast

A useful principle is:

Detect invalid states as early as possible.

Suppose:

Student student =
    new Student("", -3);

If empty names and negative IDs are invalid, reject them in the constructor.

Do not allow an invalid object to travel throughout the program.

The longer invalid data survives, the harder the eventual bug may be to diagnose.

61. When to catch and when to throw

A useful guideline:

Throw an exception when:

A method detects a problem that prevents it from completing its contract.

Catch an exception when:

The current part of the program knows what meaningful action to take.

For example:

parseGrade()

may throw an exception.

The file-processing code may catch it because it knows it can skip the malformed record.

62. Exception propagation

Suppose:

main()
   calls loadStudents()
      calls parseStudent()
         throws an exception

If parseStudent() does not catch it, the exception travels to:

loadStudents()

If loadStudents() does not catch it, it travels to:

main()

This process is called:

exception propagation

The runtime searches the call stack for a compatible handler.

63. Connections to object-oriented programming

Exceptions reinforce concepts we already learned.

objects

Exception types are organized through:

inheritance

A catch block can demonstrate:

polymorphism

For example:

catch (Exception e)

can catch objects belonging to many subclasses of Exception.

Thus, exception handling is also an application of the object-oriented model.

72. Key takeaways

  1. Programs should expect that things can go wrong.
  2. Exceptions provide a structured mechanism for handling abnormal situations.
  3. Throw exceptions when a method cannot fulfill its contract.
  4. Catch exceptions when you know how to meaningfully recover.
  5. Do not use exceptions as a substitute for ordinary validation.
  6. Validate input as early as practical.
  7. Use try-with-resources for files and other closeable resources.
  8. Separate computation from input/output to improve testability.
  9. Test boundaries and invalid inputs, not only typical cases.
  10. Passing tests increases confidence but does not prove correctness.
  11. Robust error handling and systematic testing are fundamental software engineering skills.
