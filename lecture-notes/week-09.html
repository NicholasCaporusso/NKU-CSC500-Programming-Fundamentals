CSC 500 — Programming fundamentals

Week 9: Exceptions, file I/O, defensive programming, and testing

Course index

1. Overview

Until now, many of our programs have focused primarily on the happy path: the situation in which every input is valid, every object is in the expected state, every file exists, and every operation succeeds.

For example:

int age = scanner.nextInt();

This assumes that the user enters a valid integer.

Or:

int result = total / count;

This assumes that count is not zero.

Or:

Scanner input = new Scanner(new File("students.txt"));

This assumes that the file exists and can be opened.

Real software cannot safely make all of these assumptions.

Users make mistakes. Files may be missing. Data may be malformed. Objects may contain invalid values. Programmers may misunderstand requirements. Operations may fail for reasons outside the program's control.

Week 9 introduces four closely related ideas for dealing with these realities:

  1. Exceptions — representing and responding to abnormal situations.
  2. File input/output — reading and writing persistent data.
  3. Defensive programming — preventing invalid states and making assumptions explicit.
  4. Testing — systematically checking whether software behaves as intended.

Together, these ideas help us move from simply writing programs that work under ideal conditions toward writing programs that are robust, maintainable, and testable.

By the end of Week 9, you should be able to:

  • test expected exceptions;
  • structure code so that it is easier to test.

Part I — Errors and exceptions

3. Three major categories of programming errors

Before studying exceptions, we need to distinguish several different types of errors.

3.1 Syntax errors

A syntax error occurs when code violates the grammatical rules of Java.

Example:

int x = 10
System.out.println(x);

The first line is missing a semicolon.

Another example:

if (x > 5 {
    System.out.println("Large");
}

The closing parenthesis after the condition is missing.

These programs cannot be compiled successfully.

Syntax errors are usually discovered by the compiler before the program runs.

Typical syntax-error causes

  • missing semicolons;
  • missing parentheses;
  • mismatched braces;
  • misspelled keywords;
  • malformed declarations;
  • invalid expressions.

For example:

double total = ;

Java cannot determine what value should be assigned to total.

3.2 Logic errors

A logic error occurs when a program compiles and runs but produces incorrect behavior.

Example:

double average = total / 2;

Suppose total represents the sum of 10 grades.

The program may compile successfully.

It may run successfully.

It may never throw an exception.

However, its result is wrong.

A more subtle example is:

public static boolean isAdult(int age) {
    return age > 18;
}

Suppose the requirement says that a person becomes an adult at age 18.

The correct condition should be:

return age >= 18;

The original method contains a logic error.

Important point

The Java compiler does not know what the programmer intended.

Testing is therefore one of our main tools for detecting logic errors.

3.3 Runtime errors

A runtime error occurs while the program is executing.

Example:

int[] numbers = new int[5];

System.out.println(numbers[10]);

This code compiles.

However, valid array indices are:

0
1
2
3
4

Index 10 is invalid.

When the program attempts to access it, Java reports an exception.

4. What is an exception?

An exception is an object representing an abnormal or exceptional situation that occurs during program execution.

Consider:

int x = 10;
int y = 0;

int result = x / y;

Integer division by zero is invalid.

When Java executes:

x / y

it creates and throws an object of type:

ArithmeticException

If nobody handles that exception, Java terminates the current execution path and usually prints diagnostic information such as:

Exception in thread "main" java.lang.ArithmeticException: / by zero

An exception therefore provides a structured way to represent failure.

5. Why does Java use exceptions?

Without exceptions, a method would often need to communicate failure using ordinary return values.

Suppose we write:

public static double divide(double a, double b) {
    if (b == 0) {
        return 0;
    }

    return a / b;
}

What does a returned 0 mean?

It might mean:

0 / 5 = 0

which is a legitimate result.

Or it might mean:

the operation failed

The caller cannot distinguish the two cases.

A better approach is:

public static double divide(double a, double b) {
    if (b == 0) {
        throw new IllegalArgumentException(
            "Denominator cannot be zero."
        );
    }

    return a / b;
}

Now success and failure are represented differently.

Exceptions also help separate:

normal program logic

from:

error-handling logic

6. Exceptions are objects

Java exceptions are objects.

Therefore, exception classes participate in inheritance just like other Java classes.

A simplified hierarchy is:

Object
   |
Throwable
   |
   +-- Error
   |
   +-- Exception
          |
          +-- RuntimeException

For this course, we mainly work with classes below Exception.

Common exception classes include:

ArithmeticException
NullPointerException
ArrayIndexOutOfBoundsException
NumberFormatException
IllegalArgumentException
IOException
FileNotFoundException

Because exceptions participate in inheritance, a catch block can sometimes handle multiple related exception types.

This is another example of polymorphism in Java.

7. Common runtime exceptions

7.1 ArithmeticException

Example:

int result = 10 / 0;

Java throws:

ArithmeticException

Important detail

For integer arithmetic:

10 / 0

throws an exception.

Floating-point arithmetic behaves differently:

double result = 10.0 / 0.0;

System.out.println(result);

The result is normally:

Infinity

Therefore, do not assume that every form of division by zero behaves identically.

For our methods, we may still choose to reject zero denominators explicitly if zero violates the method's contract.

7.2 ArrayIndexOutOfBoundsException

Consider:

int[] values = {10, 20, 30};

System.out.println(values[3]);

Valid indices are:

0
1
2

Index 3 is outside the array.

Java throws:

ArrayIndexOutOfBoundsException

7.3 NullPointerException

Consider:

String name = null;

System.out.println(name.length());

The variable name exists.

However, it does not refer to a String object.

Calling a method through a null reference causes:

NullPointerException

A useful debugging question is not merely:

Where did the NullPointerException happen?

Also ask:

Why was this reference allowed to become null?

The actual cause of the bug may have occurred earlier.

7.4 NumberFormatException

Consider:

String text = "hello";

int value = Integer.parseInt(text);

Java cannot interpret "hello" as an integer.

It therefore throws:

NumberFormatException

Other examples that cannot normally be parsed directly as integers include:

"twenty"
"20 years"
""
"   "

7.5 IllegalArgumentException

IllegalArgumentException is often thrown deliberately by programmers when a method receives an unacceptable argument.

Example:

public static double squareRoot(double x) {
    if (x < 0) {
        throw new IllegalArgumentException(
            "x must be nonnegative"
        );
    }

    return Math.sqrt(x);
}

The exception communicates that the caller violated the method's expectations.

8. Throwing an exception

The keyword:

throw

actually throws an exception object.

Example:

throw new IllegalArgumentException(
    "Age cannot be negative."
);

Breaking this expression apart:

new IllegalArgumentException(...)

creates the exception object.

Then:

throw

transfers control away from the current normal execution path.

For example:

public static void setAge(int age) {
    if (age < 0) {
        throw new IllegalArgumentException(
            "Age cannot be negative."
        );
    }

    System.out.println("Valid age: " + age);
}

Calling:

setAge(-5);

causes the method to stop at the throw.

The later println statement is not executed.

9. Handling exceptions with try and catch

A program can respond to an exception using a try-catch statement.

General form:

try {
    // code that may throw an exception
}
catch (ExceptionType e) {
    // code that handles the exception
}

Example:

try {
    int result = 10 / 0;
    System.out.println(result);
}
catch (ArithmeticException e) {
    System.out.println("Cannot divide by zero.");
}

Output:

Cannot divide by zero.

The exception was caught, so the program can continue after the catch.

10. Understanding try-catch control flow

Consider:

try {
    System.out.println("A");

    int x = 10 / 0;

    System.out.println("B");
}
catch (ArithmeticException e) {
    System.out.println("C");
}

System.out.println("D");

The output is:

A
C
D

Why is B missing?

When the exception occurs here:

int x = 10 / 0;

Java stops executing the remaining statements in the try block.

Control transfers immediately to the matching catch.

Therefore:

System.out.println("B");

is skipped.

After the catch finishes, execution continues with:

System.out.println("D");

11. What happens if no matching catch exists?

Suppose:

public static void methodA() {
    methodB();
}

public static void methodB() {
    int x = 10 / 0;
}

methodB() throws an ArithmeticException.

If methodB() does not catch it, Java looks at the method that called it:

methodA()

If methodA() does not catch it either, the exception continues upward to the caller of methodA().

This process is called exception propagation.

You can think of it as:

main()
   |
   v
methodA()
   |
   v
methodB()
   |
   v
exception thrown
   |
   v
look for handler in methodB
   |
   v
look for handler in methodA
   |
   v
look for handler in main

If no compatible handler is found, the program terminates.

12. Stack unwinding

When an exception propagates through method calls, Java removes method calls from the call stack while searching for a handler.

This is often called stack unwinding.

Suppose:

public static void main(String[] args) {
    first();
}

public static void first() {
    second();
}

public static void second() {
    third();
}

public static void third() {
    int value = 10 / 0;
}

At the moment of failure, the call stack conceptually contains:

third()
second()
first()
main()

Java first asks:

Does third() handle ArithmeticException?

If not:

Does second() handle it?

Then:

Does first() handle it?

Then:

Does main() handle it?

If nobody does, Java terminates the program.

13. The exception object

In:

catch (ArithmeticException e) {
    ...
}

e is a reference to the exception object.

The name could also be:

catch (ArithmeticException ex)

or:

catch (ArithmeticException exception)

e is simply a common convention.

Useful methods include:

e.getMessage();

and:

e.printStackTrace();

Example:

try {
    int result = 10 / 0;
}
catch (ArithmeticException e) {
    System.out.println(
        "Message: " + e.getMessage()
    );
}

The message might be:

/ by zero

14. Reading a stack trace

Suppose Java reports:

Exception in thread "main" java.lang.NullPointerException
    at Student.getName(Student.java:18)
    at Course.printRoster(Course.java:42)
    at Main.main(Main.java:10)

Do not treat this as random error text.

It contains useful debugging information.

The top tells us the exception type:

NullPointerException

Then:

Student.getName(Student.java:18)

indicates that the exception occurred in:

Student.java

at line:

18

That method was called from:

Course.java:42

which was called from:

Main.java:10

Practical debugging strategy

When reading a stack trace:

  1. identify the exception type;
  2. read the message;
  3. find the first line referring to your code;
  4. inspect that line;
  5. inspect relevant variable values;
  6. determine why the invalid state was possible.

Do not immediately suppress the exception.

Investigate its cause.

15. Multiple catch blocks

One try block may produce several kinds of exceptions.

Example:

try {
    String text = "abc";

    int value = Integer.parseInt(text);

    int result = 100 / value;

    System.out.println(result);
}
catch (NumberFormatException e) {
    System.out.println(
        "The string is not a valid integer."
    );
}
catch (ArithmeticException e) {
    System.out.println(
        "Cannot divide by zero."
    );
}

If text is:

abc

then NumberFormatException is thrown.

If text is:

0

then parsing succeeds, but division causes an ArithmeticException.

Different failures can therefore produce different responses.

16. Catch ordering

Because exception types participate in inheritance, catch order matters.

This is incorrect:

try {
    // code
}
catch (Exception e) {
    // general handler
}
catch (NumberFormatException e) {
    // specific handler
}

Why?

NumberFormatException is already a subtype of Exception.

The first catch would already handle it.

The second block could therefore never be reached.

Correct:

try {
    // code
}
catch (NumberFormatException e) {
    // specific handler
}
catch (Exception e) {
    // general handler
}

Rule

Place more specific exception types before more general ones.

17. Should we catch Exception everywhere?

Technically, this is possible:

catch (Exception e) {
    System.out.println("Something went wrong.");
}

But it is often poor design.

Compare:

catch (Exception e) {
    System.out.println("Error.");
}

with:

catch (NumberFormatException e) {
    System.out.println(
        "Please enter a valid integer."
    );
}

The second response is more meaningful.

A broad catch may also accidentally hide programming defects.

Better principle

Catch an exception when the current part of the program knows how to respond meaningfully.

18. Empty catch blocks are dangerous

Avoid code such as:

try {
    loadData();
}
catch (IOException e) {
}

The program now gives no indication that loading failed.

The failure silently disappears.

If an exception is caught, the program should normally do something meaningful, such as:

  • recover;
  • retry;
  • notify the user;
  • skip a bad record;
  • record diagnostic information;
  • translate the exception;
  • terminate cleanly.

19. finally

Java also provides an optional finally block.

try {
    // risky code
}
catch (Exception e) {
    // handle exception
}
finally {
    // cleanup
}

The finally block is intended to run whether or not the try block succeeds.

Example:

try {
    System.out.println("Trying operation...");
}
catch (Exception e) {
    System.out.println("Error.");
}
finally {
    System.out.println("Finished.");
}

The final message is printed whether an exception occurs or not.

Historically, finally was heavily used for resource cleanup.

For file handling, modern Java usually provides a cleaner approach:

try-with-resources

which we will study shortly.

20. Checked and unchecked exceptions

One of Java's important distinctions is between checked and unchecked exceptions.

20.1 Unchecked exceptions

Unchecked exceptions are normally subclasses of:

RuntimeException

Examples include:

NullPointerException
ArithmeticException
ArrayIndexOutOfBoundsException
IllegalArgumentException
NumberFormatException

Java does not force the programmer to catch or declare them.

Example:

public static int parse(String text) {
    return Integer.parseInt(text);
}

Integer.parseInt() may throw NumberFormatException.

However, the compiler does not require:

throws NumberFormatException

20.2 Checked exceptions

Checked exceptions are exceptions for which Java requires explicit acknowledgment.

Examples include:

IOException
FileNotFoundException

When a checked exception may occur, the programmer generally must either:

  1. catch it, or
  2. declare it using throws.

Example:

Scanner input =
    new Scanner(new File("students.txt"));

Opening the file may produce:

FileNotFoundException

Java therefore requires us to address that possibility.

21. The throws keyword

The keyword:

throws

appears in a method declaration.

Example:

public static void readFile()
        throws FileNotFoundException {

    Scanner input =
        new Scanner(new File("data.txt"));
}

This does not mean that the exception definitely occurs.

It means approximately:

This method may allow a FileNotFoundException to propagate to its caller.

The caller must then either:

catch it

or:

declare it again

22. throw versus throws

These keywords have related names but different purposes.

throw

Used inside a method to actually throw an exception.

throw new IllegalArgumentException(
    "Invalid age"
);

throws

Used in a method declaration to state that an exception may propagate.

public static void loadData()
        throws IOException {
    // ...
}

A useful memory aid:

throw  = perform the throwing
throws = declare the possibility

23. Catch or propagate?

Suppose:

public static double parseGrade(
        String text) {

    return Double.parseDouble(text);
}

Should this method catch NumberFormatException?

Not necessarily.

Ask:

Does this method know how the application should recover?

Perhaps it does not.

The caller may have more context.

For example:

while (input.hasNextLine()) {
    String line = input.nextLine();

    try {
        double grade = parseGrade(line);
        System.out.println(grade);
    }
    catch (NumberFormatException e) {
        System.out.println(
            "Skipping invalid grade: " + line
        );
    }
}

The file-processing code knows that its policy is:

skip malformed records and continue

Therefore this layer is a sensible place to catch the exception.

General guideline

Throw or propagate when the current method cannot fulfill its contract and does not know how to recover.

Catch when the current layer knows what meaningful action should be taken.

Part II — Defensive programming

24. What is defensive programming?

Defensive programming means writing code that anticipates invalid input, incorrect assumptions, unexpected states, and external failures.

Instead of thinking:

Everything should be correct.

a defensive programmer asks:

What could go wrong?

How would I detect it?

What should the program do?

This does not mean checking every imaginable possibility.

It means identifying important assumptions and enforcing them deliberately.

25. Validate at boundaries

A useful design principle is:

Validate data when it enters a part of the system that depends on it being valid.

Examples of boundaries include:

  • user input;
  • constructor parameters;
  • public method parameters;
  • data read from files;
  • data received from external systems.

Suppose a BankAccount cannot have a negative starting balance.

public class BankAccount {

    private double balance;

    public BankAccount(double initialBalance) {

        if (initialBalance < 0) {
            throw new IllegalArgumentException(
                "Initial balance cannot be negative."
            );
        }

        balance = initialBalance;
    }
}

Now every successfully created object satisfies:

balance >= 0

assuming later methods also preserve that rule.

26. Preconditions

A precondition is something that must be true before an operation is valid.

Consider:

withdraw(100);

Possible preconditions might be:

amount > 0
amount <= balance

We can enforce them:

public void withdraw(double amount) {

    if (amount <= 0) {
        throw new IllegalArgumentException(
            "Withdrawal must be positive."
        );
    }

    if (amount > balance) {
        throw new IllegalArgumentException(
            "Insufficient funds."
        );
    }

    balance -= amount;
}

27. Invariants

An invariant is a condition that should remain true throughout the valid lifetime of an object.

For a bank account where overdrafts are prohibited:

balance >= 0

may be an invariant.

For a Student class:

0.0 <= GPA <= 4.0

might be an invariant.

For example:

public class Student {

    private String name;
    private double gpa;

    public Student(String name, double gpa) {

        if (name == null || name.isBlank()) {
            throw new IllegalArgumentException(
                "Name cannot be blank."
            );
        }

        if (gpa < 0.0 || gpa > 4.0) {
            throw new IllegalArgumentException(
                "GPA must be between 0.0 and 4.0."
            );
        }

        this.name = name;
        this.gpa = gpa;
    }
}

Constructors and mutator methods should preserve the object's invariants.

28. Fail fast

Another useful principle is:

Detect invalid states as early as practical.

Suppose invalid objects are allowed:

Student student =
    new Student("", -3.0);

and no validation occurs.

That object might travel through many parts of the program before something finally fails.

The eventual error may appear far away from the place where the invalid data originally entered.

Rejecting invalid data early reduces this distance.

This is often called failing fast.

29. Exceptions are not a substitute for ordinary logic

Do not use an exception when a simple condition expresses the rule clearly.

Poor design:

try {
    System.out.println(values[index]);
}
catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("Bad index.");
}

Better:

if (index >= 0 && index < values.length) {
    System.out.println(values[index]);
}
else {
    System.out.println("Bad index.");
}

Similarly, avoid:

try {
    while (true) {
        System.out.println(values[i]);
        i++;
    }
}
catch (ArrayIndexOutOfBoundsException e) {
    // loop finished
}

Write the intended loop directly:

for (int i = 0; i < values.length; i++) {
    System.out.println(values[i]);
}

Guideline

Use ordinary control structures for ordinary conditions.

Use exceptions to report failures or situations that prevent an operation from completing normally.

30. Validation versus exception handling

These ideas are related but not identical.

Validation

Validation checks whether input satisfies expected rules.

if (grade < 0 || grade > 100) {
    // invalid
}

Exception handling

Exception handling responds to an exception that has been thrown.

try {
    // operation
}
catch (NumberFormatException e) {
    // response
}

A program may use both.

Example:

public static double parseGrade(String text) {

    double grade = Double.parseDouble(text);

    if (grade < 0 || grade > 100) {
        throw new IllegalArgumentException(
            "Grade must be between 0 and 100."
        );
    }

    return grade;
}

Here:

Double.parseDouble(text)

may throw a NumberFormatException.

Then our own validation checks the grade's allowable range.

31. Correctness versus robustness

These terms are related but different.

Correctness

Does the program produce the right result for valid input?

Example:

average of 80, 90, 100 = 90

Robustness

Does the program behave sensibly when something unusual occurs?

Examples:

missing file
malformed number
empty data set
invalid object state
unexpected user input

A good program should strive for both.

Part III — File input and output

32. What is file I/O?

I/O means:

input/output

Input brings data into a program.

Output sends data from a program elsewhere.

So far, we have often used:

keyboard -> program -> screen

For example:

Scanner keyboard = new Scanner(System.in);

and:

System.out.println("Hello");

Files give us another model:

file -> program -> file

Files are useful because their contents can remain after the program terminates.

Examples include:

students.txt
grades.csv
configuration.txt
transactions.txt

33. Text files and binary files

A text file stores characters using a character encoding.

Example:

Alice,95
Bob,87
Charlie,91

Text files can usually be opened and inspected in an ordinary text editor.

A binary file stores raw bytes in some structured format.

Examples include:

  • images;
  • compressed archives;
  • compiled .class files;
  • many media formats;
  • many database files.

Week 9 focuses mainly on text files.

34. File paths

A file path identifies the location of a file.

A relative path might be:

data/students.txt

An absolute path identifies a full location on a particular system.

For example, a Windows-style absolute path could resemble:

C:\Users\Student\Documents\grades.txt

Absolute machine-specific paths are usually inconvenient for course projects because they may work on one computer but not another.

Relative paths are often preferable.

35. The working directory

Suppose your program contains:

new File("grades.txt")

Java looks for grades.txt relative to the program's current working directory.

That directory may not be the same directory as the .java source file.

This is a frequent source of confusion.

If Java reports that a file cannot be found, check:

  • the current working directory;
  • the filename spelling;
  • capitalization;
  • the extension;
  • the directory structure;
  • whether the file is actually named something like grades.txt.txt.

36. Reading a text file with Scanner

We already know how to use Scanner for keyboard input.

Scanner keyboard =
    new Scanner(System.in);

We can also create a Scanner from a file.

Required imports:

import java.io.File;
import java.io.FileNotFoundException;
import java.util.Scanner;

Example:

public class FileReaderExample {

    public static void main(String[] args)
            throws FileNotFoundException {

        File file = new File("students.txt");

        Scanner input = new Scanner(file);

        while (input.hasNextLine()) {
            String line = input.nextLine();
            System.out.println(line);
        }

        input.close();
    }
}

If students.txt contains:

Alice
Bob
Charlie

the program prints:

Alice
Bob
Charlie

37. Why can opening a file fail?

The code:

new File("students.txt")

does not guarantee that the file exists.

A filename is only a request.

Problems may include:

  • the file does not exist;
  • the path is incorrect;
  • the program lacks permission;
  • the directory does not exist;
  • the resource is unavailable.

For this reason, file operations commonly involve checked exceptions.

38. Handling FileNotFoundException

Instead of propagating the exception from main, we can handle it.

import java.io.File;
import java.io.FileNotFoundException;
import java.util.Scanner;

public class FileReaderExample {

    public static void main(String[] args) {

        try {
            Scanner input =
                new Scanner(new File("students.txt"));

            while (input.hasNextLine()) {
                System.out.println(input.nextLine());
            }

            input.close();
        }
        catch (FileNotFoundException e) {
            System.out.println(
                "Could not find students.txt"
            );
        }
    }
}

This provides a controlled response instead of an abrupt termination.

39. Why files should be closed

Opening files uses operating-system resources.

A program should release those resources when it finishes using them.

Failing to close resources can potentially:

  • waste system resources;
  • leave output buffered and unwritten;
  • keep files locked;
  • interfere with future operations.

We could manually write:

Scanner input =
    new Scanner(new File("data.txt"));

try {
    // use input
}
finally {
    input.close();
}

But modern Java provides a cleaner mechanism.

40. Try-with-resources

The preferred approach for many file operations is try-with-resources.

Example:

try (Scanner input =
        new Scanner(new File("data.txt"))) {

    while (input.hasNextLine()) {
        System.out.println(
            input.nextLine()
        );
    }
}
catch (FileNotFoundException e) {
    System.out.println(
        "File not found."
    );
}

The key syntax is:

try (Resource resource = ...) {
    // use resource
}

When the block ends, Java automatically closes the resource.

This happens even when an exception occurs.

Scanner can participate because it implements the closeable-resource mechanism used by Java.

41. Reading token-based structured data

Suppose a file contains:

Alice 92
Bob 85
Charlie 78

You can use token-oriented methods:

while (input.hasNext()) {

    String name = input.next();
    int grade = input.nextInt();

    System.out.println(
        name + ": " + grade
    );
}

This works well when the input format is simple and whitespace-separated.

However, many real records are easier to process line by line.

42. Reading CSV-style data

Suppose grades.csv contains:

Alice,92
Bob,85
Charlie,78

We can read one line at a time:

while (input.hasNextLine()) {

    String line = input.nextLine();

    String[] parts = line.split(",");

    String name = parts[0];
    int grade =
        Integer.parseInt(parts[1]);

    System.out.println(
        name + " -> " + grade
    );
}

This combines several earlier topics:

  • file input;
  • loops;
  • arrays;
  • strings;
  • parsing;
  • numeric conversion;
  • exceptions.

43. What is parsing?

Parsing means converting raw text into a more structured representation.

Suppose we read:

Alice,95

First:

String[] parts = line.split(",");

may produce:

parts[0] = "Alice"
parts[1] = "95"

Then:

String name = parts[0];
int grade =
    Integer.parseInt(parts[1]);

converts the text "95" into the integer 95.

Parsing is where many failure conditions appear.

44. Why we must validate file data

Suppose the input file contains:

Alice,95
Bob,eighty-seven
Charlie
Dana,103

Several problems exist:

Bob,eighty-seven

contains a nonnumeric grade.

Charlie

contains only one field.

Dana,103

contains two fields and a valid number, but the number violates the expected grade range.

A robust parser cannot assume every line is valid.

45. Handling malformed records

Consider:

while (input.hasNextLine()) {

    String line = input.nextLine();

    try {
        String[] parts =
            line.split(",");

        String name = parts[0];

        double grade =
            Double.parseDouble(parts[1]);

        System.out.println(
            name + ": " + grade
        );
    }
    catch (NumberFormatException e) {
        System.out.println(
            "Skipping invalid record: "
            + line
        );
    }
}

Notice that the try-catch is inside the loop.

That design is intentional.

If one record is invalid, perhaps the application should skip that record but continue processing later records.

If the entire loop were inside one large try, the first bad record might terminate all further processing.

46. Error handling is a policy decision

Imagine a program processes 10,000 records and record 5,328 is malformed.

Possible policies include:

terminate immediately
skip the record
log the record and continue
replace the value with a default
ask the user for correction
propagate the exception

There is no universally correct choice.

A payroll application may need strict correctness and stop.

A data-cleaning tool may log the bad row and continue.

An interactive application may ask the user for corrected input.

Therefore:

Error handling is part of software design.

47. Writing text files with PrintWriter

A simple way to write text is:

PrintWriter

Imports:

import java.io.FileNotFoundException;
import java.io.PrintWriter;

Example:

public class FileWriterExample {

    public static void main(String[] args) {

        try (PrintWriter output =
                new PrintWriter("results.txt")) {

            output.println("Alice,92");
            output.println("Bob,85");
            output.println("Charlie,78");
        }
        catch (FileNotFoundException e) {
            System.out.println(
                "Could not create output file."
            );
        }
    }
}

The resulting file contains:

Alice,92
Bob,85
Charlie,78

48. Overwriting versus appending

Creating a new PrintWriter for an existing filename normally replaces the previous contents.

For example:

new PrintWriter("results.txt")

typically truncates the file.

Sometimes a program instead needs to append.

One possible approach uses:

new FileWriter("results.txt", true)

The true indicates append mode.

The important design question is:

Should this operation replace the existing data or add new data to it?

Do not leave this behavior accidental.

49. Buffering

Some I/O classes use buffering.

Conceptually:

program
   |
   v
memory buffer
   |
   v
file

Rather than physically writing every tiny piece of output immediately, the program may accumulate data temporarily and transfer it in larger chunks.

This improves efficiency.

It also explains why closing resources matters: some output may still be waiting in a buffer.

50. Worked example: Basic grade reader

Suppose grades.txt contains:

Alice,92
Bob,85
Charlie,78
David,95

We want to calculate the average.

import java.io.File;
import java.io.FileNotFoundException;
import java.util.Scanner;

public class GradeReader {

    public static void main(String[] args) {

        double total = 0;
        int count = 0;

        try (Scanner input =
                new Scanner(
                    new File("grades.txt")
                )) {

            while (input.hasNextLine()) {

                String line =
                    input.nextLine();

                String[] parts =
                    line.split(",");

                String name =
                    parts[0].trim();

                double grade =
                    Double.parseDouble(
                        parts[1].trim()
                    );

                System.out.println(
                    name + ": " + grade
                );

                total += grade;
                count++;
            }

            if (count > 0) {
                double average =
                    total / count;

                System.out.println(
                    "Average: " + average
                );
            }
        }
        catch (FileNotFoundException e) {
            System.out.println(
                "Could not locate grades.txt"
            );
        }
    }
}

This works only when every record has the expected format.

We can improve it.

51. Worked example: Robust grade parser

Suppose valid grades must lie between:

0 and 100

Define a reusable method:

public static double parseGrade(
        String text) {

    double grade =
        Double.parseDouble(text.trim());

    if (grade < 0 || grade > 100) {
        throw new IllegalArgumentException(
            "Grade must be between 0 and 100."
        );
    }

    return grade;
}

This method has two important failure cases.

If:

parseGrade("excellent");

is called, Double.parseDouble() throws:

NumberFormatException

If:

parseGrade("105");

is called, our method throws:

IllegalArgumentException

The distinction is useful:

not a number        -> NumberFormatException
number out of range -> IllegalArgumentException

52. Worked example: Robust file processing

Now combine file reading, parsing, and validation.

import java.io.File;
import java.io.FileNotFoundException;
import java.util.Scanner;

public class RobustGradeReader {

    public static double parseGrade(
            String text) {

        double grade =
            Double.parseDouble(text.trim());

        if (grade < 0 || grade > 100) {
            throw new IllegalArgumentException(
                "Grade must be between 0 and 100."
            );
        }

        return grade;
    }

    public static void main(String[] args) {

        double total = 0;
        int validCount = 0;
        int invalidCount = 0;

        try (Scanner input =
                new Scanner(
                    new File("grades.txt")
                )) {

            while (input.hasNextLine()) {

                String line =
                    input.nextLine();

                try {
                    String[] parts =
                        line.split(",");

                    if (parts.length != 2) {
                        throw new IllegalArgumentException(
                            "Expected exactly two fields."
                        );
                    }

                    String name =
                        parts[0].trim();

                    if (name.isEmpty()) {
                        throw new IllegalArgumentException(
                            "Name cannot be empty."
                        );
                    }

                    double grade =
                        parseGrade(parts[1]);

                    System.out.println(
                        name + " -> " + grade
                    );

                    total += grade;
                    validCount++;
                }
                catch (NumberFormatException e) {
                    System.out.println(
                        "Invalid numeric value: "
                        + line
                    );

                    invalidCount++;
                }
                catch (IllegalArgumentException e) {
                    System.out.println(
                        "Invalid record: "
                        + line
                        + " ("
                        + e.getMessage()
                        + ")"
                    );

                    invalidCount++;
                }
            }

            System.out.println(
                "Valid records: "
                + validCount
            );

            System.out.println(
                "Invalid records: "
                + invalidCount
            );

            if (validCount > 0) {
                System.out.println(
                    "Average: "
                    + total / validCount
                );
            }
        }
        catch (FileNotFoundException e) {
            System.out.println(
                "Unable to open grades.txt"
            );
        }
    }
}

This program makes several design decisions explicit:

  • failure to open the file is handled at the file-processing level;
  • malformed rows are handled individually;
  • one bad row does not terminate the entire file;
  • numeric parsing errors are distinguished from validation errors;
  • invalid grades are rejected;
  • empty names are rejected;
  • valid and invalid records are counted separately;
  • the resource is automatically closed.

Part IV — Testing

53. What is software testing?

A program that compiles is not necessarily correct.

Consider:

public static int max(int a, int b) {
    return a;
}

This program compiles.

It runs.

It throws no exception.

But:

max(5, 10)

incorrectly returns:

5

How do we discover this?

Through testing.

Software testing is the systematic process of evaluating whether software behaves as expected.

The important word is:

systematic

Running the program once and saying:

"It seems to work."

is not sufficient.

54. A test case

A test case represents one particular scenario.

It usually involves:

input
expected behavior
actual behavior
comparison

For:

public static int max(int a, int b)

possible tests include:

InputExpected
max(10, 5)10
max(5, 10)10
max(10, 10)10
max(-5, -10)-5

Each case investigates a different behavior.

55. Why one test is not enough

Suppose we test only:

max(2, 5)

and it works.

The method could still fail when:

  • the first argument is larger;
  • the arguments are equal;
  • both arguments are negative;
  • unusually large values are used.

Testing requires us to think about the space of possible inputs.

56. Categories of test cases

A useful test-design strategy is to consider several categories.

56.1 Normal cases

Normal cases represent typical expected inputs.

Example:

isValidGrade(75);

or:

max(10, 5);

Normal cases are necessary, but they are not enough.

56.2 Boundary cases

Boundary cases occur at or near limits.

Suppose:

public static boolean isValidAge(
        int age) {

    return age >= 0 && age <= 120;
}

Important test values include:

-1
0
1
119
120
121

Why?

Because bugs frequently appear around boundaries.

A common example is accidentally writing:

age > 0

instead of:

age >= 0

or:

age < 120

instead of:

age <= 120

57. Off-by-one errors

A classic boundary problem is the off-by-one error.

Incorrect:

for (int i = 0;
     i <= array.length;
     i++) {

    System.out.println(array[i]);
}

The last valid index is:

array.length - 1

So the loop should be:

for (int i = 0;
     i < array.length;
     i++) {

    System.out.println(array[i]);
}

Boundary testing is especially effective at finding these errors.

58. Invalid and exceptional cases

Good tests should also deliberately supply invalid inputs.

Examples include:

negative age
grade greater than 100
empty string
null reference
missing file
malformed record
zero denominator
empty array

If your method explicitly rejects invalid input, the rejection itself should be tested.

59. Edge cases

An edge case is an unusual or extreme condition that may expose hidden assumptions.

Examples:

  • empty array;
  • one-element array;
  • empty string;
  • zero;
  • negative numbers;
  • duplicate elements;
  • maximum allowed value;
  • minimum allowed value;
  • empty file;
  • file containing only one record.

For a method:

findLargest(int[] values)

important cases include:

{3, 8, 2}
{5}
{-10, -3, -20}
{7, 7, 4}
{}

The empty array forces a design question:

What should findLargest() mean when there is no value?

Perhaps the method should throw an exception.

That behavior then becomes part of its contract.

60. Manual testing

We can manually test methods:

System.out.println(max(10, 5));
System.out.println(max(5, 10));
System.out.println(max(10, 10));

Then visually inspect the results.

This is useful while learning and debugging.

But manual testing becomes increasingly difficult as the program grows because:

  • tests must be repeated manually;
  • expected results must be remembered;
  • failures can be overlooked;
  • testing many cases becomes tedious.

This motivates automated unit testing.

61. Unit testing

A unit test tests a relatively small component of software independently.

A unit is often:

a method

or:

a class

Suppose:

public class MathUtils {

    public static int square(int x) {
        return x * x;
    }
}

We can test square() without running an entire application.

62. JUnit

JUnit is a widely used Java testing framework.

A simple test might look like:

import static
    org.junit.jupiter.api.Assertions.*;

import org.junit.jupiter.api.Test;

public class MathUtilsTest {

    @Test
    public void testSquarePositive() {

        assertEquals(
            25,
            MathUtils.square(5)
        );
    }
}

The annotation:

@Test

marks the method as a test.

The assertion:

assertEquals(expected, actual);

checks whether the actual result equals the expected result.

63. Multiple unit tests

A single method usually requires multiple tests.

public class MathUtilsTest {

    @Test
    public void squarePositiveNumber() {
        assertEquals(
            25,
            MathUtils.square(5)
        );
    }

    @Test
    public void squareZero() {
        assertEquals(
            0,
            MathUtils.square(0)
        );
    }

    @Test
    public void squareNegativeNumber() {
        assertEquals(
            25,
            MathUtils.square(-5)
        );
    }
}

Each test targets a different condition.

64. Common assertions

Useful JUnit assertions include:

assertEquals(expected, actual);

Checks equality.

assertTrue(condition);

Checks that a Boolean condition is true.

assertFalse(condition);

Checks that a Boolean condition is false.

assertNull(value);

Checks that a reference is null.

assertNotNull(value);

Checks that a reference is not null.

assertThrows(ExceptionType.class, ...);

Checks that a particular exception occurs.

65. Testing Boolean methods

Suppose:

public static boolean isEven(int x) {
    return x % 2 == 0;
}

Tests might be:

@Test
public void evenNumberShouldReturnTrue() {
    assertTrue(
        MathUtils.isEven(10)
    );
}

@Test
public void oddNumberShouldReturnFalse() {
    assertFalse(
        MathUtils.isEven(7)
    );
}

We should also consider:

0
negative even value
negative odd value

For example:

@Test
public void zeroShouldBeEven() {
    assertTrue(
        MathUtils.isEven(0)
    );
}

66. Testing expected exceptions

Suppose:

public static double divide(
        double numerator,
        double denominator) {

    if (denominator == 0) {
        throw new IllegalArgumentException(
            "Denominator cannot be zero."
        );
    }

    return numerator / denominator;
}

A normal test is:

@Test
public void divideShouldReturnQuotient() {

    assertEquals(
        5.0,
        MathUtils.divide(10, 2)
    );
}

But zero is also important.

@Test
public void divideByZeroShouldFail() {

    assertThrows(
        IllegalArgumentException.class,
        () -> MathUtils.divide(10, 0)
    );
}

The exception is not a test failure.

It is the expected behavior.

67. Understanding the lambda in assertThrows

This syntax may look unfamiliar:

() -> MathUtils.divide(10, 0)

For now, treat it as meaning:

Run this operation when JUnit performs the exception test.

So:

assertThrows(
    IllegalArgumentException.class,
    () -> MathUtils.divide(10, 0)
);

means approximately:

When MathUtils.divide(10, 0) executes, I expect an IllegalArgumentException.

You do not need a deep understanding of lambda expressions for this week's testing concepts.

68. Testing classes

Consider:

public class BankAccount {

    private double balance;

    public BankAccount(double balance) {

        if (balance < 0) {
            throw new IllegalArgumentException(
                "Initial balance cannot be negative."
            );
        }

        this.balance = balance;
    }

    public void deposit(double amount) {

        if (amount <= 0) {
            throw new IllegalArgumentException(
                "Deposit must be positive."
            );
        }

        balance += amount;
    }

    public double getBalance() {
        return balance;
    }
}

Possible tests include:

@Test
public void constructorShouldSetBalance() {

    BankAccount account =
        new BankAccount(100);

    assertEquals(
        100,
        account.getBalance()
    );
}

And:

@Test
public void depositShouldIncreaseBalance() {

    BankAccount account =
        new BankAccount(100);

    account.deposit(50);

    assertEquals(
        150,
        account.getBalance()
    );
}

And:

@Test
public void negativeDepositShouldFail() {

    BankAccount account =
        new BankAccount(100);

    assertThrows(
        IllegalArgumentException.class,
        () -> account.deposit(-20)
    );
}

And constructor validation:

@Test
public void negativeInitialBalanceShouldFail() {

    assertThrows(
        IllegalArgumentException.class,
        () -> new BankAccount(-1)
    );
}

69. Arrange — Act — Assert

A useful way to structure a unit test is:

Arrange
Act
Assert

Example:

@Test
public void depositShouldIncreaseBalance() {

    // Arrange
    BankAccount account =
        new BankAccount(100);

    // Act
    account.deposit(50);

    // Assert
    assertEquals(
        150,
        account.getBalance()
    );
}

Arrange

Create the required objects and initial state.

Act

Perform the operation being tested.

Assert

Verify the expected outcome.

This structure makes tests easier to read.

70. Good test names

Compare:

@Test
public void test1() {
    ...
}

with:

@Test
public void negativeDepositShouldThrowException() {
    ...
}

The second tells us what behavior is being tested.

Good test names help tests act as documentation.

71. Tests as executable specifications

Suppose we write:

assertThrows(
    IllegalArgumentException.class,
    () -> account.deposit(-100)
);

This test does more than verify implementation.

It also documents the contract:

negative deposits are invalid

Likewise:

assertEquals(
    100,
    parseGrade("100")
);

documents that:

100 is a valid grade

Tests can therefore serve as executable specifications of expected behavior.

72. What makes a good unit test?

A good unit test is usually:

  • small — focused on one behavior;
  • repeatable — produces the same result when run again;
  • independent — does not unnecessarily depend on other tests;
  • clear — its purpose is obvious;
  • automatic — determines pass/fail without manual inspection.

A test should make it easy to answer:

What behavior failed?

73. Testing is not proof

Suppose your program passes 100 tests.

Can we conclude:

The program contains no bugs.

No.

There may still be a case we did not test.

Testing provides evidence of correctness.

It does not generally prove that a nontrivial program is correct for every possible input.

Therefore, test design matters.

74. Testing versus debugging

These are related but different activities.

Testing

Testing asks:

Does the software behave correctly?

Its goal is to discover failures.

Debugging

Debugging asks:

Why did the software fail, and how do we fix it?

A common workflow is:

write code
    |
    v
run tests
    |
    v
observe failure
    |
    v
debug
    |
    v
fix
    |
    v
run tests again

Testing tells us that a problem exists.

Debugging investigates the cause.

75. A systematic debugging strategy

When a program fails:

  1. reproduce the failure;
  2. read the exception type;
  3. read the exception message;
  4. inspect the stack trace;
  5. locate the first relevant line in your code;
  6. inspect the values used there;
  7. determine which assumption was violated;
  8. fix the underlying cause;
  9. rerun the test;
  10. rerun other tests to make sure the fix did not break existing behavior.

Avoid changing random pieces of code until the failure disappears.

That approach often creates new defects.

76. Debugging a NullPointerException

Suppose the failure occurs here:

student.getAddress().getCity();

Possible null values include:

student

or:

student.getAddress()

Investigate each reference.

Then ask:

Why was this reference null?

For example, perhaps the constructor failed to initialize a field.

The correct solution may be to repair object construction, not simply add:

if (student != null)

everywhere.

77. Debugging a NumberFormatException

Suppose:

int age =
    Integer.parseInt(text);

throws an exception.

Inspect the exact contents of:

text

For example:

"twenty"
"20 years"
""
" "

will not parse as integers.

When parsing files, it can be helpful to inspect the raw line before conversion.

78. Debugging file problems

Break file processing into stages.

Ask:

Can the file be opened?

Then:

Can one line be read?

Then:

Can the line be split correctly?

Then:

Can each field be parsed?

Then:

Does each field satisfy validation rules?

This is more effective than treating the entire file-processing system as one indivisible problem.

Part V — Designing testable programs

79. Separation of concerns

Consider:

public static void process() {

    Scanner input =
        new Scanner(System.in);

    System.out.println(
        "Enter two numbers:"
    );

    int a = input.nextInt();
    int b = input.nextInt();

    System.out.println(a + b);
}

This method mixes:

  • input;
  • computation;
  • output.

That makes the actual addition harder to test independently.

A better design is:

public static int add(
        int a,
        int b) {

    return a + b;
}

Now input/output can live elsewhere.

Testing becomes trivial:

assertEquals(
    7,
    add(3, 4)
);

80. Separate I/O from computation

A useful architecture is:

input layer
    |
    v
processing layer
    |
    v
output layer

For example:

public static double average(
        double[] grades) {

    if (grades.length == 0) {
        throw new IllegalArgumentException(
            "No grades provided."
        );
    }

    double total = 0;

    for (double grade : grades) {
        total += grade;
    }

    return total / grades.length;
}

This method does not know whether its grades came from:

  • a file;
  • the keyboard;
  • a graphical interface;
  • a database;
  • a unit test.

That makes it reusable.

And easy to test:

@Test
public void averageShouldCalculateMean() {

    double[] grades =
        {80, 90, 100};

    assertEquals(
        90,
        GradeUtils.average(grades)
    );
}

81. Testing exceptional behavior of computation

We also test the empty input:

@Test
public void emptyGradesShouldFail() {

    double[] grades = {};

    assertThrows(
        IllegalArgumentException.class,
        () -> GradeUtils.average(grades)
    );
}

This establishes the method's contract:

An empty grade array is not accepted.

82. Integrated example: Student record parser

Suppose a file contains:

Alice,95
Bob,82
Charlie,not-a-number
Dana,105

Valid scores are:

0 through 100

Assume a simple Student class:

public class Student {

    private String name;
    private int score;

    public Student(
            String name,
            int score) {

        this.name = name;
        this.score = score;
    }

    public String getName() {
        return name;
    }

    public int getScore() {
        return score;
    }

    @Override
    public String toString() {
        return name + ": " + score;
    }
}

Now write a parser.

public static Student parseStudent(
        String line) {

    String[] parts =
        line.split(",");

    if (parts.length != 2) {
        throw new IllegalArgumentException(
            "Invalid record format."
        );
    }

    String name =
        parts[0].trim();

    if (name.isEmpty()) {
        throw new IllegalArgumentException(
            "Student name cannot be empty."
        );
    }

    int score =
        Integer.parseInt(
            parts[1].trim()
        );

    if (score < 0 || score > 100) {
        throw new IllegalArgumentException(
            "Score must be between 0 and 100."
        );
    }

    return new Student(
        name,
        score
    );
}

83. Testing the parser

Normal case:

@Test
public void validStudentShouldParse() {

    Student student =
        parseStudent("Alice,95");

    assertEquals(
        "Alice",
        student.getName()
    );

    assertEquals(
        95,
        student.getScore()
    );
}

Boundary value:

@Test
public void zeroShouldBeValidScore() {

    Student student =
        parseStudent("Bob,0");

    assertEquals(
        0,
        student.getScore()
    );
}

Upper boundary:

@Test
public void hundredShouldBeValidScore() {

    Student student =
        parseStudent("Charlie,100");

    assertEquals(
        100,
        student.getScore()
    );
}

Below lower boundary:

@Test
public void negativeScoreShouldFail() {

    assertThrows(
        IllegalArgumentException.class,
        () -> parseStudent("Dana,-1")
    );
}

Above upper boundary:

@Test
public void scoreAboveHundredShouldFail() {

    assertThrows(
        IllegalArgumentException.class,
        () -> parseStudent("Eve,101")
    );
}

Nonnumeric value:

@Test
public void nonnumericScoreShouldFail() {

    assertThrows(
        NumberFormatException.class,
        () -> parseStudent("Frank,abc")
    );
}

Missing field:

@Test
public void missingScoreShouldFail() {

    assertThrows(
        IllegalArgumentException.class,
        () -> parseStudent("Grace")
    );
}

Empty name:

@Test
public void emptyNameShouldFail() {

    assertThrows(
        IllegalArgumentException.class,
        () -> parseStudent(",90")
    );
}

84. File processing using the parser

Now file I/O becomes a separate concern:

try (Scanner input =
        new Scanner(
            new File("students.txt")
        )) {

    while (input.hasNextLine()) {

        String line =
            input.nextLine();

        try {
            Student student =
                parseStudent(line);

            System.out.println(student);
        }
        catch (NumberFormatException e) {
            System.out.println(
                "Skipping nonnumeric score: "
                + line
            );
        }
        catch (IllegalArgumentException e) {
            System.out.println(
                "Skipping invalid record: "
                + line
            );
        }
    }
}
catch (FileNotFoundException e) {
    System.out.println(
        "Could not open students.txt"
    );
}

This separation gives us:

parseStudent()

for computation and validation, and:

file-reading code

for resource management and policy decisions.

That makes the program easier to understand and test.

Part VI — Common mistakes and misconceptions

85. Mistake: “If my program compiles, it is correct”

False.

Compilation primarily tells us that Java's syntax and type rules are satisfied.

A compiled program can still contain:

  • logic errors;
  • runtime exceptions;
  • incorrect calculations;
  • incorrect assumptions;
  • malformed output;
  • incomplete behavior.

Compilation is only one stage in evaluating a program.

86. Mistake: Catching every exception

Avoid:

try {
    // huge amount of code
}
catch (Exception e) {
    System.out.println("Error");
}

This can:

  • obscure the original problem;
  • catch failures you did not expect;
  • provide weak error messages;
  • make debugging harder.

Prefer specific catches when possible.

87. Mistake: Wrapping the entire program in one try

A huge try block makes it difficult to determine:

  • which operation failed;
  • why it failed;
  • what recovery action makes sense.

Place exception handling near code whose failure behavior is understood.

88. Mistake: Empty catch

Bad:

catch (FileNotFoundException e) {
}

Now the program hides the failure.

At minimum, the application should have a deliberate policy.

89. Mistake: Using exceptions as loop conditions

Bad:

try {
    int i = 0;

    while (true) {
        System.out.println(values[i]);
        i++;
    }
}
catch (ArrayIndexOutOfBoundsException e) {
}

Better:

for (int i = 0;
     i < values.length;
     i++) {

    System.out.println(values[i]);
}

90. Mistake: Returning misleading values after errors

Bad:

public static double divide(
        double a,
        double b) {

    if (b == 0) {
        System.out.println("Error.");
        return 0;
    }

    return a / b;
}

Returning 0 confuses success with failure.

A better design may be:

if (b == 0) {
    throw new IllegalArgumentException(
        "Denominator cannot be zero."
    );
}

91. Mistake: Assuming file data is always valid

Even if a file was created by your own program, do not automatically assume it can never be corrupted or edited.

Input such as:

Alice,90
Bob,abc
Charlie
Dana,120

should cause deliberate, specified behavior.

92. Mistake: Testing only the happy path

Weak tests:

70
80
90

for:

public static boolean isPassing(
        double grade) {

    return grade >= 60;
}

All three values test the same logical region.

Stronger values include:

59
60
61
0
100

The value:

60

is particularly important because it is the boundary.

93. Mistake: Treating stack traces as noise

A stack trace is debugging information.

Read:

exception type
message
first line in your code
line number
method call sequence

These clues frequently lead directly to the failing operation.

Part VII — Conceptual connections

94. Exceptions and object-oriented programming

Exceptions are themselves objects.

Exception types use inheritance.

A statement such as:

catch (Exception e)

can accept instances of many subclasses of Exception.

Therefore, exception handling reinforces concepts from Weeks 6–8:

  • objects;
  • classes;
  • inheritance;
  • polymorphism.

95. Defensive programming and exceptions

Defensive programming identifies invalid conditions.

Exceptions provide one way to report them.

Example:

public void deposit(double amount) {

    if (amount <= 0) {
        throw new IllegalArgumentException(
            "Deposit must be positive."
        );
    }

    balance += amount;
}

The check:

amount <= 0

is validation.

The decision to reject the operation is defensive programming.

The IllegalArgumentException communicates the failure.

96. File I/O and exceptions

Files exist outside the program.

The program can request:

grades.txt

but cannot guarantee that:

  • it exists;
  • it is readable;
  • it contains valid data.

Therefore robust file-processing naturally combines:

resource management
exception handling
parsing
validation
error policy

97. Defensive programming and testing

Defensive programming asks:

What could go wrong?

Testing asks:

Can I create a case that verifies the program handles that situation correctly?

If a method rejects negative ages:

if (age < 0) {
    throw new IllegalArgumentException();
}

then a natural test is:

assertThrows(
    IllegalArgumentException.class,
    () -> setAge(-1)
);

The assumptions enforced by defensive code therefore generate excellent test cases.

98. Method contracts and tests

Suppose a method has this conceptual contract:

Method:
sqrt(x)

Precondition:
x >= 0

Postcondition:
returns the nonnegative square root of x

Its implementation might enforce the precondition:

if (x < 0) {
    throw new IllegalArgumentException(
        "x must be nonnegative."
    );
}

The test suite should then contain both:

valid positive input
zero
invalid negative input

Tests and method contracts should reinforce one another.

Part VIII — In-class coding exercises

99. Exercise 1 — Robust integer input

Write:

public static int readPositiveInteger(
        Scanner input)

The method should repeatedly ask for input until the user provides a positive integer.

Possible interaction:

Enter positive integer: hello
Invalid integer.

Enter positive integer: -10
Number must be positive.

Enter positive integer: 0
Number must be positive.

Enter positive integer: 42

One possible solution:

public static int readPositiveInteger(
        Scanner input) {

    while (true) {

        System.out.print(
            "Enter positive integer: "
        );

        String text =
            input.nextLine();

        try {
            int value =
                Integer.parseInt(
                    text.trim()
                );

            if (value <= 0) {
                System.out.println(
                    "Number must be positive."
                );
            }
            else {
                return value;
            }
        }
        catch (NumberFormatException e) {
            System.out.println(
                "Invalid integer."
            );
        }
    }
}

Notice that user input is read as a string first.

That gives us explicit control over the parsing failure.

100. Exercise 2 — Defensive division

        double numerator,

  • return the quotient;
  • throw IllegalArgumentException when the denominator is zero.

Possible solution:

public static double divide(
        double numerator,
        double denominator) {

    if (denominator == 0) {
        throw new IllegalArgumentException(
            "Denominator cannot be zero."
        );
    }

    return numerator / denominator;
}

10 / 2

-10 / 2

101. Exercise 3 — Temperature file

Suppose temperatures.txt contains:

72.5
68.2
invalid
75.1
70.0

Write a program that:

  1. opens the file;
  2. reads every line;
  3. converts valid lines to double;
  4. skips invalid values;
  5. counts valid temperatures;
  6. calculates their average.

One possible solution:

import java.io.File;
import java.io.FileNotFoundException;
import java.util.Scanner;

public class TemperatureReader {

    public static void main(String[] args) {

        double total = 0;
        int count = 0;

        try (Scanner input =
                new Scanner(
                    new File(
                        "temperatures.txt"
                    )
                )) {

            while (input.hasNextLine()) {

                String line =
                    input.nextLine();

                try {
                    double temperature =
                        Double.parseDouble(
                            line.trim()
                        );

                    total += temperature;
                    count++;
                }
                catch (NumberFormatException e) {
                    System.out.println(
                        "Skipping invalid value: "
                        + line
                    );
                }
            }

            System.out.println(
                "Valid temperatures: "
                + count
            );

            if (count > 0) {
                System.out.println(
                    "Average: "
                    + total / count
                );
            }
        }
        catch (FileNotFoundException e) {
            System.out.println(
                "Temperature file not found."
            );
        }
    }
}

105. Exception syntax reference

Catch an exception

try {
    // risky operation
}
catch (NumberFormatException e) {
    // response
}

Multiple catches

try {
    // risky operation
}
catch (NumberFormatException e) {
    // specific response
}
catch (IllegalArgumentException e) {
    // another response
}

Finally

try {
    // operation
}
catch (Exception e) {
    // response
}
finally {
    // cleanup
}

Throw an exception

throw new IllegalArgumentException(
    "Invalid value."
);

Declare a checked exception

public static void load()
        throws IOException {

    // ...
}

Read a text file

try (Scanner input =

String[] parts =

Part XII — Key takeaways

108. Week 9 summary

The major lesson of Week 9 is that software must be designed for more than ideal conditions.

Exceptions

Exceptions are objects that represent abnormal runtime situations.

Important Java constructs include:

try
catch
finally
throw
throws

Remember:

throw  -> actually throw an exception
throws -> declare that an exception may propagate

Catch an exception when your code knows what meaningful response should occur.

Do not catch failures merely to hide them.

Checked and unchecked exceptions

Unchecked exceptions are commonly subclasses of:

RuntimeException

Examples include:

NullPointerException
NumberFormatException
IllegalArgumentException
ArrayIndexOutOfBoundsException
ArithmeticException

Checked exceptions require explicit handling or declaration.

File I/O commonly introduces checked exceptions such as:

FileNotFoundException
IOException

Defensive programming

Make important assumptions explicit.

Validate:

  • public method arguments;
  • constructor arguments;
  • user input;
  • file data;
  • values that affect class invariants.

Remember:

validate early
reject invalid states
fail fast when appropriate

But do not use exceptions in place of clear ordinary logic.

File I/O

Files provide persistent data.

Important classes in this week's examples include:

File
Scanner
PrintWriter

Use try-with-resources when appropriate:

try (Scanner input =
        new Scanner(new File("data.txt"))) {

    // use input
}

Do not assume files exist or contain valid data.

Testing

Testing systematically compares expected and actual behavior.

A good test suite includes:

normal cases
boundary cases
edge cases
invalid cases
exception cases

JUnit allows expectations to become executable assertions.

Examples:

assertEquals(...)
assertTrue(...)
assertFalse(...)
assertThrows(...)

Passing tests increases our confidence.

It does not prove that no bug exists.

Testing and design

Code is easier to test when responsibilities are separated.

Prefer:

input
processing
output

as distinct concerns when practical.

A reusable method such as:

parseGrade()

is much easier to test than a large main() method that simultaneously reads files, parses records, computes results, prints messages, and handles errors.

110. Central idea of Week 9

A beginning programmer often asks:

How do I make this program work?

A stronger software developer also asks:

What assumptions does this program make?

What happens when those assumptions are violated?

How will the program communicate failure?

Can I test that both successful and unsuccessful cases behave correctly?

That shift—from merely producing correct output on one example to explicitly designing, validating, handling failure, and testing behavior—is the central software-engineering lesson of Week 9.
