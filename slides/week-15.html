Abstraction and Interfaces

Focus on what something does; hide how it does it.

Abstraction

Abstraction: focusing on what something does while hiding unnecessary details about how it does it.

Consider Java's ArrayList. We can write:

names.add("Bob");

System.out.println(names.get(0));

We do not need to know:

Those details are hidden. We use the abstraction:


a resizable list

Choosing the Right Data Structure

There is no universally best data structure — only one that fits the operations you perform.

Choosing a Data Structure

One of the most important design decisions is choosing how to represent collections of data.

Do not ask
Which data structure is best?

There is no universally best data structure.

Instead ask
Which data structure is appropriate for the operations this program performs?
Key ideaThe question is never "best in general". It is "best for these operations, at this size, in this program".

One of the most important design decisions is choosing how to represent collections of data.

We should not ask "Which data structure is best?" There is no universally best data structure. Instead ask: which data structure is appropriate for the operations this program performs?

The next several slides walk the catalogue — array, ArrayList, LinkedList, stack, queue, set, map — and in each case the deciding question is the same one: what do you actually do to this collection, and how often?

Arrays

Use an array when:

  • the number of elements is fixed or predictable,
  • indexed access is important,
  • simple storage is sufficient.

Example:


double[] temperatures = new double[365];

Advantages

  • simple
  • fast indexed access
  • low overhead

Disadvantages

  • fixed size
  • insertion/removal may be inconvenient

Use an array when the number of elements is fixed or predictable, indexed access is important, and simple storage is sufficient. The canonical example is a year of daily temperatures: 365 doubles, and the count will not change.

Advantages: simple, fast indexed access, low overhead. Disadvantages: fixed size, and insertion or removal may be inconvenient.

Point out that "fixed or predictable" is the operative phrase. A 365-element array is not a guess; it is a fact about calendars.

Use an ArrayList when:

  • the collection changes size,
  • order matters,

Example:

A linked structure can be useful when frequent insertion and removal occur at known positions.

An object that cannot control its own state cannot enforce any rule about it.

Designing Around Responsibilities

Suppose our registration system has:

find course using course code

We might initialize them as:

    students = new HashMap<>();
    courses = new HashMap<>();

The two lookup methods that follow

    return students.get(id);

    return courses.get(courseCode);

Both methods are one line long, because the data structure was chosen to make them one line long.

The RegistrationSystem holds two private maps: students keyed by ID, courses keyed by code. Why maps? Because the common operations are "find student using student ID" and "find course using course code".

The constructor initialises both as HashMaps. Then findStudent is a single get, and findCourse is a single get.

The data structure supports the behavior of the system. Run the argument backwards for students: if findStudent had been written first as a loop over a list, the maps would never have appeared. Design the operations, then pick the structure that makes them cheap.

Suppose Course exposes its student list as a public field. Any part of the program can now call course.students.clear(), or course.students.add(student), at any time and for any reason.

This means the Course object cannot control its own state. A better design makes the list private and exposes controlled operations — a boolean enroll method that performs validation.

Preserve Class Invariants

Invariant: a condition that should always be true for an object.

For a course, possible invariants include:


number of enrolled students <= capacity
capacity >= 0
course code is not null
course code is not empty

Suppose we allow this:


course.setCapacity(-100);

The object may enter an invalid state.

A better class protects its invariants:


public Course(String code, String title, int capacity) {

    if (capacity < 0) {
        throw new IllegalArgumentException(
            "Capacity cannot be negative"
        );
    }

    this.code = code;
    this.title = title;
    this.capacity = capacity;
}
Where the check has to live

The validation is in the constructor, before any field is assigned. That ordering matters: an object either exists in a valid state or does not exist at all.

A setter that accepts -100 can put a fully constructed object into an invalid state at any later moment, which is why setCapacity is the dangerous shape here.

Do thisObjects should protect themselves from invalid states when practical.

An invariant is a condition that should always be true for an object. For a course, possible invariants include: number of enrolled students less than or equal to capacity; capacity greater than or equal to zero; course code is not null; course code is not empty.

Suppose we allow course.setCapacity of negative one hundred. The object may enter an invalid state — and from that moment on, every method that assumes a sane capacity is unreliable.

A better class protects its invariants: the constructor checks capacity and throws IllegalArgumentException with the message "Capacity cannot be negative" before assigning any field. Objects should protect themselves from invalid states when practical.
