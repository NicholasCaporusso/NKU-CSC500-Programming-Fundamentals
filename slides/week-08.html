Part I

Why Inheritance?

Two classes, one idea — and the duplication that tells you a superclass is missing.

Two Classes, One Idea

So far, we have designed programs using classes and objects. For example:


public class Student {
    private String name;
    private int id;

    public Student(String name, int id) {
        this.name = name;
        this.id = id;
    }

    public String getName() {
        return name;
    }

    public int getId() {
        return id;
    }
}

Suppose our program also contains employees:


public class Employee {
    private String name;
    private int id;
    private double salary;

    public Employee(String name, int id, double salary) {
        this.name = name;
        this.id = id;
        this.salary = salary;
    }
}
Watch outThere is duplication here.

So far, we have designed programs using classes and objects. Here is a Student class with a name, an ID, a constructor, and two accessors — exactly the kind of class Week 6 taught you to write.

Suppose our program also contains employees. Employee has a name, an ID, a salary, and a constructor that initialises all three. Put the two side by side and the problem is visible without any theory: the name field, the id field, and the two lines of constructor that set them are written twice.

Duplication in two classes is annoying. Duplication in twelve classes is a maintenance defect waiting to happen. The rest of this Part is about what to do with it.

What the Duplication Is Telling Us

Both Student and Employee have:

  • a name
  • an ID
  • behaviors associated with a person

Conceptually:


Student is a Person
Employee is a Person
Key ideaThe repeated fields are not a coincidence. They are the shared concept — Person — showing through two classes that have not yet been told about it.
The full argument, start to finish

Both Student and Employee have a name, an ID, and behaviors associated with a person. Conceptually, a Student is a Person and an Employee is a Person.

That English sentence is the whole insight. When two classes repeat the same fields, it is usually because they are both specialisations of a more general type that has not been written down yet.

Note the direction of the sentence. We do not say a Person is a Student. The specialised type is the subject; the general type is the predicate. That asymmetry decides which class becomes the superclass.

We could capture the common behavior in a superclass called Person, holding the name field, the id field, the constructor that initialises them, and the two accessors.

Then Student extends Person, and Employee extends Person. Notice that both subclass bodies are empty here. They are empty and still useful — each one already has a name, an ID, getName, and getId, without a single line repeated.

This relationship is called inheritance. That is the whole of Part 1: duplication, a shared concept, a superclass, and the keyword extends.

Part II

extends and super

Writing a subclass, initializing the superclass portion, and knowing what you got for free.

A Basic Inheritance Example

Consider a superclass representing bank accounts.


public class BankAccount {

    private String accountNumber;
    private double balance;

    public BankAccount(String accountNumber, double balance) {
        this.accountNumber = accountNumber;
        this.balance = balance;
    }

    public void deposit(double amount) {
        balance += amount;
    }

    public void withdraw(double amount) {
        balance -= amount;
    }

    public double getBalance() {
        return balance;
    }

    public String getAccountNumber() {
        return accountNumber;
    }
}

Consider a superclass representing bank accounts. BankAccount holds an account number and a balance, both private, and exposes four public methods: deposit, withdraw, getBalance, and getAccountNumber.

This is an ordinary Week 6 class. Nothing about it anticipates inheritance — no special keyword, no annotation. Any well-encapsulated class is already a candidate superclass.

Point at the private fields before moving on. Those two words, private and private, are what makes the next slide's super(...) call necessary rather than optional.

A Specialized Account

Now suppose we want a specialized account:


public class SavingsAccount extends BankAccount {

    private double interestRate;

    public SavingsAccount(
            String accountNumber,
            double balance,
            double interestRate) {

        super(accountNumber, balance);

        this.interestRate = interestRate;
    }

    public void addInterest() {
        double interest = getBalance() * interestRate;
        deposit(interest);
    }
}

The SavingsAccount class inherits accessible methods from BankAccount.

Key ideaaddInterest() is written entirely out of inherited parts: it calls getBalance() and deposit(), neither of which SavingsAccount defines.
Why getBalance() and not balance?

The balance field is private to BankAccount, so the subclass cannot name it directly. It reaches the value through the public accessor instead.

This is the same rule Part III states in general: a subclass inherits accessible members, and a private field is not accessible.

Now suppose we want a specialized account. SavingsAccount extends BankAccount and adds one field of its own, interestRate. Its constructor takes three parameters, passes the first two up with super, and stores the third itself.

The addInterest method is where the payoff shows. It computes the interest from getBalance times interestRate and then calls deposit. Both getBalance and deposit come from the superclass. The subclass wrote one new method and reused two.

The SavingsAccount class inherits accessible methods from BankAccount. The word "accessible" is doing real work in that sentence and Part III unpacks it.

Inherited Methods in Use

For example:


SavingsAccount account =
    new SavingsAccount("A123", 1000.0, 0.05);

account.deposit(200);
account.addInterest();

System.out.println(account.getBalance());
NoteAlthough SavingsAccount does not explicitly define deposit() or getBalance(), those methods are inherited.
The whole BankAccount example

We create a SavingsAccount with account number A123, a balance of one thousand, and a rate of five percent. Then we call deposit with two hundred, call addInterest, and print the balance.

Two of those three calls are on methods SavingsAccount never wrote. Although SavingsAccount does not explicitly define deposit or getBalance, those methods are inherited.

Have students predict the printed number before you run it. Deposit takes the balance to twelve hundred; addInterest adds five percent of twelve hundred; the answer is 1260.0. Getting that right requires understanding that addInterest reads the balance after the deposit, which is a small but real lesson in shared mutable state.

Constructors Are Not Inherited

When a subclass object is created, the superclass portion of the object must also be initialized.


public class Person {

    private String name;

    public Person(String name) {
        this.name = name;
    }
}

Then:


public class Student extends Person {

    private String major;

    public Student(String name, String major) {
        super(name);
        this.major = major;
    }
}

The statement super(name); calls the constructor of the superclass.

The statement itself 

super(name);

Read it as an ordinary constructor call whose target is the superclass rather than a named class. It runs Person's constructor with the argument name, which is what stores the value into the private name field that Student cannot reach.

Constructors are not inherited. That is the headline, and it surprises students who have just been told that everything accessible is inherited.

The reason is in the second sentence: when a subclass object is created, the superclass portion of the object must also be initialized. A Person constructor initialises Person's fields; a Student needs that to happen, but it needs it to happen as part of building a Student, not as a separate act.

So Student's constructor takes name and major, calls super(name) to hand the name up to Person, and then initialises its own major field. The statement super(name) calls the constructor of the superclass.

Constructors and super, in full

Conceptually, creating a new Student with the arguments Alice and Computer Science runs two constructors in order: the Person constructor initializes name, and then the Student constructor initializes major.

A call to a superclass constructor must occur before the subclass constructor finishes initializing the subclass. That is the principle. The Java rule that enforces it is narrower and stricter: if used explicitly, super with arguments must be the first statement in the constructor.

Students will meet the compiler error for this the first time they try to validate an argument before calling super. Tell them now that the check has to move — into a static helper or into the superclass — because the ordering rule is not negotiable.

What Does a Subclass Inherit?

A subclass inherits accessible members of its superclass. Suppose:


public class Animal {

    public void eat() {
        System.out.println("Eating...");
    }

    public void sleep() {
        System.out.println("Sleeping...");
    }
}

Then:


public class Dog extends Animal {

    public void bark() {
        System.out.println("Woof!");
    }
}

A Dog object can use:


Dog dog = new Dog();

dog.eat();
dog.sleep();
dog.bark();

A subclass inherits accessible members of its superclass. Animal declares eat and sleep; Dog extends Animal and adds bark.

A Dog object can use all three. The first two methods come from Animal. The third comes from Dog. From the caller's side there is no visible difference — dog.eat() and dog.bark() are written identically and neither one announces where it was declared.

That uniformity is the point of inheritance from the client's perspective. Callers see one interface; the class hierarchy is an implementation detail of where the code happens to live.

The word "accessible" is not decoration. It decides what a subclass can actually touch.

Will not compile

Because name is private to the Person class.

A common misunderstanding is that subclasses can directly access private fields inherited from a superclass. They cannot.

Person declares a private name field. Student extends Person and tries to print name directly. This will not compile, because name is private to the Person class.

Be precise about the mental model here. The field is present in every Student object — the memory is there, the constructor set it — it is simply not nameable from Student's source code. Presence and accessibility are different things, and conflating them is the source of the misunderstanding.

The Fix: Let the Superclass Provide a Method

Instead, the superclass should provide an appropriate method:


public String getName() {
    return name;
}

Then:


public class Student extends Person {

    public void printName() {
        System.out.println(getName());
    }
}

The one-word difference

The broken version printed:

The working version prints getName(). The subclass stopped reaching into the superclass's storage and started asking the superclass a question instead.

That is the entire difference between breaking encapsulation and respecting it, and it costs six characters.

Instead, the superclass should provide an appropriate method — a public getName that returns name. Then Student's printName calls getName rather than naming the field.

This preserves encapsulation. Person still owns its field, still controls how the value is read, and could later change how the name is stored without breaking a single subclass.

This is the same argument Week 6 made for accessors on ordinary classes. Inheritance does not weaken it; if anything, inheritance raises the stakes, because now there may be many subclasses depending on the representation.

Part IV

Method Overriding

A subclass keeps the method's name and replaces what it does.

Method Overriding

A subclass can provide its own implementation of an inherited method. This is called method overriding.


public class Animal {

    public void makeSound() {
        System.out.println("Some animal sound");
    }
}


public class Dog extends Animal {

    @Override
    public void makeSound() {
        System.out.println("Woof!");
    }
}


public class Cat extends Animal {

    @Override
    public void makeSound() {
        System.out.println("Meow!");
    }
}

A subclass can provide its own implementation of an inherited method. This is called method overriding.

Animal declares makeSound, printing "Some animal sound". Dog overrides it to print "Woof!". Cat overrides it to print "Meow!". All three methods have the same name, the same return type, and the same empty parameter list — that sameness is what makes them overrides rather than three unrelated methods.

Notice that the superclass did nothing to permit this. Any accessible, non-final method can be overridden by a subclass; the superclass author does not opt in.

Which Implementation Runs?

Now:


Dog dog = new Dog();
dog.makeSound();

prints:


Woof!
Key ideaThe Dog implementation replaces the inherited behavior for Dog objects.
Replaces, not adds

After overriding, there is no way for outside code to call Animal's version on a Dog object. The superclass implementation is still there in the superclass, but for a Dog it has been shadowed completely.

The one exception is the subclass itself, which can still reach the original through super.makeSound(). That is the subject of the last slide in this Part.

Create a Dog and call makeSound on it. The output is "Woof!", not "Some animal sound". The Dog implementation replaces the inherited behavior for Dog objects.

At this point the variable and the object have the same type, so nothing surprising is happening yet. Part V changes exactly one thing — the declared type of the variable — and the same call keeps printing "Woof!". That is where overriding stops being a convenience and becomes polymorphism.

The @Override argument in full

Therefore: use at-Override whenever you intend to override a method. This is the classic case of a compile-time error being enormously cheaper than a logic error, which is the same lesson Week 1 drew about the three error categories.

These concepts are frequently confused.

Overloading

Same method name, different parameter lists.

These concepts are frequently confused, and the confusion is understandable — the two words differ by three letters and both involve methods with the same name.

Overloading means the same method name with different parameter lists. Here print is declared three times, taking an int, a double, and a String. The compiler decides which method to call based on the arguments.

Emphasise "the compiler decides". Overloading is resolved entirely at compile time from the static types of the arguments. Hold on to that, because overriding is resolved at runtime, and that contrast is the cleanest way to keep the two apart.

The comparison table is worth memorising verbatim. Overloading: same method name, different parameters. Overriding: subclass replaces inherited method behavior.

One diagnostic question settles almost every case in practice: are the two methods in the same class or in two classes related by extends? Same class means overloading. Two classes in a hierarchy, same signature, means overriding.

Calling a Superclass Method

Sometimes a subclass overrides a method but still wants to use the superclass implementation. Use:


super.methodName()


public class Person {

    public void describe() {
        System.out.println("I am a person.");
    }
}


public class Student extends Person {

    @Override
    public void describe() {
        super.describe();
        System.out.println("I am also a student.");
    }
}

Sometimes a subclass overrides a method but still wants to use the superclass implementation. Use super dot methodName.

Person's describe prints "I am a person." Student overrides describe, calls super.describe() first, and then prints "I am also a student."

This is the extend-rather-than-replace pattern, and it is extremely common: do everything the superclass did, then add the subclass's own contribution. Note that unlike super in a constructor, super.method() may appear anywhere in the body — before, after, or in the middle of the subclass's own work.

The Combined Output

Calling:


Student s = new Student();
s.describe();

produces:


I am a person.
I am also a student.
Key ideaTwo lines of output from one call. The subclass did not discard the inherited behavior — it wrapped it.
Order matters

Because super.describe() is the first statement in the override, the superclass line prints first. Move it after the println and the two lines swap.

Compare this with the constructor rule from Part II, where super(...) has no such freedom: it must be the first statement. Constructors are ordered by the language; method calls are ordered by you.

Creating a Student and calling describe produces two lines: "I am a person." then "I am also a student."

Ask the class where the first line came from. The call site made exactly one call, on a Student object, and got behavior from two classes. That is the wrapping pattern working as intended.

The Runtime Type Decides

The output is:


Dog

Why? Java determines the overriding method using the object's actual runtime type. The object is a Dog. Therefore:

runs.

Dynamic method dispatch: selecting the overridden method at runtime, based on the object's actual type.
Why "dynamic"?

The choice cannot be made when the program is compiled. At compile time, all Java knows is that a is declared Animal; the object it will refer to may depend on user input, a file, or a random number.

So the decision is deferred until the call actually happens, when the object — and therefore its class — is known for certain. Deferred to runtime is exactly what "dynamic" means here.

The output is "Dog". Java determines the overriding method using the object's actual runtime type. The object is a Dog, therefore Dog.makeSound() runs.

This is known as dynamic method dispatch, and it is the mechanism the entire second half of the week rests on. Abstract classes, interfaces, and polymorphic collections are all just convenient ways of arranging for dynamic dispatch to happen.

Contrast this once more with overloading from Part IV: overload resolution is done by the compiler from declared types, override resolution is done by the runtime from actual types. Same-sounding words, opposite mechanisms.

Circle and Rectangle

    @Override
    public double perimeter() {
        return 2 * Math.PI * radius;
    }
}

    private double height;

    public Rectangle(double width, double height) {

        this.height = height;

        return 2 * (width + height);

In-Class Example: Assignments

Suppose we need to model different types of course assignments. Every assignment has:


title
points possible

public abstract class Assignment {

    private String title;
    private double pointsPossible;

    public Assignment(
            String title,
            double pointsPossible) {

        this.title = title;
        this.pointsPossible = pointsPossible;
    }

        return title;
    }

    public double getPointsPossible() {
        return pointsPossible;
    }

    public abstract double calculateScore();
}

Suppose we need to model different types of course assignments. Every assignment has a title and points possible. Different assignment types may calculate scores differently.

So Assignment is abstract. It holds the two shared fields privately, provides accessors for both, and declares calculateScore abstract.

This is the Employee pattern again — shared state plus one required operation — and it is worth naming as a pattern, because the lab and the homework are both instances of it.

A Concrete Assignment


public class Exam extends Assignment {

    private int correct;
    private int totalQuestions;

    public Exam(
            String title,
            double pointsPossible,
            int correct,
            int totalQuestions) {

        super(title, pointsPossible);

        this.correct = correct;
        this.totalQuestions = totalQuestions;
    }

    @Override
    public double calculateScore() {
        return ((double) correct / totalQuestions)
                * getPointsPossible();
    }
}

Another subclass might calculate a score differently. The grading system can still process all assignments uniformly:


for (Assignment a : assignments) {
    System.out.println(
        a.getTitle()
        + ": "
        + a.calculateScore()
    );
}
Why the cast to double?

correct and totalQuestions are both int, so correct / totalQuestions would be integer division — 18 out of 20 would give 0.

Casting one operand to double forces floating-point division, exactly as in Week 1. Inheritance does not suspend the arithmetic rules.

Exam extends Assignment, adds correct and totalQuestions, passes title and points possible up with super, and overrides calculateScore as the fraction correct times the points possible.

Another subclass might calculate a score differently — a participation grade, a project with a rubric, a late-penalised homework. The grading system can still process all assignments uniformly with one loop over Assignment.

The cast to double inside calculateScore is worth pausing on. It is a Week 1 issue surfacing inside a Week 8 design, and students who miss it will get zeros for every exam score.
