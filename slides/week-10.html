Part I

What Recursion Is

A method that calls itself, a base case that stops it, and a recursive case that shrinks the problem.

What Is Recursion?

Recursive: a method is recursive if it calls itself, either directly or indirectly.

Consider the mathematical definition of factorial:

n! = n × (n−1) × (n−2) × ⋯ × 1

For example:

5! = 5 × 4 × 3 × 2 × 1 = 120

Factorial can also be defined recursively:

n! = 1   if n = 0

n! = n × (n−1)!   if n > 0

Key ideaTo find n!, we reduce the problem to a smaller version of the same problem.
Factorial: from mathematics to Java

A method is recursive if it calls itself, either directly or indirectly. Direct recursion is what we spend the week on; indirect recursion — A calls B, B calls A — is mentioned so that students recognise it when they meet it later.

Consider the mathematical definition of factorial: n factorial is n times n minus one times n minus two, and so on down to one. For example, 5 factorial is 5 times 4 times 3 times 2 times 1, which is 120.

Factorial can also be defined recursively, as a two-case definition: n factorial is 1 if n is 0, and n times the factorial of n minus one if n is greater than 0. This definition says two things. We already know the answer for zero factorial. And to find n factorial, we reduce the problem to a smaller version of the same problem. That idea is the essence of recursion.

Factorial in Java

In Java:


public static int factorial(int n) {
    if (n == 0) {
        return 1;
    }

    return n * factorial(n - 1);
}

Calling:


factorial(4)

conceptually produces:


factorial(4)
= 4 * factorial(3)
= 4 * 3 * factorial(2)
= 4 * 3 * 2 * factorial(1)
= 4 * 3 * 2 * 1 * factorial(0)
= 4 * 3 * 2 * 1 * 1
= 24
Read the Java line by line against the mathematics

The two-case mathematical definition and the two-branch Java method line up exactly. The if (n == 0) branch is the case "1 if n = 0". The return n * factorial(n - 1); line is the case "n × (n−1)! if n > 0".

Nothing has been invented in the translation. The definition told us there were two cases, so the method has two cases, and each one is a single return.

The Java implementation is five lines. If n is zero, return one. Otherwise return n times factorial of n minus one.

Calling factorial of four conceptually produces the chain shown on the right: four times factorial of three, which becomes four times three times factorial of two, and so on until factorial of zero returns one and the whole product collapses to twenty-four.

Emphasise the word "conceptually". The chain on the right is not what the machine literally writes down — it is a way of seeing what the nested calls amount to. Part II replaces this picture with the call stack, which is what actually happens.

The Two Essential Parts of Recursion

Almost every recursive algorithm needs two components.

Base case

Base case: a condition for which the method can return an answer immediately without making another recursive call.

In factorial:


if (n == 0) {
    return 1;
}
Watch outWithout a base case, recursion does not stop.

Recursive case

Recursive case: the part that reduces the original problem to a smaller problem of the same form.

In factorial:


return n * factorial(n - 1);

Almost every recursive algorithm needs two components. The base case is a condition for which the method can return an answer immediately without making another recursive call. In factorial it is the test for n equals zero, returning one. Without a base case, recursion does not stop.

The recursive case reduces the original problem to a smaller problem of the same form. In factorial it is the line returning n times factorial of n minus one.

Students who can reliably point at these two pieces in an unfamiliar method are already most of the way to reading recursive code. Ask them to identify both in every example this week.

Why the Recursive Case Terminates

The important idea is that:


factorial(n)

depends on:


factorial(n - 1)

and n - 1 is smaller than n.

Key ideaA well-designed recursive method has three properties:
  1. A base case exists.
  2. Each recursive call moves toward the base case.
  3. The recursive result is used to solve the current problem.

The important idea is that factorial of n depends on factorial of n minus one, and n minus one is smaller than n. That single observation is what guarantees the chain of calls is finite.

A well-designed recursive method therefore has three properties. A base case exists. Each recursive call moves toward the base case. And the recursive result is used to solve the current problem.

Keep these three on the board all week. Part VII is entirely about what happens when property one or property two is missing, and the checklist in Part XII turns all three into questions students can ask of their own code.

Part II

The Call Stack and Unwinding

Descending, then unwinding — and why the position of a statement relative to the recursive call changes everything.

The Call Stack

To understand recursion, you need to understand the call stack.

Whenever Java calls a method, information about that method call is placed on the stack. This information includes things such as:

  • parameter values,
  • local variables,
  • where execution should return after the method finishes.

Consider:


public static int factorial(int n) {
    if (n == 0) {
        return 1;
    }

    return n * factorial(n - 1);
}
The call stack, in full

To understand recursion, you need to understand the call stack. Whenever Java calls a method, information about that method call is placed on the stack.

This information includes things such as parameter values, local variables, and where execution should return after the method finishes. That third item is the one students forget, and it is the one that makes unwinding possible.

Nothing on this slide is special to recursion. Every method call in every program the class has written since Week 4 has pushed a frame. Recursion is only remarkable because many frames for the same method are alive at once.

Descending: The Stack Grows

When we call:


factorial(3)

the stack grows approximately like this:


factorial(3)
factorial(2)
factorial(1)
factorial(0)

At the deepest point:


factorial(0)

returns 1.

Then the stack begins to unwind.

Descending: the program repeatedly makes smaller recursive calls.

When we call factorial of three, the stack grows approximately like this: factorial three, factorial two, factorial one, factorial zero — four frames, stacked.

At the deepest point, factorial of zero returns one. Then the stack begins to unwind.

The word "approximately" is deliberate. The real frame contains more than the parameter, and the JVM is free to optimise. But for reasoning about the program, the parameter is the part that matters.

Unwinding: The Stack Returns

The recursive calls return in reverse order:


factorial(1) returns 1 * 1 = 1
factorial(2) returns 2 * 1 = 2
factorial(3) returns 3 * 2 = 6
Unwinding: the recursive calls return in reverse order.
Key ideaThere are two conceptual stages of recursion: descending and unwinding.
Where the multiplication actually happens

Look at where the arithmetic occurs. Nothing is multiplied on the way down — each frame evaluates n * and then has to wait, because the right-hand operand is not known yet.

All three multiplications happen on the way back up, in the order shown. This is the first hint of the idea Part II develops next: work placed after the recursive call runs during unwinding.

Then the stack begins to unwind. Factorial of one returns one times one, which is one. Factorial of two returns two times one, which is two. Factorial of three returns three times two, which is six.

There are therefore two conceptual stages of recursion. Descending: the program repeatedly makes smaller recursive calls. Unwinding: the recursive calls return in reverse order.

These two words are the vocabulary for the rest of the week. Every recursive method is doing work in one stage, the other, or both — and knowing which is how you predict its output.

This is the moment where recursion stops being "a loop written strangely" and becomes its own thing. A loop has one place to put work. Recursion has two.

The Trace That Explains It

Reading the trace

Read it top to bottom. The four call lines descend, deepest at example(0). Then the print lines climb back out, and the indentation tells you which frame is doing the printing.

print 1 sits at the indentation of example(1), because that is the frame whose n is 1. Its recursive call has just returned, and only now does it reach its own print statement.

Trace it. Example three calls example two, which calls example one, which calls example zero. Example zero hits the base case and returns immediately. Now example one resumes and prints one. Then example two resumes and prints two. Then example three resumes and prints three.

This ability to perform operations during the unwinding stage is one of the most powerful aspects of recursion. We will use it directly in Part VIII to reverse a string and in Part XII to print a number in binary.

Recursive Sum

Suppose we want to calculate 1 + 2 + 3 + ⋯ + n. An iterative solution is straightforward:


public static int sum(int n) {
    int total = 0;

    for (int i = 1; i <= n; i++) {
        total += i;
    }

    return total;
}

We can also define the problem recursively:

sum(n) = n + sum(n−1)

with:

sum(0) = 0

Suppose we want to calculate one plus two plus three and so on up to n. An iterative solution is straightforward: a running total, a for loop from one to n, add each i.

We can also define the problem recursively. Sum of n is n plus sum of n minus one, with sum of zero equal to zero.

Note the shape of the recursive definition: it is exactly the two-case form we saw for factorial. A base value, and a rule expressing the answer for n in terms of the answer for something smaller.

Recursive Sum in Java

Java implementation:


public static int sum(int n) {
    if (n == 0) {
        return 0;
    }

    return n + sum(n - 1);
}

For:


sum(4)

we get:


4 + sum(3)
4 + 3 + sum(2)
4 + 3 + 2 + sum(1)
4 + 3 + 2 + 1 + sum(0)
4 + 3 + 2 + 1 + 0
10
Compare the two implementations

The iterative version needs a local variable, total, and a loop counter, i. The recursive version needs neither. The accumulating sum lives in the pending additions held on the call stack.

That is the trade. Recursion moves bookkeeping out of your variables and into the call stack. Sometimes that is a clarity win; Part VI is about when it is not.

The Java implementation follows the definition directly. If n is zero, return zero. Otherwise return n plus sum of n minus one.

For sum of four we get four plus sum of three, then four plus three plus sum of two, and so on down to four plus three plus two plus one plus zero, which is ten.

Point out that the base case here returns zero, not one. The base-case answer must be the correct answer for the smallest problem — and for addition, the identity is zero. Part XII's product exercise turns exactly this point into a trap.

Writing recursive programs requires a slightly different mindset from writing loops.

The leap of faith, on factorial

factorial(4)

5 * factorial(4)

Writing recursive programs requires a slightly different mindset from writing loops. When designing an iterative solution, you often ask: how do I perform every step? With recursion, a more useful question is: if I could already solve a smaller version of this problem, how could I use that solution to solve the current problem?

For example, imagine we somehow already know how to compute factorial of four. Then computing factorial of five is easy: it is five times factorial of four. You do not need to mentally work through every deeper recursive call while writing the method. You assume that the recursive call correctly solves the smaller problem. This assumption is sometimes called the recursive leap of faith.

That shift is the whole difficulty of the week for most students. They keep trying to be the computer; the skill being taught is to stop. It is not really faith — it is induction, and it is rigorous — but calling it faith captures the psychological move students have to make.

The same three properties from Part I hold. A base case exists: the empty string. Each call moves toward it, because s.substring(1) is always exactly one character shorter than s. And the result — here, printed output rather than a returned value — is produced at the right moment.

Length is the quantity that decreases. In factorial it was the value of n. Every correct recursive method has some such quantity.

Recursion is not limited to arithmetic. Suppose we want to print the characters of a string one at a time. The base case is the empty string. Otherwise, print the first character and recurse on everything after it. Calling printChars of the string CAT produces C, A, T on three lines.

The two String methods doing the work are charAt of zero, which gives the head, and substring of one, which gives the tail. Students met both in Week 5; here they become the recursive decomposition of a string.

The recursive calls are printChars of CAT, then of AT, then of T, then of the empty string; the last one hits the base case and returns. The problem gets smaller because the string becomes shorter with each call — worth writing on the board next to the factorial version. In one case a number shrinks, in the other a string shrinks, but the structure is identical.

Part IV

Recursion on Arrays

An array never gets smaller — so we shrink the remaining portion with an index instead.

Recursion with Arrays

Arrays require a slightly different approach. A recursive method usually needs an index to indicate which portion of the array remains to be processed.

Suppose we want to calculate the sum of an array.


public static int sumArray(int[] values, int index) {
    if (index == values.length) {
        return 0;
    }

    return values[index] + sumArray(values, index + 1);
}

Given:


int[] values = {5, 8, 2};

calling:


sumArray(values, 0)
NoteThe base case is index == values.length — the empty remaining portion.

Arrays require a slightly different approach. A recursive method usually needs an index to indicate which portion of the array remains to be processed.

Suppose we want to calculate the sum of an array. The method takes the array and an index. If the index has run past the end, the remaining portion is empty and the sum is zero. Otherwise, return the element at the index plus the sum of everything after it.

Given the array five, eight, two, we call sumArray with the array and zero.

Tracing sumArray

Calling sumArray(values, 0) produces:


5 + sumArray(values, 1)
5 + 8 + sumArray(values, 2)
5 + 8 + 2 + sumArray(values, 3)
5 + 8 + 2 + 0

Key ideaThe array itself never gets smaller. Instead, the remaining portion of the problem becomes smaller because the index moves forward.
Why not shrink the array itself?

You could copy a shorter array on every call, the way substring makes a shorter string. But that copies every remaining element at every level — a great deal of work to compute a sum.

Moving an index costs nothing. Part XI returns to this as a general design technique: additional parameters can describe the part of the problem that remains.

Calling sumArray with the array and zero produces five plus sumArray at index one, then five plus eight plus sumArray at index two, then five plus eight plus two plus sumArray at index three, which is the base case and returns zero. The total is fifteen.

The array itself never gets smaller. Instead, the remaining portion of the problem becomes smaller because the index moves forward.

This is the single most important sentence in Part IV. Students who miss it write recursive array methods that never terminate, because they keep passing the same array and looking for it to shrink.

Finding the Maximum Recursively

Suppose we want to find the largest element in an array. One recursive approach is:


public static int max(int[] values, int index) {
    if (index == values.length - 1) {
        return values[index];
    }

    int maxOfRest = max(values, index + 1);

    if (values[index] > maxOfRest) {
        return values[index];
    }

    return maxOfRest;
}

Suppose we want to find the largest element in an array. One recursive approach names the answer for the rest of the array, then compares the current element against it.

Note the base case: index equals values dot length minus one, the last element. A single element is its own maximum. Unlike sum, there is no sensible answer for an empty portion — there is no identity value for maximum — so the recursion stops one element earlier.

That difference between the sum base case and the max base case is worth a minute. The base-case answer must be correct, and what counts as correct depends on the operation.

Trusting the Recursive Call

Think about the statement:


int maxOfRest = max(values, index + 1);

We are saying:

Assume that the recursive method can correctly find the maximum of everything after the current position.

Then we only need to compare that answer with the current element.

Key ideaThis is a good example of recursive problem decomposition.
The leap of faith, applied

Naming the recursive result — maxOfRest — is a small trick with a large payoff. Once the answer to the smaller problem has a name, the rest of the method is ordinary code: an if and two returns.

Compare with sumArray, where the recursive call is buried inside an expression. Both are correct; the named form is easier to reason about, and Part X's general template uses it.

Think about the statement assigning maxOfRest. We are saying: assume that the recursive method can correctly find the maximum of everything after the current position.

Then we only need to compare that answer with the current element. If the current element is bigger, it is the maximum; otherwise the answer from the rest is.

Recursion and Searching

One particularly important recursive algorithm is binary search. Binary search works on a sorted collection.

Suppose we have:


[3, 7, 12, 18, 25, 31, 42]

and want to find 25.

Instead of examining every element, binary search examines the middle element.

Middle:


18

Since:

[25, 31, 42]
Key ideaThe problem gets approximately half as large after each step.
7 elements→ 3 elements→ 1 element
Why "approximately"?

Discarding the left half also discards the middle element we just tested. Seven elements minus the middle leaves six, split into three and three — so the remaining range is three, not three and a half.

The counting is never exactly halving, which is why the notes say approximately. For the purpose of understanding the algorithm, approximately is enough; Week 11 makes it precise.

One particularly important recursive algorithm is binary search. Binary search works on a sorted collection — that precondition is not optional, and it is the reason Week 11 spends time on sorting.

Suppose we have the sorted array three, seven, twelve, eighteen, twenty-five, thirty-one, forty-two, and want to find twenty-five. Instead of examining every element, binary search examines the middle element, which is eighteen. Since twenty-five is greater than eighteen, and the array is sorted, twenty-five cannot be anywhere to the left. We can ignore the entire left half and search only twenty-five, thirty-one, forty-two.

The problem gets approximately half as large after each step. Contrast with the linear scan the class wrote in Week 5: there, ruling out one element cost one comparison; here, one comparison rules out half the array.

Recursive Binary Search

A recursive implementation might look like:


public static int binarySearch(
        int[] values,
        int target,
        int low,
        int high) {

    if (low > high) {
        return -1;
    }

    int mid = low + (high - low) / 2;

    if (values[mid] == target) {
        return mid;
    }

    if (target < values[mid]) {
        return binarySearch(values, target, low, mid - 1);
    }

    return binarySearch(values, target, mid + 1, high);
}
Binary search: full walkthrough

A recursive implementation takes the array, the target, and the two bounds of the range currently under consideration. If low has passed high the range is empty and we return minus one. Otherwise compute the midpoint, test it, and recurse into whichever half can still contain the target.

The midpoint is computed as low plus the quantity high minus low over two, rather than low plus high over two. Both give the same answer for small arrays; the form used here avoids overflow when the indices are large.

Note that the two recursive calls are the last thing the method does. Nothing happens during unwinding here — binary search does all its work on the way down.

Recursion Is Not Magic

A recursive call is still just a normal method call. The computer does not "understand recursion" as a special concept. It simply:

  1. calls a method,
  2. creates a stack frame,
  3. executes the method,
  4. possibly calls another method,
  5. waits for that call to return,
  6. continues execution.

isSorted in Java


public static boolean isSorted(
        int[] values,
        int index) {

    if (index >= values.length - 1) {
        return true;
    }

    if (values[index] > values[index + 1]) {
        return false;
    }

    return isSorted(values, index + 1);
}
Key ideaThe base case is "one element or fewer left to compare" — there is no pair to be out of order, so the answer is true.

The Java takes the array and an index. If the index is at or past the second-to-last element, there is no pair left to compare, so return true. If the element at index is greater than the next, they are out of order, so return false. Otherwise recurse on the next index.

The comparison uses strictly greater than, not greater than or equal to, precisely because equal neighbours are permitted in nondecreasing order.
