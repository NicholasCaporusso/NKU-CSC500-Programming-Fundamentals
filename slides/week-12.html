It is the same principle as section 6: separate what something does from how it does it.

Instead of declaring the variable as an ArrayList, Java programmers often declare it as a List and assign a new ArrayList, after importing both java dot util dot List and java dot util dot ArrayList.

Why? Because the variable describes what we need — a List — while the constructor specifies which implementation we choose — ArrayList. Later we might change the constructor to a LinkedList without changing much of the surrounding code.

This is an important example of programming against an abstraction rather than a specific implementation, and it is the practical form of the WHAT-versus-HOW slide from Part I.

Two Live-Coding Exercises

Implement public int get(int index)


public int get(int index) {

    if (index < 0 || index >= size) {
        throw new IndexOutOfBoundsException();
    }

    Node current = head;

    for (int i = 0; i < index; i++) {
        current = current.next;
    }

    return current.data;
}

What is the runtime? O(n) in the worst case.

Implement public void clear()

What is the simplest implementation?


public void clear() {
    head = null;
    size = 0;
}
NoteStudents may initially expect that we must visit every node. In Java, we do not. Once head becomes null, assuming no external references exist, the nodes become unreachable and can eventually be garbage collected.

First exercise: implement get of an index for our linked-list class. Guard the index, start at head, take exactly index steps with a counted for loop, and return current dot data. Then ask the class what the runtime is — O(n) in the worst case.

Second exercise: implement clear. Students may initially expect that we must visit every node and null out each link. In Java, we do not. Once head becomes null, assuming no external references exist, the nodes become unreachable and can eventually be garbage collected.

The second exercise is the best single demonstration of the garbage-collection idea from Part VII.

Key Takeaways

  • A list is an abstraction — an ordered collection and its operations.
  • A list can have different implementations: array-based and linked.
  • ArrayList uses an array internally, growing by occasionally allocating larger storage.
  • Linked lists use nodes and references: [data | next] chained to null.
  • Arrays provide efficient random access — O(1).
  • Linked lists give efficient reference-based insertion, but locating the position may still be O(n).
  • References must be manipulated carefully: a wrong arrow loses part of the structure, creates a cycle, or throws a NullPointerException.
  • Data-structure choice involves tradeoffs. There is no universally best data structure.
