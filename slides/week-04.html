Parameters behave like local variables. The parameter name exists only during that invocation of greet; when the method finishes it is gone, and the next call creates a fresh one. Part V works this out in full with square(5) followed by square(10).

Example: Maximum of Two Numbers

A variable is not necessarily accessible everywhere in a program.

Variable Scope

Scope: the region in which a variable exists.
Fine 

public static void printNumber() {
    int number = 10;

    System.out.println(number);
}

The variable number exists only inside printNumber.

Would not work 

public static void main(String[] args) {
    printNumber();

    System.out.println(number);
}
Common errorJava would produce a compilation error because number does not exist inside main.

A variable is not necessarily accessible everywhere in a program. The region in which a variable exists is called its scope.

The variable number exists only inside printNumber. Calling printNumber from main runs fine, but the second statement in main does not compile: Java would produce a compilation error because number does not exist inside main.

This is not a rule Java invented to be difficult. It is what makes methods independent — Part I's promise that you can debug one method at a time only holds if its variables cannot be disturbed from outside.

Variables declared inside a method are called local variables.

Variables declared inside a method are called local variables. In calculateArea, both radius and area are local to this particular invocation of calculateArea.

Stress the phrase "this particular invocation". It is not merely that the variables belong to the method — they belong to one run of the method. That distinction becomes concrete in the next two slides and again when we study recursion.

Other methods cannot directly access them. The only channels between methods are parameters going in and a return value coming out.

Second: did the method return the expected result? A DEBUG line printing a known call with known arguments answers this immediately.

Third: is the error inside the method or in the caller? Those two questions are answered by different fixes, and confusing them wastes most of a debugging session. Test methods independently.

Key Takeaways

  • Program decomposition is breaking a large problem into smaller, manageable pieces; in Java, the method is our primary tool for it.
  • A method is a named block of code that performs a particular task — a named computation.
  • Parameters are information going into a method; a return value is information coming out.
  • Scope is where a variable exists. Local variables and parameters belong to one invocation of one method.
  • A method call transfers execution and then returns; the call stack is how Java remembers where.
  • One method, one responsibility — and prefer returning a value to printing one.
  • Do not think of a program as one long sequence of statements. Think of it as a collection of smaller operations that cooperate.
Week 4 summary, in full

This week introduced one of the most important transitions in programming. Until now, we mainly focused on individual statements: variables, conditionals, loops. Methods allow us to organize those statements into larger conceptual units.

The central ideas are: method equals named computation; parameters equal information going into a method; return value equals information coming out of a method; scope equals where a variable exists; decomposition equals dividing a large problem into smaller problems.

The most important habit to develop is this: do not think of a program as one long sequence of statements. Instead, think of a program as a collection of smaller operations that cooperate to solve a larger problem.
