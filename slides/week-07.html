Review: Classes and Objects

Class: describes a type of object.
Object: an instance of that class.
Where does the state live?

Each object has its own state. Two Student objects created from the same class hold two independent copies of name and id.


public class Student {

    private String name;
    private int id;

    public Student(String name, int id) {
        this.name = name;
        this.id = id;
    }

    public String getName() {
        return name;
    }

    public int getId() {
        return id;
    }
}

A class describes a type of object. An object is an instance of that class. This is review from Week 6, but it is worth restating precisely because the whole week rests on it.

The Student class here has two private fields, a constructor that initialises both, and two accessor methods. Nothing in this class is new; what is new is the question of whether Student should exist at all, and what else belongs in it.

Part II

Encapsulation

An object controls access to its internal state.

Encapsulation: The Idea

Encapsulation: an object controls access to its internal state.

Suppose we have a bank account. A poor design might look like this:

Poor design 

public class BankAccount {

    public double balance;
}

Now another part of the program can write:


BankAccount account = new BankAccount();

account.balance = -1000000;
Common errorNothing prevents the balance from becoming invalid.
Which line is the mistake?

Not account.balance = -1000000; — that line is legal Java and the compiler accepts it. The mistake is public double balance;, written in a different file, possibly by a different person, which is what allowed the assignment to exist at all.

One of the central principles of object-oriented programming is encapsulation. Encapsulation means an object controls access to its internal state.

Suppose we have a bank account. A poor design declares the balance as a public field. Now another part of the program — any part, anywhere — can assign minus one million to it. Nothing prevents the balance from becoming invalid.

Stress that the compiler is perfectly happy with this. The damage is done at runtime, by code that was never reviewed by the class that owns the data.

A Better Design Hides the Field


public class BankAccount {

    private double balance;

    public BankAccount(double initialBalance) {
        balance = initialBalance;
    }

    public double getBalance() {
        return balance;
    }

    public void deposit(double amount) {
        if (amount > 0) {
            balance += amount;
        }
    }
}
  • Now outside code cannot directly change the balance.
  • Instead, changes must go through controlled methods.
Do thisThe field is private; the operations are public. The class decides which changes are legal.
What does the if in deposit buy us?

A deposit of zero or a negative amount is silently ignored, so no caller can use deposit to reduce the balance. The rule lives in one place — inside the class that owns balance — instead of being repeated at every call site.

The whole BankAccount story

A better design hides the field. The balance becomes private; a constructor sets the initial value; getBalance reports it; and deposit is the only way to increase it, and only when the amount is positive.

Now outside code cannot directly change the balance. Instead, changes must go through controlled methods. Every rule about what a valid balance is can now be written once, inside the class.

Why Encapsulation Matters

Encapsulation helps us enforce the rules of an object. For example:


public void withdraw(double amount) {

    if (amount > 0 && amount <= balance) {
        balance -= amount;
    }
}

The BankAccount class is responsible for ensuring that the account remains valid.

The class that owns the data should usually enforce the rules for that data.
Two conditions, two different jobs

amount > 0 rejects a nonsensical request — a negative withdrawal would be a deposit in disguise. amount <= balance protects the invariant that the balance never goes negative, which Part X names explicitly as balance >= 0.

Encapsulation helps us enforce the rules of an object. The withdraw method checks two conditions before touching the balance: the amount must be positive, and it must not exceed the balance.

The BankAccount class is responsible for ensuring that the account remains valid. This idea is important: the class that owns the data should usually enforce the rules for that data.

If that check lived in the caller instead, it would have to be repeated in every caller — and the one place someone forgets is where the bug lives.

Do Not Expose All Fields

A class should not simply expose all of its fields.

Avoid 

public double balance;
public String accountNumber;
public String owner;
Prefer 

private double balance;
private String accountNumber;
private String owner;
Do thisMake the fields private — and provide appropriate operations.
"Appropriate operations" — appropriate to what?

Appropriate to the problem domain. A bank account's operations are deposits, withdrawals and transfers, because those are the things that actually happen to accounts. The list of operations should read like a description of the business, not like a list of the fields.

A class should not simply expose all of its fields. Avoid declaring balance, account number and owner as public; prefer declaring all three as private, and provide appropriate operations.

Note that the two listings differ by one keyword per line. The design difference between them is enormous: the first surrenders control of the account's rules to every other class in the program.

Getters and Setters

Students often learn the following pattern:


private int age;

public int getAge() {
    return age;
}

public void setAge(int age) {
    this.age = age;
}
Watch outObject-oriented design does not mean automatically creating a getter and setter for every field.

Consider:


public void setBalance(double balance) {
    this.balance = balance;
}

This method allows outside code to bypass the rules of the bank account.

Students often learn the getter-and-setter pattern: a private field, a getAge that returns it, and a setAge that assigns it. It is a useful pattern, and it is also over-applied.

Object-oriented design does not mean automatically creating a getter and setter for every field. Consider setBalance. A public setter on balance undoes everything the private field bought us: this method allows outside code to bypass the rules of the bank account.

Meaningful Operations Instead

Instead, we might provide meaningful operations:

Better 

deposit(amount)
withdraw(amount)
transfer(amount)

This is usually better than:

Weaker 

setBalance(...)

because the methods describe actual operations in the problem domain.

Getters, setters, and what to write instead
Is a getter ever the right answer?

Yes — getBalance() is in the good BankAccount design on the earlier slide, because reading the balance is a real operation a customer performs. The asymmetry is deliberate: reading state is usually harmless, while writing it is where the rules live.

Instead of a setter, we might provide meaningful operations: deposit of an amount, withdraw of an amount, transfer of an amount. This is usually better than setBalance, because the methods describe actual operations in the problem domain.

This is the first appearance of an idea we return to in Part X: tell an object what you want it to do, rather than manipulating its internal data from the outside.

Part III

Instance and Static Members

Does this belong to one object, or to the class as a whole?

Instance Variables

Instance variable: belongs to a particular object.

public class Student {

    private String name;
}

If we create:


Student s1 = new Student("Alice");
Student s2 = new Student("Bob");

then each object has its own name. Conceptually:


s1
name = "Alice"

s2
name = "Bob"
Key ideaTwo objects, two independent name variables.

An instance variable belongs to a particular object. If the Student class declares a private String name, and we create two students named Alice and Bob, then each object has its own name.

Draw the two boxes on the board. Each object is a box; the instance variable lives inside the box; creating a second object creates a second box with its own copy. Everything about static variables in the next few slides is a contrast with this picture.

Instance Methods

Instance method: operates on a particular object.

For example:


public String getName() {
    return name;
}

When we call:


s1.getName();

the method operates on the object referred to by s1.

NoteThe method body says return name; with no object named — the object is whichever one you called it on.
Which name does return name; return?

The one belonging to the object the method was called on. Calling s1.getName() returns Alice; calling s2.getName() on the same method returns Bob. One method definition, many objects to operate on.

An instance method operates on a particular object. When we call s1.getName(), the method operates on the object referred to by s1.

This is why the body can simply say return name; without qualifying which name it means. The receiver of the call supplies the object, and therefore the field.

Static Variables

static variable: belongs to the class, rather than to one particular object.

public class Student {

    private String name;

    private static int numberOfStudents = 0;

    public Student(String name) {
        this.name = name;
        numberOfStudents++;
    }
}

Every student object shares the same:


numberOfStudents
Key ideaThe constructor increments a counter that no single object owns.
Why the counter is incremented in the constructor

The constructor runs exactly once per object, so incrementing there counts objects precisely. The field is also private: the count is state the class owns, and the next slide's static method is how the outside world reads it.

A static variable belongs to the class, rather than to one particular object. Here the Student class has an instance field name and a static field numberOfStudents, initialised to zero.

The constructor does two things: it stores this object's name, and it increments the shared counter. Every student object shares the same numberOfStudents.

One Shared Copy

Suppose we create:


Student s1 = new Student("Alice");
Student s2 = new Student("Bob");
Student s3 = new Student("Carlos");

There are three different name variables, but only one shared:


numberOfStudents = 3
3 objects→ 3 names→ 1 counter
Where does the counter live?

Not in any of the three objects. It belongs to the class itself, so it exists even before the first Student is created — which is why it can be initialised to zero at the point of declaration.

Suppose we create Alice, Bob and Carlos. There are three different name variables, but only one shared numberOfStudents, and after the three constructor calls its value is three.

This is the whole distinction in one example. Instance state multiplies with the objects; static state does not.

Static Methods

Static methods belong to the class rather than to a particular object. Example:


public static int getNumberOfStudents() {
    return numberOfStudents;
}

We call it using the class name:


Student.getNumberOfStudents();

This is different from an instance method:


s1.getName();
If a method depends on the state of a particular object, it should usually be an instance method.

If it represents behavior associated with the class as a whole, a static method may be appropriate.

Static methods belong to the class rather than to a particular object. We call getNumberOfStudents using the class name — Student.getNumberOfStudents() — not through an object. Contrast that with s1.getName(), which needs an object to operate on.

A useful rule: if a method depends on the state of a particular object, it should usually be an instance method. If it represents behavior associated with the class as a whole, a static method may be appropriate.

The Math Class as an Example

Java's Math class contains static methods. For example:


double x = Math.sqrt(25);
double y = Math.pow(2, 10);

We do not create a Math object:

Not how it works 

Math m = new Math();

Instead, we call methods directly on the class.

WhyThis is appropriate because sqrt does not depend on the state of a particular Math object.
Applying the rule from the previous slide

If a method depends on the state of a particular object, it should usually be an instance method. Math.sqrt(25) depends only on its argument, so there is nothing for an object to hold — and therefore no reason to create one.

Static vs. instance, side by side

Java's Math class contains static methods: Math.sqrt(25), Math.pow(2, 10). We do not create a Math object with new Math(); instead, we call methods directly on the class.

This is appropriate because sqrt does not depend on the state of a particular Math object. There is no state a Math object could usefully hold — which is exactly the test from the previous slide, applied to a class students have used since Week 1.

Real programs usually contain many classes, and those classes interact with one another. For a course registration system, possible classes include Student, Course, Instructor and Department.

These classes are related: a Course has an Instructor; a Department has Courses; a Student has a list of Courses. Read those three sentences aloud — the verb in each is "has". That leads to the concept of composition.

Composition

Composition: one object contains or uses another object.

Example:


public class Instructor {

    private String name;

    public Instructor(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }
}

A plain class, with nothing composed inside it — yet. It is about to become part of another class's state.

NoteComposition needs two classes: the container, and the thing contained. This is the second one.

Composition means that one object contains or uses another object. Start with a plain Instructor class: a private name, a constructor, and a getter.

There is nothing composed here yet. The interesting move happens on the next slide, when a Course declares a field whose type is Instructor.

A Course Has an Instructor


public class Course {

    private String code;
    private Instructor instructor;

    public Course(String code, Instructor instructor) {
        this.code = code;
        this.instructor = instructor;
    }
}

A Course contains a reference to an Instructor.

We describe this relationship as:

A Course has an Instructor.
Key ideaA field's type can be another one of your own classes. That is all composition is.
Where does the Instructor come from?

The constructor takes one as a parameter. A Course does not create its instructor; it is handed one that already exists, which is what makes it possible for two courses to be given the same instructor object.

Both classes, and the relationship they encode

Now consider the Course class. It has two fields: a String code, and an Instructor instructor. The second field is the new idea — its type is one of our own classes.

A Course contains a reference to an Instructor. We describe this relationship as: a Course has an Instructor.

Composition with Collections

Objects often contain multiple related objects. For example:


public class Student {

    private String name;
    private ArrayList<Course> courses;

    public Student(String name) {
        this.name = name;
        courses = new ArrayList<>();
    }
}

We might add a method:


public void enroll(Course course) {
    courses.add(course);
}

Now a student can contain references to many courses.

Why the constructor builds the list

The field courses is created empty in the constructor, so a newly built Student always has a usable list. Without that line the field would be null, and the first call to enroll would fail — see Part IX.

Objects often contain multiple related objects. A Student holds a name and an ArrayList of Course — composition with a collection rather than with a single object.

We might add an enroll method that adds a course to the list. Now a student can contain references to many courses. This is exactly the relationship stated earlier in words: a Student has a list of Courses.

Is-a, Has-a, and Responsibility

Two relationships, and one question: does this behavior really belong in this class?

"Is-a" vs. "Has-a"

Object-oriented design frequently involves two important relationships.

Has-a


A Car has an Engine.

This suggests composition.

Is-a


A Dog is an Animal.

This suggests inheritance.

Inheritance will be studied in more detail next week. For now, remember:


has-a → composition
is-a → inheritance

Object-oriented design frequently involves two important relationships. A Car has an Engine — that suggests composition. A Dog is an Animal — that suggests inheritance.

Inheritance will be studied in more detail next week. For now, remember the two-line mapping: has-a goes to composition, is-a goes to inheritance. Getting this mapping backwards is the single most common structural mistake in beginner designs.

Part VI

Designing from a Problem Description

Before writing code, identify important nouns.

Start from the Requirement

A Practical Design Process

When designing a small Java application:

  1. Read the requirements — understand what the program must do.
  2. Identify candidate classes — look for meaningful nouns.
  3. Assign responsibilities — what should each class know and do?
  4. Identify relationships — ask:

has-a?
is-a?
uses-a?
  1. Design public interfaces — determine what methods other objects should be allowed to call.
  2. Protect internal state — use private fields unless there is a strong reason not to.
  3. Implement incrementally — create and test one class at a time.

The interface hides implementation details. Software objects work similarly — and note that the four controls on the left are far fewer than the mechanisms on the right. A good interface is smaller than the thing it covers.

Public Interface vs. Private Implementation


public class Counter {

    private int count;

    public void increment() {
        count++;
    }

    public int getCount() {
        return count;
    }
}

The public interface is:


increment()
getCount()

The internal representation is:


private int count;

Outside code should depend primarily on the public interface.

Key ideaThis gives the class freedom to change how it works internally.

The Counter class has one private field and two public methods. The public interface is increment() and getCount(); the internal representation is private int count.

Outside code should depend primarily on the public interface. This gives the class freedom to change how it works internally — the field could become a long, or the count could be derived from a list, and no caller would need to change.

For BankAccount, the three calls — deposit, withdraw, getBalance — form part of its public interface. Good object-oriented design tries to keep that interface small, clear, and meaningful.

Key Takeaways

  • Classes model concepts — a class should represent a meaningful abstraction.
  • Objects contain state and behavior — state in fields, behavior in methods.
  • Encapsulation protects object state — fields should normally be private.
  • Objects collaborate — large programs are built from multiple interacting objects.
  • Composition models "has-a"; inheritance models "is-a" (next week).
  • Static members belong to the class; instance members belong to individual objects.
  • Enums represent fixed sets of values and let the compiler reject invalid ones.
  • Good OOP requires design — decide which objects should exist before writing code.
Week 7 summary, in the notes' own words

The most important ideas from this week: classes model concepts; objects contain state and behavior; encapsulation protects object state; objects collaborate; composition models has-a relationships; static members belong to the class while instance members belong to individual objects; enums represent fixed sets of values; and good OOP requires design.

Before coding, ask: what objects should exist, what should each object know, what should each object do, and how should the objects interact? Those four questions are the week in four lines.
