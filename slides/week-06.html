Part III

Behavior: Methods and State

Objects do not only store information. They can also perform operations.

Objects Can Also Have Behavior

Objects do not only store information. They can also perform operations. These operations are represented by methods.

For example:


public class Rectangle {

    double width;
    double height;

    public double area() {
        return width * height;
    }

}

Now we can write:


Rectangle r = new Rectangle();

r.width = 5;
r.height = 3;

System.out.println(r.area());

Output:


15.0

Objects do not only store information. They can also perform operations, and these operations are represented by methods.

Adding an area method to Rectangle lets the object compute its own area. Notice the method body: return width times height. It names no object and takes no parameters, yet it clearly means one particular rectangle's width and height.

A Method Uses the Object's Own Fields

When we call:


r.area();

Java executes the area() method using the values stored inside the object referenced by r.

Key ideaThe method operates using the object's own fields.

That is why r.area() gives 15.0 here and would give something else entirely if r referred to a different rectangle.

The same expression, a different answer

The expression r.area() does not have one fixed value. It depends on which object r currently refers to and what that object's fields contain at the moment of the call.

This is the first appearance of an idea Part V makes explicit with the this keyword: an instance method always runs "on behalf of" one particular object.

The method operates using the object's own fields. When we call r.area(), Java executes the area method using the values stored inside the object referenced by r.

Emphasise the phrase "the object referenced by r". We have not yet defined reference — that is Part IV — but the language of the notes is already careful about it, and it pays to be careful with students from the start.

Instance Methods

Instance method: a method that operates on a particular object.

public class BankAccount {

    double balance;

    public void deposit(double amount) {
        balance = balance + amount;
    }

    public void withdraw(double amount) {
        balance = balance - amount;
    }

}

A method that operates on a particular object is called an instance method. The BankAccount class here has two of them: deposit adds an amount to the balance, and withdraw subtracts one.

Note that neither of these methods yet checks anything. A deposit of a negative amount would work, and a withdrawal larger than the balance would work. Part VI is where we fix that — but only after the fields have been made private, because otherwise outside code can bypass the methods entirely.

Calling Instance Methods

Usage:


BankAccount account = new BankAccount();

account.balance = 1000;

account.deposit(200);
account.withdraw(50);

System.out.println(account.balance);

Output:


1150.0

Notice that the methods do not need a balance parameter. Why? Because the method already belongs to a particular object. When we write:


account.deposit(200);

the deposit method operates on account's balance.

Where does 1150.0 come from?

The balance starts at 1000. The deposit adds 200, giving 1200. The withdrawal subtracts 50, giving 1150. It prints as 1150.0 rather than 1150 because balance is declared double.

Set the balance to 1000, deposit 200, withdraw 50, and print — the output is 1150.0.

Object State

State: the collection of values stored in an object's fields.

Consider:


public class LightBulb {

    boolean on;

    public void turnOn() {
        on = true;
    }

    public void turnOff() {
        on = false;
    }

}

Initially:


on = false

After:


bulb.turnOn();

the object's state changes:


on = true

The collection of values stored in an object's fields is called the object's state. The LightBulb class has a single boolean field, on, and two methods that change it.

Initially on is false — that is the default value Java gives a boolean field. After calling bulb.turnOn(), the object's state changes and on is true. Nothing else about the object changed; state is exactly the field values.

Constructor Syntax

A constructor looks similar to a method, but there are two important differences. First, its name must match the class name. Second, it does not have a return type.

Correct 

public BankAccount(double initialBalance) {
    balance = initialBalance;
}
Incorrect 

public void BankAccount(double initialBalance) {
    balance = initialBalance;
}
Common errorAdding void turns it into a normal method rather than a constructor.
Why the compiler does not complain

The incorrect version is perfectly legal Java — it is simply a method that happens to be named BankAccount. The class therefore still has its default no-argument constructor, and new BankAccount(1000) fails to compile for a reason that looks unrelated to the real mistake.

This is why the notes present the two versions side by side rather than describing the rule in prose.

The correct form is public BankAccount(double initialBalance). The incorrect form adds void, which turns it into a normal method rather than a constructor. Put the two on the board together — the difference is one word, and it changes everything.

The this Keyword — the Problem

Suppose we write:


public class Student {

    String name;

    public Student(String name) {
        name = name;
    }

}

What does:


name = name;

mean?

Watch outBoth uses of name refer to the constructor parameter. The field does not get assigned.

Suppose we write a Student class whose constructor parameter is also called name, and whose body says name equals name. What does that mean?

Both uses of name refer to the constructor parameter. The field does not get assigned — the parameter is assigned to itself, which does nothing at all. The object is created with its name field still null, and the bug surfaces much later as a NullPointerException or an empty printout.

The this Keyword — the Fix

To distinguish the object's field from the parameter, Java provides the keyword:


this

We write:


public class Student {

    String name;

    public Student(String name) {
        this.name = name;
    }

}

Here:


this.name

means the name field belonging to this object, while:


name

means the constructor parameter named name.

Do thisThis pattern is extremely common in Java.

To distinguish the object's field from the parameter, Java provides the keyword this. We write this.name equals name.

Here this.name means the name field belonging to this object, while a bare name means the constructor parameter named name. The left side is the field, the right side is the parameter, and the assignment finally does what the programmer intended.

This pattern is extremely common in Java — you will see it in almost every constructor written in this course from now on. Section 43 lists the version without this as a common mistake.

A BankAccount That Protects Itself

        }
    }

    }

}

One purpose of encapsulation is to protect these invariants. If external code can directly modify every field, maintaining invariants becomes much harder — every place in the program that touches the field becomes a place the rule can be broken.

This slide is the answer to a student who asks why private fields are worth the trouble.

Forgetting new

What the program actually does

A declared-but-unassigned local variable will not compile at all if it is used, and a field left unassigned holds null — which produces the NullPointerException from Part IV as soon as a method is called on it.

Count the objects by counting the new expressions that have run. Count the references by counting the variables and fields that currently hold an arrow.

Accidentally Shadowing Fields

Incorrect

    name = name;
}

The first version assigns the parameter to itself.

Correct

}

The second assigns the parameter value to the object's field.

Common errorThe incorrect version compiles cleanly and runs without complaint. The field is simply never set.

The incorrect constructor writes name equals name, which assigns the parameter to itself. The correct constructor writes this.name equals name, which assigns the parameter value to the object's field.

The reason this mistake survives so long in student code is that it is not an error. Nothing fails at the point of the bug; the object is simply built wrong, and the symptom appears somewhere else entirely.
