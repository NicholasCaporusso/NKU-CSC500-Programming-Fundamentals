We handle exceptions using a try-catch statement. The try block holds code that might throw an exception; the catch block holds code that handles it.

Java distinguishes between two important categories. Unchecked exceptions generally represent programming errors or invalid operations — a null reference, a bad index, an argument that violates a method's rules.

Defensive Programming and Validation

Anticipating possible errors instead of assuming valid input.

Defensive programming: anticipating possible errors instead of assuming valid input.
Assumes valid input 

public static double calculateAverage(double total, int count) {

}

What happens when:


count == 0
Safer 

public static double calculateAverage(double total, int count) {

    if (count <= 0) {
        throw new IllegalArgumentException(
            "count must be greater than zero"
        );
    }

    return total / count;

Do thisNow the method explicitly defines acceptable input.
Why the guard says <= 0 and not == 0

A count of minus three is no more meaningful than a count of zero, and it would not throw — it would return a negative "average" and keep going.

Defensive programming means anticipating possible errors instead of assuming valid input, so the guard rejects the whole invalid range rather than the one value that happens to crash.

Defensive programming means anticipating possible errors instead of assuming valid input. The naive calculateAverage simply divides total by count.

What happens when count equals zero? Because total is a double, this does not even throw — it produces infinity or NaN, and the wrong number travels onward silently. That is worse than a crash.

The safer method rejects count less than or equal to zero with an IllegalArgumentException. Now the method explicitly defines acceptable input. The guard is documentation as much as it is defence.

Validate at the Boundary

Validate data when it enters your system.

Suppose a class represents a bank account.


public class BankAccount {

    private double balance;

    public BankAccount(double initialBalance) {

        if (initialBalance < 0) {
            throw new IllegalArgumentException(
                "Initial balance cannot be negative."
            );
        }

        balance = initialBalance;
    }
}
Key ideaThis prevents the object from entering an invalid state.

A useful software engineering rule is: validate data when it enters your system. The boundary is wherever untrusted data first becomes your program's data — a constructor, a setter, a parse method, a file reader.

In the BankAccount constructor, a negative initial balance is rejected before the field is ever assigned. This prevents the object from entering an invalid state.

Compare this with checking the balance later, at withdrawal time. By then the invalid object has already been passed around, stored in collections, and printed. Part XI calls this principle "fail fast".

Exception Handling Is Not a Substitute for Good Logic

Do not write 

try {
    System.out.println(array[index]);
}
catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("Bad index.");
}
When you could simply validate 

if (index >= 0 && index < array.length) {
    System.out.println(array[index]);
}
else {
    System.out.println("Bad index.");
}
Key ideaExceptions should normally represent exceptional situations. They should not replace ordinary conditional logic.
How to tell which one a situation calls for

Ask whether you can cheaply test the condition before acting. An array index can be range-checked in one comparison, so an if is right. Whether a file exists cannot be reliably tested before opening it, so an exception is right.

Mistake 3 in Part IX is exactly this error committed in its worst form — with an empty catch block that discards the evidence.

Do not wrap an array access in a try-catch for ArrayIndexOutOfBoundsException when you could simply validate the index with an if statement. Both versions print "Bad index." — but only one of them says what it means.

Exceptions should normally represent exceptional situations. They should not replace ordinary conditional logic. Beyond style, the try-catch version is also slower and it swallows out-of-range accesses from anywhere in the block, not only the one you meant.

Alice 92

Charlie 78
NoteWhitespace-separated fields, so next() and nextInt() can pick them apart directly.

We can write:


while (input.hasNext()) {

Why hasNext() rather than hasNextLine() here?

The loop no longer processes a line at a time — it processes a token at a time, taking two tokens per iteration. hasNext() asks whether another token exists, which is the right question when the body calls next() and nextInt().

This also means the loop does not care how the records are spread across lines. Two names on one line would still parse.

When the file contains a name and a number separated by a space, Scanner's token methods do the work: next reads the name, nextInt reads the grade, and the loop prints them joined by a colon.

Note the shift from hasNextLine to hasNext. The loop is now consuming two tokens per iteration rather than one line.

Also note what happens if a grade is not a number: nextInt throws. We are one slide away from that problem being the whole topic.

A Helper Method: parseGrade


public static double parseGrade(
        String text) {

    double grade =
        Double.parseDouble(text);

}

Two failures, two exception types:

  • The guard throws IllegalArgumentException when the number is out of range.
Key ideaThe method does not decide what to do about either failure. It only reports them.
Why two different exception types matter here

The caller can distinguish them. The file-processing code catches NumberFormatException to print "Invalid number" and IllegalArgumentException to print "Invalid record" — two different messages, from one method.

Note the ordering constraint from Part II applies: NumberFormatException is a subclass of IllegalArgumentException, so it must be caught first.

parseGrade parses the text and then validates the range. Double.parseDouble handles the format question and throws NumberFormatException on failure; the explicit guard handles the range question and throws IllegalArgumentException.

The method does not decide what to do about either failure — it only reports them. This is Part XI's guideline arriving early: throw when a method cannot fulfil its contract, catch where you know how to recover.

Detect invalid states as early as possible.

main calls loadStudents, which calls parseStudent, which throws. If parseStudent does not catch it, the exception travels to loadStudents. If loadStudents does not catch it, it travels to main.

This process is called exception propagation. The runtime searches the call stack for a compatible handler — "compatible" meaning a catch clause whose type is the thrown type or a supertype of it.

Connect this back to the stack trace: the frames printed there are exactly the frames the exception travelled through on the way out.
